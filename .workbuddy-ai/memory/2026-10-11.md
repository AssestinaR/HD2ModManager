### E1 的第二半：补上缺失的缓存（这才是真收益）

**先讲清楚为什么必须有这一步**：`CreateGameDataMappingFactsService(paths)` **每次调用都 new 一个实例**，
所以 6 个消费者各持一份 → 实例级缓存**等于零共享**。而该服务**今天完全没有缓存**：
实测 `FindAssetArchivesAsync` 对每个请求的 asset key **各发一条 SQL**。

新增 `HD2ModCore/Infrastructure/GameDataFactCache.cs`：进程级、有界（`Capacity = 16`）、
`Dictionary<string, object>` + 锁。**键完全由来源指纹构成**：

| 事实 | 键组成 |
|---|---|
| `AssetMetadata` | 三个元数据文件各自的 `(path, length, mtime)`；该目录与 selector 无关 → 一次解析服务所有消费者，3 次 `stat` 取代重新解析两个大文本文件 |
| `GameDataMapping` | data 目录 + 索引 generation + 元数据 generation + selector 指纹 → per-key 的 SQL 循环按三元组跑一次，而不是每次调用跑一遍 |

**"缓存不取代真实性"是结构性保证，不是承诺**（用户那条硬约束的落地方式）：

1. **键即指纹** → 来源一变键就变，旧值不可达。"游戏更新了却还返回旧数据"结构上不可能。
2. **不落盘** → 只是记忆；丢光它代价是时间，不是数据。
3. **重建路径不读缓存** → 测试 `RebuildNeverConsumesTheFactCache` 对 `AssetArchiveIndexService.BuildOrRebuildAsync`
   的**源码文本**断言：全文不得出现缓存类型名，且必须仍然调用 `_archiveIndexer.BuildAsync(` 与 `ComputeSourceFingerprintAsync(`。
   → **"重建能完整从资产文件与加密注册表重新取数"这件事被测试钉住**，不是靠注释声明。
4. **双向覆盖** → `GameDataFactCacheTests` 8 条用例同时验证：同源只算一次（`Assert.Same` 跨两个不同实例）；
   来源被改/被删/selector 换了 → **真实重算**且结果反映新内容。

### 1. 依赖公告从"错误"降级为"警告"

`TreatWarningsAsErrors` 会把 NuGet 审计警告（NU1901–NU1904）也升级为错误，
于是**任何一个传递依赖出公告都会挡住构建**。用户明确不担心这个（本应用是单机 Mod 管理器，
不对外服务、不处理不可信输入），所以加：

```xml
<WarningsNotAsErrors>NU1901;NU1902;NU1903;NU1904</WarningsNotAsErrors>
```

**只降级、不静默**：警告照常打印，只是不再中断构建。编译期零警告护栏保持锋利。

**验证方式（值得复用）**：用 `tmp/`（gitignored）下的临时探针工程引用会传递引入受影响包的版本，
两种配置各构建一次：
- 带 `WarningsNotAsErrors` → **2 警告 / 0 错误 / 成功**
- `-p:WarningsNotAsErrors=`（清空）→ **error NU1903 / 失败**

**顺带查清的一个反直觉事实**：**NuGet 只对 net9.0+ 目标审计传递包**。
探针最初是 net8.0 → 一条警告都没有（尽管 `dotnet list package --vulnerable --include-transitive` 明确列出漏洞）；
改成 net10.0 才复现。这也解释了为什么当初 NU1903 只出现在 net10.0 的 Cli/Manager 上，
而 net8.0 的 `HD2ModCore` 自己从来没报过。

### 3. 阶段 3 第一半：部署图按来源指纹记忆

**热点**：`DeployedOverrideGraphService.BuildAsync` 对**每个已部署 patch 文件**算两次 SHA-256
（目标文件 + 激活状态记录的源文件），再扫每个 base 的 TOC。
而 `CoreServices.CreateDeployedOverrideGraphService()` **每次调用都 new 实例**，
护甲页 / GameData 浏览器页每开一次就全量重算一遍。

**顺带查清**：`DerivedStateCoordinator` 里 `deployed` 是被**主动置空**的
（`// Do not scan GameData while a profile page is opening...` + `deployed = null;`），
所以 L4 那层根本不建部署图，**生产路径上唯一调用者就是 `GameDataArchiveBrowserService.BuildAsync`**。

**改动**：
- 新增 `SourceFingerprintMemo.cs`（可复用的"按来源指纹键控"的有界记忆）+ `DeployedGraphFactCache.cs`
- `GameDataFactCache` 改为持有 `SourceFingerprintMemo(16)` 的薄壳（对外 API 不变）
- `DeployedOverrideGraphService.BuildAsync`：**先算来源指纹**，命中直接返回上次的图；未命中才走原路径
- 关键顺序点：`ComputeGeneration(dataFiles, state)` 原本在末尾才调用，但它只依赖"一开始就有"的东西
  （已部署文件列表 + 激活状态）→ 把它的输入提前用于缓存键，就能在昂贵校验**之前**决定要不要做。
  `DeployedOverrideGraph.Generation` 的算法**没改**，对外那个值不变。

**键的三部分**：激活状态内容 + 每个已部署文件的 (名字, 长度, mtime) + **状态里每个源文件的 (存在性, 长度, mtime)**。

**为什么"源文件"必须在键里**：`ValidateFileAsync` 会读源文件（存在性 + 长度 + SHA-256）。
只盯已部署文件的话，"部署的 patch 没动、它引用的源被改了"不会让键变化，
缓存会把上一次的"一切正常"当成事实返回 → 正是 §20.3 禁止的"缓存取代真实性"。

**为什么两族记忆分开**：`GameDataFactCache`(16) 与 `DeployedGraphFactCache`(4) 各自持有 memo 实例。
体积差一个量级、访问节奏不同；共用一个字典会让部署图把映射结果挤出去；
而且分开之后"命中记忆"这类断言才是确定性的（否则并行测试写入可能清空字典）。

### 踩到的一个大坑：第一版"只改源"的用例是假的

**真实 `ApplyExecutor` 只支持硬链接与符号链接**
（`"Only hard-link and symbolic-link deployment are supported."`）。
链接之下"目标"与"源"**本来就是同一个文件**，改源必然同时改目标 → 两件事分不开。

所以第一版 `ChangingARecordedSourceFileForcesAGenuineRebuild` 用 `ApplyExecutor` 铺部署时，
**它能通过，但不是因为指纹对，而是因为目标也被一起改了**。
用**探针**（把源那一段从 `ComputeSourceCacheKey` 里拿掉）才暴露出来 —— 探针下它**依然通过**。

**修法**：改用 `DeploymentMethod.Copy` 手写激活状态（修复/导入流程与外部文件会记录这一种），
才真正让目标与源分离。改完再跑探针：

```
[FAIL] ChangingARecordedSourceFileForcesAGenuineRebuild
       Assert.NotSame() Failure: Values are the same instance
       失败! - 失败: 1，通过: 5
```

失败的那一条正好是它 → 用例真的在钉"源文件在指纹里"。探针已还原。

> **可复用的方法论**：写完一条"应该能抓住某个 bug"的用例后，**主动把被保护的那一行破坏掉再跑一次**。
> 如果它仍然通过，说明用例是假的。这一轮就是靠这个才发现第一版用例无效。

## 第十四轮：无节点事实的请求与失效形态（设计文档 §22）

### 用户授权

按文档顺序继续落地，本轮做 §21.7 点名的"仍未做的一半"。

### 做了什么

**核心问题**：中心此前**所有**请求都挂在 `ModNode` 上，而 game-data 侧与部署侧的事实没有节点
（身份是"游戏目录 + 来源指纹"）。所以阶段 2 页面半边与阶段 3 登记半边一直没做——缺的是**形态**，不是几个方法。

**身份**：新增 `FactSubject.GameData(string scope)`。作用域写进**主体**而不是 `Revision`：
- `GameDataIndex` → `GameData("index")`
- `GameDataMapping` → `GameData($"mapping:{SHA256(排序后的资产键集合)}")` ← 不同批次资产是**不同的映射事实**
- `DeployedGraph` → `GameData($"deployed:{游戏目录}")`

口径：`Subject` = "哪一件事"，`Revision` = "同一件事的输入指纹"。把作用域塞进 `Revision` 会让身份表述失真。

**合并**：三类事实**共用一本账**
`ConcurrentDictionary<FactRevisionKey, Lazy<Task<ModInformationResult<object>>>> _gameDataTasks`，
取出时 `Unwrap<T>` 还原类型（键里已含 Kind，不会撞）。

**失效边界（本轮唯一"少做一件事"的决定）**：`_gameDataTasks` **刻意不参与 `InvalidateNodeAsync`**。
它们的输入不含 Mod 目录，"某个 Mod 变了"不构成失效理由，清掉只会白做。

**生产者**：中心构造函数尾部加三个**可选**依赖（`IAssetArchiveIndexService` / `IGameDataMappingFactsService` /
`IDeployedOverrideGraphService`），不新建 producer 接口——这三个 application 接口本身就是单方法的生产者形状。
可选的意义是只读宿主可不配置，此时返回 `Unavailable` 而非抛异常。

**投影解耦**：新增 `IGameDataFactSource`（三方法）+ 两个实现
（`CenterGameDataFactSource` 走中心给 Manager；`DirectGameDataFactSource` 直问旁路服务、刻意不建/不刷中心缓存，给 CLI 只读）。
`GameDataArchiveBrowserService` 两个构造重载只收 `IGameDataFactSource`，**类里不再出现任何旁路服务名**。
新增 `GameDataIndexFacts`（指纹 + 全部归档摘要包成一个值——同一次读取的产物，拆开会让"指纹新、摘要旧"成为可能）。

**失败语义**：索引未建 → `Unavailable` + **空 Issues**（与直读版返回 null 对齐）；
生产真失败 → 适配器**还原成 `InvalidOperationException`**，不静默成空结果。

## 第十五轮：护甲页改造（阶段 4，设计文档 §23）

### 用户授权
"可行，继续任务吧" → 继续按文档顺序落地，本轮做阶段 4（护甲页改造）。

### 问题
护甲页 `ReadArmorDisplayFactsAsync` 为每件护甲只取**两个字段**（是否命中 Unit 覆盖 + 覆盖者图标），
却调用 `GameDataArchiveBrowserService.BuildAsync` **整包构建** GameData 归档浏览器。
而 `BuildAsync` 里有一句 `GetAssetInventoryAsync`——**对每一个 Mod 节点**请求一次资产清单（逐包解析 patch）。
于是打开护甲页的代价与整个 Mod 库规模挂钩。这是 §1.3 / §13.2 / `2026-10-10.md` 记录的"首开卡顿"根因。

### 做了什么
**新增第四条无节点事实 `ArmorCoverage`**（复用 §22 的形态，零新机制）：
- `ArmorCoverageEntry(HasEffectiveUnitOverride, UnitWinnerNodeId, CoverWinnerNodeId)`；
  `ArmorCoverageFacts(CoverageGeneration, Archives, Issues)`。
  两个赢家字段回答两个问题：Unit 赢家 = "模型被换了吗"；Cover 赢家 = "外观被谁改了"（无 Unit 赢家时退回到任意资产）。
- 登记：`GameData` 主体 / `Session` 范围 / `Composite` 生产者 / 依赖 `[GameDataIndex, GameDataMapping, DeployedGraph]`。
  登记表 24 → **25** kind。
- 中心新增 `RequestArmorCoverageAsync(游戏目录, 归档集合, 请求)`：复用 `_gameDataTasks` 合并账，
  内部**按依赖顺序自己请求**三条上游（因此与页面直接请求共用同一本账）。
- 投影 `ArmorCoverageProjection`（internal static）：`(index, mapping, deployed, archiveIds) → facts`。

**喂给映射的键刻意更小**：只取"已部署且**有归属**"的资产键，
而不是浏览器的"全部 Mod 资产键"——后者需要逐节点资产清单，正是要摆脱的那一步。
与浏览器覆盖层的等价性逐条核对过（见 §23.3），不是推断。

**两条铁律**：
1. **图标不进事实**。§4 #23 写的依赖含"+6 图标"，本轮**故意不纳入**——理由是 §7 护栏 3
   （"改图标 → ArmorCoverage 不重算"）。图标是对赢家节点的库内查找（内存字典 + 父链），
   塞进事实会让"换图标"变成"覆盖事实重算"，正好与护栏相反。图标留在页面。
2. **"读不到" ≠ "没有覆盖"**，三种情形三种正确行为：
   索引里有但没被覆盖 → 确定的 `false`（筛选器要能筛到它）；
   **不在索引里 → 事实里缺席**（页面显示"未知"）；
   索引未建 → 整个事实 `Unavailable`。把后两种写成 `false` 就是从缺失数据推出否定事实。

**页面**：`ReadArmorDisplayFactsAsync` 只剩一句 `library.InformationCenter.RequestArmorCoverageAsync(...)`；
父链与图标查找原样保留；生产失败时补一条 `LogService.Warn`（否则"读失败"静默变成"没有护甲被覆盖"）。

**结构护栏**（`ModInformationCenterArchitectureTests` 新增）：
`ArmorPageProjectsCoverageInsteadOfBuildingTheGameDataArchiveBrowser` ——
护甲页源码里不得再出现 `CreateGameDataArchiveBrowserService` / `BuildAsync`，且必须出现 `RequestArmorCoverageAsync`。

### A. 护甲页启动预热（§24）

三层各占一个空闲回合：
- **VM**：`ShellViewModel.QueueWorkspacePagePrewarm`（`ContextIdle`）建 `ArmorRegistryPageViewModel`。
  必须趁 UI 线程空闲时建——它的构造给三个集合挂 `CollectionView`，而 **`CollectionView` 绑定创建它的那个 Dispatcher**。
- **数据**：`QueueArmorRegistryPrewarm()`（`ApplicationIdle`，**且在启动维护之后**）→ `WarmUpAsync()`。
- **视图**：`WorkspacePagePresentationController` 预热链 profile → library → **armor**，各一个回合。
  宿主 `PrewarmArmorPageHost` 是**单独一层占满工作区**（护甲页是整页布局），不与上排两张并排成三列
  ——并排会让三列宽度都变，顺手改掉已经调好的预热条件。

**单飞加载**：`catalogLoadTask ??=`，`InitializeAsync` 与 `WarmUpAsync` 共用同一次。
没有它会掉进两个坑：各读一遍；或预热在跑时用户点开页面被 `if (IsBusy) return;` 挡回**空页面**。

**取数闸门（本轮唯一真正危险的地方）**：视觉预热会在窗口刚 `Loaded` 时建出护甲页视图 → `OnLoaded` → `InitializeAsync`，
那**早于**"库快照已加载"与"启动部署已落定"。此时算出的显示事实是错的（图标查不到、覆盖算在旧部署上），
而 `hasLoadedCatalog` 一旦置位，之后打开只走 `RefreshRuntimeStatusAsync`（只重读快照）——**不会自愈**。
闸门由 `ShellViewModel` 在启动维护的 **`finally`** 里放行（放 `try` 末尾的话，失败/取消时会永远停在"尚未读取"）。

**预热不占 UI 线程**：`RefreshAsync` 拆成 `LoadCatalogInputsAsync`（纯 IO+投影，可线程池）与 `ApplySnapshot`
（**必须 UI 线程**——`BulkObservableCollection` 挂着 `CollectionView`，跨线程改会抛）。

### C. 阶段 5 明确不做（§26）

不是懒，是成本/风险/收益不匹配：
1. `ThumbnailService` 缺的是**磁盘键**（仍是源路径 SHA-256，不是事实里的 `Generation`），
   而要做到这点必须先把 `Generation` 搬进 `ModCardViewModel`——
   `GetExistingThumbnailPath` 是在**同步属性**里被调的（库页 4 处 + `PageViewModels` 3 处）；
2. `DeleteCachedThumbnailsForSource` 靠"按源路径重算键"删缓存，**换键后它删不掉任何东西**
   （generation 无法从路径反推），替代方案只能是缓存清扫或另立索引——**新的失效协议**，

3. 换键 = 现存缩略图全部作废，第一次打开库页要全量重生成；
4. 它是**一致性清理**，不是性能收益，且要动刚优化过的热路径——发版前不做。

结论：留到下一轮单独做，届时应先写设计（尤其"换键后删除路径与缓存清扫怎么办"）。

### A. 侦察推翻了 §26 的两条结论

§26 曾判断阶段 5 是"成本/风险与收益不匹配的一致性清理"。侦察后两条理由都不成立：

1. **§26.1 的"必须把 Generation 搬进 `ModCardViewModel`"是错的。**
   磁盘键可以由**源路径本身**算出来（`OfSource(path)` 自己做一次 stat），
   所以 `GetExistingThumbnailPath` 的 7 处同步调用点一行都不用改。
2. **§26.4 的"与用户关注点无关"是错的——存在一个真实 bug。**
   磁盘键只有源路径 ⇒ **同一路径换内容，缩略图永远不更新**：
   - `LibraryPageViewModel.UpdateIconAsync`（库页"更新图标"）：把新图复制成 `icon{原扩展名}`
     （扩展名没变 ⇒ 路径没变 ⇒ 键没变 ⇒ `EnsureThumbnailAsync` 见到 `File.Exists` 直接 return false）；
   - `ModDetailsPageViewModel` 更新图像：事实确实是新的，但磁盘键仍是旧路径，同样卡住。
   两条路径的结果都是"换了图标但卡片没变"，**重启也不恢复**，
   只有走"替换 Mod 文件"流程（那里会手工删缓存）才恢复。
   `ModDetailsPageViewModel` 里那句注释"缩略图失败时由下次库页刷新重试"是乐观的错话。

### B. 还有一个此前没人查清的事实：**两个不同的 generation 字符串**

| | 生产者 `ModThumbnailProducer` | 中心 `ComputeThumbnailGeneration` |
|---|---|---|
| 有图标 | `SHA256(nodeId:N + "文件名:长度:mtime")` | `SHA256(nodeId:N + "\|" + 文件名小写 + ":长度:mtime")` |
| 无图标 | `SHA256(nodeId:N + "missing")` | `ComputeNodeGeneration`（**整个 Mod 目录**的哈希） |

哪个算数？`RequestThumbnailAsync` 里 `generation = request.Generation ?? ComputeThumbnailGeneration(...)`
之后 `effectiveRequest.Generation` 永不为 null，于是 `ProduceThumbnailAndRemoveAsync` 的
`request.Generation ?? data.Generation` **永远取左边**——生产者那份只活在返回对象字段里，
**生产代码没有任何地方读它**。也就是说统一它们**零行为风险**。

### C. 做了什么（3 新增 + 7 修改）

- **新增 `HD2ModCore/Infrastructure/ThumbnailFingerprint.cs`**：指纹唯一定义。
  `OfSource(path)` = `SHA256(绝对路径|长度|mtimeTicks)`（文件不存在 → 常量 `Missing`）；
  `OfNode(nodeId, path)` = `SHA256(nodeId:N|OfSource)`（事实缓存的命名空间前缀）。
- 生产者与中心的 `ComputeThumbnailGeneration` 都改为委托；无图标分支不再退化成目录哈希。
- **`ThumbnailService` 磁盘键 = `OfSource(path)`** ⇒ 服务降级为纯渲染器（只解码/落盘）。
- **删除路径与清扫的分工**（§26.4 点名要先回答的问题）：
  * **失效协议只有一套**：内容指纹；
  * **垃圾回收是另一件事**，且只有一个入口——启动时一次性 `SweepAsync`（旧键 `File.Move` 改名 +
    无主文件清扫，只删早于本次开始的文件以免和并发写入抢）；
  * 因此 `ModLibraryService` 两处 `DeleteCachedThumbnailsForSource` **全部删除**（2 → 0）。
- **顺手收掉旧管道**：`PreGenerateAll` / `EnsureThumbnailsAsync` / `RegenerateThumbnailAsync`
  三个零调用点的公开方法；`CancelPendingGeneration` 及 4 处调用点
  （`PreGenerateAll` 删掉后它只在换一个没人读的 CTS，已是空操作）。
- 小收益：读路径不再调 `Directory.CreateDirectory`（旧 `GetThumbPath` 每次都会调）。

### D. 新增测试（+10）

- `HD2ModManager.exe`、`bin/hd2mod.exe`、`hostfxr.dll` 的 PE machine 均为 `0x8664`（x64）。

**一个查清后确认不是问题的差异**：`HD2ModCli/skills/` 下有 **28** 个 `SKILL.md`，导出/打包的却是 **27** 个。
第 28 个是 `mod-management`，在 `CliSkillCatalog` 里显式标了 `IsLegacy: true`
（"兼容聚合 Skill：请优先使用更窄的 mod-metadata / option-management / safe-library-deletion"），
而 `ListCapabilitySkills()` 会同时过滤 router 与 legacy；router 对应的是 `HD2ModCli/SKILL.md`（不在目录里）。
→ **27 是设计值，不是漏打包**；旧技能仍以嵌入资源保留，供旧式导出路径使用。

**校验中自己踩的坑**（免得下次再踩）：清单里的 sha256 是**大写**十六进制，而 Python `hexdigest()` 是小写 →
第一版脚本误报 27 个"哈希不符"，实际 `bytes` 全部一致。忽略大小写后全绿。
另：PowerShell 的 `Add-Type` 被安全策略拦（"compiles and loads .NET code at runtime"）→
读 ZIP 改用 Python 的 `zipfile`，比 `System.IO.Compression` 更省事。

**打标签**：`v1.5` → `5c56314`。用**轻量标签**，与仓库既有 `v1.3`/`v1.4` 保持一致（那两个都是 `type=commit`）。
纯本地，未推送。

**结论：优化重构阶段 0–6 全部完成并已发布 v1.5，工作区干净。**

## 第二十轮：三项"可推迟工作"的实地核查

用户问：这几项与什么有关、现在能不能做、有什么好处。以下全部是**实测**，不是照抄文档。

### 1. 先纠正一处：文档里有一行已经过期

§20.8 表格第一行"**§6 那一版的页面收编**（让浏览器页/护甲页不再直调 `MapAsync` / `GetArchiveSummariesAsync`）"
写着"留待单独拍板"——**其实已经做完了**：§22.6 把 `GameDataArchiveBrowserService` 降级为纯投影
（只认识 `IGameDataFactSource`），§23.6 又用架构测试钉住护甲页。§6.1 的进度表也已记为 ✅。
所以这三项里真正还没做的只有下面两条（外加一个不算错的声明）。

### 2. 实测：登记表里那两个字段到底有没有人读

| 字段 | 实地状态 |
|---|---|
| `FactDescriptor.CacheScope` | 全仓**只有一处**生产用途：`ModInformationReader.Validate`（`HD2ModCore/Infrastructure/ModInformationReader.cs:402`）——"调用方要求持久化、但该 kind 声明自己不该持久化 → 抛异常"。它是一道**防呆护栏**，不是"决定缓存放哪层"的开关。 |
| `FactDescriptor.Producer` | `FactProducerKind` 有 13 个值，登记表写了 27 遍，**读取处 0 个——连测试都不读**。纯声明。 |

也就是说，"这次读的东西放哪层缓存"实际由**调用方自己**在
`ModInformationRequestContext.Create(scope)` 里写死（默认 `Persistent`；CLI 显式传 `None` / `Operation`）。
登记表里的声明与运行时行为**没有连起来**——这正是 E2「分层归位」要补的那一段。

### 3. 实测：6 个直调 `MapAsync` 的服务是什么状况

`ProfileOverrideGraphService`、`ProfileMaterialDiagnosticsService`、`ModAssetRoleFactsService`、
`AdvancedModAssetQueryService`、`MaterialDeliveryFactsService`、`ModAssetSummaryProjector`。

关键发现：**它们已经持有 `IModInformationCenter`**，而且其中几个**已经在用中心**问别的事实
（例：`ProfileOverrideGraphService.cs:128` 调了 `_informationCenter.RequestAssetInventoryAsync`）——
只有"要映射"这一件事绕过了中心。中心的入口 `RequestGameDataMappingAsync(assetKeys, request, ct)` 也**已经存在**。
唯一没接中心的是 `ModAssetSummaryProjector`（`CoreServices.CreateModAssetSummaryProjector(paths)` 直接
`new GameDataMappingFactsService(...)`，没有中心参数）。

**缓存收益已经拿到了**：§20.3 给映射服务加的进程级缓存（`GameDataFactCache` → `SourceFingerprintMemo`）
是 **static** 的，注释里明说"6 个消费者各 new 一个实例，实例级缓存等于零共享"——所以 6 家**已共享同一份缓存**。

**只有走中心才拿得到的四样**：
1. **并发合并**：`SourceFingerprintMemo` **只有结果记忆，没有"正在算"的门**（我读了源码确认）——
   并发问同一批资产会各算一遍；中心的 `_gameDataTasks` + `Lazy<Task>` 才会合并成一次生产。
2. **可观测性**：直调**不记** `ProductionStarted` / `DiagnosticRecorded`，所以这 6 条路的命中率今天完全看不见
   （正是 §7 护栏 4 说的"该往哪细分由数据决定"所缺的数据）。
3. **尊重调用方声明的 scope**：`MapAsync` 签名里**根本没有 scope 参数**，所以一个声明 `CacheScope.None`
   的 CLI 只读操作照样会读写进程缓存。
4. **取消跟随中心关闭**，而不是各自传 `CancellationToken`。

### 4. 第 3 项（`GameDataMapping` 声明 `Persistent` 但不落盘）**不是 bug**

`CacheScope` 的定义是"**最多**允许活多久"（上限），不是"实际一定会落盘"。用比上限短的寿命合法。
要"做"就得先给 game-data 侧**建一套磁盘持久层**——那是新功能，不是收尾，而且直接撞上
"缓存不能取代真相"这条红线（落盘后要处理损坏、升级、多进程并发写）。

### 5. 建议（待用户拍板）

| 项 | 能否做 | 值不值得 | 建议 |
|---|---|---|---|
| 6 个服务改走中心 | 能，机械改动（6 文件 7 处） | **值得**：并发合并 + 可观测性 + 尊重 scope | **可做** |
| E2 分层归位 | 能，但有一个未拍板的设计问题（请求 scope 与登记表 scope 如何合成） | 结构收益，**用户无感**；且会改所有读取路径的缓存层（刚优化过的热路径） | 缓，等下次动架构一起做 |
| `GameDataMapping` 落盘 | 无对象可做（要先建持久层） | 低，且有红线风险 | 不做 |
