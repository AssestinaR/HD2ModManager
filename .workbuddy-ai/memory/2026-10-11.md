### E1 的第二半：补上缺失的缓存（这才是真收益）

**先讲清楚为什么必须有这一步**：`CreateGameDataMappingFactsService(paths)` **每次调用都 new 一个实例**，
所以 6 个消费者各持一份 → 实例级缓存**等于零共享**。而该服务**今天完全没有缓存**：
实测 `FindAssetArchivesAsync` 对每个请求的 asset key **各发一条 SQL**。

新增 `HD2ModCore/Infrastructure/GameDataFactCache.cs`：进程级、有界（`Capacity = 16`）、
`Dictionary<string, object>` + 锁。**键完全由来源指纹构成**：

| 事实 | 键组成 |
|---|---|
| `AssetMetadata` | 三个元数据文件各自的 `(path, length, mtime)`；该目录与 selector 无关 → 一次解析服务所有消费者，3 次 `stat` 取代重新解析两个大文本文件 |
| `GameDataMapping` | data 目录 + 索引 generation + 元数据 generation + selector 指纹 → per-key 的 SQL 循环按三元组跑一次，而不是每次调用跑一遍 |

**"缓存不取代真实性"是结构性保证，不是承诺**（用户那条硬约束的落地方式）：

1. **键即指纹** → 来源一变键就变，旧值不可达。"游戏更新了却还返回旧数据"结构上不可能。
2. **不落盘** → 只是记忆；丢光它代价是时间，不是数据。
3. **重建路径不读缓存** → 测试 `RebuildNeverConsumesTheFactCache` 对 `AssetArchiveIndexService.BuildOrRebuildAsync`
   的**源码文本**断言：全文不得出现缓存类型名，且必须仍然调用 `_archiveIndexer.BuildAsync(` 与 `ComputeSourceFingerprintAsync(`。
   → **"重建能完整从资产文件与加密注册表重新取数"这件事被测试钉住**，不是靠注释声明。
4. **双向覆盖** → `GameDataFactCacheTests` 8 条用例同时验证：同源只算一次（`Assert.Same` 跨两个不同实例）；
   来源被改/被删/selector 换了 → **真实重算**且结果反映新内容。

### 1. 依赖公告从"错误"降级为"警告"

`TreatWarningsAsErrors` 会把 NuGet 审计警告（NU1901–NU1904）也升级为错误，
于是**任何一个传递依赖出公告都会挡住构建**。用户明确不担心这个（本应用是单机 Mod 管理器，
不对外服务、不处理不可信输入），所以加：

```xml
<WarningsNotAsErrors>NU1901;NU1902;NU1903;NU1904</WarningsNotAsErrors>
```

**只降级、不静默**：警告照常打印，只是不再中断构建。编译期零警告护栏保持锋利。

**验证方式（值得复用）**：用 `tmp/`（gitignored）下的临时探针工程引用会传递引入受影响包的版本，
两种配置各构建一次：
- 带 `WarningsNotAsErrors` → **2 警告 / 0 错误 / 成功**
- `-p:WarningsNotAsErrors=`（清空）→ **error NU1903 / 失败**

**顺带查清的一个反直觉事实**：**NuGet 只对 net9.0+ 目标审计传递包**。
探针最初是 net8.0 → 一条警告都没有（尽管 `dotnet list package --vulnerable --include-transitive` 明确列出漏洞）；
改成 net10.0 才复现。这也解释了为什么当初 NU1903 只出现在 net10.0 的 Cli/Manager 上，
而 net8.0 的 `HD2ModCore` 自己从来没报过。

### 3. 阶段 3 第一半：部署图按来源指纹记忆

**热点**：`DeployedOverrideGraphService.BuildAsync` 对**每个已部署 patch 文件**算两次 SHA-256
（目标文件 + 激活状态记录的源文件），再扫每个 base 的 TOC。
而 `CoreServices.CreateDeployedOverrideGraphService()` **每次调用都 new 实例**，
护甲页 / GameData 浏览器页每开一次就全量重算一遍。

**顺带查清**：`DerivedStateCoordinator` 里 `deployed` 是被**主动置空**的
（`// Do not scan GameData while a profile page is opening...` + `deployed = null;`），
所以 L4 那层根本不建部署图，**生产路径上唯一调用者就是 `GameDataArchiveBrowserService.BuildAsync`**。

**改动**：
- 新增 `SourceFingerprintMemo.cs`（可复用的"按来源指纹键控"的有界记忆）+ `DeployedGraphFactCache.cs`
- `GameDataFactCache` 改为持有 `SourceFingerprintMemo(16)` 的薄壳（对外 API 不变）
- `DeployedOverrideGraphService.BuildAsync`：**先算来源指纹**，命中直接返回上次的图；未命中才走原路径
- 关键顺序点：`ComputeGeneration(dataFiles, state)` 原本在末尾才调用，但它只依赖"一开始就有"的东西
  （已部署文件列表 + 激活状态）→ 把它的输入提前用于缓存键，就能在昂贵校验**之前**决定要不要做。
  `DeployedOverrideGraph.Generation` 的算法**没改**，对外那个值不变。

**键的三部分**：激活状态内容 + 每个已部署文件的 (名字, 长度, mtime) + **状态里每个源文件的 (存在性, 长度, mtime)**。

**为什么"源文件"必须在键里**：`ValidateFileAsync` 会读源文件（存在性 + 长度 + SHA-256）。
只盯已部署文件的话，"部署的 patch 没动、它引用的源被改了"不会让键变化，
缓存会把上一次的"一切正常"当成事实返回 → 正是 §20.3 禁止的"缓存取代真实性"。

**为什么两族记忆分开**：`GameDataFactCache`(16) 与 `DeployedGraphFactCache`(4) 各自持有 memo 实例。
体积差一个量级、访问节奏不同；共用一个字典会让部署图把映射结果挤出去；
而且分开之后"命中记忆"这类断言才是确定性的（否则并行测试写入可能清空字典）。

### 踩到的一个大坑：第一版"只改源"的用例是假的

**真实 `ApplyExecutor` 只支持硬链接与符号链接**
（`"Only hard-link and symbolic-link deployment are supported."`）。
链接之下"目标"与"源"**本来就是同一个文件**，改源必然同时改目标 → 两件事分不开。

所以第一版 `ChangingARecordedSourceFileForcesAGenuineRebuild` 用 `ApplyExecutor` 铺部署时，
**它能通过，但不是因为指纹对，而是因为目标也被一起改了**。
用**探针**（把源那一段从 `ComputeSourceCacheKey` 里拿掉）才暴露出来 —— 探针下它**依然通过**。

**修法**：改用 `DeploymentMethod.Copy` 手写激活状态（修复/导入流程与外部文件会记录这一种），
才真正让目标与源分离。改完再跑探针：

```
[FAIL] ChangingARecordedSourceFileForcesAGenuineRebuild
       Assert.NotSame() Failure: Values are the same instance
       失败! - 失败: 1，通过: 5
```

失败的那一条正好是它 → 用例真的在钉"源文件在指纹里"。探针已还原。

> **可复用的方法论**：写完一条"应该能抓住某个 bug"的用例后，**主动把被保护的那一行破坏掉再跑一次**。
> 如果它仍然通过，说明用例是假的。这一轮就是靠这个才发现第一版用例无效。
