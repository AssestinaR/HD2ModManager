### 实机现象（用户报告）
1. 被替换 unit **全部透明**；2. 阴影变成**围绕玩家做布朗运动的钢丝球**，每帧变化；

### 权威依据（全部在仓库内）
- SDK `stingray/unit.py::AddBoneData` 行 1796–1934：**一个 unit 的 TransformInfo 怎么拼**。
  逐骨遍历 armature；`NameHashes.index(hash)` **已存在就复用、否则追加**；
  `TransformMatrices[i] = bone.matrix`（世界）；`Transforms[i] = decompose(parent.matrix⁻¹ @ bone.matrix)`
  （**locals 是父坐标系下的局部变换**，根骨全 0）；`TransformEntries[i].ParentBone = 父骨在本表的下标`。
- SDK 行 615 / 2094–2111：`origin = matrices[MeshInfo.TransformIndex]⁻¹`；
  `Bones[i] = (origin @ M_bone).inverted().transposed()` ⇒ **mesh 变换是单位阵时 `Bones[i]=inv(M_bone)`**。
- SDK `__init__.py` 1740–1746（AutoLods）：所有 LOD 共享 lod0 的变换矩阵。
- SDK `CreateModel` 行 2375–2483：反导入时 `bone.matrix = TransformMatrices[i]`（世界），父链取 `TransformEntries`。
- 管理器 `CanonicalTransformInfoExpander.ExpandTransformInfo`：同名节点**必须覆写**（locals+matrices+parent 全取 avatar），
  `ValidateTransformInfo` 要求 **`NameHashes.Distinct().Count()==count`**（不许重复哈希）。
- 管理器 `CanonicalUnitRebuilder` 行 503–504：`MeshID` 写 +40、`TransformIndex` **照抄目标** 写 +48。

### 6 项根因（`_probe_unitdiag.py` 实测）
1. **`locals[]` 全填 0**（`DEFAULT_LOCAL`）⇒ 引擎/Blender 按父链建骨架 ⇒ 全部塌到节点 0（107/107 与 avatar 不一致）。
2. **`entries[]` 全填 `(1,0)`** ⇒ 父链压平到节点 0（avatar 是 `[(0,0),(1,0),(1,1),…]`）。
3. **`matrices[]` 全填 `IDENTITY16`** ⇒ `BoneInfo.bones[k]=inv(I)=I` ⇒ 静止时 `G_b@B_b=G_b≠I`，

随后用户确认 `_miptest_last2MB.png`（= `vtf_bytes[96:][-2097152:]` 解成 2048²）**就是正确的图像**。

**根因（已定位并修复）**：`hd2_vtf.VTF.read` 从 `header_size` 起**按 largest-first** 切 mip。实际布局是
`[16×16 低清缩略图 128B][mip N-1][mip N-2]…[mip 1][mip 0]`，即**缩略图在链首、mip 链 smallest-first、mip0 在图像块尾部**。
把整链当一张图解码 ⇒ 小 mip 被重解释为行 ⇒ 画面重复、压扁、逐层减半，只有下方约 2/3 是真图（1398104/2097152 = 66.7%，与用户「60%」吻合）。
精确算术：`128 + 699048 + 2097152 = 2796328 = len(data)`，零残留。

**五条独立证据**（全部一致）：
1. **视觉**：`_probe_mipviz.py` 三栏图 —— largest-first = 金字塔；smallest-first / 尾部 m0 = 干净单图（white、lace、face 均如此）。
2. **缩略图位置**：`_probe_vtflayout.py` 把 `data[0:128]` 当 16×16 DXT1 解码 —— `shinano_face` 一眼就是该图集的缩略图
   （左上/右上紫发、中央粉脸）；`data[-128:]` 是纯色平板 ⇒ **缩略图在链首**（排除「缩略图在链尾」）。
3. **用户确认** `data[-m0:]` 正确。
4. **尺寸账**：14 张贴图 `header + lowres + Σmips == 文件长度`，trailing 全 0。
5. **缩略图相关性**：`_probe_verifylayout.py` 用 16×16 缩略图与 mip0 下采样比 Pearson r —— 新顺序 13/14 胜（face .974 vs −.030、
   white .912 vs −.128、hair_ear .940 vs −.021）；`lace` 因近乎纯色、缩略图无信息量而失效（视觉判据仍决定性）。
   反例记录：`_probe_miporder2.py` 的 box2 自洽判据被 BC1 重压缩噪声污染（white/face 误判），**不作为判据**。

**修复**：`hd2_vtf.VTF.read` 改为先算全部 mip 尺寸，`chain_start = header_size + lowres`，`chain_end = chain_start + Σsizes`，
从尾部逐个剥出（`off = chain_end; for m in range(mip_count): off -= sizes[m]`），`lowres = data[header_size:header_size+lo]`。
docstring 同步改写。`v.mips[0]` 是唯一被下游使用的位置（`hd2_texpack.vtf_to_dds`），改动安全。

## 第 60 轮 · M7（🔴 透明/镂空：根因是材质父类，不是贴图）

**用户实机确认 M6「贴图终于正确了」**，提出最后一个难题：透明区域/镂空（裙子的蕾丝花边），
并注意到我们贴图里的"绿色底色图层"就是那些透明区域；要求研究 L4D2 如何判定透明、HD2 是否支持、
以及参照模组（同款带蕾丝衣服）怎么做。

### 三个问题的答案（证据齐全）

1. **L4D2**：透明存在 **VTF 的 alpha 通道**里（DXT5），白=有布/黑=洞；VMT 只是用
   `$translucent 1` 让引擎去读它。绿色 RGB 只是 alpha=0 区域的无关底色。
   实测 14 个源材质，真正生效 `$translucent 1` 的只有 **5 个**：
   headdress_white01_catears / lace_white01_catears / bra_white01_bra_inner /
   shoes_white01_highheels / shoes_02。`ornament_metal_underwear` 是 `$alphatest 1` 但贴图 1×1 无效。
   dress / glove / lower_white01 的 VMT 两行都被 `//` 注释 ⇒ L4D2 里就是不透明（贴图有 alpha 但引擎不用）。
2. **HD2**：支持，但**透明是"材质父类"的属性，不是贴图 alpha 的属性**。
   SDK 权威表 `docs/HD2SDK-CommunityEdition-3.8.0/__init__.py :: Global_Materials`：
   - `advanced` = "**No transparency**"（SDK 明写），槽 5 是 Color/**Emission** Mask，不是 alpha；
   - **`alphaclip` = "A material that supports an alpha mask"**，3 槽 = Normal/AO/Roughness + **Alpha Mask** + BaseColor/Metallic；
   - `translucent` 能软透明但**只有单色槽、没有底色贴图**，不适合我们的衣服；
   - `armorlut`（**原版护甲用的**）没有任何 alpha 槽 ⇒ **原版护甲根本不支持透明**，带蕾丝的护甲模组必须换父类。
   官方 Wiki（HD2-Modding-Wiki dev/materials/alphaclip）："The White of the mask is visible and the black will be transparent"，
   且 "Alpha Clip has no capabilities for partial transparency"（只能硬镂空）。
3. **参照模组 Chiffon-LUNALICE**：只有 2 个材质。第 2 个父类 `0x8f669f365f24594e`
   （槽位布局与 `original` **逐字节相同**），`OpacitySharpness=64 / OpacityOffset=−0.5`，
   其 `SclarFieldOpacity` 槽（键 `479fb1ef`）挂一张 **1024² 纯灰度图 = 蕾丝花边图案**
   （黑 40%/白 42%/中间 18%，`out/mask/ref_8043d2a0dd881788.png`）。
   ⇒ 做法 = 灰度遮罩 + 阈值裁切；它没用 `alphaclip` 只是因为早期模板是 `original`。

**关键教训**：遮罩存在 **RGB 灰度**里，不在 alpha 通道里 —— 第一版普查用 alpha 统计看错了通道
（参照那张 mask 的 alpha 全是 255，RGB 才是图案）。`_probe_maskcensus.py` 同时报亮度与 alpha 才看出来。

### 根因一：金属变黑 = **NekoToon 的 matcap 被整个丢掉**

- 源模型 92 槽 **全部**是 L4D2 社区着色器 **`NekoToon`**（`_probe_neko.py` → `out/_neko.txt`）。
  取色：`最终色 = 底色 × 光照 + matcap贴图 × matcaptint`（`$matcap 2` = 相加）。
- 装饰件（`Ornament_metal_*`/`_jewel_*`/`_Pearl_*`，38 槽）`$basetexture` 全指向
  `Ornament_metal_Underwear` = **1×1 RGB888 像素 (15,15,15)** 近黑；观感全在 matcap。
  实测 matcap 覆盖面：`11`(52727 tri, 82%, 均值 (199,196,198) 亮银) /
  `6`(8991 tri, 14%, (104,105,110) 中灰=宝石) / `Matcap8`(2622 tri, 4%, (218,215,216) 珍珠)。
  我们只搬了底色 ⇒ 纯黑。**完全对上用户现象。**
- **SDK 权威槽位语义**（`__init__.py :: SetupAdvancedBlenderMaterial` 1490-1521 行）：
  `advanced` 槽2 `Nar`(4c567810) RGB=法线、**Alpha=粗糙度**；槽3 `IlluminateData`(90b84a53)→金属度；
  槽5 `AlbedoEmissive`(e67ac0c7) RGB=底色、Alpha=自发光强度。
  ⇒ 我们共享平面法线 alpha=255 ⇒ 粗糙度拉满；金属度=6/255 ⇒ 全非金属；底色近黑 ⇒ 黑到底。
  `alphaclip` 槽0=Normal/AO/Roughness、槽1=Alpha Mask、槽2=Base Color/Metallic（节点图 1456-1471）。
- 源 VMT 全部键（92/92）：`lightingscale`/`basetexture`/`lightwarptexture`/`matcap`/`matcaptexture`/
  `matcaptint`/`matcaplighting`/`outline*`/`emission`/`emissiontint`/`lightingrange`；
  `bumpmap` 88、`nocull` 89、`alphatest` 38、`translucent` 30、`outlinetexture` 2、`emissiontexture` 1。

### 根因二：M7 漏 3 组 = 同底色多 VMT

`_probe_slots.py`（`out/_slots.txt`）遍历模型自己的 92 槽：**同一 `$basetexture` 被多个 VMT 共用**，

`glove_white01_wristcuffs` / `dress_white01_dress_corset` / `lower_white01_underwear`（共 30 槽有生效 translucent）。
另：装饰件 `$alphatest 1` 生效但贴图 1×1 RGB888 无 alpha ⇒ 必须靠"贴图真有 alpha"判定。

### M8 两条通用规则（零硬编码）

- **A 透明**：`opts_in`（组内任一 VMT 有生效 `$translucent`/`$alphatest`）**且**
  `has_alpha`（该组 VTF alpha 跨度≥3/255 且 <250 像素≥0.5%）→ `alphaclip` + alpha 遮罩（阈值 0.5）；否则不动。
- **B matcap**：`tint=max($matcaptint)` ≥ 0.9 → 底色 `:= clamp(底色 + matcap加权均值×tint)`、
  槽3=金属度、槽2 alpha=粗糙度；< 0.9 → 该组一字节不改（matcap 只是视角描影，advanced 表达不了）。
  0.9 的分界是数据读出来的：只有装饰件是 `[1 1 1 1]`，其余 `[.5 .5 .5 1]`/`[.1 .1 .1 1]`。
- 组内多 matcap 时取**按三角形加权平均**（装饰件 (186.6,184.2,186.5)，与主 matcap `11` 差 7%）。
  **一个 HD2 材质只能一个底色**，因为 Unit 里材质表 14 项是已实机验证部分，**不能改数量**。

## 第 61 轮：半透明蕾丝普查 + 逐 VPK 材质拆分 + 覆盖生效性核对

### 1. 半透明蕾丝普查（`_probe_lace.py` → `out/lace_report.txt`、`out/lace/sheet_*.png`、`out/lace_summary.png`）

判据：VTF alpha 里 `0<a<255` 的中间值像素做 **1px / 3px 腐蚀**，纯抗锯齿边一腐蚀就消失。

- 8 个带 alpha 的组里 **7 组是真半透明**（3px 腐蚀后存活率）：

  `bra_white01_bra_inner` 52.5%；只有 `shoes_02` 23.7% ≈ 纯镂空。

**一句话**：这个能力在现有系统里**已完整存在**，不需要新协议字段、不需要新 Lua 接口。它 = 「重写协议文档 + revision 自增」，Lua 每秒轮询全文、重新规划、**只重建签名变了的那一个目标**。要接的只是管理器侧 UI/工作流。
- 协议（`armor_registry_protocol.lua`）：`model_piece=<model>,<body>,<unit>,<slot>,<piece_type>,<tone>[,<enabled>[,<default_base>]]`（第 7 字段 `false` = 不参与合成）；`piece_override=<owner>,<body>,<unit>,<slot>,<piece_type>,<enabled>`；`target_mode=<item>,follow|manual`；`composition_mode=full|existing_only`。
  **位置唯一性**：同一 `(body,slot,piece_type)` 只能一个 Unit ⇒ 想挂 N 个可独立开关的部件，必须给 N 个不同 `piece_type`（层号）。
- 合成（`armor_registry_composition.lua`）：`piece.enabled~=false and enabled(body,unit,slot,piece_type)` **两个开关串联**，任一为假该 Unit 就不出现。护栏：`#rows 1..16`、`total<=4096`、每行 ≥1 piece；权重 `resolve_weight` 求不出唯一多数 ⇒ 该目标被跳过。新 piece 的 8 个 aux hash 取自**目标在该位置原有的 piece**（`by_position[key] or 全零`）⇒ **piece 必须落在目标已有位置上**。
- 发布（`armor_registry_transaction.lua`）：`signature = plan.payload`，未变则**复用**（不重建）；变了才 `build()`。**已发布 buffer 永不释放**（上限 32 MiB / 8192 个）⇒ 反复切换会累积内存。**签名不含 revision** ⇒ 只改 revision 不产生重建。
- 运行时（`armor_registry_runtime.lua`）：`poll_protocol()` 每秒读全文、内容变了才 parse；失败只改状态不动旧版本；`step_apply` 每帧 1ms 预算分帧跑；`attempts>=3` 后放弃；`runtime.status` 写 `revision=`。
- C# 侧已同构：`RuntimeArmorRegistryModelPiece.Enabled`、`RuntimeArmorComponentProjection.Project` 就是 `piece.Enabled && override`。**「按 unit 逐个开关」是现成能力，管理器数据结构上已打通，缺的只是 UI 与工作流。**
- **待做清单**（P0~P4）：P0 先回答「游戏到底能扛多少 piece」（4~6 个起步，20~32 属未测区间）；P1 bodygroup 拆 Unit（需决策：跨左右部件如鞋/裙落哪个 slot、`piece_type` 层分配、权重元数据必须落在目标已有位置）；P2 管理器开关 + 换装方案快照；P3 游戏内热切换（建议最后做，会绕开既有事务模型）；P4 与「VPK 作为一等公民」是同一功能的两个入口，建议 P1 直接按终局设计。

### 结论（已交付 `tmp/rig-lab/ROUND65_ARM_AND_SLEEVE.md`）

**A. 用户假设成立，但量级不是主因。**
两款源模型各自按管线自己的对齐映射进 HD2 空间后逐关节相减（`_probe_armfit.py`）：
- 臂总长 `UpperArm→Hand` 574.09 → 537.44 mm（**−36.65 mm，ratio 0.936**）；
  大臂段 285.64→265.20（−20.44）、小臂段 288.45→272.24（−16.21）。
- 手位差 **40.54 mm**，各手指关节差 **37.08~45.88 mm**。
- 手指本身只差 0.16~6.03 mm（中指几乎相同、无名指还长 1.38）。
- 最小二乘最优 `arm_scratch_upper_gain` ≈ **0.0895**（现状 0.05，需再加 39.5 mm）。
  加完后残差 中位 13.5→**10.2**、最差 24.0→**17.5** mm ⇒ **到不了 5 mm**。
  剩下的不是臂长：**肩关节本身差 9.71 mm**（对齐钉的是头部）+ **拇指根 Y 差 16.03 mm**（朝向差）。
- 出货网格上（已剔除袖子）：**真手指 core 质心差 中位 32.5 / 最大 35.9 mm**。

**B. 真凶：Lilium 的两片大飘袖被 `region` 兜底绑到了小指。**
- 源模型 `source_extra_93..106` 是一串挂在 **`L_UpperArm`/`R_UpperArm`** 下的专属骨头
  （hops 3~7），HD2 里无对应骨。
- `region` 兜底先取已映射祖先（`L_UpperArm`→`l_shoulder`），再把候选池限制在
  **祖先整棵子树（含 15 根手指）+ 同肢体**，最后**按到关节的距离取最近**。
  飘袖向外伸到 1.6 m，比任何关节都远 ⇒ "最近关节"变成链最外端的
  `l_pinky_finger1` / `r_pinky_finger1`。
- 实测（`_probe_hops.py`）：8 根 → `*_pinky_finger1`（0.807~1.629 m）、2 根 → `*_elbow`（0.596 m）。
  **对照 Lunalice：77 根兜底骨最远只有 0.432 m（头发→head），没有一根落手指。**
- 出货网格实测：`l_pinky_finger1` 1530 顶点（其中 **1430 个离骨 >80 mm**，最大臂长 **1.902 m**）、
  `r_pinky_finger1` 1681（1586）；**袖子渗漏合计 3016 顶点，Lunalice 为 0**。
- **小指弯 40° 时最大位移 1301 mm / 中位 876 mm** ⇒ 游戏里飘袖会飞 1.3 米。
  这不是"离得远"，是**绑错了骨**，拉长手臂修不了。

## 第 65 轮（续）：实施方案 A —— `region` 兜底加「链规则」，重建并交付

### 改动（`tmp/rig-lab/hd2_style.py`，唯一改动点 = `resolve_bone_map`）
新增**链规则**：一串未映射的骨头（父子成链）是**一个刚体件**，整条必须绑到同一根 HD2 骨，
由**链的根**（自身父骨已映射的那一根）决定。实现：
- 主循环里，`b['parent']` 也是未映射骨 → 只记 `hops`，不解析，放进 `chain` 集合；
- 循环后**反复扫**（不依赖 `src` 是否 parent-first）把 `resolved[parent]` 传播下来；
- 兜底：若某链的父骨始终没解析（环/截断），退回旧的"最近已映射祖先"。

## 先纠正我上轮的一个错误结论

上轮 `_probe_armfit.py` 第 3 节打印的「最小二乘最优 gain = 0.03965，所以现状 0.05 已经太大」
是**比较基准选错了**：`resid(g) = |b + u*g − a|`，其中 `a` 是 Lunalice 的**未加 gain** 对齐关节，
而 Lunalice 的**出货**网格是 `a + u*0.05`。所以正确的目标函数是

    resid'(g) = |b + u*g − (a + u*0.05)| = resid(g − 0.05)
    ⇒ 最优 g = 0.03965 + 0.05 = 0.08965（不是 0.03965）

我上轮在简报里写的 0.0895 / 0.08946 反而是**对的**，探针那一行 `gain=0.08665 → 48.3 mm` 才是错的读数。
**教训：拟合函数一定要拿"出货量"当参考，不要拿中间量。**

## 基准怎么定：直接量出货网格

`rest_hd2` 是 A-pose、源模型是 T-pose，关节直接相减是假误差（`_probe_armtarget.py` 实测
Lunalice 的手比 HD2 的 `l_hand` "远" 396.72 mm —— 全是姿态差，无意义）。
**长度**可以比，但回答不了"手该落在哪"。

所以改用**出货网格**（两款模型 `b_head` 逐字节相同，都绑在同一套骨头上）：

    出货骨架 l_shoulder->l_hand = (-0.4465, 0.2090, -0.2556)  |555.3 mm|   (A-pose 斜线距)
    HD2 自己 rest_hd2: 肩->肘 302.85 / 肘->手 287.36 / 肩->手 555.26 mm
    对齐后源模型:  Lunalice 285.64 / 288.45 / 574.09    Lilium 265.20 / 272.24 / 537.44

## 机制改动（`hd2_style.retarget`，+约 40 行）

新增参数 `arm_scratch_upper_shift=(0,0,0)`，把原来只能沿臂轴推的标量扩成

    delta = u * gain + shift        # u = T-pose 肩->肘单位向量（由 rest_sym 取，是 T-pose 不是 rest_hd2）

`shift` 按**左臂**给定，右臂 X 取反（HD2 +X = 角色右）。两者走**同一套 ramp**
（`arm_stretch_field`：肩端 0、肘以下强制 1），所以肩缝仍被钉住，**不引入新的撕裂风险**。
`shift` 默认 0 ⇒ 老行为逐字节不变。

拟合值（全部由出货网格反解，不是目视）：
    `gain = 0.0814 m`（原写死 0.05）、`shift = (0.0014, 0.0097, 0.0005) m`
`shift` 几乎全在 **+Y（世界"前"）**上 —— 那不是模型缺陷，是**对齐钉的是"头顶高度"**，
两个模型肩相对头骨的位置不同 ⇒ 手臂落在不同的 Y 上。
