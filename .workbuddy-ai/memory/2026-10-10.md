# 2026-10-10

## 任务：护甲映射页（Armor Registry）UI 性能分析（只读，未改任何源码）

用户目标：优化 HD2ModManager 护甲映射页每次启动/首开时"重载护甲列表"造成的卡顿。
本轮仅分析，不修改现有代码；结论写入本记忆文件。

### 护甲页加载链路（首开慢的根因）

- 入口：`Views/ArmorRegistryPageView.xaml.cs` 的 `Loaded` → `ArmorRegistryPageViewModel.InitializeAsync()`。
  - `InitializeAsync()`：`hasLoadedCatalog ? RefreshRuntimeStatusAsync() : RefreshAsync()`。
  - 页面 VM 在会话内被缓存（`ShellViewModel._armorRegistryWorkspacePage ??=`），
    因此**卡顿集中在每次应用启动后的首次进入**（`hasLoadedCatalog=false`）；之后进入只走便宜的 `RefreshRuntimeStatusAsync`。
- `RefreshAsync()`（ArmorRegistryPageViewModel.cs:350）三步：
  1. `service.ReadArmorCatalogAsync()`（SQLite `game_data_authority_kits`，每次新开连接，未走缓存）
  2. `service.ReadSnapshotAsync()`（读 protocol/workspace/status 文件，便宜）
  3. `ReadArmorDisplayFactsAsync(catalog)`（:505）—— **重灾区**
  4. `ApplySnapshot`（:405）+ `RebuildProjections`（:963）—— UI 线程上做集合重建/排序

### 重灾区 1：`ReadArmorDisplayFactsAsync` 为"两个字段"构建整个浏览器

- 调用 `CoreServices.CreateGameDataArchiveBrowserService(...)` 后 `browser.BuildAsync(library.Snapshot, ModsRootDirectory, gameData)`。
- `GameDataArchiveBrowserService.BuildAsync`（HD2ModCore）内部：
  - index fingerprint + 全部 archive summaries
  - `GetAssetInventoryAsync` 遍历**所有 Mod 节点**请求资产清单
  - `_mappingFactsService.MapAsync(全部 AssetKey)`
  - `_deployedGraphService.BuildAsync(gameData)` → **`DeployedOverrideGraphService.BuildAsync` 无任何缓存**：
    枚举 Data 全部 patch、对每个 group 扫 TOC（`PatchTocScanner`）、
    并对每个已部署文件与其源文件**做 SHA-256 校验**（`ValidateFileAsync`/`HashFileAsync`）。
  - 最后聚合所有 archive 的 overlay（大量 LINQ + 字典）。
- 但结果**只用于**每个 catalog 项的：`HasEffectiveUnitOverride`(bool) 和图标路径。
  为 ~400–800 条护甲/头盔取两个字段，却重建了整张部署覆盖图 —— 巨大浪费。
- 同一 `DeployedOverrideGraphService.BuildAsync` 无缓存，还被 GameData 浏览器页
  (`GameDataBrowserPageViewModels.cs:86`) 与详情页跨护甲计划 (`ModDetailsPageViewModel.cs:1517`) 各自重复调用。

### 重灾区 2：per-item 循环在 UI 线程 + O(N×M)

- `ReadArmorDisplayFactsAsync` 中 `await browser.BuildAsync(...)` **未加 ConfigureAwait(false)**，
  后续循环恢复在 **UI 线程**；且它被 `RefreshAsync`（UI 线程）await，整条链都在 UI 上下文。
- 循环内对每个 catalog 项：
  - `snapshot.Archives.FirstOrDefault(...)` 线性扫描全部 archive（O(catalog×archives)，未建字典）
  - 对 `archive.Overlay.EffectiveAssets` 反复 `Any(...)` + `Where().GroupBy().OrderByDescending().ThenByDescending().ThenBy()`（3–4 遍枚举/分配）

### 重灾区 3：`ApplySnapshot` + `RebuildProjections`（UI 线程）

- `ApplySnapshot`：重建 `Choices` 字典（每项 new `RuntimeArmorChoiceViewModel`）、Mappings、CustomModels。
- `RebuildProjections`：`BuildDisplayChoices` 用 `GroupBy(CombinationKey)` + `OrderBy(Name, StringComparer.CurrentCultureIgnoreCase)`
  （文化比较偏慢）；每个 provider 做 `Mappings.Count(...Contains...)`（O(P×M)）；逐项 `SetRolePresentation` new presentation。
- 已用 `BulkObservableCollection.ReplaceWith`（单次 Reset）与虚拟化列表（App.xaml `ModListBox`：Recycling + Pixel + CacheLength 1）。
  列表渲染与图片（`ImagePlaceholderConverter` 静态缓存 + DecodePixelWidth）本身已高效，非瓶颈。

### 可借鉴的高效范式（仓库其它部分做得好的地方）

1. `ModInformationCenter` + `JsonModInformationCache`/`JsonModFileFactsCache`：
   generation、`ModInformationCacheScope`(None/Operation/Session/Persistent)、`RequireFresh`、请求合并、按节点失效。
   —— 仓库最成熟的缓存层，护甲页的显示事实完全可以套用。
2. `ModDetailsPageViewModel` 的 per-node 缓存 + NodeId 守卫（`_cachedAdvancedAnalyses`/`_cachedMaterialDeliveryFacts`）。
3. `AdvancedEquipmentIndexService`：增量构建 + `IsCurrentAsync` 版本守卫 + `CanonicalHiddenUnitOutputCache`。
4. `GameDataArchiveBrowserService` 双构造：CLI 走 `directInventory` 避免为渲染而刷新管理器缓存
   —— 说明"不要为了渲染而重建缓存"是既有设计意识，护甲页违反了它。
5. `UiPerformanceDiagnostics.Measure/RecordElapsed`：已有慢操作埋点框架（护甲页只在图片解码处用了）。
6. `BulkObservableCollection.ReplaceWith`、虚拟化 `ModListBox`、`ThumbnailService` 磁盘缩略图缓存。

### 下轮可考虑的优化方向（尚未实施）

### 补充：数据库与"重建缓存"（2026-10-10 续）

  另有独立的 `data/indexes/mod-facts.sqlite`（`ModFactsDbPath`）。库内 `data/` 位于程序根目录。
- 表：`archives`/`archive_entries`/`assets`/`asset_archives`/`game_data_unit_parts`/
  `game_data_stream_layouts`/`game_data_authority_kits`/`game_data_authority_pieces`/
  `game_data_authority_resources`/`game_data_authority_entities`/`game_data_archive_names` 等。
  护甲页的"护甲列表"读的就是 `game_data_authority_kits`。
- 设置页"建立 / 重建资产索引"按钮 → `PageViewModels.BuildAssetIndexAsync` →
  `AssetArchiveIndexService.BuildOrRebuildAsync`（重建基础索引）。
  另有独立按钮"重算 Armor / Helmet Unit 部位" → `AdvancedEquipmentIndexService`（部位事实）。
- **重要事实纠正**：游戏更新后**不会自动重建**。启动时只做"检查"：
  `ShellViewModel.CheckGameDataIndexOnStartupAsync` 比较指纹，过期则提示用户手动重建
  （提示语："索引过期或缺失；不会自动重建，请确认后手动启动重建。"）。
  唯一会顺带重建的是首页"一键修复过时 Mod"（`RepairOutdatedModsAsync` 先重建索引）。
- 概念分层（用于向用户解释）：①游戏固定数据索引(SQLite，慢但少变) ②Mod 分析缓存(有 generation)
  ③部署覆盖图(每次现算、无缓存) ④护甲页显示事实(每次现算)。护甲页卡顿来自 ③+④，**不是**①。
  ①的 catalog 查询本身很便宜。

### 补充：护甲页重载触发点与"会话内缓存"（2026-10-10 再续）

- 启动预热**不含**护甲页：`WorkspacePagePresentationController.QueueVisualPrewarm` 只预热 Profile + Library
  （`ShellViewModel.GetOrCreateWorkspaceVisualPrewarmPages`）。故护甲页重活发生在"本次会话第一次打开它"时。
- 页面 VM 会话内缓存：`ShellViewModel._armorRegistryWorkspacePage ??=`；库切换/重置时会 `Dispose()` 并置 null（约 :967-970），
  下次打开又是重活。`InitializeAsync()` 仅在 `hasLoadedCatalog=false` 时走重路径。
- 重路径 `RefreshAsync()` 也会被手动"刷新"按钮触发（`RefreshCommand`），即手动刷新同样重算显示事实。
- 澄清：SQLite catalog 是**持久**的（重启仍在），重启后丢的是内存里的 VM/`hasLoadedCatalog`/`cachedCatalog`/`cachedArmorDisplayFacts`。
  所以不是"临时缓存没了"，而是"算出来的结果没被持久化/复用"。
- Mod 资产清单缓存（`ModInformationCenter`）在护甲页浏览器构建中**已被复用**；未被复用的是③部署图与④显示事实。

### 设计讨论：指纹缓存 + 简化投影（2026-10-10，未实施）

- 代码里**已有现成指纹**可当缓存键：
  - `DeployedOverrideGraph.DeploymentGeneration`（部署图自带，由 文件名+大小+修改时间+激活配置 profile/revision 算出）
  - `GameDataMappingFacts.MappingGeneration` / `IndexGeneration` / `MetadataGeneration`
  - `AssetArchiveIndexService` fingerprint（`SourceFingerprint`）、`LibrarySnapshot.Version`
  - `ModInformationCenter` 的 generation
- 问题：这些指纹是"干完重活之后"才得到的，重活本身没被 memoize。要当缓存键，需把"算指纹"**提前且变便宜**
  （只列 Data 目录 + 读 FileInfo，不扫 TOC、不算 SHA-256）。
- 设计：`DeployedOverrideGraph` 加指纹缓存（内存 + 可选磁盘持久化），按廉价指纹命中即返回；
  受益者不止护甲页：GameData 浏览器页、详情页跨护甲计划也用同一个 `BuildAsync`。
- 简化：护甲页其实只要"每个护甲 archive 有无 Unit 被覆盖 + 赢家节点→图标"。
  可只对**部署图里有赢家的 asset key**做 `MapAsync`（而非全库所有 Mod 的所有 key），
  并跳过浏览器的 `modsByArchive/activeByArchive/competition` 等无关 overlay 构建。
  注意保留 `GameDataMappingFactsService` 的"新 asset 指到原版 archive"映射语义。
- 组合键需含：部署指纹 + `LibrarySnapshot.Version` + 索引指纹（+ Mod 图标/名称若不在 version 里）。
- 风险：指纹若漏掉某个依赖（如 Mod 图标改名未 bump version）→ 陈旧图标；需保证"刷新"按钮可强制绕过缓存。
- 解决"每次启动首开慢"必须用**磁盘持久缓存**（按指纹），仅会话内缓存无效。

### 信息中心（ModInformationCenter）现状盘点（2026-10-10，只读）

用户提出想自建"缓存控制系统（消费端只管要 / 生产端只管生产+报指纹 / 中心统一判过期与发放）"，
并问"项目最初似乎有类似的信息中心，现在什么状态"。结论：**它不但存在，而且已经是用户设想的那套架构，正在运行，且有测试强制保护。**

- 接口：`HD2ModCore/Application/IModInformationCenter.cs`（`IAsyncDisposable`）
  - 7 个 `Request*Async`：FileFacts / AssetInventory / ReferenceGraph / MaintenanceAnalysis /
    UnitVersion / AdvancedUnitAnalysis / Thumbnail（各自带 `ModInformationRequest` + `CancellationToken`）。
  - `GetAssetRelationSummaryAsync(assetKeys, excludedNodeId)`（非 per-node 键，是"键模型可扩展"的先例）。
  - `InvalidateNodeAsync(nodeId)`；事件 `DiagnosticRecorded`、`ProductionStarted`。
  - 注释原文："统一编排 Mod 派生信息请求；业务代码不直接启动派生缓存生产。"
- 实现：`HD2ModCore/Infrastructure/ModInformationCenter.cs`（约 707 行）。
  - 持有 7 个 Producer 接口 + `IModFileFactsCache`/`IModInformationCache`/`IModDataIndex`/`IReferenceGraphIndexWriter`。
  - **请求合并**：`ConcurrentDictionary<string, Lazy<Task<...>>>`（`_fileTasks`/`_assetTasks`/`_referenceTasks`/…）按 key 去重并发。
  - **失效**：`_invalidatedNodes` + `_nodeCancellations`（`InvalidateNodeAsync` 取消并移除含该节点的 in-flight 请求）。

  - **陈旧回退**：`TryLoadStaleAsync`（stale-while-revalidate）。`RequireFresh` 可强制绕过缓存。
  - 命中返回 `ModInformationStatus.Cached`（否则 Produced），消费端可感知命中。
- 缓存三层：
  - `InMemoryModInformationOperationCache`（操作内）
  - `JsonModFileFactsCache`（持久，FileFacts）
  - `JsonModInformationCache`（持久 JSON 信封）：路径 `data/indexes/mod-information/{kind}_{nodeId:N}_{generation}.json`，

#### 关键结论：中心只覆盖了"Mod 派生事实"，另一半在中心之外

护甲页卡顿涉及的链路**恰好落在中心之外**，它们各自实现了（或干脆没有）缓存：

| 中心之外的服务 | 有无缓存/指纹 | 备注 |
|---|---|---|
| `GameDataMappingFactsService.MapAsync` | 只算 `MappingGeneration` 指纹，**无缓存** | 被 `GameDataArchiveBrowserService:42` 直接调用，未走中心 |
| `DeployedOverrideGraphService.BuildAsync` | **无缓存**，每次全量 SHA-256 校验 | 被 `:43` 直接调用；三个页面各自重复调用 |
| `AssetArchiveIndexService` | 有 fingerprint（SQLite 侧） | 自成体系，不属中心 |
| `RuntimeArmorRegistryService.ReadArmorCatalogAsync` | SQLite 直读（便宜） | 不属中心 |

即：用户的"缓存控制系统"设想 = 已有 `ModInformationCenter`；但要把护甲页治快，需要把上表前两项
**收进中心**（或至少按中心的 generation/cache 约定补齐），而不是新增第四套缓存。

#### 对"自建缓存控制系统"设想的评估（待向用户说明）

- 可行，且**不建议另起一套**：已有中心的接口、指纹、scope、合并、失效、诊断、架构测试全部可复用；
  新建第二套中心 = 正中用户最担心的"屎山/缓存山"。
- 正确做法是"**一个中心，向外扩**"：把 GameData 侧产品（MappingFacts / DeployedOverrideGraph）登记为
  `ModInformationKind`，配 Producer + generation key + 持久缓存。
- 主要设计障碍：中心目前以 `ModNodeId` 为键，而游戏数据侧事实是按"游戏数据目录 / 索引 generation"为键，
  需要一般化键模型（`GetAssetRelationSummaryAsync` 已是先例）。
- 真正的风险不在"有没有中心"，而在**指纹是否覆盖全部输入**：指纹漏掉任一依赖 → 静默返回陈旧数据。
  中心无法替生产端保证这点，必须靠生产端 + 测试。其次风险：scope×RequireFresh×合并×失效 四维组合膨胀，
  以及中心类本身膨胀（707 行）。缓解：保持中心只做通用"请求-生产-缓存"管道，业务语义留在 Producer。
- 必做守护：把架构测试从"禁止 new 缓存/生产者"扩展到"禁止业务代码直接调用
  `IDeployedOverrideGraphService.BuildAsync` / `IGameDataMappingFactsService.MapAsync`（必须经中心）"。

### 设计讨论：细粒度信息 / "组件系统"类比修正（2026-10-10，未实施）

用户主张：信息中心的价值在于 ①避免"分散优化后被遗忘" ②集中之后才有可能把任意一条信息**细分到很小的块**
（一个 mod 更新往往只改了图像或只改了名字，不该整体失效）。
举例：护甲映射页其实只要两样——"该护甲有没有被 mod 覆盖" + "覆盖它的 mod 的缩略图"；
如果为这么小的功能在外部单独优化是浪费，但集中在中心里按需细分就值得。用户类比游戏业界的组件系统（ECS）。

**我的评估（本轮结论）：**

- 方向正确，但类比需修正：ECS 的组件彼此**独立无依赖**；而信息事实之间**有依赖**（缩略图依赖 mod 文件、
  覆盖关系依赖部署图与映射）。所以正确的类比是**增量计算图 / 构建系统**（Salsa / rust-analyzer、Bazel、Nix）：
  「一张带依赖的 DAG，每个节点自带输入指纹，输入变则只有下游重算」。
  → 可抄 ECS 的**接口风格**（消费端声明式按需查询）；**不能**抄 ECS 的失效模型（组件独立增删）。
- **三种粒度必须分清，不能混为一谈**：
  1. **请求粒度**——消费端要什么（护甲页：覆盖? + 缩略图）
  2. **失效粒度**——什么变了（部署状态变了 / mod 图标文件变了）
  3. **存储粒度**——物理怎么落盘
  用户把 1 和 2 混在一起了。三者不必相同：**逻辑细分、物理分桶**。
  现有 `JsonModInformationCache` 是 per-`(kind,nodeId,generation)` 单文件；若把"护甲级"事实也做成 per-armor 文件，
  800 条护甲 × N 种属性 = 数千个小 JSON，文件系统开销反而成瓶颈。应"每事实类型一个文件装字典，
  条目级用 generation 判定失效"。
- **细分判据（何时值得拆）**：
  `细分收益 = Σ(避免的重算) − Σ(额外指纹探测成本) − 复杂度成本`。
  仅当"单条生产成本 ≫ 判断它是否过期的成本"**且**"属性之间变化频率不相关"时才拆。
  例：icon 与 name 同在 mod 元数据里、变化频率接近 → **可合**；override 与 icon 频率差异极大 → **应拆**。
  即细分应按**失效频率聚类**，而不是按字段数无脑拆。
- **集中最被低估的价值是"可观测性"**：`DiagnosticRecorded` / `ProductionStarted` 事件能让中心统计
  每条事实的命中率与生产耗时。有了全局数据，"该往哪细分"就是**数据驱动**而非拍脑袋。
  这是"集中"相对"分散优化"除复用之外的第二个决定性好处，直接回应了用户"分散优化容易忘"的担忧。
- **聚合投影不应独立持久化缓存**：像"护甲显示事实""覆盖关系"这类派生结果，应作为 DAG 的一个派生节点
  memoize，输入指纹变即自动重算；一旦给它单独落盘缓存，就又多了一个"会忘记失效"的缓存（回到屎山）。
- **细粒度只解决"后续失效"，不解决冷启动**：护甲页"每次启动首开慢"是冷启动问题，
  仍需"磁盘持久缓存 + 便宜的前置指纹门"；细粒度让**之后的**每次变更只重算受影响的块。

**护甲页的正确拆法（两条独立子路径）：**

| 子路径 | 事实 | 依赖输入 | 变化频率 |
|---|---|---|---|
| ① 覆盖关系 | 护甲 archive → 是否被 Unit 覆盖 + 赢家节点 | 部署状态指纹 + 游戏数据索引指纹 | 每次部署变 |
| ② 缩略图 | mod → 图片 | Mod 文件指纹 | 很少变 |

- ②**中心已经有了**：`RequestThumbnailAsync` / `IModThumbnailProducer`（`ComputeThumbnailGeneration`）。
- ①需要新增一个**细粒度**产品：只返回 per-armor 的 `bool + winnerId`，**不要**返回整个 browser snapshot。
- 护甲页据此分别向中心请求两项，各自独立失效——正是用户说的"只去找中心要缩略图，中心就只获取缩略图"。

**落地护栏（防屎山）：**
1. 中心用**数据注册**事实类型（`ModInformationKind` 表），而不是 30 个命名 `Request*Async` 方法。
2. 每个事实**必须声明依赖指纹列表**，中心据此自动传播失效（生产端只提供"怎么算"+"怎么算输入指纹"）。
3. **聚合/派生事实禁止持久化**，只能 memoize。
4. 测试：加"依赖声明完整性"测试（每个 kind 必须列出依赖）+ "改 icon 不重算 override"的行为测试。

### 相对设计文档 §15.3 的三处偏离（已在 §17.2 记录理由）
1. `RequestAsync` 多了 `FactReadOperation<T>` 形参——5 个方法各需不同底层输入，读取器不是按 kind 分派的工厂
2. 缓存身份是 `(FactKey, Revision)` 而非裸 `FactKey`——§0.4 原文就是 `(FactKey, RevisionKey)`，且 §3.3 把 L3 的 generation 归入 Revision；丢掉 generation 会让"同节点不同 generation 的并发请求"错误合并
3. `FactSubject` 增加 `LibrarySnapshot(nodeIds)`——`FileFacts` 是库快照级事实，节点集合是身份的一部分（旧实现靠它做精确失效），语义与旧实现逐字等价

### 顺手做掉的改进
