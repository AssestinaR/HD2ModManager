# 管理器对「一个 Mod 对象」的能力盘点与操作页融合设计

**日期：** 2026-10-26
**状态：** 只做盘点与设计，不改代码。
**前置：** 护甲部位命名已在 `2fe05ac` 收敛到 `ArmorStructure`，本文所有部位/身形术语沿用那一套。

---

## 0. 结论先行

Mod 详情页现在平铺 **22 个命令**（`ModDetailsPageViewModel` 的 22 个 `RelayCommand`，
其中约 16 个是带文字的可见按钮，其余是图标或内部刷新），
另外还有 5 个独立规划页、1 个护甲映射页、2 个全局设置区。

它们看起来五花八门，但按**用户意图**只有四类：

| 类别 | 用户心里的话 | 数量 |
|---|---|---|
| **改库内状态** | "把它挪个位置/改个名/删掉" | 3 |
| **改库内产物** | "把这个 Mod 的部署结果改一下" | 2 |
| **造**（产出一个新 Mod） | "我想要一个做 X 的新 Mod" | 10 |
| **看**（只读，不产出） | "我想知道它到底改了什么" | 4 |
| 无副作用 | 打开文件夹 | 1 |

真正需要用户决策的变量只有三个：**目标是什么**、**输出到哪**、**要不要立刻导入**。
现在这三个变量在 10 个"造"功能里各被问了一遍，这就是屎山的来源。

建议：把 Mod 页面重构成 **一个信息条 + 四个分区 + 一条统一执行底栏**，
"造"类全部共用同一个骨架（来源 → 目标 → 预览 → 输出 → 导入）。

## 1. 现状盘点（用户视角）

## 2. 用户视角的问题（为什么现在乱）

### 2.1 二十多个命令同等权重

按钮区没有分组、没有主次。"修改备注"和"生成替换其他护甲的模组"视觉上一样重，
但前者是一次文本编辑，后者是一整套规划流程。

### 2.2 每个"造"都是一份独立向导，重复了四遍

三份独立的底栏内容文件（`CustomModelConversionBottomBarContent`、
`MaterialPackagingBottomBarContent`、`SameKeyRebuildBottomBarContent`）
加上跨护甲页里内联的一套，都在问同一件事：

```
[浏览...]  [生成]  [✓ 自动导入 Mod 库]
```

用户在 10 个地方各回答一遍"输出到哪、要不要导入"。

### 2.3 "改自己"和"造一个新的"混在一起

- 「修复 patch」→ 产出新目录，**不改**当前 Mod
- 「切换（头盔合并）」→ **改**当前 Mod 的部署产物

两者在同一个按钮区，用户无法预判哪个会动到自己手上的东西。

### 2.4 同一件事有两个入口，且默认路径不同

| 事情 | 详情页入口 | 另一处入口 |
|---|---|---|
| 跨护甲替换 | 「生成替换其他护甲的模组」 | 独立规划页 |
| 自定义素体 | 「一键转为自定义素体」 | 护甲映射页的素体卡片 |
| 装饰 | 「生成装饰 Mod」/「批量生成装饰」/「编辑装饰 Mod」 | 无（只有这里） |
| 头盔合并 | 「头盔合并到盔甲并输出」/「切换」 | 无 |

用户不知道"我该点哪个"，因为两个入口的描述都在讲同一件事。

### 2.5 前置条件不可见

`CanUsePatchTools`、`CanRepairPatch`、`CanPlanCrossArmorTransfer` 等 18 个 `Can*` 属性
直接映射成 `IsEnabled`。结果是**一片灰按钮，但不告诉你为什么灰**。
用户看到的是"这个按钮点不动"，而不是"这个 Mod 没有 Patch 内容"。

### 2.6 产出物去哪了不明确

- 「修复 patch」「重构 patch」→ Manager 的 `Output/`
- 「跨护甲」「装饰」「素体」→ 用户选目录，可勾选自动导入
- 「头盔合并」「重打包」→ 用户选目录

同样是"生成"，落点规则有三种，用户得记住哪种是哪种。

### 2.7 装饰有 3+1 个入口，关系说不清

「生成装饰 Mod」「批量生成装饰」「编辑装饰 Mod」+「切换（附加装饰到主体）」。
前三个产出新 Mod，第四个改现有主体的 Overwrite。四者共享"装饰"这个词，
但作用对象和产物完全不同。

### 2.8 诊断散成 6 个按钮

「详情表格」「模型解析」「依赖图测试」「依赖图对比」+ 页面上的材质诊断、DataIndex 摘要。
前四个是按钮，后两个是自动刷新的文本。用户不知道什么时候该点哪个。

## 3. 融合原则

1. **按动词分组，不按实现分组。** 用户的心智是"改 / 造 / 看"，不是"Canonical / Direct-reuse / Repackaging"。
2. **"造"共用一套骨架。** 来源 → 目标 → 预览 → 输出 → 导入，五个步骤永远一样。
3. **前置条件变成状态，不是灰按钮。** 不能做的功能显示"需要：Patch 内容"，并给出一条修复建议。
4. **落点规则统一。** 所有"造"默认写到同一个 `Output/<Mod名>+<时间戳>+<动作>/`，
   勾选导入才进 Mod 库。
5. **一次执行只产出一个东西。** 现在「头盔合并到盔甲并输出」和「切换」是同一件事的两种落点，
   应该合成一个操作 + 一个"应用方式"选择。

## 4. 建议的页面结构（用户视角）

Mod 页面改成：

```
┌─ 信息条（固定）────────────────────────────────────────────┐
│ 名称 · 类型（标准/选项/装饰/ReShade） · 配置归属 · 部署状态  │
│ 版本兼容（Unit 版本 / Patch 指纹） · 冲突摘要                │
└───────────────────────────────────────────────────────────┘

┌─ ① 概览 ──────────────────────────────────────────────────┐
│ 它改了什么：Patch 组、条目数、AssetKey 列表、材质诊断        │
│ 部位摘要：胸部－护甲－健壮，左腿－内衣－通用（沿用统一命名）  │
│ 诊断详情：可展开的详情表格（原「详情表格」+「模型解析」合并）│
└───────────────────────────────────────────────────────────┘

┌─ ② 参与 ──────────────────────────────────────────────────┐
│ 加入配置 / 插入位置 / 设为选项 / 启用禁用 / 部署            │
│ （原选择栏里与"归属"有关的 6 个动作收进来）                  │
└───────────────────────────────────────────────────────────┘

┌─ ③ 修复（就地改，会动到手上的东西）────────────────────────┐
│ 修复失效 Unit · 重构 Patch · 资源重打包 · 规整护甲包         │
│ 每个都标注：改的是这个 Mod 的哪份产物、能不能撤销             │
└───────────────────────────────────────────────────────────┘

┌─ ④ 派生（产出一个新 Mod）──────────────────────────────────┐
│ 目标类型：[替换其他护甲] [头盔合并] [装饰包] [材质包] [素体] │
│ 选定类型后展开同一个骨架：                                   │
│   来源（自动填当前 Mod） → 目标（护甲/主体多选）             │
│   → 预览表（部位/命中/影响） → 输出位置 → [生成]            │
└───────────────────────────────────────────────────────────┘

┌─ 底栏（统一）──────────────────────────────────────────────┐
│ 当前操作摘要 · 预览计数 · 输出位置 · [生成] [生成并导入]     │
└───────────────────────────────────────────────────────────┘
```

**关键变化**：

- 22 个命令 → 1 个类型选择 + 1 个统一骨架
- "改 / 造"在视觉上分开（③ 和 ④ 是两个分区，③ 有醒目的"会改动现有产物"提示）
- 「切换头盔合并」和「头盔合并到盔甲并输出」合并成一个操作 + "应用方式：临时 / 导出新 Mod"
- 「详情表格」「模型解析」合并到 ① 的可展开诊断区
- 前置条件显示成"需要 X"，不是灰按钮

## 5. 代码视角：操作 → 干涉面

### 5.1 干涉面总表

| 操作 | CLI 对应 | 读 | 写 | 失效的缓存 | 前置 | 落点 | 可撤销 |
|---|---|---|---|---|---|---|---|
| 改名/备注/图像 | `mod rename` / `notes set` / `image set` | `library.json` | `library.json` | Mod 列表投影 | — | 库 | 是 |
| 删除 | `mod delete plan/apply` | `library.json` + 目录内容 | `library.json`、`.hd2modmanager-trash` | 全库投影 + 部署图 | 桌面端关闭 | 库 | 是（trash） |
| 加入配置 | `profile add/insert/move` | `profiles.json` | `profiles.json` | 部署图 | — | 库 | 是 |
| 设为选项 | `mod convert-to-option` | `library.json` | `library.json` | 全库投影 | 有主体 | 库 | 是 |
| 启用/禁用 | `option enable/disable` | `library.json` | `library.json` | 部署图 | 是选项 | 库 | 是 |
| 部署 | `deploy plan/apply` | 库 + GameData + 索引 | `Overwrite/`、部署状态、GameData | 部署图、材质诊断 | 游戏退出、双租约 | GameData | 是（deactivate） |
| 修复失效 Unit | `patch repair plan/apply` | Patch + `asset-index` | **新目录** | 无 | 有 Patch | `Output/` | 是（新目录） |
| 重构 Patch | 同上（batch） | 同上 | **新目录** | 无 | 有 Patch | `Output/` | 是 |
| 资源重打包 | `patch repackage` | Patch 条目 + 材质/贴图 | **新目录** | 无 | 有 Patch | 用户选 | 是 |
| 规整护甲包 | `equipment armor-normalize` | Patch + 装备表 | **新目录** | 无 | 有 Patch + 装备表 | 用户选 | 是 |
| 头盔合并（导出） | `equipment helmet-merge` | Patch + 装备表 | **新目录** | 无 | 有 Patch | 用户选 | 是 |
| 头盔合并（临时） | `host-derived plan helmet` | 主体 + 装饰状态 | 主体 `Overwrite/` | 部署图 | 已部署 | 库内 Overwrite | 是（关闭） |
| 跨护甲替换 | `equipment cross-armor` | Patch + `asset-index`（部位事实） | **新目录** | 无 | `Confidence==100` 的部位事实 | 用户选 | 是 |
| 自定义素体 | `custom-model convert` | Patch + 装备表 + `asset-index` | **新目录 + registry** | 护甲映射页、`wardrobe.links` | 有独占 Unit | 用户选 | 部分（registry 条目要手删） |
| 装饰包 | `decoration package` | Patch + 装备表 | **新目录** | 无 | 有 Patch | 用户选 | 是 |
| 批量装饰 | 同上（多主体） | 同上 | **新目录 × N** | 无 | 同上 | 用户选 | 是 |
| 编辑装饰 | `decoration edit` | `library.json` + Patch | `library.json` + 主体 Overwrite | 部署图 | 已导入装饰 | 库 | 是 |
| 材质拆分/替换/外链 | `material packaging`（GUI 专有） | Patch + 引用图 | **新目录** | 无 | 有 Patch | 用户选 | 是 |
| 护甲映射 | `armor-registry` / `wardrobe project` | registry + 装备表 + 工作区 | `armor-registry.protocol`、`wardrobe.links`、`wardrobe.masks` | 运行时轮询（1 秒） | — | 注册表目录 | 是 |
| 详情/诊断 | `mod analyze` / `unit show` | Patch + `mod-facts` | `logs/` | 无 | — | — | — |

### 5.2 三条清晰的边界

从表里能看出，操作其实只落在**三个位置**：

1. **库内状态**（`library.json` / `profiles.json` / `decoration-activations.json`）→ 可撤销，便宜
2. **库内产物**（`Overwrite/`）→ 可撤销，但会影响部署结果
3. **库外新目录**（`Output/` 或用户选的目录）→ 不可撤销（但也不破坏任何东西）

**融合的核心判断：用户按下按钮前必须知道这次落在哪个位置。**
现在这三类混在一起，只有"修复 patch"的提示文字里隐约提了一句"不会自动导入或部署"。

### 5.3 前置条件其实只有四个变量

18 个 `Can*` 属性看起来很多，但底层只有：

| 变量 | 影响哪些功能 |
|---|---|
| `HasPatchContent` | 所有"修复"与"派生"（12 个） |
| `IsDecoration` / `IsOption` / `IsReShade` | 装饰编辑、附加装饰、设为选项 |
| `asset-index` 是否可用 + 部位事实是否 `Confidence==100` | 跨护甲、素体（部位必须可信） |
| 游戏是否退出 + 库租约 | 部署、删除 |

**所以前置条件可以做成 4 个状态灯，而不是 12 个灰按钮。**

## 6. 事实与缓存

### 6.1 事实源（谁说了算）

| 事实 | 来源 | 粒度 | 谁在用 |
|---|---|---|---|
| 哪件护甲含哪些 unit、什么部位/身形/槽 | 注册文件 `generated_customization_armor_sets` | 件 | 跨护甲、素体、护甲映射、头盔合并、规整 |
| 一个 unit 自己的部位字符串 | unit TocData `CustomizationInfo` | unit | 衣柜树、unit show |
| 一个 unit 的 mesh 级部位 | `game_data_unit_parts`（件表覆盖 + 骨名 + 字符串） | mesh | 装饰、诊断摘要 |
| 哪个 Mod 改了哪些 AssetKey | `mod-facts.sqlite` | Mod | 详情、部署图 |
| 谁最终赢 | `asset-index.sqlite` + 部署图 | 全局 | 覆盖状态、冲突 |

### 6.2 缓存与失效边界

| 缓存 | 位置 | 什么时候失效 |
|---|---|---|
| 库快照 | `library.json` | 任何库内状态改动 |
| 配置 | `profiles.json` | 配置归属改动 |
| Mod 事实 | `data/indexes/mod-facts.sqlite` | 导入 / 重新分析 / 删除 |
| 资产索引 | `data/indexes/asset-index.sqlite` | 游戏更新（buildid 变）、索引重建 |
| 部署图 | 内存 + 部署状态文件 | 部署 / 停用 / 库改动 |
| 护甲映射协议 | `ArmorRegistry/armor-registry.protocol` | 护甲映射页"应用" |
| 运行时链接 | `ArmorRegistry/wardrobe.links` | 协议变更后由 `WardrobeLinkCompiler` 重编 |
| 衣柜掩码 | `ArmorRegistry/wardrobe.masks` | `wardrobe project` |
| 材质诊断 | 内存 | 部署变化 |

**关键事实：所有"造"类操作都不失效任何缓存**——它们只写新目录。
这就是为什么它们可以安全地合并在一个骨架里：无论用户在骨架里怎么试，都不会弄脏现有状态。

反过来，4 个"改"类操作（部署、编辑装饰、头盔合并切换、删除）会失效部署图和库投影，
**它们必须在视觉上与"造"分开**。

## 7. 融合的收益

| 指标 | 现在 | 融合后 |
|---|---|---|
| Mod 页按钮 | 20 | 1 个类型选择 + 4 个分区动作 |
| 重复的"输出目录 + 导入"UI | 4 份 | 1 份 |
| 用户需要记住的落点规则 | 3 种 | 2 种（库内 / 库外） |
| 灰按钮数量 | 18 个 `Can*` | 4 个状态灯 + 文字原因 |
| 同一功能两个入口 | 4 组 | 0（详情页为主，护甲映射页只留映射本身） |

## 8. 风险

1. **迁移期两套 UI 并存会加倍混乱。** 要么一次切换，要么旧按钮保留但收进"高级"折叠区。
2. **"造"的骨架要能容纳差异。** 10 个派生功能的输入差异很大
   （跨护甲要选目标护甲；素体要命名；装饰要选附着主体；材质包要选材质/贴图）。
   骨架只能统一"输出 + 导入 + 预览"，中间的目标选择必须各自实现。
3. **诊断合并有信息损失风险。** 「模型解析」输出的是完整 Unit 结构，塞进折叠区可能太长。
   建议折叠区里只放摘要，点"完整报告"再开窗口。
4. **不要在这一步动部署语义。** 部署是唯一碰 GameData 的路径，融合页面时它必须保持原样。

## 9. 建议的实施顺序
