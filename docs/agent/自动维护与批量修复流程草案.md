# 自动维护与批量修复流程草案

> 状态：讨论草案。本文只记录已达成的流程方向，不规定具体实现、数据结构或界面细节。

## 目标

管理器的重要目标之一，是识别因游戏更新而过时的 Mod，并在用户确认后，以安全、可回滚的方式批量修复可自动处理的 Patch。

Patch 是 Mod 的独立外壳；一个 Mod 可以包含多个 Patch。修复必须保留这种多 Patch 结构，不应将多个 Patch 合并为一个。

## 用户确认的维护流程

1. 应用启动时自动检查游戏数据是否变化。
2. 若发现 Game Data 资产索引过时，在主页提示用户“更新资产库”，但**不自动重建资产库**。
3. 用户确认后，更新 Game Data 资产索引。
4. 新索引完成后，自动检查全部 Mod 是否过时。
5. 主页展示检查结果，包括可修复、不可自动修复、正常和未确认的 Mod 数量。
6. 管理器不得自动重构 Patch；应等待用户确认“批量修复可修复 Mod”。
7. 用户确认后，管理器为本次批量操作创建一个安全的修复批次。
8. 批次成功提交后，重新分析相关 Mod，并按需要重新部署活动配置。

## 兼容性状态

Mod 的状态不应只有“过时/不过时”两种。草案状态包括：

- `Unknown`：尚未检查或结论已失效。
- `Current`：确认与当前游戏数据兼容。
- `OutdatedRepairable`：确认过时，且可由自动修复流程处理。
- `OutdatedUnsupported`：确认过时，但当前不支持自动修复。
- `RepairPending`：等待用户确认修复。
- `Repairing`：正在修复。
- `RepairFailed`：修复未完成，原始 Mod 保持或已恢复。
- `Repaired`：修复完成并通过内部验证。

兼容性结论应同时依赖 Mod 内容、当前游戏数据世代、检测器版本和修复器版本；游戏或 Mod 内容变化后，旧结论应失效。

## 多 Patch 修复语义

- 一个 Mod 的每个 Patch 均视为独立外壳。
- Same-key 修复采用一对一方式：每个原 Patch 重建为对应的新 Patch。
- 不合并多个 Patch。
- 输出 Mod 仍保留原有 Patch 集合及其 sidecar 关系。
- 批量修复以整个 Mod 为操作单位：所有需要修复的 Patch 都成功后，才提交该 Mod 的修复结果。

## 备份批次

备份不放在 Mod 库目录，而放在管理器便携目录中，以避免污染 Mod 扫描、部署、导出和指纹计算。

建议的逻辑结构：

```text
管理器目录/
  backups/
    <时间戳批次>/
      backup.json
      mods/
        <Mod 原库内相对路径>/
          Patch 与 sidecar 文件
```

每次用户确认的批量修复对应一个时间戳备份批次。`backup.json` 作为该批次的索引与审计清单，记录参与的 Mod、原始路径、原始指纹、修复结果、Patch 结果、报告位置和恢复状态。

备份使用独立文件拷贝，不使用硬链接，确保后续替换不会影响备份内容。

## 失败与提交原则

- 候选生成或内部验证失败时，原 Mod 不应被修改。
- 候选阶段失败的 Mod 不进入最终备份批次，仅在批次报告中记录失败。
- 只有候选准备完成后，才为可提交 Mod 建立最终备份。
- Mod 库的替换应以安全、完整的提交方式进行，避免 Patch 或 sidecar 半写入。
- 提交失败时，必须保留备份并进入可恢复状态；不能直接删除备份。
- 一次批量修复完成后，应重新分析并重新检查结果，避免重复修复或无限循环。

## 部署原则

不要依赖“直接修改硬链接内容”来保持部署同步。修复完成后，应由管理器统一处理活动配置的重新部署，使硬链接、软链接和复制部署方式得到一致结果。

## 主页信息方向

主页后续应能呈现：

- Game Data 是否更新、资产索引是否过时。
- 更新资产库的确认入口。
- 全部 Mod 的兼容性检查进度与汇总。
- 批量修复可修复 Mod 的确认入口。
- 最近修复批次的结果、报告与恢复入口。
