# P4b 规划：VPK 模型合并到一个独有部件后专属切换

日期：2026-11-14。上接 `kit-instance-vpk-exclusive-plan-20261114.md`（P4a，已提交 18c1f6b）。用户已于 2026-11-14 要求做 P4b，2026-11-14 用户已拍板 §7：F1–F4 全部按推荐。

## 1. 要解决什么

P4a 的专属切换要求：模型的每个部位（slot × 身形）在目标护甲上都有**只属于它**的原版部件来承载。138 套护甲里只有 53 套满足。玩家神射手 `3970674111` 不满足，因为它的躯干、胯、腿、手臂全跟别的护甲共用。

爱弥斯民主官说明了另一条路：只要目标护甲有**一个**独有部件，把整个模型放进这一个部件，再把其余原版部件按实例隐藏，就能做到专属。P4b 就是把这条路做进「专属」开关。

## 2. 数据（Release 索引，138 套身体护甲，不含披风；“独有”指只被这一条记录引用，「任意身形」的部件两种身形都算）

| 类别 | 单条记录 | 同名记录合并看 | 说明 |
|---|---|---|---|
| 两种身形都有独有**躯干** | 97 | 102 | 模型可以合并进躯干 |
| 有独有部件但不是躯干（肩、胯、腿） | 10 | 12 | 只能合并进非躯干部件，第一人称风险见 §4 |
| 至少一种身形没有任何独有部件 | 31 | 24 | 仍然做不了 |

对照：P4a 能做的 53 套全部在第一行里。

神射手：
- 单条看，玩家神射手 `3970674111` 一个独有部件都没有。它的左肩 `90b57e54`（健壮）/`755f0bcd`（苗条）也被 `1490803405` 引用。
- `1490803405` 和它同名（FS-05“神射手”），归档 `ccac0a57`，用途未知。把这两条当成一组，左肩就是这一组独有的，神射手就能做。
- 民主官 `124623533` 有自己的左肩 `82595b5d`，不受影响，爱弥斯照旧。
- 代价：穿 `1490803405` 的单位也会显示模型。

## 3. 方案

### 3.1 规划器（在 `SectionalExclusivePlanner` 上扩展）

1. 先按 P4a 逐格找承载件。全部找到就按 P4a 走，**行为不变**。
2. 有格子找不到时，进入合并模式：
   - **主承载件**：每种身形选一个目标独有的部件。优先躯干；没有躯干才用别的槽位，顺序是胯、腿、肩。
   - 有自己独有承载件的格子仍按 P4a 单独承载（混合方案，§7 F3）。
   - 找不到承载件的格子，几何**合并进同身形的主承载件**。
   - 任一身形连主承载件都找不到，整个失败（沿用 E2）。
3. 「独有」的判断可以放宽到同名记录组（§7 F2）：拥有者集合只要落在同名组内就算独有。预览里列出同组其它记录，提示「它们也会显示这个模型」。
4. 隐藏集、签名、规则名、头盔：全部沿用 P4a。签名取主承载件。

### 3.2 几何合并

- 复用仓库里唯一的几何合并代码 `SectionalSplitter` + `CanonicalDecorationUnitAppender`：按名字哈希对齐骨骼，重算剔除包围盒。
- 新情况：要把多个 slot 的 section 合进一个 unit，原有代码只合同一个 slot。需要确认这几件事：
  - 承载件自己的骨骼是否够用。肩部 unit 可能没有腿和躯干的骨，缺骨时要补节点还是失败，需要实现方先查明。
  - 材质槽数上限。
  - LOD。
  - `BoneInfo.Remaps`。
  - 物理骨（physbone）。
- 写出仍走 `SectionalUnitPatchWriter` + `OverwriteMaterializer`，带 `VpkRekey` 标记，有备份和回滚。

### 3.3 界面

- 「专属」下拉的状态从两种变成三种：
  - **可专属**（逐格，P4a）；
  - **可专属·合并**：附「模型合并进 躯干/左肩…」；
  - **不可**。
- 主承载件不是躯干时，预览加一行警告：「第一人称可能看到模型」。实机结果出来后，这行定稿或删掉。
- 预览照旧列出落点、隐藏件、头盔，另外列出被合并的部位。

## 4. 风险（只能实机回答）

1. **第一人称。** 游戏在第一人称下隐藏躯干和头盔。
   - 合并进躯干：模型在第一人称整个消失。如果手臂也被合并进躯干，加上原版手臂被按实例隐藏，第一人称**可能看不到手臂**。需要实测。
   - 合并进肩部：第一人称不会隐藏它，模型的身体可能挡住镜头。`ArmorCell.cs:47-51` 明令禁止躯干几何挂到别的槽位，就是因为这个。很可能是硬伤。
2. 骨骼和物理骨挂到一个 unit 上之后，动画是否正常。
3. 签名在 0.3 米半径内是否还能稳定命中。肩部承载件离根节点比躯干远。

## 5. 实测顺序（用户）

1. **躯干合并**：选一套在第二类、但不在 P4a 53 套里的护甲（实现方从数据里挑一套玩家能穿的给出名字），对雫做专属切换。进游戏看：
   - 第三人称整体；
   - 第一人称有没有手臂；
   - 动作和物理有没有问题。
2. **神射手（左肩合并）**：同上，重点看第一人称有没有东西挡镜头。
3. 两项都确认其它护甲是原版、民主官仍是爱弥斯。

结果怎么处理：
- 第 1 项不行，P4b 整体放弃，回退代码。
- 第 2 项不行，只保留躯干合并，非躯干的情况标「不可」，原因写「只能合并到肩/腿，第一人称会挡镜头」。

## 9. 结果（2026-11-14）

### 实现了什么
- **规划器**：`SectionalExclusivePlanner.BuildWithMerge`。P4a 能逐格承载就原样返回；否则合并模式：每种身形选主承载件（躯干 → 胯 → 腿 → 肩），有自己独有承载件的格子仍逐格承载，缺的格子合并进主承载件；「独有」放宽到同名记录组；签名取主承载件；非躯干承载时加「第一人称可能看到模型」警告；同组其它记录列在预览与警告里。头身合并时，躯干没有第二层就把头并进合并 unit。
- **几何合并**：新增 `SectionalUnitMerger`（宿主 = 第一个来源 unit，其余当 donor，复用 `CanonicalDecorationUnitAppender`，每段独占材质槽、包围盒取并集）。`SectionalUnitPatchWriter` 能写合并产物；`SectionalCompiler.Exclusive.cs` 合并分支先在来源副本上预烘关闭的 section，再合并，组表不写。
- **界面**：下拉三态（可专属 / 可专属·合并（实验）：合并进 X / 不可：…）；预览标「合并（实验）」并列出合并清单、同名记录、第一人称警告。
- **共享代码改动（一处，默认关闭）**：见下。

### 卡在哪里、开关改了什么
真实 VPK Mod「雫」的 7 个 unit，skin palette 里有原版 Avatar 骨架没有的自定义骨（头 30 个、躯干 4 个、胯 2、左腿 1、右腿 1、右臂 1）。`CanonicalTransformInfoExpander.EnsureHash` 对 donor palette 里每根骨先查 Avatar，查不到就抛，所以现有 appender 合并雫的任何部位都会失败（旧版拆件只处理原版骨，没碰到过）。
开关：`CanonicalTransformInfoExpander.Expand(..., allowTargetOwnedBones = false)`，`CanonicalDecorationUnitAppender.TryAppendLodFamily(..., allowTargetOwnedBones = false)`。打开时：骨不在 Avatar 但宿主 TransformInfo 已有同 hash → 复用宿主节点（不改它）；宿主也没有 → 仍抛。只有 `SectionalUnitMerger` 传 `true`；其它调用方（CanonicalDecorationUnitAppender 的旧调用、SameKeyCanonicalUnitRebuilder、CanonicalCrossArmorOrchestrator、UnitAuthor）一行没改。`CanonicalTransformInfoExpanderTests` 新增两条（开关打开复用宿主骨 + 关闭时照旧抛；宿主也没有时打开也抛），原有两条不变。
雫能合并是因为躯干（宿主）已包含胯/腿/臂需要的全部自定义骨。别的 Mod 如果 donor 有宿主没有的自定义骨，仍会在编译时失败并给出骨 hash。

### 离线验证了什么
- 真实索引（138 套护甲）：P4a 逐格 53、躯干合并 49、非躯干合并 12、不可 24，与 §2 一致；P4a 的 53 套结果逐项不变（头身合并开/关）。
- 神射手 3970674111：P4a 不可 → 合并进左肩（`90b57e54…`/`755f0bcd…`），列出同组 1490803405，带两条警告。民主官的左肩不受影响。
- 合并几何（雫，6 个身体 unit 合一）：LOD 数与宿主一致（4 级）、每级 section 数 = 来源之和（30）、三角形一个不少、材质槽互不相同、BoneInfo 每级一致（57 骨，Remaps 30 条 = 槽数）、包围盒包住宿主的盒。
- 端到端编译（雫 → CE-67 躯干合并、→ 神射手左肩合并、含「关掉一个 section」）：`Overwrite/` 里只有承载件，无来源 unit、无披风，承载件归目标记录/同名组/同套头盔记录所有；合并产物的 section/三角形数与来源一致，关掉的 section 不再贡献三角形。
- 没有游戏 data 目录时合并编译明确失败，不写半套。

### 没验证的（只能实机）
- 自定义骨 / 物理骨（`physbone-rig.bin`）挂到另一个 unit 之后，动画和物理是否正常。合并 unit 里的骨节点、BoneInfo 在离线检查里结构正确，但游戏怎么用它没验证。
- 第一人称：躯干合并会不会看不到手臂；左肩合并会不会挡镜头。
- 签名在 0.3 米半径内是否稳定命中（尤其肩部承载件）。
- 合并后「就地开关 section」不再支持：改勾选要再点一次「切换」。
- 观察（P4a 遗留，未改）：P4a 规划器按部位只取一个来源，不区分来源 unit 的身形；VPK 产物的 7 件都是「任意身形」所以没有影响，若来源有健壮/纤细两套会取错。

### 实测建议
1. CE-67“泰坦”（item_id 4081083564）：躯干合并，对雫专属切换，看第三人称、第一人称有没有手臂、动作与物理。
2. 玩家神射手（3970674111）：左肩合并，重点看第一人称有没有东西挡镜头；`1490803405` 也会显示模型。
3. 其它护甲是原版，民主官仍是爱弥斯。

## 10. 实机失败复盘（2026-11-14）：宿主缺 donor 的自定义骨

**现象**：用户在真实库里把 VPK Mod 切到 FS-05 三条记录（3970674111、1490803405、124623533），三次都报「合并几何失败：DecorationTransformExpansionFailed Canonical Avatar TransformInfo does not contain required bone hash 0x046d44f9」。

**为什么测试是绿的**：测试只用了「雫」（3730700338）。`0x046d44f9` 不在雫的任何 unit 里（也不在 Avatar 里）；它是刚导入的另一个 Mod「蚀骨魂龙-伊莎贝娜」（3621723720，unit 前缀 `46ca388f…`）的**胯 unit（0003）**的 19 根自定义骨之一。该 Mod 各部位 unit 的自定义骨互不相同（头 20、躯干 3、胯 19、左臂 1、右臂 1），躯干宿主一根都没有胯的。雫恰好是「躯干包含所有身体 donor 要的骨」，所以 §9 的「复用宿主已有的骨」够用；这个 Mod 不够。

**修法**（仍然只在 P4b 合并路径打开，默认行为不变）：
1. `CanonicalTransformInfoExpander`：开关 `allowTargetOwnedBones` 打开时，一根骨不在 Avatar 里的处理顺序是 ① 宿主已有就复用；② 宿主没有就从**第一个带这根骨的 donor 自己的 TransformInfo** 搬进来（局部变换、矩阵、increment 照搬），**父链按 donor 的父关系递归解析**（父可能是 Avatar 骨、宿主已有骨或另一根 donor 自定义骨）；③ donor 里也没有可用父链（根/越界）仍然抛，不硬塞。没有把整套 Avatar 骨架塞进去。
2. `SectionalUnitMerger`：宿主改选**自定义骨最多**的来源（并列保持传入顺序）。合并结果最后写到承载件的键上，宿主是谁和写到哪里无关；选得好只是少搬几根骨。
3. 测试：`CanonicalTransformInfoExpanderTests` 里 3 条（宿主已有则复用；donor 独有则连父链搬入且默认关闭仍抛；donor 父链坏掉开关打开也抛）；真实数据两条——任何 VPK Mod 的全部 unit 轮流排第一都能合成一个（调色板骨全部进结果、父下标都在表内、Remaps 条数 = 材质槽数），以及 FS-05 三条 + CE-67 × 头身合并开/关「能规划就必须能编」。蚀骨魂龙与雫两份真实 Mod 上全绿。

**仍然只能实机验证**：搬进来的自定义骨在新宿主里的骨骼动画、物理骨（`physbone-rig.bin` 按骨名挂，搬运后是否仍生效）、第一人称。搬运时父链的 `Matrices`（绑定矩阵）照 donor 搬，前提是各部位 unit 的骨骼空间一致（同一具素体导出，目前的 VPK 产物如此）。

### 10.1 实机第二个问题：身体对了但没有头（神射手）
**现象**：蚀骨魂龙 → 神射手 3970674111，身体正常，但是原版 FS-05 头盔直接扣在模型脖子上。**原因**：FS-05 的头盔 unit `ffc28ef4b7c57c38` 被 8 条同名头盔记录共用（202045192、255960702、910516311、1146282869、1386151525、2070152922、3642074737、3826757243，set 都是 285623237，别的记录不用它）。头盔规划仍按「拥有者数 = 1」判独有，永远找不到，走了 E4：保留原版头盔，头被丢掉（P4a 时 DS-42 的老问题同类）。
**修法**：头盔承载件也按同名组放宽——拥有者全在「同套 ∪ 同名」的头盔记录（外加目标护甲自己）里就算独有；**只在合并这一遍放宽**，P4a 逐格那一遍仍严格，所以 P4a 的 53 套与 DS-42 的结果不变（真实数据测试逐项核对）。放宽后头落在 `ffc28ef4…` 上，头盔组里其余原版部件按 P4a 规则隐藏。预览多一条：「同名的 N 条头盔记录都会显示这个头」。（曾加过一条点名民主官 NPC 的警告，用户确认 NPC 不戴头盔、头部也已被另一个 Mod 遮挡，已删除，预览不写民主官相关内容。）
**测试**：规划器真实数据（头落在 `ffc28ef4…`、含 8 条提示、预览不含民主官相关内容）；编译真实数据在雫与蚀骨魂龙上各断言写出了 `ffc28ef4…`。
