## 骨架兼容性

原版玩家 90 根，现代 SEAF 88 根，**68 个骨名相同，共用骨名的排列顺序也不同**。玩家独有的骨包括 `cape1` 至 `cape8`、`support_mg`、`backpack`，SEAF 独有的骨包括 `jaw`、眼睛、眼睑和 `weapon_aim_l` / `weapon_aim_r`。源模型可以用同名骨作为重定向起点。要按士兵 Unit 的静止姿态、目标骨序和蒙皮矩阵重建权重，并显式处理玩家专属骨影响，避免直接沿用玩家索引或舰船 NPC 的 69 骨头部修补逻辑。全局替换 SEAF 的骨架还会影响共用者。

## 实施方案

1. **选品器**沿用 `KitNpcRecords` 与 NPC 套装行的入口，给现代 SEAF 本体一个稳定的内部 ID。目标条目单独保存归档、`unit` 资产键和骨架引用。先支持头身合并的模型，行名体现覆盖对象是 SEAF 士兵整体。
2. **转换**以原版 `75f7e96af7dcd303` 及 `7a3637cd33a54e4c` 的骨架为目标。保留原版 Unit 的挂点、物理、IK、状态机和剔除结构。保留游戏引用的网格标识及 LOD 路由，构建各档可见网格，验证人物组和装甲组同时启用时只显示预期几何。附件资源及其共享材质继续由原版提供。
3. **打包和回读**使用本项目的生成流程，写现代本体及自有模型的派生材质与贴图。回读检查目标键、骨骼索引与矩阵、各档材质闭包、原版挂点和生成条目。检查包中没有原版共享骨架、灯效、旧本体或武器的覆盖。两套参考 Mod 的状态机 payload 都和本机原版有差异，首轮使用当前原版状态机验证兼容性。
4. **细分兵种和环境**先从角色配置追踪网格可见性、材质参数和背包绑定。查明可独立控制的绑定后，再为相应兵种或环境规划独立行。四个兵种和四套配色用于验收，离线先查近远 LOD 和背包挂点。

## 验证范围

- 用仓库已有 `hd2mod gamedata extract asset` 导出 9 个原版资产，包括现代本体、三个背包、两个灯效、两套骨架和旧本体。再用独立读取器从 NXA 读取，导出的每个 TOC 和存在的 GPU payload 都逐字节匹配。主键的只读查询示例为 `hd2mod gamedata extract show e0a48d0be9a7453f 75f7e96af7dcd303 792b2a2ba11ae85d --game-data <data> --json`。
- 两个参考 ZIP 均直接读取 TOC，按 `(TypeId, FileId)` 对比原版。三个背包及主 Unit 的几何身份通过离线顶点和索引投影确认。临时导出已清理。
- 本阶段完成资源调查、原版导出和独立回读。自有模型的转换、生成补丁及补丁回读属于实现阶段。四种兵种和环境的配置绑定、旧本体出现场景仍待确认。应用代码和游戏数据未改动。
