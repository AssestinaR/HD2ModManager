## 2. 结论：缺的不是编译器，是「容器 + 变体池」

- 我们**能**写 HLSL、**能**编译成 DXBC（F10），也**能**读引擎 ABI（F5 的 RDEF/ISGN/OSGN）。
- 缺的是把 DXBC 装进引擎认识的载荷容器（F4/F7），以及选对变体键。
- 因此本计划聚焦「容器格式」这一件事，其余（HLSL、编译、材质 TocData）都是已知能力。

## 3. 步骤与验收（每步都有硬判据，不靠观感）

| 步骤 | 产出 | 验收判据（硬） |
|---|---|---|

## 4. 风险与边界

- **变体键未知**：引擎按材质特性选变体，键的编码未解；S1 必须同时把「记录里的键字段」找出来，否则 S5 可能装进去了却不被选中。
- **同尺寸替换优先**：S3 先做「等长替换」，避免动长度字段；S2 证明能改长度后再推进。
- **不进游戏的部分全部离线**；S3/S5 各需一次重启，且每轮只改一个变量。
- **不作为**：不接触反作弊、不修改游戏可执行文件、不联网；只在 `E:\mod` 下的 patch 里做实验。

## 4.1 S1 现场记录（2026-11-14，按轮累积）

### 已确认的容器骨架（目标 mod 的载荷，4,037,328 B）

```
0x00 u32   记录数 179（33 份本体样本同为 0xb3）
0x04 u32   根材质 id 低 32 位
0x08 u32   文件长度 - 8
0x0C u32 A / 0x10 u32 1 / 0x14 u32 B / 0x18 u32 C(最大段) / 0x1C u32 D
0x20 u32 E / 0x24 u32 0x2C / 0x28 u32 F / 0x2C u32 G(记录条数 36/20)
0x30 u32 哈希 / 0x34 u32 1
0x40 …     记录区
0x42D80    首个 DXBC
```

- DXBC 的块表是**偏移数组**（`+28` 块数，`+32` 起每项 u32 偏移），每块 = `fourcc + u32 size + data`；`RDEF/ISGN/OSGN/SHEX/STAT`（部分带 `PCSG`）。
- 相邻 blob 间距呈「小(顶点) / 大(像素)」交替（7424 / 50168 / 6408 / 50112 …），与 116 VS + 156 PS 相符。

### 变量描述表（材质侧）

- 记录形如 `{id(4) offset(4) elemSize(4) count(4)}`，材质的 **82 个变量 id 全部命中**，其中 77 个集中在 `0x40000..0x41e08`。
- 关键字段：`opacity@0x7c`、`metallic@0x58`、`basecolor@0x70`、`opacity_sharpness@0xa0`、`opacity_offset@0x120`、`clearcoat_roughness@0xe0`、`subsurface_thickness@0xa4`。

### 值区定位的两条否定结论（不要再重复）

1. 头部四个候选基址（`0x416bc/0x416e8/0x416f0/0x41e08`）+ 上述偏移 → 全为 0，**不成立**。
2. 载荷里搜不到 `(0.01,0.01,0.01,0.5)`、`(0,1,1,1)`、`(0,0,0,0.01)` 等材质真值 → **载荷存的不是 TocData 变量值的直拷**，而是编译期折叠后的常量。

### 已证明「生效」的字节（唯一且可复现）

- 载荷内 34 处 `(0.01,0.01,0.01)` 字面量：改成 `(0,1,0)` → 丝袜**消失**；说明它落在实际使用的像素着色器的**指令立即数**里（不是 RGBA 缓冲）。
- 20 处 `mov o0.w, l(0.25)` → 改 0.80 **无变化** → 那不是丝袜使用的 pass。

### 当前待读的实验

- 34 处三元组改为 `(1.0, 0.01, 0.01)`（仅 R 通道 0.01→1.0）：变红 = 底色；变实 = 阈值/不透明度；又消失 = 开关量。备份 `.abtest-backup\20261114-141832-redtest\`。

## 4.2 S1 第二批结论（同日，记录级）

**载荷记录图已建立**（工具：`.dsh/tmp/payload_parse.py`）：

- 272 条 DXBC 记录 + 271 段空隙；记录覆盖 **83.8%**（3,381,884 / 4,037,328）。
- 空隙呈两种固定尺寸：**92 字节** 与 **3,780 字节**（各 271 段交错）。
- 每条记录的块集合恒为 `RDEF+ISGN+OSGN+SHEX+STAT`（部分另有 `PCSG`）。

**决定性发现：材质参数被"折叠"进着色器代码**

- 那 34 处 `(0.01,0.01,0.01)` 字面量 **34/34 全部落在 DXBC 记录内部**（0 处落在空隙里）。
- 也就是说：这份载荷按材质**特化**过，材质参数是**指令立即数**，不是可调常量块 → 这解释了为什么改 TocData 的变量值 100% 无效（引擎根本不用它）。

**新的技术障碍（下一步要解）**

- 这 34 个"含材质字面量"的 blob，`fxc /dumpbin` **全部失败**（34/34），而同一载荷里其它 blob 有 23/30 可正常反汇编。
- 它们的 `STAT` 段内容与正常 blob 不同构（`12 00 00 00 01 00 00 00 06 …` vs `fa 04 00 00 22 00 00 00 00 …`），怀疑是**另一类着色器容器**（或 STAT 采用不同版本）。
- 下一步：手工解析 SHEX token 流（绕过 fxc），或者解出这批 blob 的容器差异；拿到 `o0.w` 的写入路径后，才能定位"不透明度"的立即数。

### 4.4 第四批：拿到「作者的改动到底是什么」（同日，关键）

拿本体的 `advanced` 根材质（`0xef9b3fc2fc1ba61e`）载荷里的同名材质 pass 记录（60,412 B）与作者那份（62,652 B）逐块对比：

| 对比项 | 结果 |
|---|---|
| 记录字节差 | **206 B（0.34%）**，其中大半是尺寸位移导致的错位 |
| SHEX 长度 | 本体 49,980 B / 作者 52,220 B（**作者多 2,240 B**） |
| SHEX 内 token 差异 | **52 个**（共约 12,495 个） |
| 第一处实质差异 | SHEX `+29,872`：本体 `0.01` → 作者 `1.0`（后随两个 `0.01`） |
| **收尾指令** | 本体：`mov o0.w, l(1.0)` （**常量 1.0，不透明**）<br>作者：`mov o0.w, <寄存器>` （**alpha 是算出来的**） |

**结论：作者干的事就是把「不透明度」从常量 1.0 改成"由一段新增代码计算出来的寄存器值"**，那段代码就是多出来的 2,240 字节（约 560 条指令，位于 SHEX 尾部）。

也就是说：
- 这不是"换根材质/调参数"能得到的，**确实是改了着色器并重新编译**（印证 F6：93 个唯一 DXBC 里 64 个本体没有）；
- 但改动**范围极小**：一个立即数 + 一段尾部代码 + 一个输出寄存器替换。

### 4.8 读懂了 alpha 的算法（自研 SM5 反汇编器）

工具：`.dsh/tmp/sm5disasm.py`（opcode 表与操作数编码依据 DXBC 规范；SHEX 数据前面有 8 字节 `version + length`，必须跳过）。

作者版材质 pass 的尾部（`SHEX +51,4xx` 起）是一条以 **N·V** 为自变量的 alpha 曲线：

```
dp3  r21.w = dot(normal, view)          ; N·V
add  r21.x = N·V + (-0.21)              ; 立即数 @ SHEX+51,476
mul  r21.x = r21.x * 1.2658228          ; 立即数 @ SHEX+51,504（=1/(1-0.21)）
max  r21.x = max(r21.x, 0)
mad  r21.y = r21.x * (-2) + 3
mul  r21.x = t*t ; mul r21.x = t*t      ; t^4
mad  r21.x = -t^4 * (3-2t) + 1
mul  r27.w = r21.x * r21.x              ; alpha = 上式的平方
mov  o0.w  = r27.w                      ; ← 写进输出 alpha
```

即 **alpha = (1 − t⁴·(3−2t))²，t = saturate((N·V − 0.21) · 1.2658228)**。

代入两次端点即可对上肉眼观察：
- `N·V = 1`（正对）→ t≈1 → **alpha = 0（全透）**
- `N·V = 0.21`（掠射）→ t=0 → **alpha = 1（不透明/全黑）**

这正是"正面透、边缘黑"的来源，也证明它确实是**重编译过的着色器**而不是参数。

### 4.11 字节码级改写（第一个"改行为而不只是改常量"的证据）

做法：把曲线里的 `mul rX.x, rX, rX`（7 个 dword：指令 + 3 个操作数各 2 dword）替换成 **7 个 `nop`**（`0x0100003A`），等长、不需要动任何长度字段。

- 目标：`+51564` 与 `+51592` 连续两条 `mul`（`0x07000038`），后者是 `t⁴` 的第二段；打掉它即把曲线从 `t⁴` 变成 `t²`。
- 实测：该 14-dword 模式在载荷里出现 **10 次**（正好是 10 份材质 pass 副本），全部改写成功。
- 校验（改写后回读）：`[56, 18, 21, 10, 21, 10, 21, 58, 58, 58, 58, 58, 58, 58]`
  → 第一条 `mul` 保留，第二条被 7 个 `nop` 取代，长度不变。
- 效果差异（数值）：`t=0.5` 时 `t⁴` 版 alpha≈0.766，`t²` 版 alpha≈0.25 —— 肉眼可见。

产物：`%TEMP%\milfy-inspect\milfy-payload-t2.bin`（**未部署**，只作离线验证；部署需用 `tools/payload_repackage.py replace` 等长替换）。

意义：**我们可以在不重编译的前提下改写着色器行为**（等长指令替换）。这是"自己产载荷"路线之外的第二条可行通道。

### 4.12 工具化：`tools/payload_material_profile.py`（观感 profile，一条命令切换）

```
python tools/payload_material_profile.py <payload> --show
python tools/payload_material_profile.py <payload> --threshold 0.6 --curve t2 --apply
python tools/payload_material_profile.py <payload> --threshold 0.21 --curve t4 --apply
```

**定位方式（不靠猜）**：alpha 块由不变量识别 —— `mult * (1 + bias) == 1`，再加结构判据
（`bias+96` 处必须是 `mul` 指令 `0x07000038`；`bias+124` 处是第二条 `mul` 或 7×`nop`）。
实测命中 **34 个块**（与含该常量的记录数一致）。

块内偏移（相对 bias 立即数）：`+0 bias`、`+28 mult`、`+96 mul(t*t)`、`+124 mul(再平方)`。

**曲线切换**：
- `t2`：把 `+124` 的 28 字节换成 7 个 `nop`，并把原始 28 字节存进 sidecar `<payload>.curve-t4.bin`；
- `t4`：从 sidecar 精确还原（**不能**用 `+96` 处的 mul 覆盖，两者源寄存器不同：`0x…0a` vs `0x…1a`）。

### 4.18 容器头部表（0x40 起）的初步结构

### 4.19 为什么 fxc 拒绝那 34 个 blob —— checksum（本轮定案）

对照实验（都基于同一条 3,460 字节的记录）：

| 实验 | 结果 |
|---|---|
| 原样 | `fxc /dumpbin` **OK**（233 行） |
| **只把 checksum 字段（+4..+20）翻 1 个比特** | **FAILED** |
| 在 SHEX 里翻 1 字节（checksum 不变） | FAILED（这条也可能是真把指令改坏了，不作准） |
| 按 chunk 干净重建（块表/长度/total 全部自洽，只插了 4 个 `nop`） | FAILED |

→ **`fxc` 会校验 DXBC 的 128 位 checksum**。所以：

1. **作者那 34 个 blob 之所以全部无法反汇编，是因为它们的 checksum 是旧的** —— 说明这些着色器是**被字节改写过的**（改完没重算 checksum），而不是用 fxc 重新编译出来的。这和"作者只加了 2,240 字节尾部代码"完全吻合。
2. **游戏引擎不校验 checksum** —— 否则我们这些等长改动根本不会生效（实测生效过）。
3. 因此 **fxc 只能用来反汇编"未被改动过"的 blob**；我们自己的分析必须依赖自研反汇编器（`.dsh/tmp/sm5disasm.py`，已可用）。

已尝试但**未命中**的 checksum 算法：`MD5(blob[20:])`、`MD5(blob[32:])`、`MD5(zeroed)`、`MD5(zeroed[20:])`、
`MD5(chunk 数据)`、`MD5(blob[0:4]+blob[20:])`、以及把 total 一并清零的若干组合，全部 ≠ 存储值
（存储值样例 `ae85233d5a97eefd1294c28f425d7198`）。**这一项列为未解**。

### 4.28 曲线的真实去向：**光照混合权重**，不是材质 alpha（本轮定案）

对家族 A（`4bc0104d`，60,504 B，哈希一致的 8 份）逐指令追踪，曲线的完整链路是：

```
dp3  r34.w = dot(N, V)                 ; N·V
add  r34.x = N·V + (-0.21)             ; 阈值立即数
mul  r34.x *= 1.26582 ; max 0
mad  r34.y = t*(-2)+3 ; mul t*t ; mul t*t   ; t^4
sample_l t[2] (抖动纹理) ; mul *0.266
mad  r34.x = -t^4*(3-2t) + 1
mul  r40.w = r34.x * r34.x             ; 曲线值
mov  r6.w  = r40.w
...
max  r1.xyzw = r6.xyzw, 0
mov  o0.xyzw = r1.xyzw                 ; **o0.w = 曲线**
ret
```

**语义结论**：`o0.w` 是**光照 pass 输出 alpha**，引擎按它把光照合成到画面上：

| `o0.w` | 含义 | 观感 |
|---|---|---|
| ≈1 | 该像素**完整接受光照** | 正常皮肤 |
| ≈0 | 该像素**几乎不受光** | 发黑（"黑丝"） |

因此"随视角变化的半透明"实际上是**用 N·V 抑制光照**造成的错觉，而不是材质层的 alpha 混合。
这也彻底解释了：改材质 TocData / 改材质 pass / 换 albedo / 改 parent —— 全都无效。

（注：`r34.y` 在我当前的反汇编输出里既被用作 `3-2t` 又被用作抖动坐标，说明操作数解码仍有小误差；
已用 `fxc` 在**未改动**的本体载荷上交叉验证过主体结构，此处细节留待需要时再校。）

### 4.32 旋钮矩阵：`T` 与 `M` 各自控制什么

曲线 `t = saturate((N·V - T) · M)`：

| 参数 | 作用 |
|---|---|
| `T`（bias = -T） | **起点**：`N·V ≤ T` 的区域 `t=0` → `alpha=1`（完整受光） |
| `M`（归一化系数） | **陡度与方向**：`M>0` 时 `N·V` 越大越"黑"；**`M<0` 时方向翻转**，`N·V` 越小越黑（黑边） |
| 曲线指数（`t⁴ → t²`） | 过渡带的软硬；`t²` 更平缓 |

已预生成的成形档位（家族 A，8 条，全部等长）：

| 文件 | T | M | 预期观感 |
|---|---|---|---|
| `variant_famA_T050_Mn2p0` | 0.50 | **-2.0** | **黑边**：轮廓处最黑、正面受光 |
| `variant_famA_T021_M3p0` | 0.21 | 3.0 | 陡过渡（黑得更集中） |
| `variant_famA_T021_M0p6` | 0.21 | 0.6 | 缓过渡（黑得更散） |
| `variant_famA_T035_M4p0` | 0.35 | 4.0 | 起点外移 + 陡过渡 |

实测锚点：`T=0.21/M=1.2658`（原始）→ 黑丝；`T=0.60/M=2.5` → 光腿；`alpha≡1` → 光腿。

### 7.2 为什么"改数值无效、改常数也无效"（最后一条解释）

实测汇总（全部为家族 A，8 份同时改）：

| 改动 | 曲线输出 | 观感 |
|---|---|---|
| 原始 `T=0.21` | **随 N·V 变化** | 黑丝 |
| `T=0.60` | 大部分 ≈1 | 光腿 |
| `T=0.00` | 大部分 0.77~1 | 光腿 |
| `alpha ≡ 0` / `0.5` / `1` | **恒定** | 光腿（三种都一样） |
| 抖动幅度 `0.266 → 0` | 退化为常数 1 | 光腿 |

**唯一出现黑层的条件是：输出必须随视角（N·V）逐像素变化。**

> 也就是说，可见的"黑丝"是这段代码产生的**空间图案**（抖动/逐像素差异）在缩放观察下的整体效果；
> 一旦把输出抹平成常数——无论常数是 0、0.5 还是 1——图案消失，画面就回到"完整受光 = 皮肤"。
> `T` 改变的是图案的**密度分布**，所以能影响观感；常数替换抹平图案，所以三种常数看起来完全一样。

这条解释与代码里确实存在 `sample_l t[2]` + `* 0.266` 的抖动路径一致。
**尚未验证**：把抖动幅度改成 0 时 alpha 退化为常数 1，因此该实验**无法区分**"抖动是来源"与"常数导致失效"——
需要一次"**保留图案、只改密度**"的实验（例如改抖动纹理采样的坐标缩放）才能定案，但那需要改动更多字节，且没有编译器辅助定位。

## 8. 路线修正（宏观）：从"改一个样本"改为"建材质库 + 载荷移植"

### 8.1 判断

- 这份样本只能证明"**根材质可以自带编译载荷**"，它本身是"拿本体 advanced 改字节"的产物（checksum 为旧值），
  **不代表**作者有编译器，也不代表我们能借此写出任意效果。
- 真正可复用的资产是本体里 **550 个自带载荷的材质条目**（2062 条材质记录中 dxbc>0 的部分）。
  "L4D2 式材质库"在 HD2 里的实现方式 = **挑一款已实现目标特性的本体根材质，把它的载荷移植给我们的材质**，
  而不是从零写 shader。

1. **选根**：按上表挑一款（例如"半透明+贴图" → `7b9f6c5638fcb231`）；
2. **造条目**：用 `build_adv_override.py` 同款写法生成一个单条目 patch（fileId 用新 id 或直接复用该根 id），
   TocData 原样、载荷原样；

| | 旧路线（改作者样本的曲线） | 新路线（材质库 + 移植） |
|---|---|---|
| 覆盖效果 | 只有"那一种黑丝" | 镂空/金属/自发光/半透明及其组合 |
| 依赖 | 作者的载荷 | 本体资产（不依赖任何第三方） |

**结论：路线确实需要修正——不是不该逆向载荷（那部分已经完成且有工具），而是不该把"复刻这一个样本"当作目标。**

## 9. 变长注入失败的第 5 个耦合点：头部「记录大小 + 32 位哈希」表

实测（本体 advanced 载荷 2,928,416 B）：

- 头部里存在 **每条记录的 (size, hash32)** 条目；
- 已知记录大小在头部**各出现一次**，紧随其后的 4 字节即哈希：

| 记录大小 | 位置 | 紧随的 32 位值 |
|---|---|---|
| 60,412（材质主 pass） | `0x3cb30` | `0xdd470739` |
| 2,092 | `0x3c2b0` | `0x2b3ee168` |
| 2,084 | `0x3c910` | `0xa651f1ef` |
| 13,848 | `0x3c9f0` | `0x93b33aeb` |

因此"把某条记录变长"必须同时改写：**该记录的 size 条目 + hash32**。
哈希算不出来 → 材质加载失败 → 用它的模型整片消失（两次实测都是这个现象）。

**已同步但仍失败的 4 个字段**（本轮做过的修正，证明它们不是全部）：
载荷头 `0x08`（长度−16）、载荷头 `0x18`（最大偏移）、材质 `TocData +16`（载荷字节数）、patch 条目 `gpuSize`。

### 9.1 下一步（离线可做，样本充足）

手头有 **550 个自带载荷的材质**、单份载荷内 **202 条记录**，每条都有 (size, hash32, 完整字节)：
足以对 hash32 做算法拟合。候选顺序：CRC32、FNV-1/1a、xxHash32、Murmur3-32、以及"内容前 4KB/全量"的不同取法。
一旦命中，"生成自己的载荷"就彻底打通。

### 9.2 另一条不依赖哈希的路

**保持记录长度不变**做代码替换：在同一条记录内**先回收等量的死代码**（例如该材质用不到的
阴影/天气/伤口分支，由 cbuffer 标志位门控、恒为 0），腾出空间再写入新逻辑。
这样 size/hash 都不变，只是记录内容变了——而"改内容不改长度"我们已验证过无数次能生效。
