# Manager 人机工效与自动流程讨论准备

**收集日期：** 2026-07-18
**范围：** `HD2ModManager` 的页面职责、自动行为、后台资源消耗和后续讨论问题。本文为讨论材料，不改变当前行为。

## 当前工作区与页面

| 区域 / 页面 | 用户任务 | 当前实现特征 | 初步工效关注点 |
|---|---|---|---|
| 首页 | 查看活动配置、库/配置数量、导入与部署摘要、修复部署能力 | 启动默认页面；同时后台恢复 derived facts、刷新派生状态、检查资产索引 | 用户看到首页时后台工作可能已经开始，但首页未统一解释“哪些工作正在自动进行、能否安全操作”。 |
| 状态页 | 查看路径、应用结果、任务队列、资产索引状态；手动重建索引 | 打开页面即异步检查索引状态；可启动索引重建 | 状态、后台任务和索引维护分散；应成为全局“正在做什么 / 为什么 / 可否取消”的单一入口。 |
| 配置页 | 创建/选择/激活配置、维护启用 Mod 与加载顺序 | Profile 修改同步调用 Core；活动配置修改会通知自动部署 | “编辑配置”与“立即影响游戏文件”的关系需要清楚呈现；批量排序/移除应避免重复触发部署与派生重算。 |
| 模组库 | 搜索、选择、加入配置、编辑元数据、删除、打开目录 | 每次筛选和状态刷新都重建 `Items`；状态由 `DerivedStateCoordinator` 投影 | 大库下的列表重建、搜索即时刷新、缩略图、状态重投影可能影响滚动与输入响应。 |
| 模组详情 | 查看事实、覆盖/材质状态；按需打开高级详情；same-key 重建、cross-armor 计划、材质包装 | Same-key 直接输出到 Manager `Output` 且禁止自动导入；其他候选工具仍在逐步迁移 | 高风险写出操作与只读诊断混在同一详情页，需分层为“概览—诊断—创建候选—验收/部署”。 |
| 高级详情窗口 | 资产级事实、筛选问题 | 明确按需加载并支持取消 | 表格规模大时需要虚拟化、延迟筛选或分页；关闭窗口后的取消行为应在 UI 中可见。 |
| Cross-armor 计划窗口 | 选择 source/target、自动匹配、手动改写/抑制映射、生成候选 | 多个属性 setter 同步 `GetAwaiter().GetResult()` 重算计划 | 最明显的 UI 阻塞风险：每次选择、偏好或手动映射变化都在 UI 线程同步规划；应采用防抖、取消、后台计算和“应用更改”节流。 |
| Cross-armor 候选输出窗口 | 选择输出目录、生成候选、查看报告 | 候选生成已后台执行 | 应明确不可逆风险、所需验收、候选与正式部署的差异。 |
| 材质候选 / 材质包装输出 | 分离、替换、嵌入 Material/Texture 资源 | 从详情页按需触发 | 应明确资源闭包、回退策略、是否会改变 Unit 输出，并将耗时扫描放进统一任务系统。 |
| Game Data 索引窗口 | 浏览 archive、筛选覆盖状态、查看 archive 详情 | 基于持久化索引；行双击异步读取详情 | 索引库大时 `ObservableCollection` + `CollectionView` 的客户端筛选/排序可能重；详情打开应支持 loading/cancel。 |
| 设置页 | 配置游戏 data 与 Mod 库路径、语言 | Loaded 时提示语言并刷新 | 路径改变后应明确哪些缓存、索引、派生事实失效，提供可预测的重建时机。 |
| 后台任务窗口 | 查看和取消任务 | 与 `BackgroundTaskService` 对接 | 需统一展示任务优先级、资源类型、预计影响与取消后的恢复状态。 |

## 启动与自动行为

`ShellViewModel` 初始化时会并行触发下列工作：

1. 加载模组库，但暂不构建 derived data；
2. 后台恢复全库稳定 derived facts：`RefreshDerivedDataAsync()`；
3. 启动 `DerivedStateCoordinator.RefreshAsync()`；若活动配置存在，会建立内容 facts、预期覆盖图、材质诊断，以及已部署覆盖图；
4. 检查 Game Data 资产索引指纹；索引缺失或过期时自动低优先级重建；
5. 激活配置或活动 Mod 内容改变时，会通知部署协调器执行自动部署/更新。

### 当前自动时机的风险

- 启动阶段可能同时发生全库 facts 重建、活动配置派生分析、部署图扫描和 archive 索引重建；虽然部分在后台，但 I/O、CPU、SQLite 和 UI 刷新会竞争。
- `DerivedStateCoordinator` 用取消和单一 gate 合并 refresh，但每次 profile/content 事件仍会请求刷新；连续编辑时用户看不到“旧任务已被合并/取消”。
- 状态页构造后立即索引状态检查；启动时也检查索引，存在重复读取和重复任务语义的可能。
- 导入完成后会立即对新增/变化 Mod 重建 derived facts；若导入队列连续处理多个大型 archive，可能与全库恢复、索引重建及活动配置分析叠加。
- active Profile 的单项新增、移除或排序会触发部署通知；批量操作缺少明显的事务/防抖边界。

## 已识别资源热点

| 热点 | 触发位置 | 资源类型 | 讨论方向 |
|---|---|---|---|
| Game Data archive index | 启动检查、状态页手动构建 | 大量磁盘读取、解析、SQLite 写入、CPU | 首次安装/版本变更才自动；常规启动只读指纹并延后；限制并发，显示 ETA/可暂停。 |
| 全库 derived facts | 启动恢复、导入后刷新 | Patch 扫描、facts 投影、I/O、SQLite | 分级：先显示已有缓存，再按可见页/活动配置优先增量更新；避免全库阻塞。 |
| 活动配置派生状态 | profile/content/mapping 变化 | 内容 facts、override graph、材质诊断、部署图 | 将“编辑草稿”与“提交/应用”分开；合并短时间连续变更；让用户选择自动应用或手动应用。 |
| 导入 archive / folder | 导入队列 | 解压、文件复制、Patch 扫描、事实建立 | 预检大小/条目数；队列可排序；导入与 facts 分阶段；为失败提供可重试的阶段信息。 |
| cross-armor 计划刷新 | 计划窗口的属性修改 | Unit catalog/planning，当前可能 UI 线程阻塞 | 必须异步 + cancel + debounce；只在用户确认或停止输入后计算；缓存 source-target 组合结果。 |
| same-key / cross-armor 候选生成 | 模组详情 / 输出窗口 | Unit/sidecar 读写、Game Data 查询、材质闭包 | 统一为后台任务；任务开始前显示输入摘要、预计影响、输出目录和验收要求。 |
| 高级 Mod 详情 | 打开高级详情 | 资产查询、材质包装 state、交付 facts | 按 tab/lazy load；表格虚拟化；按需只加载可见数据。 |
| 库列表刷新 | 搜索、profile/derived snapshot 更新 | LINQ、对象重建、WPF collection layout | 采用 `CollectionView` 过滤或增量 diff；输入防抖；保留滚动与选择。 |
| 缩略图预生成 | `ThumbnailService.PreGenerateAll` | 图片解码、PNG 编码、单一全局锁、磁盘 I/O | 低优先级且可暂停；按可见项按需生成；锁粒度从全局缩小到单文件/缓存键。 |
| Mod 库迁移 | 首页 | 全库复制 + 对每文件 SHA-256 双哈希 | 显式向导，展示空间/文件数/预计时间；可恢复、可跳过已有相同文件；不应作为普通首页动作。 |

## 讨论时应先定下的产品策略

1. **自动化默认值**：索引、facts、部署、材质诊断分别是“自动立即”“自动延后”“仅活动配置”“仅按需”中的哪一种？
2. **编辑与生效的关系**：配置页是否继续每次操作自动部署，还是改为草稿 + 明确“应用到游戏”？
3. **后台任务协议**：所有重任务是否必须拥有名称、阶段、可取消性、资源类型、触发原因、完成后的下一步建议？
4. **优先级**：用户可见页面与用户主动操作是否始终抢占启动维护和预生成任务？
5. **缓存策略**：哪些结果按游戏版本/Mod 内容 hash/profile revision 缓存，哪些变更应只失效局部？
6. **风险操作层级**：重建候选、材质包装、跨护甲、部署应如何明确区分“预览 / 写到候选目录 / 应用到游戏”？
7. **信息架构**：是否把首页收敛成操作入口，把状态页变成唯一任务/维护中心，把 Mod 详情拆成概览、诊断、修复工具三个层次？

## 建议的讨论顺序

1. 先确定“配置编辑是否自动部署”与“启动允许自动做哪些维护”。
2. 统一后台任务模型和任务中心信息层级。
3. 优化 cross-armor 计划窗口的同步阻塞与候选流程的分步反馈。
4. 优化库列表/高级详情的大数据体验和按需加载。
5. 最后讨论视觉层面的导航、双栏工作区、浮动操作按钮和页面信息密度。

## 已确认的补充事实

- 参考项目 `docs/参考项目/PCL-main` 的有效借鉴点是集中颜色/状态资源、统一 `MyButton` / `MyTextBox` / `MyComboBox` 模板，以及仅用于 hover、focus、展开的短动画；不得复制其源码、资源或视觉资产。
- Manager 目前至少有高级 Mod 详情、cross-armor 计划/输出/手动选择、材质候选/输出、same-key 输出、Game Data 索引/详情、后台任务等内部模态窗口；这些应逐个迁入页面工作区，系统文件选择器和最终危险确认除外。
- Same-key 已确定不需要独立页面：单 Mod 操作直接导出至 Manager `Output`，不允许自动导入或部署。设置页后续将在 Game Data 状态检测后增加“检测更新后自动重建损坏 Mod”开关，并增加一次性“重建所有损坏的 Mod”按钮；全量任务按“重建 Game Data 资产缓存 → 比较全库损坏 Mod → 修复全部护甲类损坏 Mod”执行。自动化能力本轮暂不实现，临时手动结果同样只写入 `Output`。
- 删除库 Mod 后配置页和详情页残留的根因已定位：Core `DeleteNodeAsync` 会移除 Profile entry，但 Manager `ModLibraryService.Remove()` 没有触发 `SnapshotChanged`，使 Shell 未重新加载 Profile snapshot。此项应列为首批同步修复。
- 详细的页面、控件、任务中心、设置资产卡和分批落地方案见 [manager-ux-redesign-plan.md](manager-ux-redesign-plan.md)。
- 已更正页面槽位规则：普通 Mod 详情保持单槽；高级详情才转为双槽，且高列数资产表必须跨全部槽位。配置页不新建汉堡菜单，而是收敛现有 `PageActions` / `FloatingActionCluster` 浮动菜单。
- 已完成 `docs/参考项目/new-api-main` 默认 Web UI 的卡片与数据表研究。其可借鉴的是 token → 基础控件 → 表格编排的分层、首次加载与后台刷新区分、固定表头/横向滚动/列预设和卡片化数据投影；详细结论见 [new-api-ui-table-reference-analysis.md](new-api-ui-table-reference-analysis.md)。
