`+0x3e564b / 0x0 0x0` 与 11-11 物理那一轮的签名相同，也是本仓注释里写明的

**这些转储没法用来走栈**：它们是游戏自己在崩溃处理器里用 `dbgcore.dll` 写的，
写的时候崩溃线程的栈已经被处理器自己的帧覆盖 —— 我们只能看到
`dbgcore / ntdll / runtime.dll` 的残帧，`记录地址 = 0x0`。
`HKLM\…\LocalDumps\helldivers2.exe` 虽然配了 `E:\tmp\hd2-crashdumps`（DumpType=1），
但**那个目录不存在** ⇒ WER 从来没写过（游戏自己处理掉了崩溃）。
⇒ 要干净的栈只能外部抓首次机会异常（procdump `-e 1 -ma -w`），见 §6。

## 5. 代码审查找到的两处漏洞（已修，2.1.40）

### 5.1 `skirt_apply` 不判活

它每帧遍历**所有会话**、并且在 `drive` 末尾（`pruneSessions` 之后）跑。
进来就对 `session.unit` 调 `num_scene_graph_items` / `world_position` —— 这两处都是
**原生 AV 的来源，`pcall` 拦不住**（本文件早就写过同一条）。修：进循环先
`Compat.unit_alive`，并且跳过 `session.dead ~= nil` 的。

### 5.2 `skirt_refs` 的节点下标缓存从不失效

`session.skirtRefs` 缓存的是 hips/chest/l_thigh/r_thigh 的**节点下标**。unit 被重建
（换装 / 切 LOD / 军械库换预览件）之后，同样的下标会指向别的节点甚至越界；
对越界下标读 `world_position` 就是野读。
`session_health` 只在**每 30 帧**比一次节点数 ⇒ 中间那 30 帧是盲区（而且"节点数恰好不变但节点换了"
这种情况它永远发现不了）。
修：`skirt_refs` 每帧比一次节点数（`session.skirtRefsCount`），变了就重新解析。

> 代价：每个会话每帧多一次 `num_scene_graph_items`。相对裙摆本身每帧 4 次取位可以忽略。

## 6. 验证

- `runtime-harness-test.lua` 新增 **T23**（裙摆开关用调参文件打开，rig 的链根挂在 `hips` 上）：
  - 两件都挂上；裙摆确实在跑（日志里有 `[physbone][裙摆]`）；
  - 杀掉其中一件之后，它的骨头**一次都不许再被碰**（按引擎调用计数验证）；
  - **节点数变了之后必须重新解析参照点**（`has_node` 调用数必须增长）——
    这条是 5.2 的守门员：把缓存校验去掉，它会红（实测 `32 → 32`）。
- Lua 全量回归：**461 通过 / 0 失败**。
- 说明：5.1（判活闸）目前是**纵深防御**——正常路径下 `pruneSessions` 会在同一帧把它丢掉，
  所以 T23 里即使去掉那道闸也仍然是绿的。真正抓住窗口的是 5.2。

  `has_node` 漂移"仅观察"那行日志。要彻底解决得有一个"unit 版本号"之类的判据。
