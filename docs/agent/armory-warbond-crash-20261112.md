## 5. 代码审查找到的两处漏洞（已修，2.1.40）

### 5.1 `skirt_apply` 不判活

它每帧遍历**所有会话**、并且在 `drive` 末尾（`pruneSessions` 之后）跑。
进来就对 `session.unit` 调 `num_scene_graph_items` / `world_position` —— 这两处都是
**原生 AV 的来源，`pcall` 拦不住**（本文件早就写过同一条）。修：进循环先
`Compat.unit_alive`，并且跳过 `session.dead ~= nil` 的。

### 5.2 `skirt_refs` 的节点下标缓存从不失效

`session.skirtRefs` 缓存的是 hips/chest/l_thigh/r_thigh 的**节点下标**。unit 被重建
（换装 / 切 LOD / 军械库换预览件）之后，同样的下标会指向别的节点甚至越界；
对越界下标读 `world_position` 就是野读。
`session_health` 只在**每 30 帧**比一次节点数 ⇒ 中间那 30 帧是盲区（而且"节点数恰好不变但节点换了"
这种情况它永远发现不了）。
修：`skirt_refs` 每帧比一次节点数（`session.skirtRefsCount`），变了就重新解析。

> 代价：每个会话每帧多一次 `num_scene_graph_items`。相对裙摆本身每帧 4 次取位可以忽略。

## 8. 2.1.41：判活改成"不碰句柄"的指针成员检查

### 8.1 用户补的关键现象（把机制钉死了）

> 打开债券页后只要不动页面就不崩；慢慢等一会、再缓慢切换一个页面也不崩；
> **超级快速切换页面则立刻崩溃**。而且展台上的角色在加载出来后 1~2 秒会被上物理。

"慢切不崩"是因为页面切换往往伴随一次**较大的帧间隔** ⇒ 命中了"加载空档"那道闸
（整组丢弃、一条存活都不查）。"快切必崩"没有空档 ⇒ 回到逐条查存活 ⇒
`pruneSessions → session_health → Unit.alive` 就是**对已释放内存的一次 deref**
（`0x3e564b` / 参数 `0x0 0x0`，和 11-11 是同一个签名）。`pcall` 拦不住原生 AV。

### 8.2 改法

`drive` 每帧先做**两件不 deref 句柄**的事：

1. `Application.worlds()` → 我们缓存的 `runtime.world` 还在不在（**指针相等**）。不在 ⇒ 整组丢弃；
2. `World.units(runtime.world)` → 拿到引擎**当前**的 unit 数组；每个会话按**指针**查成员。
   不在列表里 ⇒ 判死（日志记 `指针判死`），**一个 Unit API 都不调**。

只有"在列表里"的会话才允许继续走 `session_health` / 写骨 / 裙摆。

代价：每帧一次 `World.units()` + 会话数 × 数组长度的指针比较（≈10 × 2000，无分配），
比原来"每会话每帧一次 `Unit.alive`"更便宜也更安全。

### 8.3 测试（T24，有咬合力已验证）

把 unit 从 `World.units()` 的返回里摘掉、**但让 `Unit.alive` 仍然返回 true**（模拟"引擎已释放、
句柄仍指向旧内存"）。断言：它的骨头一次都没再被碰、会话被丢弃、日志出现"指针判死"。
把成员判死去掉后实测变红（`nodes+1 world+10 write+8 has+1`）—— 正是实机崩溃前的行为。

## 9. 用户定的方向：从引擎 API 拿"玩家身份"，而不只是修这一次

> "我们有必要从游戏公开的 api 中想办法拿到任何与玩家有关的信息，尽量确保只能计算玩家的物理，
> 否则我们这里可能修了，但以后还会有别的地方冒出来一个虚拟玩家造成性能浪费或严重的崩溃。"

两根独立的柱子：

| 柱子 | 问题 | 状态 |
|---|---|---|
| 生命周期 | 句柄失效后怎么不把自己炸死 | ✅ 2.1.41（§8） |
| **身份** | 这个 unit 到底是不是玩家身上的护甲 | ⏳ 探针已就位，等实测数据 |

API 现状（本机 09:22 的清单：Unit 119 / World 72 / Application 70）：

- 已可用：`World.units_by_resource(world, avatar 资源)`（列出所有玩家）、`has_animation_state_machine`、
  `World.num_units`、`Unit.debug_name`。
- 已判死：`Unit.resource_name`（**崩溃**，笔记里标了禁止）、`World.unit_by_id`（一次 nil）、
  `EntityManager → UnitComponent.instances`（nil）。
- 待验（最有希望）：`Unit.is_child(A, B)` / `Unit.scene_graph_parent(unit, node)` —— 若它们能回答
  "这件护甲是不是那个 avatar 的子/被链接者"，身份就从启发式变成**结构事实**。

### 9.1 身份链探针（已落地，默认关）

调参文件写 `probeIdentityLink = 1` 打开（`>= 2` 表示强制从第 N 步开始；写 0/删掉即关闭）。
它**只在已经有会话时**跑一次，只读，结果只进日志；每一步**先落盘再调用**：

```
%LOCALAPPDATA%\hd2pbx_ident_probe.txt   ← next = N（崩了下次从这里续）
%LOCALAPPDATA%\hd2physbone.log          ← [身份链] #N 开始 … / #N ⇒ 类型 值
```

七步：`debug_name`（对照）→ `is_child(护甲, avatar)` → `is_child(avatar, 护甲)` →
`scene_graph_parent(护甲, 1)` → `scene_graph_parent(avatar, 1)` → `id(护甲)` → `id(avatar)`。

⚠️ 这些 API 签名未知、且 2026-11-12 曾在默认路径上把游戏打死过，所以：
默认关、独立开关、静态护栏（`skirt-guard-test` 要求它们只能出现在两个探针函数里）、
独立断点文件（不要和 `hd2pbx_probe.txt` 混用 —— 那个已被另一个一致性电池占用）。

### 9.2 判读与分支

- `is_child(护甲, avatar) == true`（穿着的件）⇒ 把它作为 `tryAttach` 的硬判据：
  只挂 avatar 的子件 ⇒ 展台/预览/尸体自然被排除，虚拟玩家消失。
- 返回 false / 抛错 ⇒ 该 API 不成立，退回"同世界 + 最近 avatar + 跟随"，身份仍靠 `motion_follows`
  逐步收敛；生命周期那根柱子保证"收敛之前也不会崩"。

## 10. 实测结果（用户 2026-11-12 17:47，探针开着、继续快切债券页）

### 10.1 身份链探针：七步全跑完，**全部返回 nil**

```
#1 ⇒ string #ID[5c44f3fe7b7c0001]     ← 对照项：debug_name 可用，且这是一件**穿着**的护甲
#2 is_child(护甲, avatar)        ⇒ nil
#3 is_child(avatar, 护甲)        ⇒ nil
#4 scene_graph_parent(护甲, 1)   ⇒ nil
#5 scene_graph_parent(avatar, 1) ⇒ nil
#6 id(护甲) ⇒ nil      #7 id(avatar) ⇒ nil
```

⇒ **"结构关系"这条路（至少用这些签名）拿不到答案**。`is_child` 返回 nil 而不是 false，
更像是签名不对或该 build 不支持；`scene_graph_parent(unit,1)` 为 nil 也正常（节点 1 可能就是根）。
所以身份不能靠"谁是谁的子"，得换判据。

### 10.2 崩溃仍在，而且**不是**"驱动了已消失的成员"

- 转储仍是 `+0x3e564b` / 参数 `0x0 0x0`；
- 新加的成员检查日志里**没有** `指针判死`，也没有 `世界已不在` ⇒ 死点不在那条路径上；
- 崩溃前最后一段：17:48:51（f10880）一口气 attach 了 **7 件**（`可用链 1/2/10 条`，全是展台件），
  然后日志就断了。同一帧里还有 `[裙摆][父骨] unit=…0001/0002/…` 的 7 条记录。
- 同一时段的心跳：`已挂载 7 个 unit / 41 条链（玩家 1 个：玩家1=7件）`、
  `跳过 102 个离它所属玩家超过 5.0 m 的护甲件`。

**新认识**：债券页会把**整套外观的 7 个件**（`5c44f3fe7b7c0001…0006`）全部实例化成展台件，
而场上只有 1 个 avatar（玩家自己）。所以"1 个玩家 + 7 件同款"在军械库是**展台**，不是穿着 ——
恰好和 11-12 上午"9 件同款"那个现象同源。

### 10.3 2.1.42：两组诊断开关（都默认关）

| 开关 | 作用 | 打开后 |
|---|---|---|
| `phaseLog = 1` | 每帧在 attach / 写骨 / 裙摆 / identity_watch / scheduler / refresh_distances 各打一条 `[相位]` | 崩了看最后一条就知道死在**哪个阶段** |
| `identLog = 1` | 每次挂载成功后打一条 `[识别·位置] unit=… hipsΔ=0.xxx m` | 用来验证"hips 重合"能不能当身份判据 |

### 10.4 下一个身份候选：**hips 重合**

真正穿在身上的护甲，`hips` 骨与 avatar 的 `hips` 骨几乎同点（同一副骨架、被同一套动画驱动）；
展台件站在台子上，哪怕离你很近，`hips` 也会差出几十厘米到几米。
这条判据只用我们已经在读的世界坐标，比"离谁最近"锐利得多 —— `identLog` 就是为了先量一遍分布
（穿着件应当 < 0.1 m；展台件应当 > 0.3 m），再决定阈值。

若分布确实分得开，`tryAttach` 就加一条硬判据：**只挂 hipsΔ 小于阈值的件**，
展台/预览/尸体自然被排除，虚拟玩家消失 —— 这也是用户要的"只给玩家算物理"。

## 11. 真凶找到了（2.1.43）：`refresh_avatar_distances` 在读**已销毁的 avatar**

### 11.1 相位日志一锤定音

用户 17:58 带 `phaseLog = 1` 复现，日志最后一条是：

```
17:58:12 f11301   [physbone][相位] drive 开始
17:58:12 f11301   [physbone][相位] refresh_avatar_distances 前
（没有「后」，进程死）
```

⇒ 死在 `refresh_avatar_distances` 里面。它每帧做的事是：

```lua
for index = 1, #avatars do
    local ax, ay, az = readVector(S_, try(S_.Unit.world_position, avatar.unit, 1))
```

——对 **`runtime.avatars` 里每个 avatar 句柄**取世界坐标。而这个名单是**上一帧**的。
债券页/军械库切页时引擎会**连续重建 avatar**（展台上那个角色本身就是 avatar 资源），
句柄一失效，这一行就是野读 ⇒ `0xc0000003`… 实际是 `0xc0000005` / 参数 `0x0 0x0`，
和 11-11 那次同一个签名。`try` 只包了 pcall，拦不住原生 AV。

这也解释了 2.1.41 为什么没挡住：那道闸只管**会话的 unit**，没管 **avatar 名单**。

### 11.2 改法

同一道"指针成员检查"闸扩到 avatar：

- `drive` 开头只要"有会话**或**有 avatar"就刷新活体列表（原来只在有会话时刷）；
- 不在列表里的 avatar **从名单里摘掉**，一个 Unit API 都不调；
- 名单空了 ⇒ `runtime.avatar/avatarTag` 置空并立即安排重扫；没空 ⇒ 同步成还活着的第一个
  （`lift` / 第一人称锁定都会拿它发引擎调用）；
- `refresh_avatar_distances` 循环里再加一次防御性成员检查。

### 11.3 验证

- 新增 **T26**（有咬合力已验）：让 avatar 从活体列表消失、但 `Unit.alive` 仍返回 true，
  断言"一次都没再对它取世界坐标" + 日志出现「avatar 已不在活体列表里」。
  去掉 avatar 过滤后实测变红（`world+10`）。
  ⚠️ 这条用例必须先把假引擎的"相机"接上：`refresh_avatar_distances` 拿不到相机时会整段早退，
  那样根本咬不到真凶（第一版就是这样假绿）。
- Lua 全量回归 **476 通过 / 0 失败**。

### 11.4 顺带量到的身份数据（`identLog`）

17:57:54 那次挂载，七件护甲的 `hipsΔ` 全是 **0.000 m**，坐标与主人完全一致
（`0.10,-2.15,20.98`）—— 这符合"七个件都被挂在同一个 avatar 骨架上"（穿着态）。
展台件没进样本（它们被"距主人 > 5 m"过滤掉了），所以"hipsΔ 能不能区分展台"还**没有数据**；
要验就得对**被跳过的那些候选**也打一条（下一步再做，不影响本次修复）。
