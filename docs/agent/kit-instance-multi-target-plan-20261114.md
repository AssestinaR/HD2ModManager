# P5 规划：目标护甲下拉支持输入搜索和多选部署

日期：2026-11-14。上接 P4a（18c1f6b）、P4b（78e2b7b）、7a43e61。§6 已由用户在 2026-11-14 回答（见 §6 末尾），G2–G4 按用户的话改了方案。

## 1. 要什么

用户原话：「这个目标护甲下拉框再优化一下，能不能实现支持像 element ui 那样支持输入搜索+多选部署？」

拆成两件事：
1. **输入搜索**：下拉可以直接打字过滤，比如输入「神射手」或「3970674111」，只留下匹配的项。
2. **多选部署**：一个模型 Mod 同时专属到多套护甲，比如雫同时上 DS-42 和 CE-67，点一次「切换」就全部生效。

## 2. 现状（代码事实）

- 下拉是 `ModDetailsPageView.xaml:69` 的普通 `ComboBox`，单选，绑定 `VpkTargetArmors` / `SelectedVpkTargetArmor`。
- `wardrobe.json`（`VpkWardrobeFile`）只存一个目标：`TargetArmorArchiveId`、`TargetArmorName`、`TargetItemId`、`Exclusive`。
- 编译每次从 `sectional/` 重新生成整份 `Overwrite/`，带备份和回滚，只针对一个目标。
- 专属记录写在 `kit-instance.workspace.json`，按 ModNodeId 每个节点一条，规则名 `vpk-<item_id>-<节点前 8 位>`。一条记录已经可以展开成多条规则（P4a：头盔一条）。
- Hider 上限：64 条规则，每条最多隐藏 128 个部件，规则文件 64 KiB。

## 3. 方案

### 3.1 搜索（两种模式都有）

- 下拉改成可输入：打字时按名字和 item_id 过滤，不区分大小写。
- 专属模式下，「不可」的项排在最后、灰显、不能选，但仍然能搜到，这样用户能看到原因。

### 3.2 多选（只在专属模式）

- 专属模式的下拉改成多选：每项前面一个勾选框，选中的项显示成输入框里的标签，标签上的 × 可以单独去掉，和 element ui 的 `el-select multiple filterable` 一样。
- 点「切换」时，按**整个勾选集合**重新编译：
  - 每个目标照 P4a/P4b 规划；
  - 所有目标的承载件一起写进同一份 `Overwrite/`；
  - 规则按目标各写各的。
  - 不做增量：去掉一个勾再切换，就是用剩下的集合整份重编。
- 不同目标的承载件按定义不会重叠，因为承载件只属于各自的目标组。
- 同名组里的两条记录（比如神射手 3970674111 和 1490803405）会落到同一个承载件上，选了其中一条就等于覆盖整组。所以勾了一条以后，同组的其它记录自动显示为「已包含」。
- 预览弹窗按目标分段列出，最后汇总规则条数。
- 规则数超过 Hider 上限时，在预览里拦下并说明，这时还没写任何文件。

### 3.3 存储与兼容

- `wardrobe.json` 增加目标列表（item_id 和名字）。旧文件只有单个 `TargetItemId` 时，读成只有一项的列表。写回时单个字段也继续保留第一项，旧代码读到的仍然是合理的单目标状态。
- `kit-instance.workspace.json` 仍然每个节点一条记录，记录里改存多个目标，每个目标展开成自己的规则（规则名不变：`vpk-<item_id>-<节点前 8 位>`）。旧记录读成只有一个目标。
- 普通模式（专属关闭）保持单选，行为完全不变。

## 4. 风险

- 部署体积：每个目标多一份承载件，合并模式下每份是一整个模型 unit，大约几 MB。选 10 套就是 10 份。预览里显示总数。
- 编译时间按目标数线性增加，进度照旧走消息中心，可以取消。
- 多个目标里任何一个编译失败，整份回滚，不留半套（沿用 E2 和 `OverwriteMaterializer` 的回滚）。

## 5. 不做

- 普通模式的多选。普通模式会写全局空壳并隐藏被连带的护甲，两个目标会互相冲突。
- 拼音搜索。
- 改动 Hider 和 Lua。

## 6. 需要用户拍板

| # | 问题 | 推荐 |
|---|---|---|
| G1 | 多选只在专属模式提供，普通模式保持单选 | 只在专属模式 |
| G2 | 搜索能搜到「不可」的项，但灰显不能选 | 能搜到、不能选 |
| G3 | 选中同名组的一条后，同组其它记录显示「已包含」，不必重复勾 | 按此 |
| G4 | 任何一个目标编译失败就整份回滚，不部署部分目标 | 整份回滚 |

## 7. 测试与验收

- 单测：
  - 多目标规划互不重叠；
  - 同名组去重；
  - 规则数上限拦截；
  - 旧 `wardrobe.json` 和旧 workspace 记录的兼容读取；
  - 单目标的结果和 P4b 完全一致。
- 真实数据：雫同时专属到 DS-42（P4a 逐格）、CE-67（躯干合并）、神射手（左肩合并）。`Overwrite/` 里只有这三组的承载件，规则 3 组。
- 门：`dotnet build -c Debug` 0 警告 0 错误；`dotnet test -c Debug` 全绿；Release 用 `--no-incremental` 重建，并确认 ico 在 `g.resources` 里。
- 实机（用户）：上面三套分别穿上看；再去掉一个勾、切换一次，确认那一套恢复原版。

### 6.1 用户回答（2026-11-14，原话要点）

- **G1**：只在专属模式多选。按推荐。
- **G2（改）**：「不可」的护甲**禁用、不可选**。同名的多条记录要标清楚哪条是玩家穿的；正常只需要玩家护甲可选。神射手是特例，因为有民主官 NPC。
- **新增·全选**：要有「全选」，跳过禁用项，**只选玩家护甲**。
- **G3（改）**：同名组全选时只选玩家那一条，其它几条用户可以自己勾。取代「已包含」的设计：同名记录照常列出、各自可勾。
- **G4（改）**：编译失败时弹窗，让用户选：
  1. 回滚；
  2. 继续，跳过失败的目标；
  3. 继续并记住，以后再失败就自动跳过不再问。

### 6.2 由此带出的前置问题：哪条记录是玩家护甲

索引里没有「玩家可穿」字段，只有 item_id、dlc_id、set_id、归档和名字，dlc_id、set_id 都区分不了。已知的事实只有实测得来的两条：3970674111 是玩家，124623533 是民主官 NPC。

同名多记录的组：
- FS-05 3 条；
- B-01 9 条；
- CM-09、SC-30、B-24 各 2–3 条。

### 6.3 调研结果（2026-11-14）与定稿

- **本地游戏数据里没有依据。** 套装注册表的护甲记录只有 id、dlc、set、名字、稀有度、被动、归档和部件，没有商店或解锁信息（`HD2GameItemAssets/CustomizationArmorSetsReader.cs`）。战争债券和超级商店的数据在服务器上。
- **社区依据有两份，结论一致：**
  1. OneClickArmorSet 的 `RESEARCH.md`（MIT，2026）。它读游戏内的 offers 表，结论是：同一件护甲可以有多个可拥有的副本，B-01 有 9 个，B-24 有 3 个，FS-05 有 2 个；有些副本不在 offers 表里，谁也拿不到。
  2. helldivers-2/json 的 `items/armor/armor.json`，由官方 Items API 整理，2025-02 之后没再更新，新护甲没收录。它在三组同名记录里各漏掉一条：FS-05 124623533、CM-09 2107035846、SC-30 1969314276。
- **定稿：**
  - 同名的多条记录大多是玩家能拥有的不同版本，一般只差配色。
  - 非玩家记录只有 3 条：
    - FS-05 124623533，民主官 NPC，已实测；
    - CM-09 2107035846，拿不到；
    - SC-30 1969314276，拿不到。
  - 管理器内置一张小表，只列这 3 条非玩家记录，注明来源。其余有名字的护甲都算玩家护甲。以后出现新的非玩家记录再往表里加。
  - 下拉里：
    - 同名的玩家记录标「版本 1/2/…」，按 item_id 升序编号；
    - 3 条非玩家记录标「非玩家（民主官 NPC）」或「非玩家（拿不到）」，可以手动勾，但不进全选。
  - **全选（用户已确认）**：勾上所有可用的玩家护甲，同名的玩家版本全部勾上；跳过禁用项和非玩家记录。

## 结果（2026-11-14，P5 实现）

### 做了什么
- **搜索**：「目标护甲」换成自绘下拉 `VpkTargetPicker`，可打字，按名字、item_id、标注（版本）过滤，两种模式都有；普通模式仍单选，行为不变。
- **专属多选**（el-select multiple filterable 的交互）：每项勾选框；已选显示为输入框里的标签，点 × 去掉、空输入框按退格去掉最后一个；「不可」的项禁用；「全选」只勾可用的玩家护甲（同名玩家版本全勾，跳过禁用项与 3 条非玩家记录）；另有「清空」。
- **非玩家表** `KitNonPlayerArmors`：FS-05 124623533「非玩家（民主官 NPC）」、CM-09 2107035846 与 SC-30 1969314276「非玩家（拿不到）」，注释写明来源（OneClickArmorSet RESEARCH.md、helldivers-2/json armor.json）。同名玩家记录（≥2 条时）标「版本 N」，按 item_id 升序。非玩家记录可手动勾，不进全选。
- **按集合切换**：`SectionalExclusiveCombiner` 把各目标的 P4a/P4b 规划合成一份写出计划：承载件相同内容只写一次、来源集合相同的合并只做一次、内容完全相同的规则去重；承载件被别的目标以不同内容占用的目标记为失败。预览（`KitExclusiveService.PreviewAsync` 多目标版）按目标分段，最后汇总规则条数 / 承载件份数 / 合并模型份数；规则超过 64 条（含别的 Mod 已有的）或规则文件超 64 KiB 时在预览里拦下（`KitExclusiveWorkspace.CheckRuleLimits`），此时没写任何文件。
- **编译失败**：规划失败、承载件冲突、合并几何失败都算「目标失败」。有失败时弹窗（`KitTargetFailureWindow`）：回滚（此刻尚未物化，什么都没写）/ 继续跳过失败的 / 继续并记住（`wardrobe.json` 的 `autoSkipFailedTargets`，以后自动跳过）。详情页在记住后显示一行「已记住…」和「清除记忆」按钮。失败的目标从勾选里去掉，原因进状态栏；`wardrobe.json` 只记实际编进去的目标。
- **存储与兼容**：`wardrobe.json` 增加 `targets`（≥2 个目标才写，单目标文件与以前逐字相同），单个 `targetItemId` 始终是第一项；旧文件读成只有一项的列表。workspace 仍每节点一条记录，记录里增加 `targets`（≥2 个才写），顶层字段等于第一个目标；每个目标展开成自己的规则，规则名不变；旧记录读成一个目标。
- 「应用」「头身合并」「重构建」沿用盘上记录的整个目标集合。

### 与原规划的偏差 / 没验证
- 单目标编译失败的报错文案改成「不能专属切换到 X：原因」（以前合并失败是「专属换甲编译失败：…」）；行为（失败即整体失败、什么都不写）不变。
- 预览里目标规划失败或承载件冲突时直接拦下（不能确认），弹窗只处理**编译阶段**才暴露的失败；被禁用的项本来就勾不上，所以这条路径只在数据过期时出现。
- 规则上限核对的是「本 Mod 的规则 + workspace 里别的节点的规则」，不区分别的 Mod 当前是否启用（偏保守）。
- **没有在真实窗口里点过**：下拉的外观、弹出层、标签折行、失败弹窗是代码与 XAML 层面完成并通过编译，未做目视验证。

### 给用户的实机验证步骤
1. 打开雫的详情页，打开「专属」开关：下拉里能打字搜「神射手」「3970674111」「DS-42」，只留匹配项；「不可」项灰显点不动；FS-05 三条分别标「版本 1」「版本 2」「非玩家（民主官 NPC）」。
2. 勾 DS-42、CE-67、神射手（3970674111），点「切换」：先弹预览，按目标分三段，最后有规则条数 / 承载件 / 合并模型汇总；确认后编译。
3. 部署进游戏，三套分别穿上看是雫；穿别的护甲是原版；民主官仍是爱弥斯。
4. 去掉一个标签（点 ×），再「切换」：那一套恢复原版，另两套不变。
5. 点「全选」：确认勾上的都是可用玩家护甲，FS-05 民主官 NPC、CM-09/SC-30 非玩家记录没有被勾。
6. 失败弹窗：需要构造一个编译会失败的目标才能看到（例如换一个自定义骨缺失的 Mod）；看三个按钮行为，选「继续并记住」后详情页出现「已记住」一行，点「清除记忆」后消失。

### 范围调整（2026-11-14，用户后定）：多目标部署改用软映射
多目标部署以后改用运行时 `Application.set_resource_override` 软映射：模型只部署一份，每个目标承载件加一条映射；映射部分另写规划，下一阶段做。因此本轮：

**做了（保留）**：搜索；专属多选（标签、×、禁用、全选、清空）；非玩家表与「版本 N」；`wardrobe.json`/workspace 多目标存储与旧文件兼容；预览按目标分段 + 汇总 + Hider 上限拦截；失败弹窗三选项与「记住」开关（含清除记忆按钮）。

**临时行为**：只勾一个目标 → 「切换」与之前完全一样（P4a/P4b 补丁路径）。勾两个及以上 → 预览照常显示，确认按钮禁用，旁注「多目标部署改用映射，下一步开放」，不写任何文件（`ModDetailsPageViewModel.Vpk.cs` 的 `multiBlocked`）。

**留给映射阶段**：「按集合把多个目标的承载件写进同一份 `Overwrite/`」。该代码（`SectionalExclusiveCombiner`、`SectionalCompiler.Exclusive.cs` 的多目标分支、`exclusiveItemIds` 参数、`SyncTargetsAsync`）已写好并有测试，但界面入口已被上面的临时行为挡住，不再继续投入；映射阶段可整体替换或删除。失败弹窗在编译阶段触发，当前入口被挡后实际只会在单目标合并失败时间接可见——它的三选项与记住开关留待映射阶段接上。
