# L4D2 → HD2：边界与分工（架构决定）

> 用户问题：转换器（旧项目）与 Lua 动骨支持（WpfApp1）**分开**是否更好？
> 我的回答：**分开是对的，但真正决定成败的不是"分几个仓库"，而是"缝在哪里"。**

---

## 1. 结论

**同意分开。但要把"分开"落在正确的地方：按「数据契约」分，不是按「仓库」分。**

三个角色，一条缝：

```
┌────────────────────────────────────────────────────────────────────────┐
│ ① 转换器（离线，绝不进游戏）                                            │
│    旧项目 HD2AgentWorkbench                                            │
│    全仓唯一懂 VPK / MDL / VVD / ValveBiped / Source jigglebone 的地方   │
│    产出：一个标准 HD2 Patch  +  一个「动骨声明文件」                     │
└───────────────────────────────┬────────────────────────────────────────┘
                                │
                    ═══ 唯一的缝：动骨声明文件（版本化）═══
                                │
        ┌───────────────────────┴───────────────────────┐
        ▼                                               ▼
┌───────────────────────────────┐   ┌───────────────────────────────────┐
│ ② 管理器（WpfApp1）            │   │ ③ Lua 运行时（WpfApp1，独立 mod）  │
│    只做安装 / 校验 / 展示       │   │    只读声明文件，驱动额外骨         │
│    不认识 Source               │   │    不认识 Source                   │
└───────────────────────────────┘   └───────────────────────────────────┘
```

**关键点：① 不知道 ②③ 的存在，②③ 不知道 ① 的存在。** 三者只共享一个文件格式。

---

## 2. 为什么"按仓库分"本身不防屎山

反例就在眼前：旧项目现在通过 **绝对路径** 引用 WpfApp1 的项目：

```xml
<!-- HD2AgentWorkbench/src/HD2AssetKit/HD2AssetKit.csproj -->
<HD2ModAdaptationProject Condition="'$(HD2ModAdaptationProject)' == ''">
  E:\Data\source\repos\WpfApp1\HD2ModAdaptation\HD2ModAdaptation.csproj
</HD2ModAdaptationProject>
<ProjectReference Include="$(HD2ModAdaptationProject)" />
```

**两个仓库，却已经被焊死了。** 换台机器、换个目录名、别人 clone 下来都构建不了。
这说明"分仓库"给不了任何隔离保证 —— **隔离来自接口，不来自目录**。

反过来：如果缝定义得干净，**即使全放在一个仓库里也不会变屎山**（例如 `HD2ModCore` 与 `HD2ModAdaptation` 就在同一个仓库、同一个 sln 里，各自清晰）。

**所以判据只有一条：** 改动一边时，另一边需不需要跟着改？
- 需要 → 缝没切对。
- 不需要 → 缝切对了，放哪都行。

---

## 3. 那条缝具体是什么

**「动骨声明文件」** —— 一个版本化的 JSON，放在 Patch 旁边（或嵌进去）。它只描述：

```jsonc
{
  "schema": 1,                    // ← 版本号是这条缝的生命线
  "unit": "0x4d1c334d294dfa97",
  "extraBones": [                 // 追加在骨架末尾的骨（不改原有索引）
    { "index": 107, "parent": 5, "name": null,
      "bindPosition": [0.0, 0.0, 1.5],
      "spring": { "mode": "flexible", "length": 0.76, "tipMass": 200.0,
                  "yawStiffness": 50, "yawDamping": 7.0,
                  "pitchStiffness": 50, "pitchDamping": 7.0,
                  "alongStiffness": 100, "alongDamping": 0,
                  "angleLimit": 0.611 } }
  ]
}
```

**Lua 侧只认这个文件，不认 Source 的任何概念。** 没有 `$jigglebone`、没有 `ValveBiped`、
没有 `procindex` —— 那些都在转换器里被消化掉了。

**这条缝的三条纪律：**
1. **版本化**：`schema` 是必填。运行时遇到不认识的版本必须**拒绝**，不能猜。
2. **单向**：只有转换器写、运行时读。运行时**永不回写**。
3. **自足**：声明文件必须能脱离 Patch 单独校验（管理器据此判断"这个 mod 要求运行时做什么"）。

---

## 4. 为什么这样切能避免"牵一发动全身"

| 如果… | 会发生什么 |
|---|---|
| 转换器换了实现（比如不再用 `source-rig-fit`，改用自己的拟合） | 运行时**一行都不用改**（缝没动） |
| 运行时换成原生 C++ 插件 | 转换器**一行都不用改** |
| 以后要支持 MMD / VRM 模型 | **只加一个新的转换器**，运行时和管理器不动 |
| 以后要加第二种物理（布料、刚体挂件） | 缝里加 `schema: 2` 的新字段，旧运行时按版本拒绝 |

**每一格都是"另一边不用改"。** 这就是判据。

## 5. 顺便修掉现有的那颗屎山种子

旧项目对 `HD2ModAdaptation` 的绝对路径依赖是**当前唯一的真屎山**。两个选项：

| 方案 | 做法 | 代价 |
|---|---|---|
| **(a) 属性 + 响亮失败**（推荐先做这个） | 保留 `$(HD2ModAdaptationProject)` 覆盖能力，但默认值改成**相对路径探测**；找不到时**构建直接报错并打印怎么修** | 很小 |
| (b) 本地 nupkg | WpfApp1 构建时把 `HD2ModAdaptation` 打成包放进 `artifacts/`，旧项目引包 | 要加发布机制 |

**(a) 就够了**，而且现在的问题是"默默用了一个绝对路径"，不是"跨仓库"本身。

## 6. Lua 运行时：位置与性能纪律

**位置**：与护甲映射的 Lua mod **同仓、但独立成 mod**（独立目录 + 独立协议文件 + 独立锁）。
理由：两者生命周期与失效模式完全不同，**捆在一起会让动骨的 bug 打断护甲映射**。

**性能（用户硬约束：绝不能引入 HD2IAS 那种卡顿）** —— HD2IAS 慢的三个原因，我们逐个反向设计：

| HD2IAS 的做法 | 我们为什么不慢 |
|---|---|
| 每帧驱动 **256 根骨** × 每个 avatar | 只驱动**声明文件里列出的额外骨**（典型 20–60 根），身体骨交给 HD2 自己的动画（**零成本**） |
| 调原生 solver + 重定向（跨语言往返） | 纯 Lua **二阶积分**，无原生调用、无碰撞、无反向动力学 |
| `hd2ir_shared_body_profile`：多个 avatar **共用一个 solver 实例** → 一个玩家动，所有人跟着动 | **每个 Unit 一份独立状态**（按 unit id 索引），**结构上不可能传染** |

另外三条免费的性能护栏：
1. **静置休眠**：弹簧能量低于阈值就跳过整条链（不写、不调 `World.update_unit`）。
2. **LOD / 剔除**：骨架里本来就有 `*_culling` 骨与 `set_bones_lod`；远处/屏幕外的 Unit 直接跳过。
3. **每 Unit 每帧只调一次 `World.update_unit()`**（不是每根骨一次）。

## 7. 这条决定对 A1–A3 的影响

**没有影响，而且正好支持用户的排序。** A1–A3 是**转换器内部的数学**：

- A1 读 HD2 骨架（游戏本体）→ 属于转换器的输入
- A2 逐骨相似解 → 转换器内部
- A3 离线重定向出 OBJ → 转换器内部

**它们全都在 ① 里面，碰不到那条缝，也碰不到 WpfApp1 的 Lua。**
所以先做 A1–A3 完全正确：**缝还没开始用，改哪都不会牵动另一边。**

（唯一例外：A1 要读的 HD2 骨架来自 `HD2ModAdaptation`，也就是那个绝对路径依赖。
这恰好是 §5 要修的那颗种子 —— 但不影响 A1 的数学。）

---

## 8. 一句话总结

> **用户的分法是对的。我只加一条：把"分开"钉在一个版本化的文件格式上，而不是钉在目录结构上。
> 目录能骗人（现在就已经被绝对路径焊死了），文件格式骗不了人。**
