# 证据强度审计：dxilconv 空指针崩溃（6 份会诊结果复核）

> 审计范围：S1/S2/S4/S5/S6 的结论（S3 返回 null）＋ `.dsh/analysis/dump/*` 一手材料 ＋ `.dsh/variants/*` 构建。
> 方法：**不看叙述，只重新读原始字节**。本轮新写的 5 个复核脚本在 `.dsh/analysis/audit/`，全部可复跑。
> 结论：**归因方向是对的，但"已定论"的写法过头了**；更关键的是——**归因其实已经不需要再做实机实验**，

## 0. 一段话结论

- **贴图不是原因**，而且这不需要再跑实验证明：崩溃版与通过版（`famA_roughness_alpha_v2` → `famA_alpha_only`）
  在同一份 22,369,648 B 贴图字节上，**只差 176 字节**，且这 176 字节全部落在 8 条 DXBC 记录的
  **输入声明操作数**上（`dcl_input_ps v7.z`→`v8.x`、`v4.x`→`v4.w`）＋每条记录的 16 B 校验和。
- **真正的病灶是"读了 ISGN 没提供的输入分量"（G4），而且是两处，不是一处**。崩溃版同时读了 `v7.z`
  和 `v4.x`；记录 ISGN 只给 `TEXCOORD6=v7.xy`、`TEXCOORD3=v4.w`。
  所有报告（含落盘的 `famA_fixed_inputmask/NOTE.txt` 与 shader 证据包 §10.3）都只写了 `v7.z`，
  **漏了 `v4.x`** —— 这是 S3（dxilconv 规则）缺席留下的洞。
- **dump 的"崩溃点"game+0x9F616D 是崩溃处理器里的二次崩溃**，它对根因的语义价值接近 0；
  S5 用一整篇去给这个 thunk 的父对象定名，方向错了。
- **"上一版能跑"被普遍低估**：`famA_alpha_only` 同时带着"我们的 SHEX + 我们换过的 4096² 贴图"
  两个嫌疑因子跑通了，它单独就否证了"自定义 SHEX 必崩""换这张贴图必崩"两条一般化结论。
- **只再做一次实机**：跑"产品格"（修好的着色器 + 目标真实贴图）。归因格（坏着色器 + 原图）留着不跑，
  因为它的结果可以预测、且不改变任何决策；机制层的问题应该**离线**用 D3D12 harness 复现，不该再烧实机。

### 1.1 复核中发现的两处实体错误

**① S4 报告把崩溃指令的地址写错了 0x50**（`docs/agent/hd2-s4-texture-format-report.md:125`）。

S4 写 `009f611d mov rcx,[rax+0x58] ← 我们这次撞上的二次崩溃`；但异常流的 RIP 是 `+0x9F616D`，
`0x9F616D` 处的字节确实是 `48 8b 48 58`。真相是：这段代码是**同一族 4 个 thunk，间距正好 0x50**：

```
+9F6106  call [rip+0xA97674]  test rax,rax  cmove rax,[glob]  [9F611D] mov rcx,[rax+58] … jmp [rax+8]
+9F6140  call [rip+0xA97624]  test rax,rax  cmove rax,[glob]  [9F6156] …            [9F616D] mov rcx,[rax+58] ✓RIP … jmp [rax+0x10]
+9F6190  …                                                                          [9F61C8] mov rcx,[rax+58] … jmp [rax+0x18]
```

S4 反汇编的是**前一个**实例（vtable+8），真正崩的是**中间那个**（vtable+0x10）。所以 S4 的"形态描述"
（取接口→成员+0x58→虚调用）是对的，但"这次撞上的"这句**指错了对象**；S5 的 `+0x9F616D` 版本才是对的。
两条看起来都自洽，是因为 4 个 thunk 互为模板（各自 `call` 的位移都落回同一个 IAT 槽 0x148D780）——
这正是"看着像验证过"的假阳性陷阱。

**② 0x1A164F7640 不是第二个 EXCEPTION_RECORD，是崩溃转储器自己的头。**

我读该处得到 `Code=0x4B434150('PACK') Flags=0x504D4452('RDMP')`。也就是说，
**栈上 0x1A164F7640 以上已被 dumper 自己覆写**。这有两个后果：
(a) 任何"152 条候选里再往高地址找帧"的做法都不可靠；
(b) 反过来说明"这次 dump 是被 crash dumper 在异常处理路径里写的"——见 §3.2。

## 2. 分级清单：哪些是直接证据，哪些只是相关

### A 级：一手、可复核、不依赖任何人的叙述

1. **同线程两次异常**，第一次在 `dxilconv+0x44414` 读 0x54（RCX=0），第二次在 `game+0x9F616D` 读 0x58（RAX=0）。
   CONTEXT/EXCEPTION_RECORD 双结构互相印证，且与系统 DLL 的机器码逐字对上。
2. **0x9F616D 的真实指令** = `mov rcx,[rax+0x58]`，其前是 `test rax,rax; cmove rax,[全局]`，
   其后是 `mov rax,[rcx]; jmp [rax+0x10]`。RAX=0 意味着**间接调用返回 null 且全局兜底也为 null**。
   （S5 这条推理正确。）
3. **崩溃版着色器读 `v7.z` 与 `v4.x`；记录 ISGN 只提供 `v7.xy` 与 `v4.w`。**
   fxc 反汇编逐行可见，且两版 ISGN 完全相同（签名表一致）。
4. **崩溃版与通过版的差异只有 176 B**，贴图载荷（22,369,648 B）字节级相同。
   ⇒ 贴图**不可能是**这一对结果差异的原因。这是**因果级**证据，不是相关。
5. **贴图条目结构自洽**：BC7_UNORM / 4096² / 13 级 / gpuSize 恰等于链长；TocData 与作者原版逐字节相同。
   （S4 的 E1/E2/E3 我独立复算成立。）
6. **dump 没抓到崩溃前的调用者代码页、全局与 IAT 槽**（`s5_caller.txt:837-869`）。

### B 级：强推断（有直接锚点，但缺最后一环）

7. **两次异常的先后顺序**（dxilconv 在前、game 在后）。依据：`UnhandledExceptionFilter` 的返回址
   位于当前崩溃链**更高**的栈地址（= 更早的帧）；且我反汇编 KERNELBASE 该处，发现它正是在
   **对过滤回调的返回值做 -1/1 判定**（`lea ecx,[rax+1]; test ecx,0xfffffffd; je`）——
   这独立佐证了"那就是 UEF"，不是只靠符号表。
8. **0x9F616D 是崩溃处理器/清理路径里的二次崩溃**（不是渲染路径）。
   依据同 7：当前崩的这条链在 UEF **之后**才建立（栈位置更低 = 更新），
   加上 `PACK` 头已覆写栈、以及寄存器参数形态（见 9）。
9. **崩溃 thunk 被调用时带着 "指针 + 0x800 + …"**：RDX=RSI=RDI=0x1E00B83C9C0（堆指针）、R8=RBX=0x800、
   R9=0x100。这一组参数更像"**2 KB 缓冲区操作**"（写 dump / memcpy），不像 PSO/SRV 描述符操作。
   ⇒ 把 0x9F616D 当"渲染/资源路径的崩溃点"去归因，方向可疑。
10. **dxilconv 的 null 与"缺分量"之间的因果**。dump 只告诉我们"某个对象是 null、被 getter 解引用"，
    并没有告诉我们那个对象是谁。因果链是靠 A3+A4 的对照（只改读集就崩→不崩）**排除法**建立的。
11. **S2 的 5 个容器归属**：内容层面 A 级（无 t2/t8、无 sample、常量输出，fxc 可反汇编）；
    "Stingray 为既有顶点布局准备的占位变体"是 B 级命名推断。
12. **"dxilconv 在该进程里是常规路径"**：5 个容器全是 SM5、无 DXIL 块，说明本进程里
    SM5 DXBC→DXIL 是普遍需求。⇒ **栈上出现 dxilconv 的基率极高、鉴别力接近 0**（B 级，但足以推翻一种直觉）。

### C 级：只是相关 / 形态猜测，不能当结论

13. **"dxilconv 出现在栈上 ⇒ 与本次失败相关"** —— 相关。按 B12，任何 shader 创建都会经过它。
    S1 的 `risks` 里其实写对了（"不能把 69 个命中当 69 层父调用"），但 S2/S5/S6 都在不同程度上
    默认了"dxilconv 在场 = 转换路径是问题所在"。
14. **S5 的"父对象是 DXGI/D3D 设备或适配器包装"、"是 Release 清理路径"** —— 形态猜测。
    额外反证：该 thunk 尾部把 `rdx/r8` 原样转发，所以被调的虚方法**带参数**，
    这不支持"无参的 Release"这种具体命名；`+0x10` 只是 vtable 第 3 槽。
15. **"0x800 是着色器大小"** —— S5 已自我否证，正确。
16. **把 `hits.txt` 的 0 命中当"我们的 blob 没被加载"** —— 不成立。见 §4.3。

### D 级：缺口

17. **S3 返回 null**。而 S3 恰恰是"dxilconv 对输入的要求/拒绝模式"这条唯一能给机制定性的席位。
    结果：语料里所有"dxilconv 拒绝"的说法都没有规则层依据，全是形态推断。
18. **没有任何一份报告核对过"历史成功配置的 (S,T) 取值"** —— 见 §4.1，这是最便宜而没人捡的信息。

## 3. 把三件事彻底拆开

### 3.1 因果链现在长这样（按证据强度标注）

```
[已证] 崩溃版 SHEX 读 v7.z / v4.x，而记录 ISGN 只提供 v7.xy / v4.w        (fxc 反汇编)
   ↓ 机制未知（S3 缺席；dump 只能说"某个对象是 null"）
[已证] 该构建实机崩：dump 里先有 dxilconv+0x44414 的 AV(read 0x54, RCX=0) (CONTEXT+EXCEPTION_RECORD+系统DLL机器码)
   ↓
[强推断] 异常分发 → UEF（判定过滤回调返回值）→ 崩溃处理器/清理路径 → 二次崩 in game+0x9F616D
[已证] 只把这 2 处读集改成合法分量（176 B），同一贴图 → 跑通              (字节级 diff + 实机)
```

### 3.2 两个崩溃点的"形状"其实同构，这点没人说

- 第一处：`dxilconv+0x44414` = `mov eax,[rcx+0x54]; mov [rdx],eax; ret` —— **一个字段 getter**。
  RCX=0 说明**调用方拿一个 null 对象来取字段**，而不是"转换算法内部算错"。
- 第二处：`mov rcx,[rax+0x58]` —— **一个成员装载**，前面的 `test/cmove` 说明
  "按 id 取接口 → 取不到 → 用全局单例 → 单例也是 null"。
- 两处都不是算法/校验失败，而是**"按 id/查表拿对象 → 拿到 null → 直接解引用"**。
  这解释了为什么 S5 想给父对象定名注定失败（对象根本不存在），
  也提示真正该问的是"**是谁让它按 id 查表并接受了 null**"。

### 3.3 崩溃版 vs 通过版：逐条 dcl 对照（fxc /dumpbin 原始输出）

| | 崩溃版 `famA_roughness_alpha_v2` | 通过版 `famA_alpha_only` |
|---|---|---|
| ISGN（记录自带） | 两版**完全相同**：`TEXCOORD6 xy @7`、`COLOR0 xy @8`、`TEXCOORD3 w @4` | 同左 |
| 输入声明 | `dcl_input_ps linear v7.xy` + **`v7.z`** + **`v4.x`** | `v7.xy` + **`v8.x`** + **`v4.w`** |
| 采样/输出 | `t2`/`s0`/`o0=(0,0,0,texel.x)` | 同左 |
| 贴图载荷 | ← 22,369,648 B 字节级相同 → | 同左 |
| 结果 | 崩 | 通 |

⇒ 这一对是**单变量**（读集），且**贴图被完全控制住了**。所以"贴图致因"在证据层面已经死了，
不需要再跑 `noretex` 去证明。同时它也说明：**根因描述漏了 `v4.x` 这一处**。

## 4. 被忽略的反例与错误用法

### 4.1 "上一版能跑"——它约束得比所有人以为的更狠

现实里的"能跑"不止一版：

| 变体 | 着色器 | 贴图 | 结果 |
|---|---|---|---|
| `baseline` | 作者原版 | 原图 | 正常 |
| `famA_valid_signed_magenta` | 我们的整段替换 | 原图 | 全身品红（我们的 SHEX 被执行） |
| `famA_fixed_inputmask` | 我们的（合法读集） | **原图** | 不崩 |
| `famA_ramp_both` | 我们的（合法读集） | **我们的渐变** | 通（灰渐变 + 透明渐变） |
| `famA_alpha_only` | 我们的（合法读集） | **我们的渐变** | **通（目标达成）** |
| `famA_roughness_alpha_v2` | 我们的（越界读集） | 我们的渐变 | **崩** |

`famA_alpha_only` 这一行是**最强反例**：它同时具备"自定义 SHEX"和"换掉这张 4096² 贴图"两个嫌疑因子，
却跑通了。它单独否证：

- ❌ "引擎拒绝外来 SHEX"（S2 早期的框架、shader 证据包 §四.2 的六种失败形态都指向过这条）；
- ❌ "换这张贴图不安全"（S4 要证的那件事，其实已被这一行免费证完）；
- ❌ "我们的工具链必然产出越界读集"（同一工具、改 176 B 就能合法）。

**用法边界（必须写清，否则会被误用）**：它不能否证"**这个特定读集**会崩"。
所以正确的推论是"问题在**读集**，不在 SHEX 本身、也不在贴图"，而不是"不是 shader 的问题"。

**谁忽略了它**：S1 只在 `risks` 里提了一句"不否定此前整段替换的成功证据"；S2/S4 完全没用；
S6 提到了，但只用它来论证"t8 成功不能替代 00"，方向反了（详情见 4.2）。

### 4.2 S4 的"2×2 缺角"其实不缺，S6 的 E2 是白跑

S4 报告 §4.2 说缺 `(修好的着色器, 渐变贴图)` 这一格，要补跑——**这一格就是 `famA_alpha_only` / `famA_ramp_both`，
已经建好并跑通了**。S4 的输入集里没有这两个 09:21 / 09:23 的构建（它只拿到三个变体），
于是把一个已完成实验重新列成了待办。这类"输入集不全"是本次会诊最常见的错误来源。

同理 S6 的 `E2 = 00（原始 SHEX + 原图）`：`baseline` 就是它，正常；`famA_fixed_inputmask` 也是"合法读集 + 原图"，不崩。
花一次启动去测一个已知通过的格，是三次启动里最贵的一次浪费。

### 4.3 `hits.txt` 的阴性**没有阳性对照**，所以它什么也不能证明

`hits.txt` 里连"原始 matpass 校验和"都是 0 命中。这意味着：

- 不能读成"我们的 blob 没加载"（正确读法见 S4 的措辞："压根没被转储捕获"）；
- 也**不能**读成"没被捕获"——除非你有一个"必然存在"的阳性对照（例如任意一条原版记录）也命中。
  现在连原版都是 0，说明这份 10.1 MiB / 2,714 区的 dump 与 shader 堆根本不相交，
  **整张表的信息量为 0**。S2/S6 的保守措辞没错，但没有人指出阴性对照缺失，
  于是 S2 还要花篇幅讨论"这 5 个 blob 是不是我们的探针"——本来不必。

### 4.4 `n=1`：所有实机结论的单点风险

`崩` 与 `通` 目前都各只有**一次**观测（`ramp_both`+`alpha_only` 算两次"通"，但同一读集）。
没人提"要不要重跑一次确认可复现"。S6 在 risks 里提了"若问题偶发需重复"，算部分覆盖。

### 4.5 被忽略的第三种解释：崩溃处理器自身的 bug

若二次崩溃发生在崩溃处理器里（B8），那么它**可能是与 mod 无关的既有 bug**
（很多带 packer/反作弊的游戏在"设备已释放"状态下取接口就会撞 null）。
这条解释没人认真提，但它同时解释了为什么 thunk 会拿到 null：**崩溃时渲染设备本来就被拆掉了**。
如果这个解释成立，S5 的整篇工作对根因的边际价值为 0。

## 5. 如果只能再做一次实机

### 5.1 结论：跑"产品格"，不是归因格

**唯一值得的一次实测 = `famA_alpha_only` 的着色器 + 目标真实贴图，其他一切不动。**

理由（按信息量排序）：

1. **归因格已经没有信息了**。坏读集 + 原图（`noretex`）的结果可以预测（仍崩，因为越界读与贴图无关），
   而它要回答的问题（"贴图是否致因"）已经被 §3.3 那对干净对照回答过了。跑它只是补一张表。
2. **产品格是唯一没被覆盖的格子**，而且它就是下一步本来要做的事：现状"能跑"的是**渐变占位贴图**，
   真正要交付的是**目标图案**。它通过 ⇒ 交付 + 贴图线永久关闭；它崩 ⇒ 那是**真新信息**
   （说明还有"内容/打包/部署"层面的变量），此时 2×2 已全绿，可以直接判定是新变量而非已知因素。
3. 它同时也是对"贴图内容敏感"这条**唯一还开着**的假设的直接检验。别的格子都检验不到。

判据要预先写死（照 S6 的 P/F 就够，但缩到一次）：
走同一条固定路线 → 目标材质实际参与渲染 → 观察 60 s。P=无崩溃且贴图效果出现；F=异常码/读地址/RIP 指纹一致。

**如果你更在意"矩阵闭环"而不是交付**，那么唯一还值得的一次是 `noretex`（坏读集 + 原图）——
但请明确：它不改变任何后续动作，只是把已有结论再证一遍。

### 5.2 机制层不要再用实机，改用离线 harness

"dxilconv 为什么会崩在一个字段 getter 上"这个问题，实机再跑 10 次也答不出来（拿不到 RCX=0 的来源，
这次 dump 连调用者代码页都没抓）。可重复、零反作弊风险的做法是：

> 写一个最小 D3D12 程序：创建设备 → 用一个平凡 VS + **把 v2 的 60,504 B 记录原样当 PS** 建 PSO
> → 看 `CreatePipelineState` 是返回 `E_INVALIDARG` 还是直接 AV 在 `dxilconv+0x44414`。
> 再喂 `alpha_only` 的记录作对照。

三种可能结果都值钱：① AV 复现 → 机制坐实，且能无限重复、能挂调试器；② `E_INVALIDARG` → 说明
"shader 被拒"是**优雅失败**，那游戏里那次 AV 的 null 另有来源（B10 的因果要降级）；
③ 两者都过 → 说明触发条件与引擎侧状态有关，得回去查引擎的 PSO 创建路径。

## 7. 建议的收尾动作（按性价比）

1. **不要再为"归因"烧实机**。归因已经由 §3.3 的单变量对照给出，且被字节级证据锁死。
2. **一次实机 = 产品格**（合法读集 + 目标贴图），把 P/F 判据写进部署记录。
3. **离线 harness 复现 v2 记录**，把"dxilconv 空指针"从"推断"变成"可重复现象"（§5.2）。
4. **修 G4 的描述**：`docs/agent/hd2-shader-diff-evidence-20261115.md`（§9.2/§10.3）与
   `.dsh/variants/famA_fixed_inputmask/NOTE.txt` 里的"读 v7.z"应改为
   "读集 ⊄ 提供掩码（本例 **v7.z 与 v4.x** 两处）"，否则下一个人还会漏 `v4.x`。
5. **构建期断言**：`dcl 读取掩码 ⊆ 记录 ISGN 提供掩码` 已经从"经验"升级为"硬门"（G4），
   建议再补一条"同一构建里 8 条记录必须字节相同"（我核对过：family A 的 8 条记录确实同源，
   校验和都一致）——这次 176 B 的 diff 就是逐记录等量出现的。
6. **`hits.txt` 这类阴性证据要么补阳性对照，要么删掉**，否则会持续误导"我们的 blob 没加载"。
