### E7 崩溃点指令：一个"取接口→解 +0x58→虚调用"的转发 thunk，与贴图无关

磁盘 `helldivers2.exe` 的 `.text`/`.pdata` 熵 = 8.000（**加密/加壳**，时间戳与校验和虽与转储模块表一致，代码不可静态读）。
但 dump 在 RIP 处抓了 256 B 真实代码，我把它反汇编（`probe4.py`）：

```asm
009f6106  call  qword ptr [rip+0xa97674]      ; 同一个 IAT 槽（0x148D780）
009f610c  mov   r8, rbx
009f6112  test  rax, rax
009f6115  cmove rax, qword ptr [rip+0x103687b] ; 取不到就用 .data 里的兜底单例（0x1A2C998）
009f611d  mov   rcx, qword ptr [rax+0x58]      ; ← 我们这次撞上的二次崩溃（RAX=0，读 0x58）
009f6121  mov   rax, qword ptr [rcx]
009f612e  jmp   qword ptr [rax+8]              ; 尾调用虚表槽
```

这一段是**同一族 4 个连续 thunk**（`+0x8 / +0x10 / +0x18` 三个虚表槽各一个），形态完全一致：
`接口 = get(id); if(!接口) 接口 = 全局单例; 成员 = 接口->[+0x58]; 成员->vtable[n](...)`。
反汇编出来的 `+0x58` 与 `ExceptionInformation[1]=0x58` 严丝合缝，`RSP+0x28` 的返回地址 `game+0x9F335D` 也对上
（函数帧 = `mov[rsp+8],rbx; push rdi; sub rsp,0x20` → 返回槽在 +0x28）。

结合 S1 的还原（第一现场是 `dxilconv+0x44414` 的 `mov eax,[rcx+0x54]`，`RCX=0`）：
**真正的空指针发生在 dxilconv 内部，这次 game+0x9F616D 是异常过滤路径上的二次崩溃。**
两条都没碰到贴图。

## 2. 推理（明确区分"读到"与"推测"）

### 2.1 为什么"内容/格式层"不可能导致崩溃（推理，依据 D3D12 语义）

贴图的**尺寸、级数、上传字节数、SRV 的 format** 全部来自 TOC 里那份 DDS 头，来自**元数据**，不是从像素里推断的。
覆盖像素只改变"硬件解码出来的颜色"，改变不了任何 CPU 侧指针、长度或对象生命周期。

- 若把 BC7 数据当 BC5 声明（或反之）：块大小都是 16 B，链总字节数完全相同（都是 22,369,648），
  引擎侧一切长度计算不变，只是画面变噪声。**纯视觉故障。**
- 若格式块大小不同（例如声明 BC1 = 8 B/块）：链算出来只有 11,184,824，而条目给了 22,369,648 —— 多出来的没人读；
  反向（声明 16 B/块、只给 8 B/块的数据）才会变成越界读 —— 但那种情况下**崩在 memcpy/上传**，不会崩在 dxilconv。

### 2.2 真正能把游戏搞崩的贴图故障，只有"结构层"三类（清单 + 本次核验）

| 故障 | 机制 | 本次是否成立 | 核验方式 |
|---|---|---|---|
| **① 声明大小 ≠ 实际字节数** | 引擎按 TOC 长度拷贝 / 按头算尺寸分配，两者不一致 → 堆溢出或越界读 | **不成立**：22,369,648 = 链长 = 实际写入 | E3 |
| **② mip 级数 / 尺寸 / 格式三者互不自洽** | 建资源用一套、上传用另一套 | **不成立**：4096²/13 级/BC7 三者与 22,369,648 完全自洽 | E1/E3 |
| **③ 元数据缺失或格式=0（DXGI_FORMAT_UNKNOWN）** | `CreateCommittedResource`/`CreateShaderResourceView` 返回 E_INVALIDARG → 引擎不检查 HRESULT → 后面解引用 null | **不成立**：fourCC='DX10'、fmt=98、宽高非零 | E1 |

③ 才是"一张坏贴图能把游戏搞崩"的现实路径，但它的崩溃点会在**资源创建/上传**路径（D3D12 帧或引擎 texture loader 帧），
而本 dump 的第一现场在 `dxilconv`，且栈上没有任何资源描述符（E6）。**路径对不上。**

### 2.3 我**不能**证明的（避免过度声称）

- dump 只覆盖 10.1 MiB / 2,714 区。我能说的是"**崩溃现场与捕获范围里没有贴图描述符**"，
  不能说的是"整个进程从来没创建过贴图"。真正的决定性证据不是 dump，而是 §1 的 E1/E2/E3（mod 文件自身的自洽性）。
- 我没有复现运行游戏，也没有读游戏的私有符号。`game+0x9F616D` 那个 thunk 的**具体接口身份**（是 device、还是某个
  per-asset 对象）没有符号无法定名；我只能确定它的**形态**（取接口→成员 +0x58→虚调用）与贴图无关。
- `author_toc_emissive.patch` 我只核对了它的 6 个条目与当前变体的关系（5 张贴图 TOC 逐字节相同、材质 TOC 不同），
  没有独立验证它捕获自哪一次作者发行。但 E5 的解码结果与 11-14 的独立统计吻合，交叉支持它是原始数据。

## 3. 逐条回答任务里的四个子问题

**(1) 转储里有没有该贴图的 SRV 描述（format 字段）？**
没有。0 个 `DDS `/`DX10`，0 个 `SHADER_RESOURCE_VIEW_DESC` 形态，0 个 `RESOURCE_DESC` 形态（E6）。
DXBC 的 `RDEF` 也**不携带** SRV 的 DXGI 格式（它只有 type/dimension/bind point），所以就算抓到容器也读不出格式 ——
格式只存在于**资产的 TOC** 和**运行时的 view desc** 两处。

**(2) 搜 4096 / 22369648 等常量有没有贴图元数据？**
`22369648` **0 处**。`4096` 只有 12 处，全部落在栈/堆里的无关结构（如 `8, 0, 0x1000, 0x1800` 这类拷贝区域描述）
和模块镜像里，没有一处能与宽高/格式组成贴图描述符。

**(3) mod 侧车结构：条目只有像素数据、TocData 近乎全零，格式从何而来？**
这个描述**不准确**，需要纠正：

- Texture 的 `TocData` 恒为 **340 B**，布局固定：
  `+0 UnkId, +4 0, +8 0xFFFFFFFF` → `+12..192` 十五条 mipmap info → `+192..340` **148 B DDS 头（必须带 DX10 扩展）**。
- **那 180 B 的 mipmap info 全零是设计如此**（SDK 的 `texture.py` 就是这么写，作者自己的包也全零，
  见 `HD2SourceMigration/VpkConversion/Hd2TextureAsset.cs` 的 `WriteToc()` 注释与实测）。它不是"缺元数据"。
- **格式就在 DDS 头里**：`TocData + 320` 的 u32 = DXGI 格式（本例 **98 = BC7_UNORM**）。
  配套字段：`+204` 高、`+208` 宽、`+220` mip 级数、`+276` fourCC、`+324` resourceDimension、`+332` arraySize。
- 而且本次**这些字节根本不是我们填的**：5 张贴图的 TocData 与作者原版逐字节相同（E2）。
  所以"格式从何而来"的答案是 —— **从原条目的 DDS 头继承，我们的工具只覆盖了 GPU 载荷**。

**(4) 格式不匹配最坏是"显示错"还是"引擎崩"？**
分级如下：

| 情形 | 后果 |
|---|---|
| 同块大小格式互换（BC7↔BC5/BC3/BC6H/BC2） | **只显示错**（解码成噪声）。长度、级数、SRV 全不变 |
| 块大小不同但条目字节数不变（BC7↔BC1/BC4） | 仍然只显示错 + 浪费内存（多出来的字节没人读） |
| 条目字节数 < 头算出的链长 | 上传时越界读 → 可能在 **memcpy/上传** 崩（不是 dxilconv） |
| `dxgiFormat=0` / fourCC 不是 DX10 / 宽高=0 | 资源创建失败 → 若引擎不检查 HRESULT，后续解引用 null → **真崩**（但崩在贴图路径） |
| 本次实际发生的 | 以上都不是 |

## 5. 附：如何离线确定一张 HD2 贴图的原始格式（三级方法，含我踩的坑）

### 级别 1（权威、最省事）：读 TOC 的 DDS 头

```text
TocData（340 B）:
  +0    u32 UnkId
  +4    u32 0
  +8    u32 0xFFFFFFFF
  +12   15 × { u32 Start; u32 BytesLeft; u16 Height; u16 Width }   ← 发行包里全零，正常
  +192  148 B DDS 头（含 magic）
          +204 高 / +208 宽 / +212 pitch / +216 depth / +220 mip 级数
          +268 pf.size(=32) / +272 pf.flags(0x4=FOURCC) / +276 'DX10'
          +300 caps / +320 **dxgiFormat** / +324 resourceDimension(3=TEXTURE2D) / +332 arraySize
```

> **我踩过的坑（值得写进规范）**：`DDS_HEADER` 的字段序是 `height@+12, width@+16, pitch@+20, depth@+24, mipCount@+28`
> （此处偏移以"含 magic 的 148 B 数组"为基准）。把 `+24` 当成 mipCount 会读出 `1`，
> 从而得出"头写 1 级、载荷却是 13 级"的**假警报**。我第一版探针就栽在这里，第二版逐字段打印才纠正。

### 级别 2（没有 TOC 时）：用字节数反推块大小与级数

- 8 B/块全链（BC1/BC4）@4096² = 11,184,824
- **16 B/块全链（BC2/BC3/BC5/BC6H/BC7）@4096² = 22,369,648** ← 本例
- 未压缩 RGBA8 @4096² = 67,108,864

这一步能唯一确定"16 B/块 + 13 级"，但**不能**区分 BC2/BC3/BC5/BC6H/BC7（四者同块大小）。

### 级别 3（定到具体格式）：块统计 / 解码判别

**判据 A：BC7 模式前缀合法性（便宜、判别力极强）**
BC7 每个 16 B 块的 mode = `byte0` 最低置位的位置，必须 < 8（等价于 `byte0 & 7 != 0`）。实测：

| 样本 | 非法 mode 比例 |
|---|---|
| 原图 4096² 载荷（mip0 抽 16,384 块） | **0 / 16,384 = 0.0%** → BC7 |
| 我们自己的 1024² BC7（纯色） | 0 / 16,384 = 0.0%，mode 全 6 |
| **对照组：根材质载荷（肯定不是 BC7 块）** | **9,635 / 16,384 = 58.8%** |

对照组说明这个检验有足够判别力：非 BC7 数据会被大量判非法，而原图一个都没有。

**判据 B：套上候选格式的头去解码，看"像不像图"**
用 `texconv.exe` 把载荷按 BC7/BC5/BC3 各解一遍：正确格式得到结构完整的图（本例 `49.2 / 92.1 / 0.0`，A≈255），
错误格式只会得到噪声。这一步和判据 A 互为交叉验证。

**顺带的语义观察（供 S3/S5 参考，不影响本结论）**：这张贴图在材质里的槽位名是
`RoughnessMap / DetailNormalLeather`，而它 **B≡0、R/G 有结构** ——
形态上更像"2 通道细节法线塞进 BC7"，而不是一张真粗糙度图。用它当"粗糙度"取 `texel.x`，
拿到的其实是细节法线的 R 通道。这不影响崩溃判定，但会影响对"实验为什么没出现预期渐变"的解读。
