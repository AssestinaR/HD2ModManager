# new-api UI 与表格参考分析

**分析日期：** 2026-07-18
**参考范围：** `docs/参考项目/new-api-main/web/default/` 的 React 前端。
**用途：** 为 HD2 Mod Manager 的 WPF 控件系统、卡片和高级详情数据表建立可迁移的交互原则；借鉴结构、状态和信息层级，不复制源码、专有视觉资源或网页实现。

## 1. 参考项目的 UI 结构

new-api 的现代界面并非由单个“好看的表格”形成，而是三层可组合的系统：

1. **语义 token 层**：以背景、前景、卡片、边框、主色、状态色、表头、禁用行、骨架屏等 CSS 变量定义亮色与暗色主题；
2. **基础控件层**：`Card`、`TitledCard`、`Table`、`Button`、`Badge`、`Skeleton`、`Empty`、`Select` 等提供统一间距、描边、圆角、状态与无障碍语义；
3. **数据表编排层**：`useDataTable` 保存表格状态，`DataTablePage` 将工具栏、加载/空状态、桌面表格、卡片视图、移动列表、批量操作和分页组装为统一页面。

Manager 应借鉴这种“**token → 基础控件 → 场景编排**”的层级，而不是为每个页面独立设计卡片、表格、筛选器和加载效果。

## 2. 卡片：简洁但有完整的信息骨架

### 2.1 视觉骨架

参考项目的普通卡片使用轻量单像素边界和适中圆角，而不是厚阴影或高对比色块。其主要价值在于明确的内部区域：

- `Header`：标题、说明和右侧动作在同一结构中；
- `Content`：统一左右内边距；
- `Footer`：只有在存在后续操作时才出现，采用弱背景和顶部分隔线；
- `small` / 默认尺寸：同一组件可在列表、设置页和详情页复用。

`TitledCard` 则把图标、标题、描述、右侧操作和内容固定为一个高层组件。这与 Manager 计划中的“页面顶部卡片不塞低频表单”“卡片只承担摘要或分组”的方向一致。

### 2.2 可迁移到 Manager 的规则

Manager 的 `CardContainer` 应演进为明确的三种变体，而不是一个被所有页面随意使用的 Border：

| 变体 | 用途 | 必备区域 |
|---|---|---|
| 摘要卡 | 首页健康状态、当前配置、索引状态 | 图标/状态、标题、单行说明、主动作 |
| 分组卡 | 设置、Mod 概览、工具步骤 | 标题、说明、可选右侧操作、内容 |
| 数据卡 | 高级详情资产表、Game Data 浏览、任务列表 | 工具栏、表格/列表、空状态或骨架、可选分页 |

不建议把所有卡片都加 hover、阴影或动画。只有可点击的摘要卡、选择型卡片和列表项需要 hover / selected 反馈；纯表单或只读数据卡保持稳定，避免界面“漂浮”。

### 2.3 视觉细节可借鉴

- 使用柔和、低对比的表面与边框区分层级，而非过多蓝色容器；
- 右侧操作应属于 Header，而不是散落在正文最后；
- Footer 用于成组的后续动作、统计或危险操作，与正文视觉分离；
- 对标题、说明、数值分别使用稳定的字体重量与弱化色，不靠随机字号；
- 在 loading、empty、error 三种状态下保持同一张卡的边界和高度感，避免页面跳动。

## 3. 表格控件：真正值得迁移的是状态模型

### 3.1 页面级表格契约

参考项目把页面级表格统一为以下结构：

$$
\text{工具栏} \rightarrow \text{数据区域} \rightarrow \text{批量操作} \rightarrow \text{分页}
$$

数据区域有可替换的表现形式：宽屏表格、卡片网格、窄屏卡片列表；但它们共享筛选、排序、选择、列可见性、分页和加载状态。这样可以让不同业务页保有专属列与操作，又不重复实现状态管理。

Manager 不需要移植 Web 的 React / TanStack 技术栈，但应建立等价的 WPF 契约：

- `DataGrid` / `ListView` 外层统一由 `DataTableCard` 或 `DataTableHost` 承载；
- ViewModel 统一暴露 `IsLoading`、`IsFetching`、`IsEmpty`、`ErrorMessage`、`FilterState`、`SortState`、`SelectionState`、`PageState`；
- 表格工具栏、数据网格、空状态、骨架和分页不再在每个 XAML 各自拼装；
- 不同页面只声明列、默认排序、筛选器和行操作。

### 3.2 loading 与刷新必须区分

参考项目显式区分两种状态：

- **首次加载**：显示与最终列数、行密度匹配的 skeleton；
- **后台刷新**：保留旧行，仅降低透明度并暂时禁止交互。

此模式非常适合 Manager：高级 Mod 事实、Game Data archive、任务历史等读取较慢，切勿在刷新时把 `Items` 清空。应保持已有内容、显示轻量“正在更新”，仅在首次进入或实际没有缓存时显示骨架。

建议 Manager 的表格 host 拥有：

| 状态 | 显示 | 用户交互 |
|---|---|---|
| 首次加载 | 表头 + 对应列数的 skeleton 行 | 禁用行操作，保留取消/返回入口 |
| 后台刷新 | 保留现有数据，整体轻度淡化，工具栏显示刷新指示 | 禁止会与旧数据冲突的批量/写入操作 |
| 空数据 | 居中图标、标题、解释与可选下一步动作 | 可执行“重置筛选”“建立索引”等下一步 |
| 错误 | 数据卡保留，显示可读失败原因与重试 | 保留上次有效数据（若有） |

### 3.3 表头、列与宽表处理

参考项目的表格具备以下有效细节：

- 固定表头，正文独立滚动；
- 水平溢出时保留滚动，而不强行压缩所有列；
- 可排序列把升序、降序、隐藏等操作收敛进表头菜单；
- 列宽可拖动，支持键盘调整和自动适应内容；
- 列显示由用户选择，并按页面 / 角色 / 视图范围持久化；
- 行 hover、选中、禁用、错误等状态有一致背景规则；
- 文本型单元格截断后可显示完整值，数字采用等宽数字，标识符/Hash 采用等宽字体。

对 Manager 的具体结论：

1. **高级详情资产表必须作为全宽数据卡**，横跨高级双槽工作区；不能放入半宽卡片。
2. 初期优先做固定表头、横向滚动、列宽、文本截断 tooltip、行状态和列显示菜单；不要求一开始实现任意列拖拽。
3. 资产表的列可见性应按“普通 / 高级”预设保存，而不是给新玩家默认暴露全部诊断列。
4. 左侧识别列（如资源名称、AssetKey）和右侧操作列在列数极多时可固定；只在确有横向滚动的高级表启用，避免普通表格复杂化。
5. 排序、筛选、列显隐和分页必须由 ViewModel 有稳定状态；页面刷新后不得随意丢失用户刚选择的列布局。

### 3.4 工具栏的布局原则

参考项目的工具栏不是另一个有强背景的大卡，而是与表格紧邻的自适应行：搜索框、附加筛选、枚举筛选 chips、重置、视图、列设置和展开筛选按重要性排列；空间不足时自然换行。

Manager 应采用同样的信息优先级：

1. 左侧：搜索、常用筛选；
2. 中间：仅在需要时显示的高级筛选；
3. 右侧：重置筛选、列显示、刷新、表格/卡片视图等低频显示控制；
4. 选中多行后：工具栏之外出现批量操作条，且明确显示已选数量和危险操作。

搜索输入应做防抖，但中文输入法组合期间不能提交中间文本。现有 Library / Profile 每次 `Query` 修改均 `Clear()` 后重建的方式不适合大库，后续应改用延迟筛选与保持集合/滚动位置的投影。

### 3.5 视图不是简单“表格或卡片”开关

参考项目以列 metadata 描述一行的标题、状态徽章、隐藏字段和字段顺序，再用同一份数据生成：

- 桌面多列网格；
- 窄屏单列卡片；
- 常规表格。

Manager 不做移动端，但可借鉴其**同一行数据具有多种密度呈现**的理念：

- Mod 库默认采用信息密度较低的卡片 / 列表行；
- 配置页保持紧凑列表行；
- 高级资产事实、Game Data archive、任务历史采用完整表格；
- 当用户从普通详情切到高级详情时，使用同一资产事实投影更丰富的列，而不是重新读取和另造数据模型。

这比强行给 Manager 所有列表增加“卡片 / 表格切换”更符合桌面工具的目标。

## 4. 对现有 Manager 的映射

| Manager 场景 | 当前问题 | 建议的参考模式 |
|---|---|---|
| 高级 Mod 详情 | `DataGrid` 直接放在弹窗，列多、状态少 | 高级模式全宽数据卡：固定表头、横向滚动、列预设、skeleton / empty / error、文本 tooltip |
| Game Data 索引与 archive | 两层模态窗口，表格与详情割裂 | 强制双槽页：左侧 archive 表，右侧详情；列多资产表按需全宽显示 |
| 模组库 | 每次搜索重建所有项目 | 统一搜索工具栏 + 延迟过滤 + 虚拟化 / 增量投影；继续使用行/卡片而非大表格 |
| 配置成员 | 列表操作 hover 后出现，但筛选/状态混杂 | 紧凑列表数据卡；搜索工具栏与行操作分层；保持现有浮动 `PageActions` 的页面级操作职责 |
| 任务中心 | 单独模态窗口，任务仅是简单列表 | 数据卡内的状态表 / 列表：进行中、最近事件、可取消与失败重试；刷新不清空旧行 |
| 设置资产状态 | 多张静态卡片，状态与操作分离 | `TitledCard` 式卡片：标题/说明/右侧动作，内容区展示路径、周期、上次检查和状态 |

## 5. 不应照搬的部分

- Web 的 Tailwind、React、TanStack Table 和 CSS `oklch` 不是 WPF 依赖选择；应转换成 `ResourceDictionary`、控件模板、`CollectionView` / `DataGrid` 行为和 ViewModel 状态。
- 不应直接复制参考项目的组件代码、SVG、图标、字体、颜色数值或专有视觉资产。
- Manager 是桌面应用，不需要为窄屏移动端完整实现 `MobileCardList`；只迁移“同一数据源可有不同密度投影”的设计原则。
- 列拖拽、任意列持久化、卡片/表格切换属于第二阶段增强，不能阻碍先解决全宽高级表、加载状态和基础列显示的问题。

## 6. 建议补充到实施批次的表格工作包

在既有 UX 重构计划的“批次 0：视觉基础”和“批次 5：弹窗迁入页面系统”之间，增加一个独立的**数据展示基础**工作包：

1. 建立 `DataTableCard`、`DataTableToolbar`、`DataTableEmptyState`、`DataTableSkeleton` 和行状态资源；
2. 为 WPF `DataGrid` 统一表头、行高、hover/selected/disabled/error、横向滚动、固定表头、截断 tooltip、数值/代码列样式；
3. 为高级数据页建立列预设和列显示菜单，先支持显隐与默认列组；
4. 让 `AdvancedModDetails` 作为首个试点：高级模式双槽、关键卡片顶部保留、资产表横跨全宽；
5. 以 Game Data archive 浏览作为第二个试点，验证分页、筛选、行选择、右侧详情和取消加载；
6. 再把同一基础应用到任务中心和其他较轻量的表格。

## 7. 结论

new-api 最值得借鉴的不是某一张卡片的配色，而是它把“卡片、表格、工具栏、空状态、骨架、列布局、刷新状态”组织成可复用系统。Manager 的高级详情刚好是最适合首批落地该系统的场景：它既需要全宽多列数据表，也需要在首次加载、后台刷新和错误时保持专业、稳定、可理解的反馈。
