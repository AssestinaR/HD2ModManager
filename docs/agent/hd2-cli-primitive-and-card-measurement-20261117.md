# 原语几何 + 色卡测量：CLI 新能力与完整流程（2026-11-17）

> 目标：在自定义素体上放一块**已知图案的板子**，用游戏内截图量出引擎真实的颜色传递。
> 本文记录新增的 CLI 命令、踩到的三个 id 陷阱、以及从"生成几何"到"出偏差表"的完整命令序列。

---

## 1. 新增：`patch primitive`

把任意 Unit 的可见几何换成几何原语，输出**只含这个 Unit 的独立 patch**。
（不注入目标 mod，可独立成 mod，也可丢进素体 mod 的 `Overwrite\`。）

```powershell
hd2mod patch primitive <源 patch.toc> <形状> <尺寸> [xy|yz|xz] [x,y,z] [static] [mat=0x…] \
    --keys <0xtypeid>:<0xfileid> --output <目录> [--overwrite] [--json]
```

| 参数 | 含义 |
|---|---|
| 形状 | `tri` / `quad` / `cube` / `sphere` |
| 尺寸 | 米。quad/tri 用 `宽,高`；cube 用 `边长`；sphere 用 `半径` |
| `xy` / `yz` / `xz` | 四边形所在平面（法线分别朝 +Z / +X / +Y）。默认 `xy` |
| `x,y,z` | 中心点，unit 局部坐标，默认 `0,0,0` |
| `static` | 骨骼权重写 0（**实测：会被判为不可渲染，别用**，见 §3） |
| `mat=0x…` | 强行指定材质绑定 id（模板 unit 的绑定 id 全是 0） |

实现要点：**分量表不能自己造**。目标 Unit 的顶点流可能只有 6 个分量
（`position / normal / uv0 / uv1 / bone_weight / bone_index`），顺序、格式、
语义都由 `UnitStreamInfo.Components` 决定；生成器按它逐项填值，再交给
`CanonicalMeshPreparation.TryPrepare` 编码。代码：
`HD2ModAdaptation/PatchReconstruction/UnitMesh/Canonical/CanonicalPrimitiveBuilder.cs`。

### 1.1 首次可用：`E:\tmp\quad_mat`

```
hd2mod patch primitive wardrobe_hidden_unit.patch quad 1.2,1.2 xz 1.1,0,0.2 \
    mat=0xa990a3db10c4318b --keys 0xe0a48d0be9a7453f:0xdef7dc54e86d6054 --output E:\tmp\quad_mat
```

校验：`unit geometry` 显示 `顶点=4 三角形=2 可渲染=True`（每个 LOD 都是），
`unit TocData` 里出现 3 次指定材质 id（= 三条绑定都被注入成功）。

## 2. 三个 id 陷阱（每个都让我们白跑过一次部署）

| 陷阱 | 现象 | 正确做法 |
|---|---|---|
| **拿隐藏 unit 的 id 当外壳** | patch 正确、注册正确，但板子不显示 | `0xdef7dc54e86d6054` 是 `wardrobe_hidden_unit` 自己的 id，**语义是"把这个部件藏掉"**。必须换成自己的 id，例如素体命名空间的 `0x02e8377209ba0008` |
| **没在素体 JSON 里注册** | patch 放进 `Overwrite\` 也不出现 | 必须在 `sectional\custom-model.json` 的 `pieces` 里加一条 `(body, unit, slot, pieceType, enabled)` |
| **材质/贴图沿用原 id** | 板子显示了，但身体的同名材质/贴图被一起改掉 | 材质和贴图都要**换新 id**，再把 unit 的绑定指向新材质 |

关于槽位：源码 `ArmorStructure.cs` 里有实测表
`0 头盔 1 披风 2 躯干 3 胯 4 左腿 5 右腿 6 左臂 7 右臂 8 左肩 9 右肩`。
自定义素体本来没有披风（只用了 0 和 2~7），所以**把板子挂在 slot 1（披风）**不会顶掉任何部件。

---

## 3. `static`（不绑骨）不可用

四顶点权重全 0 会被几何分类器判为**不可渲染**：

```
不绑骨：可见 0/3，可渲染=False
绑骨  ：可见 3/3，可渲染=True
```

所以"完全不受骨骼影响"在 Unit 格式里不是一个可用状态。
可用的等价形态是**四顶点同权重绑同一根骨** —— 刚体，不会被任何骨骼形变，只是坐标系跟着那根骨走。

---

## 4. 坐标实测结论

用 `z=1.75` 的板子出现在头顶上方、`z=1.1` 出现在胸口 → 可以确定：

- **Z 轴朝上**，1 单位 = 1 米，原点≈脚底
- **+X 指向角色一侧**（屏幕右侧）
- **+Y 朝向镜头**（`xz` 平面正对相机可见）

## 5. 把色卡做进 patch 的完整序列

```powershell
# 1) 生成四边形 unit（带材质绑定注入）
hd2mod patch primitive <模板.patch> quad 1.2,1.2 xz 1.1,0,0.2 mat=<源材质id> --keys <unit> --output E:\tmp\A

# 2) 把 unit + 材质 + 贴图 合成一个自包含 patch（--pick 可重复，支持多来源）
hd2mod patch compose --header E:\tmp\A\*.patch `
    --pick E:\tmp\A\*.patch 0xe0a48d0be9a7453f 0xdef7dc54e86d6054 `
    --pick <源 patch_1> 0xeac0b497876adedf <源材质id> `
    --pick <源 patch_1> 0xcd4238c6a0c69e32 <源贴图id> `
    --output E:\tmp\B

# 3) 覆盖贴图像素为色卡（尺寸必须与目标贴图一致）
python tools\make_card_texture.py --out E:\tmp\card2048 --size 2048
texconv -nologo -f BC7_UNORM -m 1 -y -o E:\tmp\card2048 E:\tmp\card2048\card.png
python tools\embed_texture_data.py --patch E:\tmp\B\*.patch --texture <源贴图id> --dds E:\tmp\card2048\card.dds

# 4) 给 unit / 材质 / 贴图换新 id（见 §6 的脚本片段），再拷进素体
```

---

## 6. 换 id 的规则

- **unit**：`0xdef7dc54e86d6054`（隐藏模板 id）→ 自己的 id
- **材质**：`0xa990a3db10c4318b`（身体材质）→ 自己的 id，**同时把 unit TocData 里 3 处绑定一起换**
- **贴图**：`0xb990a3db10c4318b`（身体贴图）→ 自己的 id，**同时把材质 TocData 里对它的引用一起换**

patch 是"类型表 + 80 字节条目表 + TocData 区 + 侧车"：
条目里 `+0` = fileId、`+8` = typeId、`+16` = TocData 偏移、`+56` = TocData 长度。
换 id 只需改这 8 字节；TocData 内部引用用字节替换即可（id 是唯一值）。

## 7. 测量：`tools/card_measure.py`

```powershell
python tools\card_measure.py --shot <截图> --card-size 2048 --save-rectified rect.png --json out.json
```

流程：`cv2.aruco` 检出四角 → `getPerspectiveTransform` 求单应 → 按贴图坐标采样
→ 每格内缩 20% 取中位数 → 与"线性→sRGB 期望表"对比。

**离线自测**：把色卡按已知透视贴到画布上再量回去，8 个色块偏差全 0 —— 说明测量链路本身没有误差。

报告里有三块：

1. 期望/实测/偏差表
2. **通道顺序检查**（红→R 最大、绿→G 最大、蓝→B 最大）—— 能抓 BGRA 互换这类错误
3. **灰阶通道平衡 + 以灰卡为参照的归一化** —— 受光材质的绝对值会被光照整体缩放，归一化后才可比

## 9. 第一次游戏内测量结果（2026-11-17）

截图：`E:\tmp\shots\card\g2_000.png`（2562×1442，WGC 后台抓取）。
当时游戏里加载的还是**修正前**的贴图（V 反），所以 ArUco 是镜像的、检测器认不出；
改用**纯色块定位**（红/绿/蓝三块在 HSV 里是极端饱和区，12 个对应点 + RANSAC 求单应），
拉平后按贴图坐标采样。

| 色块 | 期望 sRGB | 实测中位 | 偏差 |
|---|---|---|---|
| red | 255,0,0 | **93,48,41** | -162,+48,+41 |
| green | 0,255,0 | **1,116,35** | +1,-139,+35 |
| blue | 0,0,255 | **17,34,110** | +17,+34,-145 |
| gray18 | 118,118,118 | **46,47,48** | -72,-71,-70 |
| gray50 | 188,188,188 | **62,67,74** | -126,-121,-114 |
| gray80 | 231,231,231 | **79,85,95** | -152,-146,-136 |

**判读（这是本轮最有价值的结论）**

1. **通道顺序正确**：红块 R 最大、绿块 G 最大、蓝块 B 最大 —— 没有 BGRA 互换那类错误。
2. **灰阶三档的比值基本保序**：实测 46 : 62 : 79 = 0.58 : 0.78 : 1.00，
   期望 118 : 188 : 231 = 0.51 : 0.81 : 1.00。两者吻合。
   如果链路里多做/少做了一次 sRGB 解码，这个比值会被压成平方关系（例如 0.27 : 0.66 : 1.00）或反过来。
   **⇒ 贴图→shader→屏幕 这段只做了一次 sRGB 解码 + 一次编码，没有重复 gamma。**
3. **绝对值整体偏暗约 1/3**：这是光照乘上去的结果（板子用的是受光材质），
   不是颜色通路错误。要拿绝对值必须让板子不受光。
4. 灰阶轻微偏蓝（R62/G67/B74，极差 12）：舰内环境光偏冷，属光照色温。

工具的三种定位方式（按可靠性排序）：**ArUco**（亚像素、最准）→ **纯色块**（极窄 HSV、稳）
→ **外轮廓**（最松，容易框到背景，只在板子边界清晰时用）。

### 9.1 重复性

同一状态连抓两帧（`g2` / `g3`），灰卡中位：

```
g2  62, 67, 74
g3  59, 65, 73        逐通道差 ≤ 3（0~255 尺度）
```

⇒ 测量本身稳定，后续判断"有没有改进"应以此噪声底（≈3 级）为门槛。

### 9.2 ArUco 在游戏内为什么认不出（本轮结论）

拉平图显示：板子表面被材质的**法线/粗糙度通道**叠了很强的横向条纹反光，
ArUco 的黑白格子被这些条纹切割，标准检测器（含镜像容错、亚像素细化）都认不出。

这不是 ArUco 的问题——**离线自测（干净图像）偏差为 0**。问题在于这张材质不是"平面、无光照"的。

⇒ 要稳定用 ArUco，板子的材质必须是**不叠法线/粗糙度、最好不受光**的直通材质。
这也是拿"绝对值"标定的前提。属于下一步，与测量链本身无关。

当前的替代方案（纯色块求单应）在本轮已证明可用且重复性良好，因此**测量闭环已经成立**。

环境：素体披风槽，板子 1.2 m，XZ 平面；材质 = 色卡贴图（albedo）+ 中性平贴图（其余 10 槽）。
截图 `E:\tmp\shots\card\m1_000.png`，ArUco 四角成功检出，8 个色块全部量到。

### 10.1 偏差表

| 色块 | 期望 sRGB | 实测中位 | 偏差 |
|---|---|---|---|
| red | 255,0,0 | 121,38,38 | -134,+38,+38 |
| green | 0,255,0 | 0,132,32 | 0,+132,+32 |
| blue | 0,0,255 | 0,27,126 | 0,+27,-129 |
| gray18 | 118,118,118 | 61,58,58 | -57,-60,-60 |
| gray50 | 188,188,188 | 97,94,94 | -91,-94,-94 |
| gray80 | 231,231,231 | 128,124,122 | -103,-107,-109 |
| skin | 206,166,149 | 112,87,78 | -94,-79,-71 |
| black | 0,0,0 | 37,35,36 | +37,+35,+36 |

### 10.2 灰阶拟合（本轮最硬的结论）

把三个灰阶换成线性值后拟合 `输出 = a × 反照率 + b`：

```
反照率 0.18 -> 0.0438
反照率 0.50 -> 0.1145
反照率 0.80 -> 0.2040

拟合：输出 = 0.2580 × 反照率 - 0.0066      R² = 0.9926
```

**截距 −0.0066 ≈ 0** ⇒ 链路里**没有多余的 sRGB 编码/解码**，只有一个整体增益（来自光照）。
如果多做一次解码，斜率与截距都会明显跑偏，R² 也会掉下来。

### 10.3 三个副产物

1. **黑块输出 0.0176 线性（≈36 级 sRGB）**：这是环境光/高光底噪，不是颜色通路问题。
   它解释了红块的 G/B = 0.019 —— 白环境光均匀抬高了所有通道。
2. **红块满反照率被压低 26%**（0.191 vs 线性预期 0.258）：高光被 tonemap 压了。
   所以**绝对亮度只能用中灰段反推**，满饱和色不能当标尺。
3. **灰阶通道平衡极差从 12 降到 3**（R97 G94 B94）：把法线/粗糙度等槽摊平之后，
   残留的偏差只剩环境光色温，说明之前那些 12 级的偏差是材质贴图扰动，不是引擎。

### 10.4 结论

- 通道顺序正确（红→R、绿→G、蓝→B 最大）
- **贴图 → shader → 屏幕：一次 sRGB 解码 + 一次编码，线性正确**（R² 0.9926，截距≈0）
- 剩余偏差全部可由"光照增益 0.258 + 环境底噪 0.018 + 高光 tonemap"解释，不属于颜色空间错误

要做**绝对**标定，下一步是把这块板的材质换成不受光的直通输出（或让 shader 直接输出 albedo），
那时 `输出` 应等于 `反照率`，斜率应变成 1.0。
