## 2. 逐份审计

### Q1 校验点排查 —— 最有价值，也最容易误导
- **直接证据（成立）**：SHEX 头/计数语义、`0x38=MUL` vs `0x3A=NOP`（我复核：`0x38` 带 `0x2000` saturate 位就是 `mul_sat`，`0x3A` 才是 `nop`）、checksum 范围 `[20, total)` 与算法可复现。
- **本轮最大产出**：它把"改过的 blob 无法自验证"这条死路**打通了**——项目 02:30 文档称"校验和算法未解、fxc/D3DDisassemble 都拒绝"，Q1 给出可用实现。我独立复现并验证：复签后 fxc 正常反汇编。**这一条建议直接采纳为工具链标准步骤。**
- **问题 1（重要）**：它仍把 checksum 当"待排查的校验点"并做了独立 D3D11 实验，但项目 02:30 文档 A 表已实测"**引擎不校验 DXBC 校验和**（作者载荷里那条记录本就是旧值，仍能渲染）"。我复核：作者记录的 hash 确实是旧值，且 8 份 60,504 全是旧值。**D3D11 会拒绝、游戏却能跑**，说明游戏根本不把这份 blob 原样交给 D3D11——所以"D3D11 拒绝 ⇒ 游戏拒绝"的推理链是断的，它的独立实验对本问题**没有外部效度**。它自己在 open questions 里承认了这点，但没有回头修正优先级。
- **问题 2**：它把"编译后接口"列为最高优先级，方向对，但**具体化错了**。真正的硬证据不是"寄存器分配不同"，而是：`fit_713.dxbc` 的 ISGN 语义表与原版不同（`TEXCOORD1@reg2`、`TEXCOORD3@reg2.w`、`COLOR0@reg6.z`…），而部署产物里又**直接沿用原版 ISGN**，同时 SHEX 的 `dcl_input_ps` 写的是 `v2.w`/`v4.x`/`v6.z`——**签名块与字节码自相矛盾**。这是"块间不自洽"，不是"接口被重新打包"。
- **问题 3**：它的"最小实验"要求 hook 引擎创建入口、双探针、留 debug message。信息量高但成本高，且**在已有一个更便宜的自洽性检验（§5-1）之前不值得做**。
- **置信度**：机制性陈述高；因果归因低（它自己标 low，合理）。

### Q2 等长指令重写 —— 结论可用，算术是编的
- **直接证据**：行号、指令文本、`r26` 只在 1858/1859 出现（我 grep 复核）、改写后 `r26.w` 一直活到 1910。方案可编码（我构造并反汇编通过）。
- **错误**：`sample_l` 实测 **13 dword**（首 dword `0x8D000048`），不是它写的"11 dword = 1+5×2"。11 dword 是 `sample_indexable`（`0x8B000045`，Q3 用的那条）。等长结论仍成立（操作数个数没变），但算式是虚构的——这类"看起来精确的推导"最危险。
- **遗漏**：改写后 1899/1901 读的 `r21.y/z` 变成读旧值（对输出无害，但会留下无意义计算）；目的掩码 `yz→w` 属**操作数级**改动，不是已验证的立即数级。
- **定位**：技术可行，但不是最省改动（Q7 3 dword、Q3 16 dword 都比它小/更干净）。

### Q3 长度不变注入 —— 本轮最扎实的构造
- **直接证据**：64 B 窗口 = 两条 8 dword `mov`（我核到旧字节 `08000036 001000F2 0000001C/1D …`）；16 dword 方案 = 11+5，我实跑构造 + 复签 + fxc 反汇编，得到预期两条指令，1,689 条不变。**它的字节序列完全正确。**
- **小错**：把"内部长度 13,055 DWORD"当成指令流长度（实际含 8 B 头，指令流 13,053）；不影响偏移计算。
- **未证**：所谓"内存验证"不是实机；它自己也标注了。
- **结论**：工程上最优（一条 11 dw sample + 一条 5 dw mov 塞进死 mov 槽，复用现有 `mov o0.w, r27.w`）。

### Q4 像素背包 diff —— 反向结论正确，证据充分
- **直接证据（我复核）**：holobag 里没有 `cb0[43].w`、没有 `frc`、没有 `emissive_wave*`；vanilla 有（427 行 `mad r6.w, cb0[43].w, r9.w, r6.w` + `frc`）。`t19` 采样在 512 行（`s7`，dest `r26.xyz`），`t20`/`discard` 在 311/314。`r24.x` 来自 372 行 `mov r24.x, r6.wwww`（albedo.a），`r24.y` 来自 499 行 idata；`r24` 只在 513/514 被读、之后再无写 → 它给的"尾部 `mov o0.w, r24.x`"可行。
- **推断（已标注）**：动态只能来自 t19 外部更新 / 顶点阶段 / 其他 pass。合理。
- **价值**：正确否掉了"背包提供时间动画"的想象，并指出可复用的是"逐像素 emissive"而非"UV 动画"。

### Q5 材质侧启用混合 —— **空**
这是决定项目生死的两问之一：如果 `o0.w` 只走 alpha-test/镂空，那么无论 shader 怎么改都拿不到连续半透明。报告 `result: null`。
**它本该发现的线索（现成材料里都有）**：
- 该 pass 的 RDEF 里 `opacity_sharpness`（offset 160）、`opacity_offset`（offset 288）**都存在但被 fxc 标 `[unused]`** —— 说明这条 pass 不读材质侧 opacity，材质侧路线必须换 pass/根材质；
- `global_viewport` 里有 `imp_transparent_override`（一个全局"透明覆盖"开关），是唯一像"运行时能改混合"的字段；
- VMF 源码（Q6 已抓）给出判定：`gbuffer_material` 继承的 `default` 是 `blend_enable=false`，`HAS_OPACITY` 走的是 `gbuffer_alpha_masked`（阈值 discard），真正混合在 `TRANSPARENT → hdr_transparent + transparent_base`。

### Q6 公开资料 —— 质量高，结论正确，但"最小实验"跑偏
- **我复核成立**：DXBC 16 B checksum 布局与范围；`vkd3d-dxbc --ignore-checksum`；VMF `default.blend_enable=false`、`gbuffer_material` 继承 default、`standard_base.opacity → HAS_OPACITY`、`TRANSPARENT → hdr_transparent/transparent`。
- **它做对的关键判断**：`HAS_OPACITY` ≠ 半透明，只是阈值镂空；真混合由 pass+render_state 决定，不是 shader 能给的。**这是全会诊里唯一把"目标可能根本不在这个 pass 里"说清楚的报告。**
- **问题**：它的"最小实验"是"复签后 fxc 反汇编"，那验证的是工具链，不是本项目的问题；而且项目 02:30 文档已实测引擎不校验 checksum，这一步对本项目**零信息量**。
- **未证**：HD2 的 TocData 字段名与 VMF 宏的对应关系（它自己标了 open question，诚实）。

### Q7 RDEF 与槽位 —— 补丁正确，但"唯一可行"的判断错了
- **直接证据（我复核）**：3 dword 补丁字节与偏移完全正确，复签后反汇编与它声称的一致；`r28` 只被 1902 写、`r29` 只被 1903 写、全函数无人读（我 grep 确认）；`o0.xyz ≡ 0`（1904 行 `mov r0.xyz,l(0)` 是作者新增的，之后 `div_sat` 恒 0）→ 本 pass 只有 alpha 可见。
- **错误 1（实质）**："唯一死指令槽（两条连续死 mov，共 16 dw）**塞不下** 11 dw 的 sample 除非整段重排，故只能重定向已有 sample 的 dest" —— **不成立**。Q3 的 11+5=16 正好塞满，我实测构造成功。它的"只能"结论把一个可行方案排除了。
- **错误 2（形式）**：`q7_patch.py` docstring 里 A2/A3 偏移写重（都写 52212），代码才是对的；交付物自述与实现不一致，容易被下一个人照抄错。
- **未提的风险**：A1 依赖 312 行那条 sample 被执行——我确认该行无缩进（顶层、无条件），所以没问题；但报告没给这个论证。
- **价值**：它给出的"整段光照链是死代码、只有 t7 活的"是本轮最有用的结构洞察之一，直接支撑"改 alpha 不必动别的"。

### Q8 记录选择机制 —— **空**
另一个决定性缺口：如果引擎按内容哈希/变体键选记录，那么"我们改了字节但没被选中"可以解释全部六次失败，而且与"字节码是否合法"无关。报告 `result: null`。
现成可用的材料：payload 头部偏移 4 处就是 `0xE577DB2C`（= 作者材质 id `0xe577db2cf97fcddc` 的低半），说明头部有 **64 位记录 ID 表**；272 条记录里 218 条 checksum 合法、54 条旧值，且作者改过的两族**全部**旧值。这些足以把"按内容哈希校验"与"按 ID 选取"分开设计实验，但没人做。

## 3. 被忽略的反例（本次审计最重要的部分）

### 3.1 反例一：作者自己的记录就是"整段换 SHEX + 加长 + 不重签"且能用
| 项 | 本体 advanced | 作者黑丝 |
|---|---|---|
| RDEF / ISGN / OSGN | 9,900 / 248 / 44 | **逐字节相同** |
| SHEX | 49,980 | **52,220（+2,240 B）** |
| 指令槽 | 1,578 | **1,652（+74）** |
| `dcl_temps` | 21 | **30** |
| STAT | 148 B | 148 B，**内容不同** |
| 记录总长 | 60,412 | **62,652** |
| DXBC checksum | 合法 | **旧值（未重签）** |

⇒ "整段替换 SHEX 一律不被接受"**作为一般命题是假的**；"引擎校验 checksum"也是假的。
剩下能解释六次失败的，只能是**我们产物的某个具体不自洽**，或**记录选择/外部表**，而不是"SHEX 不能换"。
**而 Q1/Q2/Q3/Q7 四份报告全部建立在"只能等长改/只能改立即数"这个被推翻的前提上。**

### 3.2 反例二：六次失败不是"一个变量"，是四处同时不自洽
我把实际部署产物（`famA_fixed.bin@517,344`，60,504 B）抽出来复签反汇编，看到：
1. RDEF 是**原版**（9 个 cbuffer、9 个 sampler、19 个资源）；
2. SHEX 里 **零个** `dcl_constantbuffer` / `dcl_resource` / `dcl_sampler`；
3. ISGN 是**原版**（寄存器 1..7），但 SHEX 的 `dcl_input_ps` 是 `v1.x / v2.x / v2.w / v3.x / v4.x / v5.x / v6.x / v6.z` —— **签名块与字节码的寄存器分配互相矛盾**（原版 ISGN 里 TEXCOORD3 在 reg4.w，字节码却读 v2.w）；
4. STAT 沿用原版（1,578 槽），而这份 SHEX 是 1,439 槽；
5. `ret` 之后还有 4 条畸形 `mul`（fxc 都只能反汇编成 `mul r, r, r`）。

**这不是一次"单变量实验"。** 六种形态各自坏了不同的地方，把它们合并成"整段替换失败"再去找单一根因，是典型的把相关性当因果。
顺带：Q1 说"错误 NOP 位于 RET 之后，所以不能解释失败"——对**执行**成立，但引擎若像 DX12 路径那样**解析并重写整个 token 流**，畸形 `mul` 会直接打挂解析器。这条不能像 Q1 那样轻描淡写地排除。

### 3.3 反例三："全零输出应全黑"这条判据会把成功判成失败
作者的 SHEX 在 1904 行有 `mov r0.xyz, l(0,0,0,0)`（diff 里是 `+`，作者新增），之后 `div_sat o0.xyz, r1, r0` 恒为 0 —— **RGB 本来就是黑的**。
所以：
- 写"全零输出"的探针，与作者正常输出在 **RGB 上无法区分**；
- 若 alpha 被消费（**已有证据**：项目 02:30 文档 A 表记录改 `0.266`/T 曲线会改变画面，而这两个常量只喂 `o0.w`），那么 alpha=0 的**预期外观就是"光腿"**；
- 他们看到"光腿、没变黑"就判"失败"——**这恰恰可能是探针生效的样子**。

这条判据是本次会诊最严重的逻辑错误，8 份报告**没有一份指出**（Q1 最接近，它说"全零应全黑"这个判别不可靠，但没给出上述推理）。

### 3.4 反例四：项目自己文档里"gbuffer 默认开混合"的推论与源码相反
02:30 文档八-B 推论 2 写"gbuffer 材质默认支持 alpha 混合"，依据是注释 "with refraction we are essentially taking over the blending in our shader, so we disable alpha blending"。
我抓了 VMF 源文件核对：`common#default.blend_enable = "false"`，`gbuffer_material` 是 `inherits = "default"`，**没有覆盖 blend_enable**；真正开混合的是 `transparent_base`（`TRANSPARENT → hdr_transparent + transparent`）。
⇒ 那句注释的正确读法是"**折射那条路**为了自己接管混合而关掉它"，不能反推"其他 gbuffer 路开混合"。**这条误读一直在给"改 shader 就能连续半透明"撑腰**，Q6 实际上已经纠正了它，但没人把两处对撞。

### 3.5 反例五：t7 本身就是 alpha 来源，且它可以被材质换图（零字节改动）
作者公式（我按指令核对，未计通道重排）：`alpha = sat((1 − 0.266·G·curve) · R)`（`curve = smoothstep(sat((N·V − 0.21)·1.265823))`）。
但该采样写的是 `t7.zxyw`（返回通道重排），所以实际取到的两个通道可能整体轮换（例如基底变成 B、调制变成 R）——**这不影响结论，只影响通道命名**，下文用灰度图规避。
`t7 = __tex_detail_normal_leather` 是**材质槽**，不是引擎全局。所以：
- 把一张**灰度渐变图**（R=G=B=ramp）绑到该槽 → alpha 直接随图变化；
- 再把 `mul r21.z, r21.z, l(0.266)` 的立即数（记录 **+62,120**，`0x3E883127`）改成 `0` → **alpha 精确等于该通道**；
- 全程 **0 个操作数改动、0 条指令改动**，全部落在已验证生效的"立即数"类别里。
- 注意两个坑：(a) 该采样用了 `t7.zxyw` 的**返回通道重排**（我核对指令确认），通道映射不确定 → 用灰度图规避；(b) UV 是 `u=0.5·v3.x+0.5 ∈ [0.500122, 0.999878]`、`v=0.5·v3.y ∈ [0.000122, 0.499878]`，只采**右上 1/4 象限、2× 放大**（立即数在 +61,932/+61,936/+61,952、+61,992、+62,036，可后续修正）。

**Q7 说 t7 "真活跃、必须避开"，Q4 说 t7 是"抖动纹理"，两份都只差一步：它是材质槽，换图即可，不需要改任何字节。** 这是全会诊漏掉的最省路径。

### 3.6 反例六：作者 shader 里没有对 alpha 的 discard
全文只有 1 条 `discard_nz`（269 行，与尾部 alpha 无关）。所以尾部 alpha 若被消费，只能在固定管线（混合/alpha-test 由 render_state 给）或下游 pass。配合 §3.4，**"连续混合 vs 阈值"至今没有被任何证据确定** —— 这正是下一次实机该测的东西。

## 5. 只允许再做一次实机测试：测什么

### 先做（免费，不需要上机）
1. **把六份失败产物逐份复签 + fxc 反汇编**，确认字节码本身是否畸形（尤其 `ret` 后的 4 条 `mul`）。工具已现成（§1）。
2. **造一份"五块自洽"的探针**：用与原版**相同的输入结构/相同的 cbuffer 与资源声明/相近的 `dcl_temps`**写 HLSL，让 fxc **一次生成** RDEF/ISGN/OSGN/SHEX/STAT，再整块替换——这才是与作者等价的做法。现在这版（原版 RDEF/ISGN/STAT + 外来 SHEX）在四个地方同时不自洽，无论实机结果如何都无法归因。
3. **用 D3D11 真正画一帧**（不是 `CreatePixelShader`）。我实测：畸形产物 `CreatePixelShader` 也返回 `S_OK`，所以现有 D3D11 结论**不能**当作"可执行"证据。画一帧才能排除"驱动编译期失败"。
4. 补齐 Q5/Q8 的离线部分：材质侧 `render_state/pass` 判定（两份原版材质对差 + 帧抓取）、payload 头部 ID 表结构（用作者 payload 与其源记录对差）。

### 实机：一次部署，两个材质，各只改一个变量（同一份**已知可用**的作者材质）

| 组 | 改动 | 字节数 |
|---|---|---|
| **A（主）** | `__tex_detail_normal_leather`（t7）槽绑**灰度渐变图**（R=G=B 平滑 ramp）；同时把记录 **+62,120** 的 `0.266` 改成 `0.0` | 1 dword + 1 张贴图 |
| **B（判读用）** | 只把记录 **+62,160** 的 `l(1.000000)` 改成 `l(0.000000)`（`alpha ≡ 0`，因为 `r21.x = 0 − 0.266·G·curve ≤ 0`） | 1 dword |

**判据矩阵（一次启动就能读出）**

| A 的现象 | B 的现象 | 结论 |
|---|---|---|
| 不透明度随图**平滑**渐变 | 整件消失 | **连续混合成立** → 目标达成，只需再用 4 个立即数把 UV 修正成 UV0 |
| 出现**一条硬边**（一边全透一边不透） | 整件消失 | 只走 **alpha-test/镂空** → 连续半透明必须换 pass/根材质（Q5 路线），shader 侧到此为止 |
| 完全无变化（还是原织纹） | 整件消失 | alpha 通路正常，但 **t7 槽/贴图覆盖没生效** → 查材质槽绑定与 UV 象限 |
| 完全无变化 | 也完全无变化 | 部署/记录选择层出问题（不是 shader）→ 转 Q8 的表结构与记录 ID |

**为什么是它，而不是别的**
- 不测"整段 SHEX"：作者记录已证明可行（§3.1），而我们每份产物都多处不自洽（§3.2），一次测不出单一结论。
- 不测"复签"：02:30 已实测引擎不校验（§3.1 复核），零信息量。
- 不测 Q2/Q3/Q7 的 operand 补丁：三者我都验证可编码，但它们回答的是"引擎收不收非立即数改动"，**不回答"连续半透明到底存不存在"**；后者才是项目瓶颈。
- A 组是**零操作数改动**（只换贴图 + 一个立即数），B 组是**一个立即数**，两者都落在"已被证明会生效"的类别里，失败也能干净归因。
- 若只准改一处：选 **A 的贴图**（0 字节）。它的正结果直接交付目标；负结果至少排除"t7 槽可被材质驱动"。
