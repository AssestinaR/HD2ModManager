# section 组按「来源」分组与命名（2026-11-10）

接 `sectional-vpk2patch-display-parity-20261110.md`。用户实机看过 sectional 产物的 21 个 section 组后：
「当前的组命名几乎没有可用性」。已确认的口径：**一个来源一个组**。

## 一、为什么现在不可用（实测，水墨牛牛那条产物）

| 组名 | 来源 | 成员 |
|---|---|---|
| `Helmet` / `Torso（Slim）` / `LeftArm` … | 规划器拼的**槽位名** | 整个 unit 的全部段 |
| `2787157324_lod4` / `hips_culling` / `LeftArm_Armor_Any_mesh0` | donor unit 的**网格语义名** | **0 段（空）** |
| `LeftArm`(cc61…) / `RightArm`(3415…c8) | 指向产物里**已不存在的 unit** | 失效 |

21 组里 7 组空成员、2 组指向不存在的 unit —— 9/21 点了没有任何反应。剩下 12 组是"整个部位"，
那不是开关，是把部位整个关掉。对比 vpk2patch 的 5 组（`美甲 / 胖次 / 裙子 / 鞋子 / 袖子`）：
名字是**做模型的人**在 `$BodyGroup` 里给的，所以它可用是白捡的。

根因两条：

1. 组的名字只能来自 `SectionalSplitSource.Name`（unit 的网格语义名）或槽位名——**没有"这块几何属于谁"这一维**；
2. 段来源账（`CanonicalAppendedSection`）只记 `InputIndex`（第几个追加输入），**不记是哪份来源**；
   宿主自己那份拷贝是"序号最大的 patch 赢"的结果，也不能当名字。

## 二、可用性从哪来：来源条目本来就有名字

`sectional-source.json` 的 `sources[]` 就是这些名字，且 `PatchFiles` 能把"patch 文件 → 来源"对上：

```
本体 / 大衣 健壮 / 上衣 / 翅膀 / 尾巴 / 短下摆 / 长下摆 / 内裤 / 丝袜 / 鞋子
（其余 9 个是材质球：淡紫白、灰、白、黑、黑红、白黑、白黑银、黑金、黑银 —— 只有材质，没有 unit）
```

每个 patch 里有哪些 unit 也实测过：`patch_0`（本体）带全部 21 个；`patch_1..9` 各带 1–3 个
（大衣 → `0ca3…`，尾巴 → `126d…`，丝袜 → `00a8…/75c5…/7938…`，鞋子 → `8e71…`…）。
所以"这段几何是谁的"是可以**精确回答**的，不需要猜。

## 三、口径

1. **组 = 一个来源**（跨部位合成一个组：`尾巴` 的那几段无论在躯干还是胯，都在同一个组里）；
   名字 = `sources[].name`；没有名字时 `来源 {n}`（n = 它在依据里的顺序 + 1）。
2. **不设互斥**（`exclusiveGroup = null`）。按 `{槽位}/{身形}` 互斥等于"躯干只能选一个"，
   与"全都要"的意图相反；这些是**部件**，不是二选一。
3. **段的归属**：
   - `InputIndex = -1`（宿主自己那份拷贝）→ 宿主拷贝所在 patch 的来源；
   - `InputIndex >= 0` → 那个追加输入所在 patch 的来源（**按 mesh 记**：每个 LOD 的可见输入列表可能不同）；
   - 说不清时归宿主来源，并记一条 warning（不静默）。
4. **不存在空组**：组只在真有段归属时才生成；反过来，"有 unit 但一段都没归到它"的来源
   要**报出来**（`unmatched` + warning），否则用户会以为这个部件不存在。
5. `SourceVpk` 写来源名，组行副标题显示「来自「尾巴」」（现在是"来自附加部件"这种泛话）。
6. **不动几何**：仍然是"所有拷贝全部并入"。所以关掉某个部件时，重复的基础拷贝还留在别的组里
   —— 去重是下一轮（见第六节）。

## 四、改动点

| 文件 | 改什么 |
|---|---|
| `SectionalSplitter.ExecuteAsync` | 新可选参数 `sourceNames`（patch 文件名 → 来源名）；追加时按 mesh 记下每个输入的来源 |
| `SectionalSplitter.BuildSourceGroups`（新） | 按来源聚合段；按首次出现顺序输出；返回 `SectionGroupDocument` |
| `SectionalSplitter`（调用处） | 传了来源名就走新分组，没传（CLI `custom-model sectional`、老测试）保持原行为 |
| `Legacy2SectionalConverter` | 从依据文件拼 `PatchFiles → Name` 传给拆件器 |
| `VpkGroupItemViewModel.Detail` | `SourceVpk` 非空时显示「来自「…」」 |
| 测试 | `BuildSourceGroups` 的三条：跨部位合并 / 每个来源一个组 / 有 unit 但零段要报 |

## 五、验收

- 水墨牛牛重构建后，组表按来源命名（实测见下方"真机复核"）；
- 关一个组的勾选仍然按 (unit, section) 存进 `wardrobe.json`（组名/组 id 变了也不丢状态）；
- 全量测试绿、0 警告。

## 六、真机复核（临时副本上跑真正的转换器，库里那条产物不动）

```
unit 组：21 个 key，来自 10 份 patch
计划：11 个 target，其中 10 个有 donor（躯干 1、胯 2、手臂 1、腿 1）
组表（3）：
  '本体'  49 段  [头盔 5, 躯干×2 6, 手臂×4 8, ...]
  '丝袜'  21 段  [胯×2 7, 右腿 7]
  '尾巴'   4 段  [左腿 4]
未成组：大衣 健壮 / 长下摆 / 翅膀 / 上衣 / 鞋子 / 内裤
        —— 它们带了 unit，但没有任何一段几何进产物
```

命名这一半成立（`本体` / `丝袜` / `尾巴` 就是来源条目的名字），
但暴露出**两个与命名无关的真问题**：

1. **宿主被追加到它自己身上。**`ReadSourcesAsync` 把 `units` 与 `Copies` 分两遍读，
   两遍是**不同实例**，所以 `ReferenceEquals(copy, host)` 恒假 ⇒ 宿主自己那份拷贝被当成 donor 又追加一次 ⇒
   每份基础几何都重复（实测 `ecc8` 的 6 段里 `#1≡#4`、`#2≡#5`；`75c5` 的 7 段里两对完全相同）。
2. **donor 的几何没进来。**11 个 target 全部报 `段来源账缺失`（`appended.Origins` 为空），
   donor 只在个别 unit 上留下 1 个三角形（`4ebb` 的 `#3`，材质 id 是 donor 的命名空间）。
   这就是那 6 个来源一段都归不到的直接原因——不是命名问题。

两条都在"所有来源全部并入"这条链上，与本次改动无关（本次只改了组表的组织方式），
所以按用户的"不动几何"口径留到下一轮，并且新代码已经会**把它报出来**（`unmatched` + 详情页那行提示）。

## 七、第二轮：修掉那两个问题（2026-11-10 晚）

按"像 vpk 侧那样"的思路修了两处，都验证过：

**① 宿主自拷贝。**`ReadSourcesAsync` 改成 **先读全部拷贝、胜者取 `copies[^1]`**（同一个实例），
再用"引用相等 + 同一份 patch"两道判据排除宿主自己。顺带省掉一次全量解析。
效果：11 个 unit 的重复指纹从"每 unit 数对"降到 **0**（`3415`/`4a52` 那两处报"重复"的其实是
`none-0` 空占位段，不是几何）。

**② 段来源账。**`CanonicalDecorationUnitAppender` 的段账从"按段数判可信"改成
**按材质槽 id 反查最终段下标**（`ResolveOriginsBySlot`）：0 三角形段与同槽合并掉的段不再让整份账作废，
只记"确实进了最终网格"的那几段。三条在役路径（跨甲合并 / 规整 / 头盔合并）行为不变。

真机复核（临时副本，跑完整 `Legacy2SectionalConverter`）：

```
改前：11 个 target 全部"段来源账缺失"，组表 3 个（本体 49 / 丝袜 21 / 尾巴 4）
改后：warnings 27 → 10（只剩"某个槽有 N 个来源 unit"的规划提示），组表 9 个：
  '本体'      30 段
  '大衣 健壮'  1 段   （ecc8#3 = 70492 三角形，大衣的真几何）
  '丝袜'       9 段
  '长下摆'     2 段   （28861 / 28861）
  '上衣'       2 段   （14740 / 14740）
  '翅膀'       2 段
  '尾巴'       2 段
  '鞋子'       1 段   （10522）
  '内裤'       2 段   （19760 / 306）
```

## 八、第三轮：重构建不再吃掉用户的组表改动（2026-11-10 深夜）

实机发现：重构建之后界面还停在上一次的 21 个组，其中 9 个组的 unit 早已不在产物里。原因不在命名，
而在 `VpkPayloadSwap.Swap`：`components.json` 与 `custom-model.json` 被列进 **PreservedFileNames**——
"用户能改组表，所以换载荷不敢覆盖它"。但转换器也没有把新组写回去，于是新的按来源命名的组永远到不了界面。

**改法（vpk 与 sectional 两条路共用）：**

1. **换载荷之后由转换器写回组表**：`SectionGroupMerge.Merge(fresh, previous, sections)`——
   这次转出来的组是权威；用户手建的组按新产物重算成员后保留；旧文件里的自动组丢掉。
2. **用户的三种改动活过重建**（`SectionGroupCustomizations`）：
   - **改名**：按"名字或成员 unit 集合"匹配上一份的组（段下标每次都会漂，不能当键），沿用旧名字；
   - **互斥设置**：同上沿用；成员/来源仍取这一次的；
   - **删除**：`components.json` 新增可选 `hidden`（用户的删除记录，带名字 + 成员 unit 集合），
     重建时抑制这些组。重新建一个同名组即恢复。格式因此升到 `hd2mod.section-groups/2`，
     旧版 `/1` 仍可读。
3. **vpk 路径**：`SectionGroupConsolidator` 末尾套用同一份改动（它本来就按材质名重算成员＋保留手建组）。

真机复核（临时副本，重构建两次 + 手工改名/删除）：

```
第一次重建：9 个组（本体 / 大衣 健壮 / 丝袜 / 长下摆 / 上衣 / 翅膀 / 尾巴 / 鞋子 / 内裤）
手工：把「尾巴」改名「尾巴（大）」、删掉「翅膀」、加一个手建组「我的手建组」
第二次重建：'本体' '大衣 健壮' '丝袜' '长下摆' '上衣' '尾巴（大）' '鞋子' '内裤' '我的手建组'
            —— 改名保住、删掉的「翅膀」没回来、手建组还在；hidden 记录随文件保留。
```

## 九、仍然留到下一轮


- **一个 LOD0 只能取一个网格。**`翅膀` 在来源里的 LOD0 有两个网格（真几何 10372 三角形 + 1 三角形外壳），
  而 `ResolveVisibleMeshAtLod` 只取一个 ⇒ 产物里只留下 1 个三角形。vpk 侧的 `UnitAuthor` 是**遍历该 LOD 的全部网格**的。
- **0 三角形占位段仍在产物里**（每个 legacy unit 的第 0 段），VPK 侧没有这种段。
- 这两条都指向同一件事：**把"合并多个来源"从"往宿主追加装饰"换成"用外壳 + 全部碎片重建 unit"**。
  那一轮做完，空段、单网格、段账三件事会一起消失。
- 同一部件的不同身形/配色（`大衣 健壮` / `大衣 纤细`）将来若要互斥，再单独加 `exclusiveGroup`。
