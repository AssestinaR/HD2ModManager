### 2.1 attach 后整组 unit 同帧消失 ✅ 已澄清（不是我们的 bug）

原以为"attach 后 30 帧全灭"是运行时判死判据太激进造成的；1.1.0 加观测后的实机日志给出答案：

```
[LIFECYCLE] 会话失效（dead）：unit=#ID[60ecdf3b…] 存活 5488 帧 链=27   ×7（同一帧）
[LIFECYCLE] 会话失效（dead）：unit=#ID[60ecdf3b…] 存活 359 帧   链=27   ×7（同一帧）
```

- **7 个 unit 在同一帧一起消失**，存活 46 秒 / 6 秒 ⇒ 场景切换（军械库→舰船、舰船→任务）。
- 若真是我们写坏，会是**逐个**死、且死因是 `rebuilt`（`场景图节点数 171→148`）；
  这里 `LIFECYCLE` 的 rebuilt 计数为 0，死因是 `alive == false`。

> ⚠️ 判死只信 `Unit.alive` 和 `num_scene_graph_items`。`has_node` 会对同一根骨假翻
> （`nodes 171→171` 而它变 false），**绝不能拿来判死**——它只用于观测。

### 2.2 22/134 条链永远挂不上 ✅ 已修（P1）

日志实证：22 次 `可用链 32 条（缺节点 0、缺锚点 7）`、20 次 `…缺锚点 6`。

**根因**（代码路径已核对）：

1. rig 里有 8 根**非 jiggle 的父骨**（idx 80/81/90/94/100/102/105/107）不在 rig 中；
2. 它们的子骨在 rig 里 ⇒ `M.build_chains` 判定"父不在 byIndex" ⇒ 子骨成**链根**；
3. 链根的 `parentName` 就是那根非 jiggle 骨的名字（`source_extra_90`、`UN_Skirt_R_02`）；
4. `M.anchor_name()` 的映射表只有 ValveBiped 名字 ⇒ 查不到；
5. 回退成"把 parentName 当 HD2 骨名查" ⇒ 不存在 ⇒ 缺锚点。

**旧文档 `physbone-status.md §9.5` 的诊断是错的**（写的"嵌套锚点链部分跳过"）。
锚点是 jiggle 骨时 `build_chains` 根本不把它当链根，那是另一回事。

**修法（不动协议、不动运行时、旧 rig 兼容）**：
`Retargeter.PlanJiggleBones` 插骨时已经算出 `resolved[父骨]` = 这根非 jiggle 骨**回退到的 HD2 原生骨下标**
（`Retargeter.JiggleBones.cs:106`）。把这个下标对应的 **HD2 骨名**写进 rig 的 `parentName` 即可 ——
`anchor_name()` 查不到映射时本来就会回退成把 `parentName` 当 HD2 骨名查，这条路已经在了。

## 6. 现在的状态（2026-11-01 收尾）

### 6.0b 源模型有三种约束形式，过去只实现了锥（2026-11-01 第二轮实机）

**这是主线的核心缺口，不是某个 mod 的问题。**

源 `mstudiojigglebone_t.flags` 的约束位有三种组合：

| flags | 含义 | 求解器过去的行为 |
|---|---|---|
| `0x11` / `0x31` / `0x39`（含 `angleCon 0x10`） | 锥限位，`angleLimit` 有值 | ✅ 正确 |
| `0x2d`（`yawCon 0x04` + `pitchCon 0x08`，**无** `angleCon`） | 偏航/俯仰**分轴**限位，`angleLimit` 为 0 | ❌ **当成完全不限位** |
| 都没有 | 真的不限位 | ✅ 正确 |

实测分布（用户库里四套资产）：三套 100% 带 `angleCon`（12–35°），**一套 21/55 根骨是 `0x2d`**。
那一套实机单节转角冲到 **174°**（画面上就是缎带乱飞），另外三套只有 34–39°。
这就是"同一个转换器，A 模型正常、B 模型乱飘"的根因。

修法（第一步已做）：`gains_of` 多收 `opts.flags`；没有 `angleCon` 时用
`max(|minYaw|,|maxYaw|,|minPitch|,|maxPitch|)` 外包成对称锥。
离线效果：偏离绑定方向峰值 91.8° → 60.1°，`不限位` 骨 21/55 → 0/55，
另外两套 `cone×55/57` 一字未变（对本来正常的模型零风险）。

**未做（第二步）**：非对称被丢掉——`pitch −45..0`（只许往下）现在变成 ±45°。
按轴分别夹要动 `step_tip` 的核心夹取逻辑，风险更大。

**这一轮同时排掉的猜测**（都有测量，别再重推）：

| 猜测 | 结论 |
|---|---|
| 作者没填重力（`tipMass=1` → g=0.019） | ❌ 把 tipMass 抬 200 倍（g=3.81），峰值角 **25.0° → 25.0°**，一点没变 |
| dt 写死 / 重复积分 | ❌ 实机 `dt=0.0083~0.012`（≈100 Hz）、`同拍重复=0`，上一笔的修法没被触发 |
| 求解器自己发散 | ❌ 锚点静止跑 60 秒，1 秒内收敛（峰值 15°、写入掉到 0.2/帧）后一动不动 |

**长期资产**见 §1.1。这套工具把"导入 → 进游戏 → 肉眼看"换成了"跑脚本 → 拿数字"，
这三轮的根因**没有一个是在游戏里猜出来的**。

### 6.0g 1.8.0 试了但没修好：换人检测一次都没触发（1.9.0）

实机：仍没物理，而且那段时间**特别卡顿**。日志给了两条硬事实：

1. [换人] 计数 **0**。
2. 重新挂载打出的是**同一批** #ID[a0cc3d23…]。

⇒ **Unit.debug_name 是按资源/描述符算的，不是按实例。** 拿它比"是不是同一个人"永远相等，
判据从根上无效。（顺带说明：之前"整组同帧死亡 = 场景切换"的结论是**碰巧对**，理由不成立。）

1.9.0 的改法：

| 问题 | 改法 |
|---|---|
| 判据无效 | 比 **userdata 同一性**（awequal） |
| 定期校验太贵（完整 discover ≈ 7 千次调用） | 换 scanAvatars：每 unit 两次调用 |
| 尸体可能仍是 avatar 候选 | 忽略表记住已判定的尸体，只认未忽略的新候选 |
| 只取"第一个"容易一直选中尸体 | cache.preferAvatar 优先上次认定的玩家 |
| 等待中轮询跑完整 discover | 超过 200 帧后拉长到 3 倍间隔 |
| 候选打分每件约 460 次调用 | 只测最近的 12 件 |

**卡顿的机制**（harness 复现）：尸体一直是候选 ⇒ 每 1.2 秒都判一次换人 ⇒ 反复 release + 重挂
（几百次引擎调用 + 姿态跳变）。T7 里反复 7 次，修后 1 次。

T7 已改成贴近实机的场景：尸体 unit 仍活着且仍是 avatar 候选，新玩家在 50 m 外出现。

### 6.0f 阵亡复活后没有物理（1.8.0）

现象：玩家阵亡后尸体留在原地，**旧 unit 不被销毁**；复活出来的新玩家没有物理。
关掉物理再进游戏则一切正常 ⇒ 又是我们这边。

根因：pruneSessions 只判 Unit.alive == false 与节点数变化。尸体活着、节点数不变，
所以会话一直"健康" ⇒ 我们持续驱动尸体，而新玩家的护甲 unit 从没被挂过。

修法（三件事）：

| 做的事 | 为什么 |
|---|---|
| 换人检测 playerChanged，约每 1.2 s 一次 | 先看原 avatar 是否还活着（1 次调用）；否则走一遍 discover 比实例名 |
| 尸体 Compat.release | 不交还姿态的话头发停在最后写入的那一帧，像被冻住 |
| maxArmorDistance（默认 5 m） | 否则重挂时会把尸体也一起挂上 |

discover 认 avatar 的条件是"有动画状态机 + 带 support_mg"，尸体是 ragdoll 通常不再满足，
所以"实例名变了"就是换人。另兜一条"实例名没变、但身边护甲一件都不是我们挂着的"，
覆盖实体被重建 / 同一 unit 只换位置的情形。

**诊断钩子**（万一下次还是没物理，看这两行就够）：
- [换人] 玩家实例变了：<旧> → <新>
- [观测] 场上有 N 个 avatar 候选 —— 若尸体也保有动画状态机，这条是判它的唯一依据。

验收：runtime-harness T7（阵亡 → 新玩家在 50 m 外出现 → 检测到换人、尸体交还、
重挂到新玩家、尸体不再被挂）。**尚未实机验证。**

### 6.0e 第五次实机：只剩左右两根不对劲（1.7.0）

现象：大多数头发正常了，只剩左右两根仍"不自然弯折 + 像掉帧一样一卡一卡"。

**量化结果（这次不靠感觉）**：写了 	mp/lua-check/saturation-probe.lua，
直接读部署出去的容器，报每条链"有一节贴在限位上的帧占比"：

`
limitRelax=1.00
  Back        89.2%
  Side.L/R    73.9%
  Back_S.L/R  70.5%
（其余 20 条链：0.0% —— 一条都没贴过墙）
`

**恰好就是被投诉的那 5 条。** 而它们饱和的原因是**作者给的限位本来就极小**：

| 链 | 作者 yaw | 自然摆动需求 |
|---|---|---|
| Side.L/R | ±15° | ±57° |
| Back | ±5° | ±57° |
| Back_S.L/R | ±30° | ±57° |

按作者值夹就必然是"几乎不动的硬杆"。放宽到 2.5 倍仍有 66~79% 饱和 ⇒ 不是"夹太狠"，
这几条链天生就动不了多少。**这是设计选择，不是 bug。**

**能修的是"卡顿"**：约束过去只改位置不改速度，朝墙外的那份速度一直堆着，
等约束不再生效时被一次性甩出来 ⇒ "卡一下再弹开"。现在夹取时同时去掉朝墙外的速度分量
（非弹性约束，分轴与锥两条路都做了），并把硬吸附换成"只往边界靠 40%"，贴着边界滑动连续。

**产品决定留给用户**：limitRelax（默认 1.0 = 完全尊重作者）。

### 6.0d 第四次实机：比上一轮差得多，头发向前翘且僵硬（1.6.0 已修）

现象：向前移动时头发向前翘、特别僵硬；**关掉物理后正常** ⇒ 确实是我们的问题。
两个独立缺陷叠在一起：

**① 参考系混用**（1.5.0 自己引入的，最严重）

分轴限位里，绑定方向用 `goalQ`（绑定时锚点朝向）旋转，而 left/up 用**当前** `q` 旋转。
参考系一错开，`l·n` / `u·n` 就不再是"偏离多少"，而是随机数 ⇒ 每帧都在被夹 ⇒
身体一动头发就被钉住。

离线复现（同一份 rig，边走边转，注入旧代码）：

| | 各节偏离 |
|---|---|
| 旧代码（混合参考系） | **179.9°**（整根翻过去） |
| 修后 | 15.0° / 30.0°（正好卡在作者上限） |

修法：三个轴统一取静止参考系，并且**在 attach 时就算好**（`goalQ` 恒定）⇒ 每帧零成本。

**② 世界朝向锚定被误加到头发上**

原判据只查 `yawCon(0x04) + pitchCon(0x08)`。当初样本恰好是"大袖子 0x3d（有 0x10）"与
"头发 0x31（没有 0x04/0x08）"，看着能分开。但真实资产里还有第三类：
**纯 yaw/pitch 的头发（0x2d，没有 0x10）**——被误判成"布料"，于是头怎么转头发都不跟。

实测：原地转头 90°，这类链相对头偏离 **180°**。

修法：判据补上 `angleCon(0x10)`，回到文档原本的意图（大袖子 0x3d）。
袖子挂在手臂上，世界锚定合理；头发长在头上，必须跟着头走（只是滞后）。

修后实测（真实 rig，原地转头 180°/s，相对**头**的偏离）：

```
Side.L / Side.R        14.5°   （作者上限 15°）
Back_S.L / Back_S.R    29.9°   （作者上限 30°）
Back                    5.0°   （作者上限  5°）
UN_Hat_L.001          114.7°   ← 锥类，逐节 35° 沿链累加（与 1.4.0 相同，未改）
Braid.002.R            89.7°   ← 同上
```

**仍未处理**：锥类（`angleCon`）的限位是"相对父节"的，会沿链累加
（5 节 × 24° = 120°）。头发里最长的辫子/刘海属于这一类。要不要也改成"相对自身静止方向"
是个设计选择——1.4.0 时这个行为没被投诉，所以先不动，等这轮实机反馈。

### 6.0c 第三次实机：头发正常了，但左右各一根翘起来（1.5.0 已修）

现象：主体已经正常，只有两侧各一根飘带翘到水平以上。

判定：**是我们的物理，不是模型。** 把 25 条链的绑定形状全量出来（HD2 世界 +Z 朝上）：

```
Side.L      3 节  bind 方向 (-0.22 -0.22 -0.95)   离正下方 18°
Back_S.L    5 节  bind 方向 ( 0.12  0.23 -0.97)   离正下方 15°
```

全部朝下，最歪的一根离垂直也只有 27° ⇒ 模型转过来是正常下垂的。

而 `Side.L/R`、`Back_S.L/R` 恰好是**唯一两组"单边 pitch"的左右对称链**：

| 骨 | yaw | pitch | 1.4.0 给的对称锥 |
|---|---|---|---|
| `Side.L/R` | −15..15 | **0..30** | ±30° ← 多给了另一边 |
| `Back_S.L/R` | −30..30 | **−45..0** | ±45° ← 多给了另一边 45° |

根因是**基准选错**：锥是"相对父节"的，会沿链累加。3 节各 30° 从下垂 18° 起能累到 70°，
足够翘到水平以上。Valve 的 min/max yaw/pitch 是每根骨相对**自身静止姿态**的范围，不累加。

修法：分轴限位改为**相对自己的绑定方向**夹（`l·n` / `u·n` 直接就是 yaw/pitch 分量，
不用 acos），这一类骨不再走父节相对的锥。

同条件离线对照（patch_24，±40° 偏航 + ±15cm 平移，逐链最大偏离绑定角）：

| 策略 | 最差链 | `Back_S.L` / `Back_S.R` |
|---|---|---|
| 完全不限位（1.3 之前） | 179.8° | 179.5°（整根翻过去） |
| 对称锥 / 相对父节（1.4.0） | 74.0° | **74.0°**（刚好翘到水平以上） |
| 分轴 / 相对绑定（1.5.0） | 67.5° | **49.0°** |

49° 从下垂 18° 算起，最远也只到水平线以下 23°。

**仍未做：非对称。** `pitch 0..30`（只许一边）现在按 `±30` 对称夹。
要真按单边夹得知道 Valve 的 min/max 符号约定；猜错会让那根骨**完全冻住**，
比多晃两下难看得多。扫过的四份 rig 里没有能反推符号的样本。

**几何事实（别当 bug）**：两轴各自夹 ±limit 时，合成偏差的上界是
`atan(√2·sin(limit))` 而不是 limit —— 矩形约束的角点必然比单边远（30° 的角点是 35.3°）。
Valve 的 min/max 本来就是两个独立区间，这是**正确**行为。

## 4. 不要重推的坑（都是实机踩出来的）

- **判死只信 `Unit.alive`**；场景图重建只信 `num_scene_graph_items`。
  `has_node` 会对同一根骨假翻（`nodes 171→171` 而 `has_node` 变 false）——**不能用来判死**。
- **不能缓存引擎句柄**（0.1 秒就变 inf）。
- **对已销毁 Unit 调任何方法 = 原生 AV**，`pcall` 拦不住 ⇒ 必须事前判断。
- **`written == 0` 不等于故障**（脏标记 + 运动门限会让静止时天然为 0）。
- **计时不可靠**：`Application.time_since_launch` 每帧只更新一次（块内首尾差恒为 0）；
  `os.clock()` 会被引擎其它线程污染（实测同工作量 1.58 ms vs 5.21 ms）。**性能只报引擎调用次数**。
- **`update` 实际约 70 次/秒**，不是 375（375 是引擎内部 tick）。
- 首行 `-- HD2-Addon:` 标记**前面不能有空行**，文件**不能有 BOM**（Lua 5.1 不跳过 BOM，编译直接失败）。

## 5. 三家加载器约定（外置包用）

Boot Mod Loader / Chef Shared Loader / MDL3 全都认同一套：

- 资源名 `mods/<作者>/<名字>`；
- **首行** `-- HD2-Addon: mods/<作者>/<名字>`；
- Boot Mod Loader 用 `io` 读 `data\9ba626afa44a3aa3.patch_0..N`，连续 64 个号缺失才停，重名时高号胜。

外置包导出到 `%LOCALAPPDATA%\HD2ModManager\LuaPackages\<功能>\`，
内含 `lua版/`（裸脚本）与 `patch版/`（manifest + 补丁三件套）。
