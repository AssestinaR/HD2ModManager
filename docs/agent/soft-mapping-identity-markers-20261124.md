# 软映射的身份问题：用"同位素标记"取代看外观猜

2026-11-24。起因：CM-17（映射 milfy）+ FS-05（映射 lilium）在实机上两个身体看起来一模一样
（lilium 整体 + 多两只 milfy 手臂），修补表无法判断穿的是哪套。

## 为什么外观不可用

`set_resource_override` 是按**承载件 unit** 全局生效的，两套护甲共用承载件时，一个 carrier 只能有
一个覆盖结果。实测（当前工作区 8 条映射，只统计 slot2–9；头盔 slot0 与披风 slot1 是独立装备）：

| 套 | 身体件 | 可见且独占的件 |
|---|---|---|
| FS-05（3970674111） | 23 | **0**（19 件与 CM-17 那组共用；4 件独占但被映射成隐藏） |
| CM-17（2509257439） | 27 | **0**（19 件共用；8 件独占但全被映射成隐藏） |

⇒ 两个身体可见的 unit 集合完全相同，**没有任何可观测差异**。此前用的两个锚点落在 slot0（头盔），
而头盔是可以单独更换的 item，用它判"穿的哪套护甲"本身就是错的。

## 解决办法：给每套护甲一件专属隐藏件

隐藏件不可见，但实例仍在世界里、登记在自己的 id 下。所以：

1. 给每套已映射护甲分配一个**专属隐藏件 id**（确定性派生：`Murmur64A("hd2modmanager/marker/{kitId}")`）。
2. 把它名下"**独占且本来就映射成隐藏**"的承载件改成指向专属隐藏件 —— 视觉零变化，实例只在
   穿那套护甲的身体上出现。
3. 协议发 `mark=<kit>,<markerHex>`；运行时在身体附近查该 id 的实例 ⇒ 直接得出穿的是哪套。

与外观无关，因此不受"头盔/披风可单独更换"、"多个视觉来源抢同一批承载件"影响。

## 可行性已验证

随包隐藏件是单条目 patch（`wardrobe_hidden_unit.patch`：1 个 unit 条目，`def7dc54e86d6054`，
TocData 4240、gpu 418、stream 0）。用 `PatchArchiveWriter.WriteAsync(..., additionalEntries)` +
`PatchArchiveAdditionalEntry(AssetKey, TocData, StreamData, GpuResourceData)` 把它复制成多个新 id，
再 `PatchTocScanner` 反解校验（条目数、类型表计数、TocData 长度）通过。
回归：`HD2ModAdaptation.Tests/MarkerHiddenUnitPatchTests`。

## 约束

- 只有存在"独占 + 已映射成隐藏"承载件的套才能免费打标。若不满足，要么放弃该套的认甲（如实记日志），
  要么牺牲一个原本可见的槽位（视觉有代价，需显式配置）。
- 认甲判别量一律排除 slot0（头盔）与 slot1（披风）。
- 标记件 id 必须确定且唯一；同一 kit 每次部署得到同一个 id，避免协议与 patch 不一致。

## 引擎侧"直接问身份"已被探针证伪（2026-11-24 实机）

只读探针 `armor_identity_probe.lua`（v1→v3，随独占 boot 投放，开关是
`ArmorRegistry/identity-probe.on`）三轮实测结论：

| 探测 | 结果 |
|---|---|
| `_G` 全局名 | 只有 51 个，**没有 `data`**，没有任何装备/护甲相关表 |
| `Application.has_data({key})` 六键 | 全 false |
| `Application.get_data({})` / `{'kits'}` / `{'armor'}` / `{'equipment'}` | 调用成功但**全返回 nil**（连空路径都拿不到，无法枚举键名） |
| `Unit.has_data(avatar, key)` × 26 键 | 全 false |
| `Unit.get_data(u, {})` / `has_data` × 12 键，对 16 个身边件 | 全 nil / 全 false |

⇒ 引擎**没有**对外暴露任何可读的"当前装备/护甲身份"数据。

## 副作用（重要）：`World.units` 扫描其实是安全的

v1 崩溃的根因**不是** `World.units`，而是用法（结论来自 `kit_instance_hider.lua` 的实机注释）：

1. **句柄不能跨帧**：每拍重新取列表，本拍处理完就丢；
2. **读坐标前必须判节点数**：`num_scene_graph_items(u) > 0` 才 `world_position(u, 1)`
   （对没有场景节点的 unit 读坐标 = 原生 AV，Hider 0.4.4 实机结论）；
3. 命中项要在**同一拍**内探完，不留到下一帧。

v3 按这三条跑完 2128 个 unit、探了 16 个身边件，**零崩溃**。
⇒ 这条路可以用，例如"民主官的头该怎么藏"：在他锚点 1 m 内扫一遍，藏掉不属于替换计划的 unit。

### 3. 键盘：`Keyboard.pressed(Keyboard.F8)` 可用

```
{"r":"keyboard_shape","ok":true,"shape":"pressed(F8)","value":"false"}
{"r":"keyboard_shape","ok":false,"shape":"Window.keyboard(main)","value":"string"}
```
静态形状（不带设备参数）直接能用、返回布尔；`Window.keyboard(main)` 返回 `string`，那种形状不通。
⇒ 以后做游戏内热键有落点了，不必再用 `probe-scan.txt` 这种文件触发。

### 4. 顺带否掉一个观察方式

- pass A 的 anim 列表上限 24 被写满 ⇒ "离玩家最近 6 个锚点"里没有玩家自己的 avatar
  （最近的锚点在 2.5 米外）。v7 把上限提到 64。

  全部报**根的位置**（dx=dy=dz=0）。两者放在一起只有两种解释：要么探针认的"玩家"

## v7 实机结果（2026-11-24，两轮：file:B / file:A）

v7 = 3 米定点扫描 + watchlist（0 节点也记）+ 全部 avatar 实例 + `units_by_resource` 键形状实测。

### 1. `units_by_resource` 的键必须是 `IdString64`（重要）

| 键形状 | `82595b5d…` | `15678e36…` | `8085023e…` | `4b6217d8…` |
|---|---|---|---|---|
| `IdString64.from_hex(hex)` | **1** | **1** | **8** | **9** |
| hex 字符串 | 0 | 0 | 0 | 0 |
| `#ID[hex]` | 0 | 0 | 0 | 0 |
| 大写 hex | 0 | 0 | 0 | 0 |

而且每种形状的数目**与全量扫描的实例数完全一致**（8/8、9/9）。⇒ 运行时那条
`World.units_by_resource(world, Id64.from_hex(hex))` 本来就是对的，
"按资源查不到"是**那个 id 在场上没有实例**，不是 API 用法错。
