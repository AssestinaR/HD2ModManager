# P4 规划：VPK 模型 Mod 的「专属切换」

日期：2026-11-14。上接 `kit-instance-isolation-productization-plan-20261113.md`（P0–P3）。用户已于 2026-11-14 拍板 §8（全部按推荐），P4a 可以开工；P4b 不做。

## 1. 为什么要有 P4

用户问：「雫游泳教练」这种 Mod 怎么办？用它替换玩家的神射手，再转专属，会怎样？

实测现象：
- 用户想转专属，被 P3 拦下，提示「这个 Mod 没有覆盖任何护甲的原版部件」。
- 「目标护甲」切换到 FS-05 后，CE-64 等护甲被一起换掉了。
- 民主官（爱弥斯）没受影响。

原因：
1. 这是 VPK 模型 Mod。导入后，模型按部位切成 7 个**新 ID** 的 unit，放在 `sectional/`（`079d12e38aec0001`…`0007`）。
2. 「目标护甲 → 切换」把这 7 个 unit 改成目标护甲的原版 unit ID，写进 `Overwrite/`，带标记 `.hd2-vpk-rekey-overwrite`。真正生效的是 `Overwrite/` 这份。
3. P3 只读 `Overwrite/` 以外的那层，看到的全是新 ID，所以说「没覆盖原版部件」。这句提示有误导性。即使读对了，`Overwrite/` 已被切换占用，P3 按 D6 也会拒绝。
4. 切换写的是 FS-05 的**共用** unit，所以 CE-64 等 13 套一起变。民主官没受影响，是因为爱弥斯的隐藏规则把民主官身上那 20 个原版部件藏掉了。雫的模型正好写在这些部件上，也就一起被藏了。

结论：P3 的「事后转专属」不适合 VPK Mod。**专属要在切换那一步就做**：改 ID 时直接落到目标套自己独有的部件上，同时生成隐藏规则。

## 2. 现状（代码事实）

调用链：
- `ModDetailsPageView.xaml:74` 的「切换」
- → `ModDetailsPageViewModel.Vpk.cs` `ApplyVpkTargetArmorAsync`（:576）
- → `ModCompileService.CompileAsync`（:52）
- → `SectionalCompiler.CompileAsync` / `CompileArmorAsync`（:83 / :212）
- → `SectionalCompilePlanner.Build`（`SectionalCompilePlan.cs:106`）
- → `SectionalUnitPatchWriter.WriteAsync`
- → `OverwriteMaterializer.Materialize(..., ManagedOverwriteMarkers.VpkRekey)`，写入 `Overwrite/`，有备份和回滚。

目标怎么选：
- 下拉框**按归档（archive）列**（`VM.Vpk.cs:541-547`），不带 item_id。
- 编译时取「归档等于目标的第一条记录」，再扩到**同 `set_id` 的全部护甲和头盔记录**（`SectionalCompiler.cs:229-241`）。

各部位怎么落：
- 每个源 unit 落到同 slot 的「整套共有层」最外层，每个身形 unit 各一份。
- 同 slot 的其它层，以及没有源的 slot（如肩），用**全局空壳 unit**（同 key、网格缩成一个三角）藏掉（`SectionalHiddenUnit.cs`）。
- 被连带的其它护甲多出来的部件也用空壳藏掉（a7e6934 `HideCollateralExtras`），让它们整套看起来也是这个模型。

切换流程里**没有**任何按实例隐藏（KitInstance）的逻辑。

几何合并：切换只做改 ID，**不合并几何**。合并头盔到身体只是换 slot 或层，不合几何。仓库里唯一真正合并几何的是旧版转换 `SectionalSplitter` + `CanonicalDecorationUnitAppender`：
- 按 (slot, 身形) 合并；
- 不跨身形；
- 骨骼按名字哈希对齐；
- 需要重算剔除包围盒。

第一人称：躯干和头盔在第一人称下隐藏。仓库明确规定躯干几何不能挂到别的槽位（`ArmorCell.cs:47-51`），否则第一人称会挡镜头。

## 3. 数据（Release 索引，不含披风；body type 0/1/3 = 三种身形行）

- FS-05 三条记录归档不同：
  - `124623533` → `31d06451…`（民主官 NPC）
  - `3970674111` → `8670598c…`（玩家）
  - `1490803405` → `ccac0a57…`（未知）

- 三条 FS-05 记录在身体部位（slot 2–7）的 12 个格子里，**一个独有部件都没有**。唯一能用的只有左肩（slot 8）：玩家和 `1490803405` 共用的 `90b57e54`/`755f0bcd`；民主官独有的 `82595b5d`。
- 全部 138 套普通护甲中：
  - **41 套**每个身体格子（slot 2–7 × 身形）都有自己的独有部件，可以零合并地专属切换。例如 AD-26、SR-24、AD-49、DS-191、SS-500、DP-00。

  - 其余的部分格子有独有部件。
- 普通切换下，雫在 FS-05 上覆盖 127 个原版 unit：
  - 37 个是 FS-05 的，含爱弥斯的签名件 `82595b5d`，两个 Mod 在这里撞车，当前爱弥斯优先；
  - 82 个是 13 套被连带护甲的空壳。

## 4. 方案：「专属切换」（P4a）

### 4.1 用户流程

1. 详情页「目标护甲」旁加一个开关「专属」，默认关。关时行为与现在完全一样。
2. 开「专属」时，下拉改为**按记录（item_id）列**，同名记录带编号区分，比如「FS-05“神射手”（3970674111）」。每项标出状态：
   - **可专属**：每个需要的格子都有独有部件；
   - **不可**：附原因，例如「躯干·健壮身形没有独有部件」。
3. 点「切换」前弹预览，列出：
   - 每个模型部件落到哪个独有部件；
   - 目标套上哪些原版部件会按实例隐藏；
   - 被占用的独有部件原本的外观（会被模型取代）；
   - 头盔怎么处理（§4.4）。
4. 确认后写 `Overwrite/` 和隐藏规则，下次部署生效。关掉「专属」再切换，或切到别的目标，旧的隐藏规则一并删除。

### 4.2 规划器（纯函数，可离线单测）

输入：源部件表（`sections.json` 的 slot/层/身形）、目标记录 T 的部件、每个 unit 的拥有者集合。

1. 对每个源格子 (slot, 身形)，在 T 的同一格子里找**只被 T 引用**的 unit 作承载件：
   - 优先最外层，同级按 ID 排序；
   - 每个承载件只承载一个源 unit。
2. 任何一个源格子找不到承载件，**整个失败**，并列出缺哪些格子（沿用 D5，不做半套）。
3. 隐藏集：
   - 包含 T 的全部原版部件（不含披风），减去承载件；
   - 有源的格子里、承载件以外的层也藏掉，避免叠穿；
   - 这些都交给 Hider 按实例隐藏，**不写全局空壳**。
4. 被连带的其它护甲：不存在。因为只改写了 T 的独有部件，没有 `HideCollateralExtras`。
5. 签名：`all=[按 ID 排序的第一个承载件]`，`none=[]`，`radius=0.3`。
6. 规则名：`vpk-<item_id>-<ModNodeId 前 8 位>`。

### 4.3 写入与记录

- 改 ID 和写文件复用现有的 `SectionalUnitPatchWriter` 与 `OverwriteMaterializer`，标记仍用 `VpkRekey`。专属只是换了一份目标 unit 清单，外加不写空壳。
- 隐藏规则写进 P1 的 workspace（`kit-instance.workspace.json`），按 ModNodeId 存，额外记 `source=vpk-exclusive`。
- **所有权**：这条记录由「切换」管理，P3 的「撤销专属」按钮对它不显示。重新切换或关专属会删掉或替换它。删除 Mod 时记录会留在文件里，但规则编译器只编译启用中、且仍在库里的节点（P1），所以它不会生效。本轮不额外清理。
- 内容指纹：沿用 P3（只算基底，不含 `Overwrite/`）。
- `wardrobe.json` 增加 `targetItemId` 和 `exclusive: true`。旧文件没有这两个字段时，按「非专属」读。

### 4.4 头盔（slot 0）

- 头盔是单独的记录（kit_kind 1）。专属时，在 T 同 `set_id` 的头盔记录里按 §4.2 找独有部件：
  - 找到就照做；
  - 找不到时**不替换头盔**，保留原版头盔，在预览里写明。不让整个转换失败。
- 「将头盔合并到身体」开着时，头的源 unit 按现有逻辑落到躯干第二层。专属模式下，躯干第二层也必须是 T 的独有部件，否则按 §4.2 第 2 条失败。
- 头盔替换时，头盔记录里其余的原版部件也进同一条规则的隐藏集。**未验证**：头盔 unit 是否落在签名 0.3 米半径内。爱弥斯那条规则没有藏头盔，没有先例。实机验收时要专门看头盔有没有叠穿；叠穿就把头盔单独做一条规则，签名取头盔承载件。

### 4.5 顺带修 P3 的误导提示

- 对带 `sectional/` 的 VPK Mod，「共用部件」卡片不显示 P3 的「转专属」，改成一行字：「这是模型 Mod，请在上方『目标护甲』打开『专属』再切换」。
- 「共用部件」卡片分析的仍是生效内容，也就是 `Overwrite/` 那份，现在已经是这样。

## 5. 神射手怎么办（P4b，探针，先不做）

玩家神射手 `3970674111` 在 P4a 下会显示「不可：躯干、手臂、腿都没有独有部件」。唯一的路是：

- 用 D9 的左肩 `90b57e54`/`755f0bcd`（每身形一个）当承载件，把 7 块模型**合并成一块**（几何合并，复用 `CanonicalDecorationUnitAppender`）后放进去；
- 隐藏玩家神射手其余全部原版部件；
- 签名按 D9 带 `none`。

已知风险，**都要实机探针才能回答**：
1. **第一人称挡镜头。** 躯干几何放在肩部槽位，第一人称不会被隐藏（`ArmorCell.cs:47-51` 明令禁止这么做）。这很可能是硬伤。
2. 合并后包围盒、LOD、材质槽数、`BoneInfo.Remaps` 都要重算。物理骨（physbone）挂在一个 unit 上的行为没验证过。
3. 穿 `1490803405` 的人左肩会显示整个模型，叠在原版身体上。

建议：P4a 做完后，用户如果仍要神射手，再单独做 P4b 探针，产出一个手工测试版本让用户进游戏看第一人称。第一人称不可接受就放弃神射手专属，在界面上把它标成「不可」并说明原因。

## 6. 不做

- 不改普通切换（专属关闭时）的任何行为。
- 不做跨格子的几何合并（P4b 才碰）。
- 不改 Hider 和规则协议（P1 的协议够用）。

## 7. 测试与验收

- 规划器单测：
  - 41 套可专属里任取一套的真实数据；
  - FS-05 失败及原因；
  - 只有部分格子有独有部件时失败并列出缺口；
  - 头盔无独有部件时保留原版；
  - 头盔合并开关。
- 写入：
  - 专属切换后，`Overwrite/` 不含任何非 T 独有的原版 unit（离线扫描验证）；
  - 再关专属切换，记录被删。
- 门：`dotnet build -c Debug` 0 警告 0 错误；`dotnet test -c Debug` 全绿；不改 Lua。
- 实机（用户）：
  1. 选一套可专属的护甲（如 DP-00“战术”），对雫专属切换；
  2. 部署后自己穿它，显示雫；
  3. 穿 CE-64、FS-05 等，都是原版；
  4. 民主官仍是爱弥斯。
