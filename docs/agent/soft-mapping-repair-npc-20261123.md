## 为什么民主官需要单独一条链

民主官穿的是**真实护甲记录** FS-05（`124623533`，23 件标准护甲件，走 Helldiver 骨架），
但他不是映射目标：软映射改的是**承载件 unit**，而他的件与若干玩家护甲共用同一批 unit，
于是只要映射了那些护甲，他身上那部分会被一起改写、剩下的还是原版 ⇒ 整身混搭。

实测（2026-11-23，6 条映射在生效时）：FS-05 的 23 件**一件都没被覆盖**，与当时 6 个映射目标共用 0 件。
也就是说这条链眼下是"预备"，真正的触发条件是把下面这些套之一加进映射：

| 套 | 名称 | 与民主官共用件数 |
|---|---|---|
| 3970674111 | FS-05“神射手”（同名另一条记录） | 21（整身） |
| 2509257439 | CM-17“屠夫” | 19 |
| 1490803405 | FS-05“神射手” | 15 |
| 1732669856 | CE-64“掷弹兵” | 15 |
| 1400802885 | FS-61“无畏” | 13 |
| 2006219485 | FS-11“行刑者” | 11 |
| 337681978 / 2613138368 / 3265410911 | SC-37 / 0xe1e36c37 / 0xefa2bd81 | 各 6 |
| 2150790862 / 2342442877 / 2886393549 / 1556124245 | B-24 三条 / AF-50 | 各 4 |
| （披风 `ea846ef460cc5ba0`） | 41 套共用 | 1 |

同期全量审计：索引里 107 套有件被覆盖，其中 103 套只被覆盖 1 件（slot1 披风 → 隐藏件），
真正"显示成别人的件"的只有当时 3 个映射目标本身。

## 硬约束：原版外观回不来

`set_resource_override` 是全局且**不可逆**的，一旦 FS-05 的件被改指，原版 unit 在那个 id 下就没了；
他的同名记录（3970674111）用的是**同一批 unit**，没有另一份原版件可克隆。
所以只有两种结果：跟随覆盖后的视觉来源（整身一致），或隐藏被污染的槽位（缺件）。
按用户决定采用前者：**整身替换成视觉来源**。

## 协议新增 `npc=`

```
npc=<NPC 护甲记录 id>,<标记 unit 十六进制 16 位>
```

- 标记 unit 同时是**定位**和**身份**。
  **（2026-11-24 修订）** 原来用的"他的脸 `7862870bc9822eeb`"是错的：探针 v7 把全船 2000+ unit 全量
  扫了一遍、又对 36 个候选 id 各做了一次 `World.units_by_resource(IdString64)` 查询，
  这个 id **一个实例都没有** ⇒ 那条 `npc=` 行从来没有生效过。
  现在的首选标记是**他的根 unit `15678e360612b805`**（`DemocracyOfficerRootUnitId`：`anim=true`、
  84 个场景节点、全船唯一，17 个护甲件都坐在它坐标上；不在任何护甲记录里 ⇒ 打映射永远改不到它），
  兜底是**他独有左肩 `82595b5d94c57343`**（`DemocracyOfficerShoulderUnitId`，`kit-instance.rules`
  一直拿它当 marker）。运行时按顺序试，第一个查得到实例的赢。
- 标记是根 unit 时**不再留信标槽位**：以前要牺牲一两个"只属于他"的槽位不替换，好让运行时还能找到他；
  根 unit 打映射碰不到，8 个槽位可以全部参与替换。
- 有了标记就不需要认甲锚点：`BuildAnchors` **不给 NPC 套写锚点**（否则穿同款的玩家会被认成 NPC）。
- 只有该 NPC 真的出现在修补表里才写这一行，否则运行时每拍空转。

## 部署期怎么定"视觉来源"

`RepairTableBuilder.BuildNpcRows`：先找 NPC 身上**被改写过**的件（`actual[carrier] = donor`），
再用 donor 反查是哪个映射素体提供的它 —— 那个素体就是他的视觉来源。然后：

- 每个槽位都换成视觉来源在该槽位的件；素体在该槽位没有件 ⇒ **隐藏**（视觉来源本来就不该显示）。
- **slot0（头）一律不碰**：见下一节。

## 民主官的头：补成他那套的 slot0 件（2026-11-24）

原来打算"部署期判断视觉来源有没有头，有就按实例藏他的脸"。**改成补一件 slot0 的件**，
`KitNonPlayerArmors.WithOfficerHead` 在权威快照读完之后把
`unit 387f271c7f49614f`（v8 实机确认就是他的头）作为 `(slot0, 身形 Any, Helmet, pt0)` 的件挂到
`124623533` 名下。补上之后，"把民主官当映射目标"和映射普通护甲**完全同构**：

| 视觉来源 | 编译器输出 | 结果 |
|---|---|---|
| 有 slot0 的件（带独立头盔/头） | `link=387f271c7f49614f,<来源的头>` | 引擎按正常换件把他的头换成来源的头 —— **位置和姿势都由引擎给**，不需要克隆、不需要按骨名重绑 |
| 没有 slot0 的件（头并进身体的两槽素体） | `link=387f271c7f49614f,def7dc54e86d6054` | 他的头消失，显示的是身体件里那个头 |

**修补表不再写 slot0 的行**（连"只隐藏"也不写）。原因：修补表克隆时只能按骨名绑，
而 `BONE_NAMES`（运行时那份词表）里**根本没有 head / neck / spine 这类骨** ⇒ 克隆出来的头
一骨都挂不上（`linked 0 bones` 直接 abort）；而"只隐藏"会连换过来的新头一起藏掉
（`hideOccupied` 会把 donor 也藏）。头和头盔只走 `link=` 换件这一条路。

回归：`HD2ModCore.Tests/OfficerHeadMappingTests`（补件幂等；有头模型 → 头换成来源的头；
没头模型 → 头指向隐藏占位）。

## 实机坑（2026-11-25）：民主官的身体整套消失，只剩头

**现象**：把民主官映射到一套 Mod 甲，刚进船时身体和头都正常，站到他旁边一会儿，
**身体整套消失、只剩头**（截图确认：头是 Mod 的头，斗篷/制服/四肢全没了）。

**根因**（从 `wardrobe.links` 就能看出来）：玩家穿的是 FS-05（3970674111），和民主官那套
（124623533）**共用承载件**；这些共用件的 `link=` 第一个写的是民主官的模型
`36a9eef0d78f…`，而 `set_resource_override` **先写生效** ⇒ 实际显示的是民主官的件。
修补表为此给玩家那套补了"藏掉错的"行：

```
repair=3970674111,2,2,36a9eef0d78f0002,-
repair=3970674111,3,2,36a9eef0d78f0003,-
…（槽位 2～7 各一条）
```

而运行时的隐藏用的是**宽松判据**（"半径 2 米内这个 id 的所有实例都藏"，为的是把展台/队友/尸体
身上显示错的件一并处理）。玩家站到民主官旁边时，民主官身上那批件就是这个 id ⇒ **被一起藏了**。
头之所以活下来，是因为玩家那套没有 slot0 的行，`36a9eef0d78f0001` 从没进过任何"要藏"的集合。

**修法**（运行时 1.10）：加 `ownedByOtherKitNpc(x, y, z, kit)` —— 如果这个实例最近的
avatar 是**另一个套的 NPC 宿主**，就不许藏。理由是那批 donor 在他身上**是对的**（他穿的是另一套，
由他自己的 `npc=` 会话负责）。宽松判据对"同套的展台/队友/尸体"照旧生效。

回归：`tests/test_armor_override_runtime_update.lua` 的用例 F（玩家身上那份要藏、
民主官身上同一件不许藏），并做了负向验证：去掉这个判断，用例立刻失败。

## 运行时（Lua 1.8）

- `findAvatars` 额外把 `npc=` 标记 unit 的实例当作宿主，`kit` 直接给定（不走认甲）。
- 已有机制全部复用：按槽位决策、per-avatar 会话、宽松隐藏 + 引用计数、teardown 恢复。
- **骨架配对的适用条件**：`rig` 是按玩家骨架（107 节点）算的，NPC 用的是飞船 NPC 共用骨架
  `0xb5c27e4a810df382`（69 节点，命名与玩家同一套但下标不同）。因此只有
  `num_scene_graph_items(avatar) == rig.avatar` 时才按表绑定，否则退回按骨名绑定。

## 其他 NPC 的边界（后续再做）

| NPC | 结构 | 根 unit | 脸 unit | 骨架 |
|---|---|---|---|---|
| 女舰长 | 伪记录，**唯一一件 = 根 unit** | `0xd87d04aacbc0269c` | `0x85d4ba84db7d27e5` | `0xb5c27e4a810df382`（69 骨） |
| 维修技术员 | 同上 | `0x93fb8680b7ff7f96` | `0x4d4017549585cb8e` | 同上（根 unit 的 header 0x20 就是骨架 id） |
| SEAF 士兵 | 原版根 unit 重建人物网格（保留骨架/挂点/LOD 路由） | `0x75f7e96af7dcd303` | — | `0x7a3637cd33a54e4c` |

这三类是"单根 unit 承载整身 + 自带骨架"，不存在护甲槽位可克隆，槽位级修补接不上；
要支持得另开一条根 unit 级链路（根 unit 克隆 + 用 `KitNpcRecords.PatchHeader` 补骨架引用 + 藏脸）。
骨架命名与玩家一致，所以那条路本身通，但属于另一块工程。

## 首次真机复盘的三个坑（1.9 修掉）

1. **会话卡死**：1.6~1.8 用"我们藏过的件还剩几件"判断会话是否成立。而 `maintain` 每拍都会把
   半径内**新出现**的实例塞进 `hidden`（实测每拍 16~20 件），于是 `touched` 永远 > 0
   ⇒ 换甲之后会话也永不失效 ⇒ 水墨牛牛的克隆继续挂在身上、新护甲再也不重新识别。
   **正解：会话是否成立只看认甲结果**；认不出或认成套外的，连续两拍才拆（一拍 0 命中是
   军械库↔飞船、死亡重生的正常抖动）。
2. **NPC 按资源查不到脸**：`units_by_resource(7862870bc9822eeb)` 拿不到实例（日志里一个
   `tag=npc:…` 都没出现）。
   **（2026-11-24 定位到根因）** 那条 API 本身没问题 —— 探针 v7 用 `IdString64.from_hex` 的键
   逐个查过，`82595b5d94c57343`=1、`15678e360612b805`=1、`8085023e1b2d62bf`=8 全都能查到；
   查不到的原因是**那个 id 在场上根本没有实例**（全量扫描 2000+ unit 也没有）。
   **修法**：标记换成根 unit（见上一节）。
3. **兜底标记不能被藏**：它是定位标记，藏掉就再也找不到他。所以旧方案里信标所在槽位**不做整身替换**
   （留在原版），最多留两个槽位，代价是民主官的肩甲保持原样。
   **（2026-11-24 已不需要）** 标记换成根 unit 之后它不会被打映射改写，8 个槽位全部参与替换。

定位结果会写成一行日志（只在变化时）：

```
repair npc: kit=124623533 15678e360612b805=1 82595b5d94c57343=1 chosen=15678e360612b805
```

格式是 `标记=实例数`，按 `npc=` 行的顺序逐个试，`chosen` 是第一个查得到的那个。
