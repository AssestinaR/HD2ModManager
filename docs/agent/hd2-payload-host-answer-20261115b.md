## 2. 你们 6 次实验里，有一次的关键前提是错的（实测）

`E:\mod\9ba626afa44a3aa3.patch_73\` 这条包，是一个**结构正确**的"覆盖本体根材质"包：

```
条目 1 个：fileId 0xef9b3fc2fc1ba61e   gpuOff=0  tocSize=2288  gpuSize=2928416
TocData：undat2=2928416  parent=0  12 槽   （与本体 toc 只差 11 字节，且都在材料变量区）
载荷头：+0=0xb3  +4=0xef9b3fc2  +16=1     （与本体逐字段一致）
```

也就是说 **材质这一层是对的**。错的是它里面那条着色器记录：

| chunk | 本体同槽（60412 B） | patch_73 里的（同样 60412 B） |
|---|---|---|
| RDEF | 9,900 | **12,172** ✗ |
| ISGN | 248 | 248 ✓ |
| OSGN | 44 | 44 ✓ |
| SHEX | 49,980 | **39,672** ✗ |
| 第五块 | **STAT 148** | **PRIV 8,184** ✗ |

对照我们**唯一被实机确认**的那份构建（`famA_alpha_only`，材质 `0xe577db2cf97fcddc`）：

| chunk | 原版（60,504 B） | 我们的（同样 60,504 B） |
|---|---|---|
| RDEF | 8,092 | 8,092 ✓ |
| ISGN | 252 | 252 ✓ |
| OSGN | 92 | 92 ✓ |
| SHEX | 51,828 | 51,828 ✓ |
| STAT | 148 | 148 ✓ |

**四份能跑的构建，五个 chunk 的名字、顺序、长度全部与 donor 逐项相同，只有 SHEX 里的字节变了。**
`patch_73` 那条则是 RDEF 变大、SHEX 变小、STAT 被换成 PRIV —— 用 `tools/gate_build.py` 一跑就是
`G1 ✗ 块布局与原版不一致`。

所以：**"护甲消失"不能用来否定"覆盖本体根材质"这条路。那次实验从头就没成立。**

## 3. MourningVeil 的结构：没有任何材质自带载荷（实测）

我把 `.abtest-backup\20261115-0950-before-rootmat\9ba626afa44a3aa3.patch_2`（E 系列改动之前的基线）整个扫了一遍：

```
patch_2：157 个条目，其中材质 92 个
   parent = 0xef9b3fc2fc1ba61e（本体 advanced 根，11 槽）  x 24   undat2=0  gpuSize=0
   parent = 0xd84d04634a1e2f60（本体另一个根，3 槽）        x 68   undat2=0  gpuSize=0
patch_0：0 个材质（7 个 0xe0a48d0be9a7453f 类型的条目）
```

**92 个材质 100% 是子材质**：`parent ≠ 0`、`undat2 = 0`、`gpuSize = 0`。
这个 mod 一个字节的着色器载荷都没有，全部继承本体根材质的载荷。

由此：

- 你们说的"本体 380 个根材质全部自带载荷"是对的，但那是**根**材质；这个 mod 里**没有根**。
- E5/E6「就地改造 unit 引用的材质 + 设 undat2/gpuSize」= 让一个子材质同时当根材质。
  **在这份文件里这种形态一次都没出现过**（不是"证明不可能"，是"没有先例"，且它确实失败了）。
- 真正"该承载载荷"的对象只有两个：`0xef9b3fc2fc1ba61e` 和 `0xd84d04634a1e2f60` —— 都是本体材质。

### 3.1 反例很重要：mod 自造根材质是**有先例**的（实测）

我们这边跑通的那份材质，在同一个 bundle `9ba626afa44a3aa3` 里有**两层定义**：

```
patch_0：  0xe577db2cf97fcddc  parent=0x8f669f365f24594e  undat2=0  gpuSize=0   13 槽   子材质
patch_1：  0xe577db2cf97fcddc  parent=0                   undat2=4037328  gpuSize=4037328  13 槽  ROOT+载荷
```

也就是说：**作者确实是"先把材质做成自带 4 MB 载荷的根材质"，然后它能在游戏里正常渲染**，
而且就在同一份 bundle 里、和我们改的着色器一起。这说明"mod 自造根材质 + 自带载荷"这条路**本身是通的**，
E1/E2/E4 失败的原因不在"能不能造根材质"，而在**载荷是从别人那儿搬来的**（§4）。

## 4. 载荷到底是什么：不是"可互换的着色器包"（实测）

以本体 `0xef9b3fc2fc1ba61e` 的载荷（2,928,416 B）为例，它的内部结构是：

```
[ 头 + 表  ≈ 251,376 B ]
[ 描述符块(变长) | DXBC 记录 ]  × 202
```

- 每条 DXBC 前面都有一小段描述符，**头 4 字节是一个 pass 哈希**；同一 pass 的 N 个变体共享同一个哈希。
- 202 条记录分属 **88 个不同的 pass 哈希**。
- 比对三份本体根载荷的 pass 哈希集合：

| 载荷 | 字节 | 记录 | 不同 pass 哈希 |
|---|---|---|---|
| `ef9b3fc2`（advanced） | 2,928,416 | 202 | 88 |
| `d84d0463` | 1,983,968 | 260 | 162 |
| `9fc2c6b7` | 3,292,704 | 428 | 251 |

`ef9b3fc2` ∩ `d84d0463` = **1 个**；`ef9b3fc2` ∩ `9fc2c6b7` = **1 个**。

**结论（强推断）：载荷里的 pass 表是绑定到"这一条材质"的 pass 集的。**
把 A 的载荷塞给 B，即使 `+4` 改得自洽、尺寸一模一样，B 要找的那个 pass 在 A 的载荷里根本不存在 ——
画不出来是**必然**，跟 `+4` 是"身份"还是"变体键"没关系。

这解释 E1/E2/E4/E5/E6 的共同结局，而且**不需要**"引擎有黑名单"这种假设。

载荷头 `+4=0xe577db2c`）里一共 272 条记录 / 81 组：

| 组 | 记录尺寸 | 条数 | ISGN | OSGN | SV_Target 数 | 绑定特征 | 改它有没有效果 |
|---|---|---|---|---|---|---|---|
| **A** | **60,504** | ×8 | 252 | 92 | **3** | `__tex_roughness_map`、`__tex_sun_shadow_map`、light probe | **有效**（半透明/渐变/品红都在这条上看到） |

## 7. 逐条回答你们那 5 个问题

**Q1 作者那条材质为什么被接受？**
因为**它自己是根材质**（`parent=0`、`undat2 = 载荷长度`、载荷头 `+4 = id 高 32 位`），
而 MourningVeil 的 92 个材质**没有一个**是这样的。差别不在 TocData 形态（那两份我逐字段比过，同构），
而在"这条材质有没有自己的载荷"。

**Q2 `+4` 是身份还是变体键？**
**不知道**，但这个问题现在不重要了 —— 见 §4：**真正决定能不能画的是载荷里的 pass 表与材质要的 pass 是否对得上**。
`+4` 至少必须等于 id 高 32 位（9/9 吻合 + 我们自己那份 4 MB 载荷也是），把它改对是必要条件、不是充分条件。
**不要再改 `+4`**，也不要把别人的载荷搬过来。

**Q3 `patch_90` / 覆盖本体根材质最终跑起来了吗？**
**没有，而且它从来没以正确的形态跑过**。`patch_73` 那条包的材质层是对的、着色器记录布局是错的（§2）。
所以这个问题的答案不是"失败了"，是"**还没试**"。§6 那份探针就是把它补上。

**Q4 两种 symptom（黑亮兜底 vs 整件不画）对应不同失败路径吗？**
**不知道**，但可以排除一种：两者都不是"着色器被引擎拒绝"。
我这边唯一确认的"整件不画"成因是**记录非法**（NOP 写成 `0x01000038`、或 chunk 布局与原版不一致），
那种情况连兜底材质都不给，直接不画。这和你们 E1 的"消失"症状最像。

**Q5 有没有第五种承载方式？**
有，而且只有一种在文件层被证明能跑：**在本体根材质上就地改它自己那份载荷的 SHEX 字节**
（不新增条目、不改任何 id/parent/undat2/gpuOff/gpuSize）。
我们四份能跑的构建全部是这个形态。§6 就是它的最小实现。
（我上次建议的"改自己那份"方向没错，但我说"你们的载荷来源不是问题"是错的 —— §4 说明来源本身就是问题。）

## 8. 工具（都在本机，可以直接跑）

| 工具 | 用途 |
|---|---|
| `python tools\payload_map.py <载荷>` | 列出载荷里每一组记录（stage / ISGN / OSGN / SHEX / **SV_Target 数** / 条数 / 偏移），并标出多渲染目标候选 |
| `python tools\payload_map.py <patch> --material 0x<id>` | 直接从 patch 里切出某材质的载荷再看结构 |
| `python tools\payload_passes.py <A> <B> ...` | 比对两份载荷的 pass 哈希集合（判断"载荷能不能互换"） |
| `python tools\payload_probe_build.py --payload <载荷> --out <输出> --paint 7:1,0,0,1 ...` | 按组号涂纯色；自动按 donor 的 OSGN 生成 HLSL、等长补 NOP、复签、记录总长不变 |
| `python tools\gate_build.py record --record <rec> --donor <载荷> --donor-size N --ours-asm <asm>` | 四道门（G1 布局 / G2 校验和 / G3 读集 ⊆ ISGN / G4 ret 与 NOP） |
| `python tools\material_graph.py <mod 目录>` | 扫一个 mod 里所有材质：谁自带载荷、谁是子材质、parent 是谁、载荷头是否自洽 |

材质扫描的判据（`material_graph.py` 用的）：

- `parent != 0` → 子材质（**不会**有自己的载荷）
- `parent == 0 && gpuSize > 0 && undat2 == gpuSize` → 根材质，载荷在 `gpuOff` 处、长度 `gpuSize`
- `gpuSize == 0` → 该条目只是个 delta，不带载荷

## 9. 我们还不知道的（别当结论用）

1. **本体根材质覆盖到底能不能画** —— §6 的探针就是为了回答它，目前尚未在游戏里跑过。
2. **子材质能不能自带载荷** —— 这个 mod 里没有先例，我们也没有正例。别在它上面花重启。
3. **`+4` 之外头部字段的语义** —— `+8` 在 advanced 上是 `size-16`、在我们的材质上是 `size-8`，
   `+12` 两份不同（243,444 / 268,008），`+16 = 1`。**都不要改。**
4. **哪些 pass 会被绘制取决于在哪看**：我们那份材质的 3 RT 组是在**看角色时**确认的；
   主界面预览 / 任务内 / 死亡镜头是否用同一组 pass，没验证过。你们做探针时要固定"在哪看"。
5. 供货方那边（HellForge 实验台）的所有结论都基于 build **25480438**，回零售版要复核。
