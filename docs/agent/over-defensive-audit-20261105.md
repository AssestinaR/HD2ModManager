# 过度防御审查（2026-11-05）

> 范围：mod 管理、mod 库里存的文件、自定义素体、section、护甲映射、gamedata 数据库。
> 不含 VPK 转换与材质算法（那部分复杂，另行处理）。
> 行号基于本次审查时的代码；如有偏移以文件为准。

---

## 一、判定标准

一句话：**能随手重建的东西不值得为它设防；设防的代价不许落在用户头上。**

具体四条，按重要性排：

1. **派生数据坏了 = 重建它**，不是拒绝服务。索引、缓存、备份、状态文件、派生注册表、编译产物都属于这类。
2. **只有两类东西值得保护**：用户不可重建的输入（自己配的映射 JSON、原始 mod 包、源贴图/模型），以及"写入目标不可写"这种环境事实。
3. **只要错误信息里出现"请联系开发者 / 请手工删除某文件 / 请重装 / 请重新导入 / 请做修复操作"，就是设计失败** —— 因为普通用户联系不到开发者，这句话对他等于"没救了"。
4. **同一个异常，能"警告 + 继续"就不要"中止"；能"自动重建"就不要"让用户点修复按钮"；能"报出具体哪个文件哪一行"就不要"报一句笼统的完整性错误"。**

由此推出一条好用的技术口径，全仓库通用：

> **保护动作（删除、覆盖、接管）可以 fail-closed；读取、扫描、展示动作必须 fail-open。**
> 现在很多地方把这两件事弄反了。

---

## 二、结论

审出 **20 条**，分三档：

| 档 | 数量 | 特征 |
|---|---|---|
| **A 级：会把人卡死** | 6 | 用户没有自救路径，只能找人；或者数据被静默弄丢 |
| **B 级：白干几分钟到几小时** | 8 | 能自救，但代价是重跑转换 / 重新导入 / 手动找文件 |
| **C 级：噪音与死代码** | 6 | 不阻断，但污染体验、误导用户 |
| 另：**反向问题** | 1 | 不是防太多，是删太多（静默删用户文件） |

已经顺手解决 1 条：管理器启动时"诊断记录读不懂就拒绝启动并要求联系支持人员"的闸门，随护甲诊断工具一起删掉了（提交 `a926f55`）。

三份子审查共同指出的**唯一写得完全正确的样板**：`CustomModelCatalog` 的"读不到 ≠ 没有" + `CustomModelReconciler` 的"首次只标记、下次才解散"。它保护的不是派生数据，而是"信息不全时不做删除决定"——这条应该复制到其余各处。

## 三、A 级：会把人卡死（6 条）

### A1. 护甲映射工作区读不懂 → 整页永久"读取失败"

- **位置**：`HD2ModCore/Infrastructure/RuntimeArmorRegistryService.cs:665-666`（读路径上调 `ValidateMappings`/`ValidateModels`）、`:1071-1099`、`:634`（`UnmappedMemberHandling.Disallow`）、`:655-656`（`compositionMode` 硬校验）
- **现在的行为**：一条映射重复、或指向一个已不存在的素体、或 JSON 里出现一个本版本不认识的字段 → 整份文件读不出来 → 页面上**所有映射消失**，只剩"读取失败"。
- **触发条件**：删过一个自定义素体、两个版本之间来回切、手工看过这个文件。都算日常。
- **用户的代价**：几百条手工映射在界面上"蒸发"。用户没法在界面里修，只能自己找到 `<模组库>\.hd2modmanager\armor-registry.workspace.json` 手改——而页面上的"打开目录"按钮指向的是 C 盘的注册表目录，**指不到这里**。
- **建议**：读路径一律宽容——未知字段忽略、坏行跳过并在页面上点名、结构校验只放在「应用」时做。
- **删掉的风险**：无。文件不删不改，最坏情况是这次少显示一条坏映射。
- **附注**：同一文件 `:667-671` 的注释自己写着"这三个字段没有在役消费者，不再校验"，而 `:655-656` 又在硬校验其中一个。**同一个文件自相矛盾**，按注释的口径统一即可。

### A2. 一个素体没部署，整次应用被否掉

- **位置**：`RuntimeArmorResourceFilter.cs:62-64`，调用点在 `RuntimeArmorRegistryService.cs:498-500`（写协议**之前**）
- **现在的行为**：应用映射时检查每个素体的 unit 是否真的已部署，缺一个就抛异常，整次应用中止。
- **触发条件**：停用某个模型包、切换配置、游戏刚更新。全是日常操作，不是损坏。
- **用户的代价**：点「应用」直接失败，用户不知道该去启用哪个包。
- **建议**：删掉那句 throw。编译阶段本来就按"找不到就跳过"处理，过滤一次就够了。
- **删掉的风险**：无。

### A3. 待删除记录读不懂 → 整个库不能重新扫描

- **位置**：`HD2ModCore/Infrastructure/ModStorageDeletionService.cs:390-409`；调用方 `HD2ModManager/Services/ModLibraryService.cs:475,482`
- **现在的行为**：`pending-deletions.json` 不是合法 JSON、缺字段、版本号变了 → 抛异常 → "校验 Mod 库"失败，提示"已停止自动同步"。
- **触发条件**：这个文件是"删 Mod 时目录被占用、登记为下次清理"的副产品，**恰恰在刚出过问题的场景之后存在**。一次异常关机、一次磁盘写失败、一次跨版本就命中。
- **用户的代价**：新拖进来的 Mod 永远不出现，删掉的永远不消失。自救办法是去库里删一个没人告诉他名字的文件。
- **建议**：读不懂就当空表 + 把坏文件改名留档 + 一条通知："本次未能确认待删除项，个别刚删的 Mod 可能重新出现，再删一次即可。"
- **删掉的风险**：可能出现"幽灵 Mod"（还在回收站里的目录被重扫加回来，新 GUID）。不丢任何用户数据。

### A4. 库快照读不懂 → 整库空白，而唯一的自救按钮会顺手清空配置

- **位置**：`JsonModLibraryStore.cs:147-158`、`ModLibraryManager.cs:24-28`；后果在 `ModLibraryService.cs:546,1448-1452`
- **现在的行为**：`library.json` 版本号不对或 JSON 坏了 → 启动只弹一条 8 秒警告；用户点"校验 Mod 库"→ 程序拿**空快照**重扫 → 保存时把 `profiles.json` 一起写成空表。
- **用户的代价**：库看起来全没了，**配置（加载顺序、每个配置勾了哪些 Mod）被清空，不可逆**。报错里没有文件路径，也没有"从库目录重建"的入口。
- **建议**：坏文件改名留档 → 自动重扫；保存时**如果 `profiles.json` 还能读就原样保留**；错误信息带完整路径。
- **删掉的风险**：⚠️ 只做"自动重扫"而不管 profiles，就会静默清空配置——**这两件事必须一起做**，不能只做一半。

### A5. 事务日志读不懂 → 整库打不开；写不出来 → 这次保存整个作废

- **位置**：`JsonModLibraryStore.cs:119,318-338`（读）、`:234,287-297`（写）、`:82-83`（严格只读路径）
- **现在的行为**：每次保存前先把 `library.json` + `profiles.json` 的**全部字节**抄一份进 journal。journal 一旦留下读不懂的残骸，库永久打不开；盘满时 journal 写不出来，这次保存整个失败。严格只读路径更绝：看到未完成事务就要求"先打开一次管理器来恢复它"。
- **用户的代价**：用户不知道有个 `.hd2modmanager-library-transaction.json` 挡着；报错还是英文的。journal 里存的只是"上次保存前的两份副本"，**它坏了不等于库坏了**，但程序按"库坏了"处理。
- **建议**：journal 读不懂 → 忽略并改名留档，继续读 `library.json`；journal 写不出来 → 跳过 journal 直接写正式文件 + 警告。顺带把 journal 里的全量副本改成"路径 + 大小 + 时间戳"。
- **删掉的风险**：失去"两份文件写到一半"的回滚能力。但每个文件本身仍是 tmp→move 原子替换，最坏是丢最后一次修改，不是丢库。

### A6. CLI 的归属证明把"状态丢了"判成永久 Blocked

- **位置**：`DeploymentOwnershipInspector.cs:97-103,219-237`、`CliManagedDeploymentTransaction.cs:48-52`
- **现在的行为**：状态文件丢了 / 某个 patch 不见了 / 出现一个不认识的 patch → 一律 Blocked，CLI 报"归属未被完整证明，不能开始部署事务"，**既不能部署也不能清理**。
- **触发条件**：Steam 校验、杀软、手工清理、游戏更新、上次部署崩在写状态之前。
- **用户的代价**：CLI 全线瘫痪，错误里没有任何"怎么办"。而且**管理器 GUI 不走这道墙**——同一个产品两套口径。
- **建议**：能接管就接管（文件名带 archive hex + 序号，本就是自己产出的身份），记录有而文件不在就收敛掉记录，只警告。只在"占着要写的目标、且文件名不是标准 patch 名"时才拦。
- **删掉的风险**：理论上可能接管别家 patch；但"接管"不等于立刻删，且标准命名本就只有本管理器产出。

## 四、B 级：白干几分钟到几小时（8 条）

### B1. `sections.json` 缺失或坏了 → 换甲与组件树整块不可用，提示"重新转换 / 重新导入"

- **位置**：`HD2ModCli/CliVpkRekey.cs:145-148`、`HD2ModCore/Infrastructure/WardrobeSectionMapFile.cs:381-396`、`ModDetailsPageViewModel.Vpk.cs:415-418`
- **关键证据**：**同一个文件的第 447 行**就在调 `WardrobeSectionMapFile.BuildAsync(patchPath)`——它自己证明了这份数据可以从 patch 字节重算。
- **用户的代价**：换甲整条失败，要重跑几分钟转换；材质包不在手边时可能根本转不出来。组件树消失时，提示还说"重新导入一次即可"（文件其实在，只是内容对不上）。
- **建议**：读失败就用 `BuildAsync` 重算覆盖写回；把"没有这个文件"和"文件坏了"分开说。
- **风险**：可能丢 `sourceMaterial` 名字；组表本体在 `components.json`，不动它即可。

### B2. 状态文件版本号不认识 → 部署 / 停用 / 导入直接失败

- **位置**：`JsonActivationStateStore.cs:25-28`、`ApplyExecutor.cs:45-51,174-185`；`OptionActivationStore.cs:39-47`、`ModImportExecutionService.cs:48-53`
- **用户的代价**：游戏里的 patch 既部署不了也撤不掉，唯一自救是去游戏目录手工删文件。CLI 所有涉及库的命令失败。而且**同一个文件，GUI 静默当空、CLI 抛错**。
- **建议**：未知版本 = "没有显式状态"，按扫描/默认规则重建 + 警告；两端口径统一。
- **风险**：可能重置手工勾选。但启用状态本来就能由结构 + 默认规则推出，GUI 现在已经在承担这个后果。

### B3. 删一个 Mod，被另一个 Mod 里一条坏掉的关系记录挡住

- **位置**：`SafeModDeletionPlanningService.cs:86-93`；`ModLibraryService.cs:964-970`
- **现在的行为**：任一会留下的 Option 的 `HostModGuids` 有非 GUID / 指向已消失的主体 → 判 Blocking，抛"删除计划被安全检查阻止：Option 'x' has an unsafe HostModGuids entry…"——**英文内部诊断原文直接弹给用户**。
- **触发条件**：历史上删过父级、手改过 `option.json`。用得久的库几乎都有。
- **建议**：降级为警告并继续；清理交给对账（首次标记、下次抹掉）。
- **风险**：只丢一条已失效的关系记录。

### B4. 删"临时头盔合并"的 Mod 被要求先回滚

- **位置**：`SafeModDeletionPlanningService.cs:492-500`
- **用户的代价**：删除报错，提示不说"去详情页关掉那个开关"，用户不知道去哪。
- **建议**：托管 Overwrite 是那个 Mod 自己的派生目录，随 Mod 删掉即正确；至少把文案改成可执行动作。
- **风险**：只丢派生覆盖，源 patch 在 `vpk2patch/` 里可重建。

### B5. `custom-model.json` 写坏 → 几分钟的"一键转素体"在最后一步失败

- **位置**：`CustomModelSectionalCompaction.cs:62-71`、`SectionalModBuilder.cs:110-116`
- **用户的代价**：拆件已经成功，最后剪枝时读文件失败，整条转换作废；而且每次都卡在同一步。
- **建议**：`CustomModelRecovery` 已经能按 unit id 找回 key，坏了就重建；重建不了就跳过剪枝 + 警告。
- **风险**：只丢派生描述，不碰 patch 与用户包。

### B6. 游戏目录在 junction / 网络盘 → 直接判非法

- **位置**：`GameDataTargetGuard.cs:54-55,113-117,182-218`
- **现在的行为**：路径祖先链上任何一级是 reparse point、或路径是 UNC，就拒绝。
- **用户的代价**：Steam 库放 junction 是很常见的合法配置。用户**无法在不搬动游戏的前提下解决**——这是最接近"必须联系开发者"的一条。
- **建议**：不预判，只在写入真的失败时报错（并说清是哪个路径、什么原因）。
- **风险**：无，失败时会自然报错。

### B7. 索引过期 → 推给用户点"重建"

- **位置**：`PageViewModels.cs:160-176`、`ArmorRegistryPageViewModel.cs:488-490,1783-1784`
- **用户的代价**：每次游戏更新后都要用户手动点一次，不点就一直提示。
- **建议**：后台自动重建，失败才提示。
- **风险**：无。

### B8. 设置读不出来 → 静默把库切到默认路径（反向：该报错的没报）

- **位置**：`HD2ModManager/Services/SettingsService.cs:441-444`（`catch { return null; }`）、`:497-507`
- **现在的行为**：`settings.json` 读不出来 = 当成"用户没设置过" = 库路径悄悄变成默认目录，**连一条日志都没有**。
- **用户的代价**：打开管理器"库是空的"，用户第一反应是 Mod 全丢了，第二反应是重新导入（几小时）。而真正的原因是一个设置文件读不出来。之后任何一次保存都会在默认目录里写一份新 `library.json`，两个库从此分叉。
- **建议**：库路径是**唯一不可重建的指针**，读不出设置就应该明确报错（带路径），并给"重试 / 选择库目录"两个按钮；界面上始终显示当前实际使用的库路径。
- **删掉的风险**：设置坏了就打不开库——但这是应该让用户看见的环境事实，修复路径（重选目录）比"库凭空变空"清楚一百倍。

## 六、反向问题：不是防太多，是删太多

### R1. 残留清理按扩展名白名单**静默递归删除用户目录**

- **位置**：`HD2ModCore/Infrastructure/ModLibraryResidualCleanupService.cs:43-48,70-85,89-109`；触发点 `ModLibraryService.cs:499-508`
- **现在的行为**：每次同步（含启动同步）遍历库根下每个顶层目录，只要"没被库引用 + 里面没有 patch + 没有可识别外部文件 + 没有逻辑 marker + 所有文件扩展名都在 `{json,txt,log,md,nfo,url,png,jpg,jpeg,webp,bmp,tmp}` 里"，就 `Directory.Delete(recursive: true)`，**只写日志，不通知用户**。
- **代价**：用户放在库里的"备份说明 + 截图"、作者随包附带的 readme、导入中途失败只剩 `manifest.json` 的半个包——**静默消失，用户不知道是谁删的**。丢的是用户看得见的东西，不是索引。
- **证据**：代码注释自己承认 `.hd2modmanager/`（护甲映射工作区）按这套判据"恰好全部命中"，2026-11-05 真实发生过一次（校验库之后所有自定义素体名称变成 key）。本机没中招纯属里面躺着几份 `.bak-*`。
- **建议**：**把判据反过来**——只删"管理器自己创建过、且带自己标记"的东西（`.hd2modmanager-trash`、带 logical marker 的空壳、带 import 临时标记的目录）。其余一律保留，并在库里显示成"未识别的文件夹"让用户自己决定。这样 A1 里"靠 `.bak-*` 侥幸活下来"的特例也就不需要了。
- **风险**：库根会重新积累空目录（零成本）。而误删用户文件不可逆——**宁留垃圾，不删用户的东西**。索引层已经写对了这条原则（`ModIndexGarbageCollector.cs:78-81`"宁可留垃圾也不误删活数据"），只是没用到这一层。

## 七、必须保留的防御（建议写进规范）

1. **删除时的路径边界检查**（`ModStorageDeletionService.cs:471-500`）：拒绝库根以外的路径、拒绝删回收站本身、拒绝删非目录。唯一会真丢用户 mod 包的地方。
2. **物理删不掉就不移除库记录**（`ModLibraryManager.cs:57-62`）：环境事实，如实报错是对的。注意要和 A3 分开看——**登记是必要的，"读不懂就罢工"不是**。
3. **所有落盘走 tmp → `File.Move(overwrite)`**：成本几乎为零，防的是"半个 JSON"，不是"防御性拒绝"。应继续作为唯一标准。
4. **dl_bin 原件副本只在首次 / 游戏更新 / Steam 校验后重建**（`ArmorRegistryDataMapper.cs:32-35,384-412`）：把被改过的文件当原件会静默写坏游戏文件。
5. **写入目标不可写如实报错**：这是环境事实，用户能自己解决。
6. **指纹 + `.manager.lock` 乐观并发**（`RuntimeArmorRegistryService.cs:474-478`）：防两个进程覆盖用户手配的映射。建议把指纹改挂到工作区，而不是派生协议。
7. **素体对账只在"删除"方向 fail-closed**（`CustomModelCatalog.cs:52`、`CustomModelReconciler.cs:92-95`）：粒度最正确，应作其余几处的样板。
8. **材质塌陷守门**（`VpkRebuildService.cs:229-238`）：新产物材质数变少就不替换。唯一会让人白干几小时的损失。

## 八、建议的批次

| 批次 | 内容 | 风险 |
|---|---|---|
| **第 1 批** | A2、B1、B5、C1、C2、C5 —— 纯删守卫 / 接上已有自愈能力 | 零 |

第 1、2 批加起来能消掉 A 级的一半和全部 C 级，改动都是"删代码"，可以先做。

## 九、需要你拍板的 5 个问题

1. **A1 的宽容读**：坏行是"跳过 + 在页面上列出来"，还是"跳过 + 只写日志"？（我建议前者，否则用户又会觉得数据凭空少了）
