# 多人局换场景闪退：取证与处置（2026-11-11）

> **一句话**：物理 Lua 在**部分会话死亡**（只有多人局才有的情形）之后，仍会继续给
> "看起来还活着"的护甲件写骨；而场景拆解这时仍在进行，写进已释放对象就是原生访问违例。
> 处置：任何会话死亡后先停写一小段，并在每次写骨前复查 unit 存活。

## 1. 用户口径（实测）

- 开着**软映射（护甲）**与**物理**两条 Lua。
- **和队友一起进战场，切换场景时必崩**；**一个人进必定不崩**。
- 崩溃表现为进程直接消失，游戏里没有任何 Lua 报错。

## 2. 取证

### 2.1 两条 Lua 各自留下什么

| | 物理运行时 | 护甲软映射运行时 |
|---|---|---|
| 日志 | `%LOCALAPPDATA%\hd2physbone.log` | `Logs\ArmorOverrideRuntime.log` |
| 崩溃前的活动 | **每帧都在写**（810 链、约 763 次引擎调用/帧） | **32 分钟一次动作都没有** |
| 最后一条 | `[LIFECYCLE] 掉了 9 个会话，剩 3 个继续跑，随后补挂缺的` → `[等待] 发现目标失败` | 停在开局那批 `queued 2005 sets / drained` |

护甲运行时只在**开局**与**协议文件变化**时动作（`POLL_SECONDS = 1`，且内容没变就不动），
崩溃发生在开局 32 分钟之后 —— 可排除。

### 2.2 转储（游戏自己写的）

游戏把转储写在 `%APPDATA%\Arrowhead\Helldivers2\dumps\`。**文件名里的时间是进程启动时间，
`LastWriteTime` 才是崩溃时刻**（这一点容易读反，我第一次就读错了）。

| 崩溃 | 转储（启动时间） | 写入=崩溃时刻 | 异常码 | 故障位置 |
|---|---|---|---|---|
| 20:12:29 | `dump-...20.08.35` | 20:12:38 | `0xc0000005` | `helldivers2.exe + 0x3e564b` |
| 20:45:16 | `dump-...20.12.52` | 20:45:24 | `0xc0000005` | `helldivers2.exe + 0x3e564b` |
| 20:49:02 | `dump-...20.47.23` | 20:49:02 | `0xc0000005` | `helldivers2.exe + 0x664db6` |

前两次**崩点完全相同**（`+0x3e564b`），第三次换了地方。都是访问违例、读野指针。

> ⚠️ **别把"崩在 exe 里"当成"与 Lua 无关"**：这游戏的 Lua 5.1 是**静态链接进
> `helldivers2.exe`** 的（`bin` 下没有 `lua51.dll`），所以 Lua 触发的原生崩溃同样落在 exe 里，
> 而且 `pcall` 抓不到。

分析脚本：`tmp/lua-check/dump-digest.py`（异常码 / 故障模块+偏移 / 字符串取证）。
`dump-stack.py` 对这个游戏的转储不兼容（线程布局对不上），暂时别指望它。

### 2.3 为什么是"部分会话死亡"

同一局里 `掉了 N 个会话，剩 M 个继续跑` 出现了 4 次，只有最后一次崩 —— 所以它不是
"一触发就崩"，而是竞态。但它**只在多人局出现**，这一点是关键：

- **单人局**：自己的护甲件**一起死** ⇒ `#runtime.sessions == 0` ⇒ 走「场景已变」分支，
  `sessions = nil`、退避重扫，**整帧不再写任何骨** ⇒ 天然安全。
- **多人局**：只死一部分（队友那套先被释放）⇒ 保留剩下的继续驱动 ⇒
  **在场景拆解过程中继续写骨** ⇒ 写进已释放对象。

## 3. 处置（运行时 2.1.18）

两处改动，都在 `HD2PhysBoneCompat/src/physbone_runtime.lua`：

1. **死亡后停写窗口**（`pruneSessions`）：任何会话死亡（销毁或重建）后设
   `runtime.driveHoldUntil = frame + deathGraceFrames`（默认 20 帧 ≈ 0.17 s）。
   - 时间照常累积进 `pendingDt`，**物理速度不变**，只是这几帧不写骨。
   - 走的是既有的"这一帧没轮到"同一条路，没有新增分支状态。
2. **写骨前复查存活**（`drive` 的会话循环）：`pruneSessions` 只在**帧首**判过，
   而拆解会在本帧中途继续释放 unit。每次驱动前再调一次 `Compat.unit_alive`，
   死了这一帧就不驱动。一次便宜的引擎调用，换掉"赌野指针"。

### 3.1 为什么不用"死亡比例超过阈值才停"

`掉 3 剩 12` 与 `掉 9 剩 3` 都出现过、也都没崩，比例不是干净判据。而停 20 帧的代价
在观感上几乎不可见（这是换代/换场景的瞬间），所以取"任何死亡都停一小段"这条简单规则。

## 4. 回归（6 项，`runtime-harness-test.lua` 的 T8）

- 正常帧确实在写骨（否则停写断言是空转）
- 窗口内**一个骨都不写**，且窗口内帧确实在推进
- 窗口过后**恢复**写骨（停写 ≠ 永久停手）
- 真让一个会话死掉时，`pruneSessions` 自己会把窗口设上

已用 `git stash` 撤掉护栏验证过：撤掉后该场景 **FAIL**，装回后 PASS。

全量：Lua 回归 **386 通过 / 0 失败**；`dotnet build` 0/0。

## 5. 没做什么 / 未证实的部分

- **没有证实**这两次崩溃一定由物理引起。转储只给到"崩在 exe + 偏移"，
  而 Lua VM 静态链接在 exe 里，符号层面无法指认。当前结论是"证据一致 + 机制成立"，
  不是"已证明"。
- 要继续坐实，仍可做 A/B：**关掉物理、保留软映射，打一局多人**。
  不崩 ⇒ 物理；还崩 ⇒ 回头查护甲覆盖（`set_resource_override` 的覆盖表从不释放，
  目标 unit 被销毁后会留下悬空指向）。
- 这台机器**历史上就有上百个转储**（2025-07 起），今晚一晚 7 个。
  所以不能把我们这两次之外的一律归到 mod 头上。
- `deathGraceFrames` 没有暴露到调参文件，目前只能改源码默认值。
