## 0. 三句话

1. **你们不需要承载别人的载荷。** MourningVeil 的 92 个材质全是子材质（`parent≠0`、`undat2=0`、`gpuSize=0`），
   这个 mod 里**一条自带载荷的材质都没有**。能改的地方只有两个父材质的**根载荷**。
2. **宝石消失的直接原因是 E5/E6 给子材质设了 `undat2`/`gpuSize`。** 这份文件里没有任何"子材质带载荷"的形态，
   你们等于让一条子材质同时当根材质。**先把这一步回退。**
3. **`patch_73`（覆盖本体根材质）从来没以正确形态跑过** —— 它的着色器记录布局是错的（见 §2）。
   所以"覆盖根材质"这条路不是被否定，是**还没试**。我给你做好了一份探针（§3）。

## 1. 你们那 6 次实验，问题出在哪

| 实验 | 你们做的 | 为什么不行 |
|---|---|---|
| E1/E2/E3/E4 | 新建材质条目，把 advanced 的载荷挂上去 | 载荷是**绑材质**的编译产物，不是可互换的 shader 包（见 §1.1） |
| E5/E6 | 就地给子材质设 `undat2`/`gpuSize` | 子材质带载荷在这份文件里没有先例；而且你们还改了 `+4` |
| patch_73 | 覆盖本体根材质 | 形态对，但**着色器记录布局错了**（§2） |

### 1.1 载荷为什么不能互换（实测）

本体 `0xef9b3fc2` 的载荷 = 头(≈251 KB，含 pass 表) + [pass 描述符 + DXBC]×202。
每条描述符头 4 字节是一个 **pass 哈希**，202 条记录分属 **88 个不同 pass**。

| 载荷 | 字节 | 记录 | 不同 pass 哈希 |
|---|---|---|---|
| `ef9b3fc2`（advanced） | 2,928,416 | 202 | 88 |
| `d84d0463` | 1,983,968 | 260 | 162 |
| `9fc2c6b7` | 3,292,704 | 428 | 251 |

`ef9b3fc2 ∩ d84d0463 = 1 个`，`ef9b3fc2 ∩ 9fc2c6b7 = 1 个`。
把 A 的载荷塞给 B，B 要找的那个 pass 在 A 的载荷里根本不存在 —— **画不出来是必然**，
跟 `+4` 是"身份"还是"变体键"无关。

## 2. `patch_73` 为什么"护甲消失"（字节级证据）

包结构是对的：条目 1 个、`0xef9b3fc2fc1ba61e`、`tocSize 2288`、`gpuSize 2,928,416`、
`undat2 = 2,928,416`、`parent = 0`、载荷头 `+4 = 0xef9b3fc2`。**材质层没问题。**

错的是里面那条着色器记录：

| chunk | 本体同槽（60,412 B） | patch_73 里的 |
|---|---|---|
| RDEF | 9,900 | **12,172** ✗ |
| ISGN | 248 | 248 ✓ |
| OSGN | 44 | 44 ✓ |
| SHEX | 49,980 | **39,672** ✗ |
| 第五块 | **STAT 148** | **PRIV 8,184** ✗ |

而我们这边**四份能跑的构建**，五个 chunk 的名字、顺序、长度全部与 donor 逐项相同，
只有 SHEX 里的字节变了。`tools/gate_build.py` 一跑就是 `G1 ✗ 块布局与原版不一致`。

**所以"护甲消失"不能用来否定"覆盖本体根材质"。那次实验从头就没成立。**

**一次进游戏同时回答两件事**：

| 看到 | 含义 |
|---|---|
| 变绿 | 载荷被读，可见 pass 是 5 RT 那条 → 以后就改这条 |
| 变蓝 | 载荷被读，可见 pass 是 4 RT 那条 |

在我们那套网格上**整组涂成亮青毫无变化** —— 大概率对网格不画（可能是 UI 预览用）。
所以绿/蓝的可能性更大。

## 4. 关键问题：怎么只影响那颗宝石，而不改全身

这是覆盖根材质最大的坑（你们见过"护甲消失"，本质是整个 advanced 族都被改了）。

**答案：光照 pass 里没有材质变量 cbuffer，但有一张"每材质独立"的贴图。**

这条 pass 的 RDEF 绑定是：

```
t2  = __tex_roughness_map      ← 来自材质槽 RoughnessMap(0xc567338d)，**每个子材质各不相同**
t8  = __tex_sun_shadow_map     ← 全局
t16 = __tex_light_probe_space_specular
```

所以：**在 `t2` 这张图里埋一个标记色，着色器按标记决定走自定义还是回退。**

```
float4 s = t2.Sample(s0, uv);
bool mine = (s.r > 0.95 && s.g < 0.05 && s.b > 0.95);   // 洋红标记 = 这是我们的材质
if (!mine) { ...走一个尽量接近原版的兜底... }
else       { ...我们的镂空 + 金属 + 半透明... }
```

宝石的材质把 `RoughnessMap` 槽换成我们画的图（左上角一小块洋红当标记），
其他护甲的图里没有洋红 → 不受影响。

> 这条我在 Milfy 上验证过同类做法（贴图驱动整条外观、换图即换效果），
> 但"用标记色做分支开关"本身没有实机验证过。风险点：BC7 压缩会让标记色轻微失真，
> 所以阈值要给宽一点（比如 `s.r > 0.85 && s.b > 0.85 && s.g < 0.15`）。

## 5. 写自己的着色器：这条 pass 上有什么可用

### 5.1 输入（反汇编确认，**注意这是 `60,504` 那条的布局，你们的 `35,576` 要自己重查**）

| 寄存器 | 内容 | 证据 |
|---|---|---|
| `v2.xyz` | 法线 | 原版 `dp3 v2,v2 → rsq → mul` 标准归一化 |
| `v3.xyz` | 世界坐标 | 原版 `add -v3.xyzx, cb0[2].xyzx` |
| `v7.xy` | 材质 UV | `t2.Sample(s0, v7.xy)` |
| `v0` | SV_Position | — |

### 5.2 常量（HellForge SDK 明说"就是游戏的寄存器"）

```
cbuffer global_viewport : register(b0) { float4 hf_viewport[51]; }
  [2].xyz     相机世界坐标     ← 与反汇编互为交叉验证
  [11..13].y  相机前向轴
  [43].w      游戏时间（秒）
  [44].x      帧 delta time
cb2[0].xyz    太阳方向（原版用 -cb2[0].xyz 作光线步进）
cb3[0].xyz    太阳颜色
```

### 5.3 三条必须遵守的判据（都是我们踩出来的）

1. **五个 chunk 的名字/顺序/长度与 donor 逐项相同**，只改 SHEX 里的字节。
2. **`ret` 之后补真 NOP `0x0100003A`**。写成 `0x01000038` 是另一条指令 → 非法着色器 → 整条 pass 被丢。
3. **读的输入分量 ⊆ 记录 ISGN 的掩码**。越界（我们那次读 `v7.z`，ISGN 只给 `v7.xy`）
   会让 **dxilconv 空指针崩溃**（`mov eax,[rcx+54h]`，`RCX=0`）。

### 5.4 ⚠️ 曝光是个坑

写在 `o0` 里的是**线性**颜色，屏幕上是 `pow(linear, 1/2.2)`：
`0.25 线性 → 0.53`（中亮灰，看起来"乳白"）。我们连着两版以为是高光太强，最后发现是曝光。
**内部乘一个 `EXPOSURE`（成品用的是 0.20），把线性压到 ~0.02 才真的发黑。**

## 7. 你们必须自己验证的（我没有你们那套材质）

1. **`35,576` 那条 pass 的 ISGN 布局**是不是和 `60,504` 一样（`v2` 法线 / `v3` 世界坐标 / `v7` UV）。
   `gate_build.py` 的 G3 会拦住越界读，但**语义对不对只能自己反汇编查**：
   看有没有 `dp3 vX,vX → rsq → mul` 这种归一化、`add -vX.xyzx, cb0[2].xyzx` 这种视线向量。
2. **探针包能不能让整身变色**（§3）。这是整条路的总闸。
3. **标记色开关**（§4）在 BC7 压缩后还准不准。
4. 你们那份 `9ba626afa44a3aa3.patch_2` 有 218 MB、92 个材质，
   **先确认宝石用的是哪个材质 id、parent 是 `ef9b3fc2` 还是 `d84d0463`** ——
   两个父材质的载荷不同（2,928,416 / 1,983,968 B），改错了父材质，宝石不会有任何变化。
