## 0. 一句话

你们缺的不是"另一种承载方式"，而是**别去承载别人的载荷**：
唯一被两个会话都证明可行的形态是「**在一条本来就自带载荷、且被 unit 引用的材质上，改它自己那份载荷里的记录内容**」。
不改 id、不改 `+4`、不换 TocData、不换载荷来源。

## 1. 逐条回答

### Q1 作者那条材质为什么被接受？

**因为载荷就是它自己的**，与"形态参数"无关。两个根材质的 TocData 头部我逐字段比过，**完全同构**：

| | 作者 `0xe577db2c` | 本体 `advanced` `0xef9b3fc2` |
|---|---|---|
| `u32@0` | 288 | 288 |
| `u32@4` | 1 | 1 |
| `u32@8` | 24 | 24 |
| `EndOffset@12` | 2404（= size−28） | 2256（= size−28） |
| `undat2@16` | 4,037,328（= 载荷长度） | 2,928,416 |
| `parent@24` | 0 | 0 |

所以"形态"不是差别。差别在：**作者 patch 里，这条 Material 与它那份 payload 是成对出现的**。

而你们的 E2/E3 其实**已经证明了同一件事**：`+4` 保持 `ef9b3fc2` 时材质**能画**，但显示的是本体外观 ——
说明引擎用了"与 `+4` 对应的那一套"，把你们注入的载荷内容**忽略了**。

另外：你们的 `vpk2patch.json` 里这些材质的 `template` 全是 `advanced`，也就是**管理器本来就是拿 advanced 的载荷生成的**。
所以"我的载荷来自 advanced"完全正常，不是问题所在。

### Q2 `+4` 是身份还是变体键？

证据倾向 **身份/归属键**，不是可以自由改的标签：

- E1：`+4` 与材质 id 不一致 → **消失**（你们的硬检查有效）
- E2/E3：`+4 = ef9b3fc2` → 能画，但画面是**本体**的 ⇒ 引擎按它找到了"那一套"，忽略你注入的字节
- E4/E5/E6：改成与 id 自洽的新值 → **不画** ⇒ 该 id 没有对应的"一套"

**结论：别改 `+4`。** 改它只能让头部自洽，不能把 advanced 的载荷变成宝石材质的载荷。

### Q3 `patch_90` 最终跑起来了吗？

**没有。** 我这边记录里覆盖本体根材质那次最终观测是"护甲消失"，之后没有成功。
成功的是改**作者自己的材质**（`0xe577db2cf97fcddc`）。所以别把那次当成功样例。

### Q4 两种 symptom（黑亮兜底 vs 整件不画）对应不同失败路径吗？

**很可能**，但别当结论：

- "整件不画"更像**材质→载荷解析失败**（引擎没拿到该材质的载荷）；
- "黑亮半透兜底"更像**记录没命中→回退到别的 pass**。

两者的共同点是都不是"shader 被拒"。

### Q5 有第五种承载方式吗？

有，就是开头那句：**就地改自己那份载荷**。具体到你们——
`0xab344c46` 的载荷在 `patch_2` 里（我们已定位 `gpuOff=218,112,192`、`gpuSize=2,928,416`，头部 `+4=0xab344c46` ✅），
那就**在这份载荷里改记录**，别把 advanced 的载荷换进来。

## 2. 三个必过判据（都是我们踩出来的）

1. **目标记录组必须是游戏内可见的 pass。**
   我在 Milfy 上把 `62,652 × 10` 那组换了三轮都"无变化"，最后才知道它游戏内不可见。
   你们的做法：先在目标载荷里**只改一个立即数**（不是换 SHEX），确认画面变了 —— 不变就是打错组了。
2. **`ret` 之后的填充必须是真 NOP `0x0100003A`。**
   写成 `0x01000038` 是另一条指令 → 非法着色器 → 整条 pass 被丢。这是我"整段替换无效"的真因。
3. **着色器读取的输入分量必须 ⊆ 记录 ISGN 提供的掩码。**
   越界读（我那次是 `v7.z`，ISGN 只给 `v7.xy`）会让 **dxilconv 空指针崩溃**（`mov eax,[rcx+54h]`，`RCX=0`）。
   我们的门禁脚本：`python tools\gate_build.py record --record <记录> --donor <载荷> --donor-size <N> --ours-asm <asm>`
   —— 它会直接报 `v# 读[…] 提供[…] 缺[…]`。

外加一条诊断经验：**崩溃后先抓转储再猜**。我们靠一个 minidump 的调用链
（`game → D3D12 → dxilconv+0x44414`）才把"引擎容错差"这个错误归因纠正过来。

## 3. 更快的路：HellForge

如果你们那台机器能跑 HellForge（离线副本，pinned build **25480438**），有一条**绕过整个"自带载荷"**的路：

- dev/0.5.0 的 data spec 支持 **`edit`** 资源类型，可直接改某个 `shader_library` 里 **stage 的字节**，
  并由 **HellForge 自动重签名**、保留 stage id：

  ```json
  { "type": "shader_library", "edit": "0x<library id>", "gpu": { "size": 52848 },
    "stages": [{ "at": "0x106C", "digest": "<容器 4..19 的 16 字节 hex>",
                 "set": { "0x1A4": "<你要写入的字节>" } }] }
  ```

  其中 `digest` 就是容器 bytes 4..19（微软定制 MD5），`set` 的偏移是容器内 chunk 表之后。
- 也就是说：**把"镂空 + 金属 + 半透明"做进一个 shader**这件事，可以不去碰材质/载荷/记录尺寸这一整套，
  而是直接改游戏 shader 的 stage 字节 + 让 HellForge 重签。

注意：HellForge 是**离线副本**，结论要回到零售版复核；`edit` 的 `digest` 按构建绑定，换构建会被拒。
