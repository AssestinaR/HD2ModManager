## 一、#21 与「一个文件夹 = 一个 Mod 条目」契约的关系

### 1.1 契约在代码里到底是怎么写的

| 位置 | 事实 |
|---|---|
| `ModLibrarySynchronizer.InspectAsync`（`EnumerateDirectories(root, "*", TopDirectoryOnly)`） | 库根**只读一层**，一层里的每个目录最多算一个节点 |
| `ModNodePayloadLayout.EnumeratePayloadFiles` 注释「只读每个目录的顶层——载荷目录里不再有嵌套」 | 节点目录里也只读顶层 + `sectional/` + `Overwrite/` |
| `ModLibraryImporter.PersistFlattenedTree`（`CreateUniqueDirectoryName` → `RelativePath = flatDirName`） | **任何**节点（含 Option）落库时都拿一个**平铺**目录名，文件只从源目录顶层拷（`CopyTopLevelFiles`）+ `sectional/` + 外部安装文件 |
| `ModFolderTreeExporter`（注释：「选项就是同名文件夹…把库里的嵌套结构一对一摊开」） | 嵌套**只是交换格式**：库里平的，导出时才翻译成 `包名/选项/` |

也就是说：**「一个文件夹 = 一个节点」是库的存储不变量；嵌套只存在于「进出库」的边界上**。
`ModFolderTreeExporter` 早就在往这个边界外写嵌套包，#21 是这条边界的**进口**。

### 1.2 结论

**#21 不破坏这个契约。** 三条硬证据：

1. **它没有碰判定层。** `ModLibrarySynchronizer`、`ModNodePayloadLayout` 在 #21 里零改动
   （`git diff master...pr21` 只有 14 个文件，不含这两个）。重扫仍然只认一层；
   「本层没有 patch」的目录仍然不会变成节点。
2. **它走的就是普通导入链路**，落库由 `PersistFlattenedTree` 完成 ⇒ 认领出来的 207 个节点
   是 207 个**平铺**目录，不是 `包名/本体/`。作者自己的选择也在注释里写明了理由：
   > 「原地登记要让每个选项子目录变成 `包名/选项` 这种两层相对路径，而库里从对账、导出、
   > 残留清理到部署都按「一层目录」写；改这一层假设的代价远大于复制一次」
   —— `ExternalPackageAdoptionService` 类注释。这个判断和契约是一致的。
3. **认领完源目录会被移走**，所以库根不会同时留下「嵌套包 + 平铺节点」两份。

换句话说：把外部包**认领进库**和「库允许嵌套」是两件相反的事——认领是把嵌套**吃掉**。
如果哪天真要「原地登记」，那才是破契约，而 #21 明确拒绝了那条路。

### 1.3 契约没被破坏，但善后有问题（要改再合）

按严重程度排。前三条是「磁盘上会留下嵌套目录」，正好踩在你担心的那条线上。

**P1 — 认领在**启动**时就跑，没有确认，也不可预览。**
`ModLibraryService.SynchronizeAsync` 里认领排在同步之前（`ModLibraryService.cs:514`），
而 `SynchronizeAsync` 的调用方包括 `ShellViewModel.RunStartupChecksAsync`
（**开管理器就同步**）、库页刷新、`CloneVariant`、以及「校验 Mod 库」按钮。
后果：用户只是打开管理器，15 个外部包就被导入、166 个选项被**默认全开**
（`OptionActivationDefaultInitializer`：Standard 父节点下直属选项全开）、源目录被搬进回收站。
CLI 那条路有 dry-run + `--confirm`，GUI 这条路一点防护都没有。
👉 建议：GUI 侧改成显式动作（发现候选后弹一句「发现 N 个外部包，是否认领」），
至少不要在启动路径上做写盘 + 搬运。

**P2 — 「导入成功但移动失败」会永久留下一份嵌套源目录，而且提示是错的。**
`AdoptOneAsync` 里移动失败时状态记 `Failed`、detail 写「下一轮只重试移动」
（`ExternalPackageAdoptionService.cs:192`）——但**下一轮不会重试**：标记已是 `imported`
且节点还在库里，会先命中还原保护分支（`:130-133`）→ `Skipped`「该包已在库中」。
于是库根上永久留着一个带嵌套的外部包 + 一份平铺副本，每轮同步都报一次。
更糟的是它给的逃生口（「删掉标记再校验」）会让整包**重新导入一遍**，变成重复节点（`_3`）。
顺带：设计文档 `docs/agent/external-package-adoption-20261109.md` 写的是
「`imported` + 有 nodeIds → **只补移动**」，代码里没有这条分支——文档与实现不一致。
👉 建议：区分 `imported` 的两种含义（`imported-pending-move` / `imported-moved`），
真的实现「只补移动」；并修 detail 文案。

**P3 — 回收站只进不出，`.hd2modmanager-trash` 会长期背着整棵嵌套树。**
全仓没有任何地方清理回收站内容：`ModStorageDeletionService` 是「移进去 → 立刻删掉」
（`:48-58`），`ModLibraryResidualCleanupService` 明确把 `.hd2modmanager-trash` 排除（`:43`）。
认领复用了这个目录当**长期**存放点 ⇒ 每个被认领的包都有一份完整目录树躺在库根下的隐藏目录里。
现在因为硬链接不额外占空间，但**链路是这样坏的**：用户以后删掉那个认领节点，
删的只是平铺那份，回收站那份仍持有数据（链接数 2→1）→ **删 Mod 不释放空间，而且永远没人收**。
👉 建议：认领成功后直接删掉回收站里那份（反正硬链接，删掉不损失任何字节），
或者给它一个可清理的入口/保留期。

**P4 — 「本层有 patch、子树也有 patch」的包不认领，子树内容静默消失。**
判据是「本层没有 base patch」（`ExternalPackageAdoptionPlanner.cs:99`），于是
`包名/9ba…patch_0` + `包名/选项/9ba…patch_0` 这种形状会被当成正常 Mod 收下，
子目录里的选项**既不进库也不报错**（重扫不递归）。
而这恰好是**我们自己 `ModFolderTreeExporter` 的输出形状**：把导出包解压丢进 `mods\`
就是这个结果。同类形状还有「patch 只在 `包名/sectional/`」——`ScanSubtree` 会跳过保留目录名
（`:249`），基数算 0，直接看不见。
👉 建议：判据从「本层没有」放宽到「子树里有、且（本层没有 或 本层有 manifest 声明了选项）」，
或者至少对「本层有 patch + 子树有 base patch」发一条 warning。

**P5 — 多单元导入中途取消/失败会重复导入。**
`ImportUnitsAsync` 是**逐单元提交**的；`AdoptOneAsync` 在 `OperationCanceledException` 和
通用 catch 里都直接 `TryDeleteMarker`。若第 1 个单元已提交、第 2 个单元失败，标记被删、
源目录还在 ⇒ 下一轮从「无标记」重新导入整包，库里出现两份。
这个坑导入压缩包时本来就有，但认领把它放大成「每轮同步都会踩」。

**P6（小）** — 单轮上限 25 个，超出的每轮都记一条 `Skipped`，GUI 因此每轮弹
「有 N 个外部包未能认领」；建议把「排队中」与「被拒」在文案上分开。

### 1.4 附带修复（我认同）

`manifest` 没声明的 payload 目录不再静默丢弃、收成 root 的直属选项
（`ModLibraryImporter.PlanManifestImport` 的 `unownedPayloadNodes` 分支）——
这是真 bug（实测 `milltina 修女` 的「腰裙」从没进过库），修法也选对了：
不拆成独立 Standard 节点，保持「一个包 = 一个 Mod + 它的部件」。
它自带 1 个用例，覆盖了 root 条目被误判成「未声明」的那个回归点。

## 二、#19 裸名 `$bumpmap` 当占位

**判断：可合并。** 判据改对了——从「按 basename 在整包里找」改成「按 VMT 声明的路径精确找」，
裸名单段不兜底。`VmtDocument.NormalizePath` 会去掉 `materials/` 前缀并转小写，
与新增的 `vtfPaths` 索引键（`NormalizePath(entry.Path)`）口径一致，不会因为前缀不同而永远 miss。

三处要注意（都不阻塞）：

1. **枚举加了成员，但有一个 `switch` 没有 `default`。**
   `NormalDelivery.PlaceholderPath = 3` 新增；`VpkPatchAssembler.cs:1207` 那个
   `switch` 只处理 `Wired` / `TextureMissing`，于是占位项既不进「已接入」也不进「缺失」的计数。
   不会崩，但「N/M 个材质声明了法线图」的 M 与分子对不上，读起来像账算错了。
   建议给 `PlaceholderPath` 单独一行（例如「N 个是模板占位，未接法线」）。
2. **他自己给的数字里有 1 例回归**：198 条 `$bumpmap` 里只有 4 条靠裸名兜底命中，
   其中 3 条是占位、**剩下 1 条是真解析**。这 1 条材质从此失去法线图（退回平面）。
   可接受，但值得在 PR 里写一句。
3. **精度只加在「判不判」这一层，读字节仍然是按 basename。**
   `BumpTexture` 最终交给 `TryBuildNormalTexture` → 裸名索引读盘，索引是 `TryAdd` 先到先得。
   所以「带目录且 basename 与另一张图撞名」时，仍可能接错图（本次的 manuku 是因为占位被丢弃才没事）。
   要彻底解决，得让下游按解析出的路径读（加一个 `TryReadVtfByPath`）。

## 三、#20 灰度贴图半成品

**判断：可合并，改法正确。** 失败时 rgba / width / height 三者一起归零是关键——
调用方只按「宽高 > 0」判「读到了」，这正是原来的崩法（空数组 + 非零宽高 → `IndexOutOfRangeException`）。
新增的 `case 5` = I8（VTEX 格式号 5 就是 I8），`Require(source, pixels, …)` 与其它分支一致，
A 补 255 而不是复制亮度，注释解释了为什么（避免被当透明度）。

唯一的建议：这是**纯增量的失败路径**，最好补一个 I8 的最小用例（48×1 的 I8 vtf + 断言 RGBA 全等
灰度），以及一个「解码返回短缓冲 ⇒ 三个输出都归零」的用例。现在这批 PR 一个测试都没带。

## 四、#22 MDL 版本高位

**判断：可合并，防护做得比要求更稳。** 只在**本来就会被拒**的分支里取低 16 位再判一次，
高字节为 0 的模型行为完全不变；放行之后还额外校验骨架父级下标是否在骨表内
（`ParentIndex < -1 || >= bones.Count` → 按不支持处理），这正好挡住「用错步长解出一具错位骨架」
这个最坏的失败模式。异常文案也换成了原始 `rawVersion`，排障时不会被掩码后的值误导。

同样建议补一个用例（`0x1A000032` 放行 / `0x1AFFFFFF` 拒绝 / 高字节 0 行为不变），
`HD2SourceModel.Tests` 里加三个断言就够。
