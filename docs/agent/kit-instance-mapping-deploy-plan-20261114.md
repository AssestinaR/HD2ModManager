# P6 规划：专属多目标改用软映射部署

日期：2026-11-14。上接 P5（`kit-instance-multi-target-plan-20261114.md`，界面与存储）。§6 的决定**待用户拍板**。

## 1. 为什么

用户转述 Mod 作者的话：用常规 patch 的方式替换全部护甲，显存和内存会暴涨；用映射的方式会好很多。

现在的专属切换（P4a/P4b）是打补丁：把模型数据用承载件的 ID 写进 `Overwrite/`。选一套目标就有一份；合并模式下每份是一整个模型 unit，选 N 套就是 N 份。P5 的多选会把这个问题放大。

用户已决定：多目标部署改用映射。P5 先把界面做完（勾两个以上目标时暂不能确认），部署由本阶段接上。

## 2. 现状（代码事实）

- **软映射链路**（护甲映射页在用）：
  - 意图写在 `armor-registry.protocol` 和 workspace；
  - `WardrobeLinkCompiler.Compile` 把意图编译成 `<ArmorRegistry>/wardrobe.links`，内容是一组 unit 对：目标 unit → 源 unit；
  - 运行时 `HD2RuntimeArmorOverride/src/armor_override_runtime.lua` 每秒读一次这个文件，对新增的映射调用 `Application.set_resource_override('unit', 源, 目标)`，每帧最多 32 条。
  - `set_resource_override` 和 `clear_resource_override` 都在 API 白名单里（`hd2pbx_api.txt:330/369`）。
- **映射只增不减。** 删除映射不会释放，要重启游戏才恢复。一次性释放大量映射会让游戏当场崩溃（`soft-mapping-armory-crash-recon-20261112.md` §1）。
- **源 unit 必须真的在游戏数据里。** 指向不存在的 unit，引擎会记住这次加载失败，之后军械库整页空白并崩溃。这就是 `WardrobeLinkCompiler.HiddenUnit` 存在的原因。
- **sectional Mod 的部署**（`ModDeployableFiles.cs:20/59`）：部署基底（`sectional/`，Mod 自己的 unit ID），`Overwrite/` 里同名的文件会顶替基底。所以切换过目标的 Mod，Mod 自己 ID 的 unit 不会进游戏。
- 按实例隐藏（Hider）和映射是两条独立的运行时链路，互不影响。

## 3. 方案

### 3.1 部署内容

- **模型只部署一份，用 Mod 自己的 ID：**
  - P4a 逐格目标：直接用基底里的各部位 unit（`079d…0001`…`0007` 这一类）。
  - P4b 合并目标：合并后的 unit 用一个新 ID 部署。同一组来源、同样的头部处理，合并结果只做一份，多个目标共用。新 ID 的生成规则要稳定、可复现，由实现方定，写进文档。
  - 头落在头盔上时，头部 unit 也只部署一份。
- **映射**：每个目标的每个承载件写一条「承载件 → 模型 unit」。同一个承载件被多个目标选中时（同名组）只写一条。
- **隐藏**：照旧，每个目标一条 Hider 规则（P5 的多目标 workspace）。
- **专属模式下不再写 `Overwrite/`**（见 §6 H2）。普通模式完全不变。

### 3.2 映射写到哪里

- 和护甲映射页共用 `wardrobe.links` 和同一个运行时，不另起一套 Lua。
- 编译时把专属的映射和映射页的映射合在一起，文件的协议和 schema 不变。
- 同一个承载件被两边都映射时，按 §6 H3 处理。

### 3.3 撤销与改动

- 去掉一个目标、关掉专属或删除 Mod：映射从 `wardrobe.links` 删掉，Hider 规则也删掉。但已经生效的映射要**重启游戏**才释放，界面要明说「重启游戏后恢复原版」。
- 重启之前，被删掉目标的隐藏规则已经撤掉，原版部件会露出来，而承载件还显示模型。这段时间外观可能不对，所以同一条提示也要写清楚这一点。

## 4. 风险

1. 源 unit 没部署成功却已经写了映射，会导致军械库崩溃。所以部署顺序必须是：先确认模型 unit 已进游戏数据，再写映射；任一步失败，整份回滚（沿用 G4 的失败弹窗）。
2. 映射是全局的。承载件按定义只属于目标组，不会波及别的护甲，但这依赖 P4a/P4b 规划的正确性。
3. 运行时映射在角色加载之前就要生效。现在映射页每秒轮询，进游戏以后才加的映射，对已经加载出来的角色可能要换一次装才生效。实机时要专门看这一点。
4. 合并后 unit 的新 ID 不能和游戏或其它 Mod 撞。

## 5. 不做

- 不改普通切换。
- 不改 Hider 协议。
- 不尝试释放映射（`clear_resource_override`）。

## 7. 定稿方案（2026-11-14，按作者方案重写；§3 只适用于详情页多选，以本节为准）

### 7.1 总览

设置页加一个全局开关「低污染模式」（J1 已定）。打开后：

1. **sectional 编译层**：每个模型 Mod（素体）编译成压缩版，只有 3 个或 2 个 unit，都用新 ID（规则稳定、可复现）：
   - 头身合并关：头、躯干（含胯、左右腿）、手臂（含左右臂），共 3 槽；
   - 头身合并开：头＋躯干（含胯、腿）、手臂，共 2 槽，头和躯干的几何合成一个 unit。
   - **物理容器跟着合并**：被合并 unit 的物理骨架和参数并进同一个 unit 的容器里。
   - `custom-model.json` 只写压缩后的件。
2. **软映射编译层**（护甲映射页「应用」）：把目标护甲映射到素体时，**只映射非污染部件**：
   - 躯干槽：固定落在目标独有的躯干部件上；
   - 头：固定落在目标头盔独有的部件上（2 槽模式没有这一项）；
   - 手臂槽：落在目标任何一个剩余的独有部件上。
   - 「独有」沿用 P4b 的口径：同名组和同 set 头盔算一组。
   - 目标其余的原版部件**不再映射**，改由 Hider 按实例隐藏。每个被映射的目标生成一条规则，签名取躯干承载件。
   - 2 槽模式下，原版头盔也进隐藏集。
3. **自动工作流**：开关打开或关闭后，依次自动执行：
   1. 一键重构建所有 sectional 系 Mod；
   2. 重新应用软映射；
   3. 重新部署。
   有进度、能取消；失败时沿用 G4 的弹窗。
4. **详情页**：压缩模式下，「目标护甲」只保留「自己的素体」，并显示一行「护甲替换请到护甲映射页」和跳转按钮。P5 做的搜索和多选组件搬到映射页复用（§8 J4）。
5. **压缩模式关闭时**：一切照旧（现有映射页、P4a/P4b 补丁专属、P5 单选）。

### 7.2 为什么能解决「100 多套」

- 素体数据只有一份：3 或 2 个 unit。映射 100 套只是 100 组映射行，加 100 条 Hider 规则。
- 只映射独有部件，所以不会连带别的护甲。

### 7.3 必须先解决的硬约束

1. **Hider 上限**：现在最多 64 条规则、文件 64 KiB。映射 100 多套就要 100 多条规则，必须提高上限。这要改 Lua 和规则协议，见 §8 J2。实现前先在 lupa 里压测：200 条规则时每帧的开销。
2. **承载件不够的护甲**：没有独有躯干的目标（约 30 套，大多是换色孪生护甲），压缩模式下怎么办，见 §8 J3。
3. **先部署、后映射**：素体的压缩 unit 没进游戏数据之前，不写映射行，否则军械库会崩溃。
4. **物理容器合并**：见 §6.2 作者补充。P4b 的缺口一起补。
5. **映射不释放**：改了映射要重启游戏才恢复，界面提示（H1）。

### 8.3 J6：专属入口并入护甲映射页（用户决定，2026-11-14）

用户提出把详情页的专属逻辑整体搬到护甲映射页。定下来的做法是「S4 搬，S3 后删」：

- **S4 搬**：详情页的专属（专属开关、预览、转专属/撤销专属、多选）去掉，防污染只在护甲映射页做。用户已转专属的 Mod 要迁移（workspace 记录转成映射页的映射，或提示重设），在 S4 设计。
- **S3 后删**：S3 实机验证映射路线（先部署后映射、映射不释放、Hider 上限）之前，专属写 Overwrite patch 的那条输出保留当退路；验证通过后在 S4 删除。
- **保留复用**：独有承载件规划器（P4）、合并器与物理自检（P4b、S1）、Hider（P1）都不动，S2/S3 本来就要用。

用户补充（同日，看过映射页截图后）：

- **映射页不要下拉**：映射页右侧本来就有带搜索的护甲列表，P5 的下拉不搬过去。
- **详情页下拉只留搜索、改单选**：详情页回到普通 patch 替换，「这边污染的还是污染」；想不污染去映射页。改单选后，P5 多选里同一套护甲能被加两次的问题（截图里两个 DP-8 2846302183）自然消失。
- **映射覆盖详情页规则（用户选 A：部署时跳过）**：部署时，如果某个 Mod 的 patch 目标护甲已经是映射页的映射目标，这套护甲就不部署那个 Mod 的 patch，详情页标「已被护甲映射覆盖」。理由：低污染模式只映射独有部件，若 patch 照部署，共用部件上会残留 patch 模型又被 Hider 藏掉，白占一份数据，还会混搭。

### 8.4 映射页的单件与组合（用户同意写入，2026-11-14）

现状：映射页右侧「可用护甲」默认「类型：自动组合」，把同名 / 同 set 的 1 件护甲 + 1 个头盔配成一条（`ArmorRegistryPageViewModel.BuildDisplayChoices`），点这行文字可循环到「仅护甲」「仅头盔」。也就是说单件已经能映射，只是入口藏得深；作者设计时默认用组合，没考虑低污染模式。

改法：

1. **（S4）筛选改成看得见的三档**：组合 / 护甲 / 头盔，替换循环文字按钮；默认仍是组合。
2. **（S4）组合名去重**：同名时显示一次名字加「头盔+护甲」标签（现在是「TG-8"神枪手" + TG-8"神枪手"」，见 `RuntimeArmorChoiceViewModel.Composite`）；名字不同才两个都写。
3. **（S4）复用 P5 的识别**：默认隐藏 0x 未命名记录和非玩家记录（`KitNonPlayerArmors`），可切换显示；同名多条标「玩家版本」；FS-05 这类有歧义的（2 护甲 7 头盔）不再平铺，改为玩家版本护甲配玩家版本头盔。
4. **（S3）低污染模式下各类型映射什么**：

| 类型 | 3 槽（头身分开） | 2 槽（头身合并） |
|---|---|---|
| 组合 | 头 → 头盔独有部件；躯干 → 护甲独有躯干；手臂 → 护甲另一个独有部件 | 头+躯干 → 护甲独有躯干；原版头盔整个进隐藏集 |
| 仅护甲 | 只上躯干和手臂；模型的头不显示，玩家戴什么头盔就显示什么 | 头+躯干、手臂全上 |
| 仅头盔 | 只上头 | 不可用（头已并进身体），标「不可」并说明 |

组合在 3 槽下最顺：头落在头盔的独有部件上，不占护甲本就紧张的承载件。
- 理由：两个入口都能决定「护甲→模型」会互相打架，也和 J4「只在映射页指定」矛盾；patch 专属每套护甲各占一份数据，正是 100 套会卡的那条路。

## 9. 物理容器（S1 调研，2026-11-14）

目的：回答 §6.2 作者说的「物理容器按 unit 分区、合并必须连容器一起合」在**本仓库的实现**里指什么。结论先写：**容器本身不按 unit 分区，没有可合并的 per-unit 条目；物理跟着「unit 的骨骼表」走。** 下面是证据，调研时没有写任何实现代码，等用户拍板（见 §9.6）。

### 9.1 容器的结构与位置

- 格式 `HD2PBX01`（`HD2SourceModel/PhysBoneContainer.cs`，协议 `docs/agent/hd2physbone-embedded-patch-protocol.md`）：48 字节头 + 索引 + 数据 + 56 字节 footer（`HD2PBFT1`）。追加在**含 unit 的 patch 的 `.gpu_resources` 末尾**，TOC 不动。
- 我们只写**一条记录**：`hd2_spring_rig.bin`（`HD2SRG01` v2：每骨 148 字节，字段是源骨下标、父骨下标、骨名偏移、父骨名偏移、flags、世界位置、29 个参数；骨名与父骨名是字符串）。协议文档里提到的 `lua_units.txt`（按 unit ID 关联）和 `hd2_ib_needle.bin`，**本仓库没有任何代码写或读**（`HD2PBX01` 的 `Entry` 只在测试里出现过这两个名字）。
- 一个 Mod 一份：转换期落 `sectional/physbone-rig.bin`（`PhysBoneRigSidecar`，`VpkPayloadCollector` 按 `physbone-*.bin` 前缀搬运，`PhysBoneAuxFiles`），`physbone embed-mod`（`VpkPhysBoneEmbedder` → `PhysBoneContainerEmbedder.EmbedAsync`）把它嵌进根目录 / `sectional` / `vpk2patch` / `Overwrite` 下**每个含 unit 的 patch**。所有走 `PatchArchiveWriter.WriteAsync` 的重写都会把来源的容器原样搬过去（`PhysBoneCarrier`），`SectionalUnitPatchWriter` 最后也走它。
- 实测（真数据只读，样本复制到临时目录）：雫 3730700338 的 `physbone-rig.bin` 34 骨（head 25 / chest 2 / hips 2 +…），蚀骨魂龙 3621723720 的 42 骨（hips 19 / head 9 / chest 3 +…）；各自只有 `patch_0`（含 unit）里有 1 个容器、`patch_1`（材质）没有；`Overwrite/` 里同样 1 个容器。

### 9.2 运行时怎么「按 unit 找物理」

`HD2PhysBoneCompat/src/physbone_runtime.lua`（约 1127–1290 行）：遍历场景里的候选 unit，对每个 unit 用 `Compat.select_rig(S, {unit}, carriers)` 给「所有 patch 载体里读出的容器」打分，打分方式是 `Unit.has_node(unit, "骨名")`——**按骨名问这个 live unit 有没有这根骨**。命中 ≥1 根就挂载，`Compat.attach` 逐链解析节点，缺节点的链跳过。判据里**没有 unit key / fileId**。所以：

- 容器里没有任何东西「属于某个 unit」；
- 「躯干 unit 只带躯干的物理、手臂 unit 只带手臂的」是转换器的 `ExtraBoneSubset`（每个 unit 的 TransformInfo 只带它顶点蒙皮用到的物理骨 + 祖先链）造成的，见 `docs/agent/physbone-per-unit-rig-for-converter.md` §7.1。

### 9.3 P4b 合并会不会丢物理（离线实测）

探针 `HD2ModCore.Tests/SectionalPhysBoneProbeTests.cs`：对每个来源 unit，取节点表里「骨名哈希（`Murmur64A(name) >> 32`）在 rig 里」的节点；再把全部来源 `SectionalUnitMerger.MergeAsync` 成一个 unit，比对。

| Mod | 来源 unit 里的 rig 骨数 | 合并后的 rig 骨数 | 丢失 |
|---|---|---|---|
| 雫，7 件全合并 | 头 30 / 躯干 4 / 胯 2 / 左腿 1 / 右腿 1 / 左臂 0 / 右臂 1（并集 34） | 34 | 0 |
| 雫，去掉头合并 6 件 | 并集 4 | 4 | 0 |
| 蚀骨魂龙，7 件全合并 | 头 20 / 躯干 3 / 胯 19 / 腿 0 / 左臂 1 / 右臂 1（并集 42） | 42 | 0 |
| 蚀骨魂龙，去掉头 6 件 | 并集 24 | 24 | 0 |

再用 `SectionalCompiler.CompileAsync` 真编 CE-67（4081083564）与神射手（3970674111）各一次（雫、蚀骨魂龙各一份副本）：4 次都成功，`Overwrite/…patch_0.gpu_resources` 末尾都带完整容器，`hd2_spring_rig.bin` 长度与来源一致（雫 5941、蚀骨魂龙 7148）。

也就是说：在本仓库「容器 = 每 Mod 一份、按骨名匹配」的口径下，P4b 合并出来的 unit 节点表里**有**所有来源的物理骨，容器也**在**产物里。§6.2 说的缺口，在节点和容器这两层**没有复现**。

### 9.4 仍然没有被证明的部分（只能实机）

1. 合并 unit 里的物理骨在游戏里是否真的按链驱动（`Compat.attach` 的 `可用链 N 条` 日志）；
2. 作者说的「按 unit 分区」是否指的是**他自己的插件**（读 `lua_units.txt`/per-unit 记录）而不是我们的 Lua 兼容层；如果用户实机用的是他的插件，规则就可能不同。

### 9.5 如果要做「合并物理容器」，对象只能是什么

按骨名匹配的口径下，唯一有意义的「合并」是**合并两个来源 Mod 的容器**（`hd2_spring_rig.bin` 之间按骨名并集 + 父骨下标重排）；同一来源 Mod 内合并 unit 时容器不用动。S2 的压缩编译也是同一个来源 Mod，同样不需要合容器。
可以补的有价值的东西：把「合并后每个来源的 rig 骨都在节点表里」做成真数据回归测试，并在合并器里加一道**自检**（合并结果缺了 rig 骨就把它报成警告，而不是静默）。

### 9.6 用户拍板：选 A（2026-11-14）与 S1 结果

### 9.7 实机怎么看物理（attach 日志）

日志：`%LOCALAPPDATA%\hd2physbone.log`（旧的是 `hd2physbone.log.1`）。进游戏、换上对应护甲后，在日志里找：

```
[physbone] attach：可用链 X 条（缺节点 M、缺锚点 K）
[physbone] 已挂载 N 个 unit / T 条链（…）；每件链数 a,b,…
```

「可用链 X」是**每个被挂载的 unit** 一行；合并之后，承载件那一行的 X 应等于它所有来源的链数之和、缺节点 M 应为 0。链数按 rig 里按锚点归并（`parse-rig.py` 可离线数：`python -I tools\physbone-audit\parse-rig.py <Mod>\sectional\physbone-rig.bin`）：

- 雫（34 骨，head 25 / chest 2 / hips 2…）：身体合并承载件只带身体部分的物理骨，**4 根**（躯干 4，胯 2、腿 1+1、右臂 1 的并集仍是 4），链数很少（几条）；头发物理在头 unit 上，不在合并件里。
- 蚀骨魂龙（42 骨，hips 19 / head 9 / chest 3…）：CE-67 合并承载件带 **22 根**物理骨（含胯的 19 根）、神射手承载件 **24 根**。链数请以日志为准；离线只能保证「骨都在」，没有逐条链的离线预期值。

判断：若合并承载件那一行「缺节点 M」> 0，或胯/腿的裙摆不动，就是 §9.4 的两个未验证点出了问题，把日志发回来。

## 10. S2 实现方案：sectional 压缩编译 + 设置开关（2026-11-14）

### 10.1 开关与传递

- `SettingsService.SettingsModel.LowPollutionMode`（默认关）；设置页一个开关「低污染模式」，下面一句说明，并固定提示「切换后需一键重构建才生效」。切换**不自动重构建**（S4 的事）。
- 传递：`VpkHostContext` 加一个可选属性 `LowPollutionMode`（默认 `false`），管理器所有构造点改走 `SettingsService.CreateVpkHostContext()`；`ModCompileService.CompileAsync` 读 `context.LowPollutionMode`，传给 `SectionalCompiler.CompileAsync(lowPollution:)`。CLI 不接（默认关，S2 不需要）。
- 头身合并沿用每个 Mod 自己的 `wardrobe.json` 的 `headMergeIntoBody`（现有的 per-mod 设置），不新增设置。

### 10.2 什么时候压缩

- 只在编译**落到自身素体**（`CompileOwnModelAsync`，即目标为空或自己的素体）且 `lowPollution` 为真时压缩。目标是游戏护甲（含专属）的编译**完全不变**；S2 不替用户改 wardrobe 目标（详情页只留自己素体是 S4）。
- 来源形状不支持时**不压缩、照常编译**，并在编译结果的 `Warnings` 里写明原因（不失败，不猜）：
  - 来源里出现 `Slim`/`Stocky` 分体的 unit（实测两份样本都是全 `Any`）；
  - 同一部位有多于一个来源 unit；
  - 来源 unit 没有可识别部位。
- 披风、肩和未知部位的来源 unit **原样保留**，不并入任何槽（Info 里说明）。
- 缺部位（比如没有手臂）：那个槽没有成员就不生成；有成员就照常。
- 需要合并（某个槽成员 ≥2）而没有游戏 data 目录时：失败并明确提示去设置页指定游戏目录（与专属合并同一口径）。没有任何合并发生（比如每槽只有一个成员）时不读游戏 data。

### 10.3 分槽规则

| 模式 | 槽 | 成员（来源部位） |
|---|---|---|
| 3 槽（头身合并关） | 头 | 头盔 |
| | 躯干 | 躯干、胯、左腿、右腿 |
| | 手臂 | 左臂、右臂 |
| 2 槽（头身合并开） | 头身 | 头盔、躯干、胯、左腿、右腿 |
| | 手臂 | 左臂、右臂 |

### 10.4 压缩 unit 的 ID 规则（稳定、可复现）

**不造新 ID，压缩 unit 沿用来源里本槽「主部位」的 unit ID。** 理由：来源 ID 是 Mod 自己的 64 位 ID（如 `079d…0002`），本来就和游戏及别的 Mod 不撞；规则只依赖 `sectional/sections.json`，所以同一个 Mod 重编 ID 一定不变，且不依赖编译顺序、时间、随机数。

| 槽 | ID 取自（按顺序取第一个存在的来源部位） |
|---|---|
| 头 | 头盔 |
| 躯干 | 躯干 → 胯 → 左腿 → 右腿 |
| 手臂 | 左臂 → 右臂 |
| 头身 | 躯干 → 胯 → 左腿 → 右腿 → 头盔 |

- 合并时 ID 所有者放在 `SectionalUnitMergeSpec.SourceFileIds` 的最前（宿主仍由 `SectionalUnitMerger` 按「自定义骨最多」自选，它只决定几何搬运方向，不影响 ID）。
- 单成员槽不合并，字节原样改名到同一个 ID（等价于原 unit）。
- 被吸收的来源 ID（胯、腿、右臂、2 槽模式的头盔等）不再出现在产物里。

### 10.5 产物

`Overwrite/` 里（`sectional/` 一个字节不动）：

1. unit patch：只含压缩后的 2/3 个 unit（外加原样保留的披风/肩）。几何合并复用 `SectionalUnitMerger`（含 S1 物理骨自检），**不另写合并**。关闭的 section 先在来源副本上烘好再合并（与专属合并同一条路径，合并后不再支持就地开关 section）。
2. `custom-model.json`：只保留压缩 unit 的注册件（主部位那几条，`body`/`slot`/`pieceType` 不变）；被吸收部位的注册件剪掉（与 `CustomModelSectionalCompaction` 同一个口径：不留悬空引用）。`CustomModelCatalog` 优先读这份。
3. **`low-pollution-layout.json`**（新，S3 靠它写 `wardrobe.links`）：

```json
{
  "schema": "hd2mod.low-pollution-layout/1",
  "mode": "three-slot | two-slot",
  "headMerge": false,
  "units": [
    { "role": "head | body | arms | head-body",
      "unit": "079d12e38aec0002",
      "idFrom": "Torso",
      "parts": [ { "part": "Torso", "sourceUnit": "079d12e38aec0002" }, { "part": "Hip", "sourceUnit": "…0003" } ] }
  ],
  "passthrough": [ { "part": "Cape", "unit": "…" } ]
}
```
   `parts[].part` 用 `ArmorStructure` 的部位名；`sourceUnit` 是来源里对应的 unit ID（供 S3 反查「这个压缩 unit 对应哪些原部位」）。内容只依赖来源，排序固定（槽顺序 → 部位顺序），同一 Mod 重编逐字节一致。
4. `sections.json`（生效层）：按压缩后的 patch 重建，身份（部位/层/身形）取 ID 所有者来源的那条；组表 `components.json` 不写（合并后序号已变，同专属合并）。

### 10.6 关闭时

开关关（默认）= 代码路径与现在完全一致：`lowPollution` 为假时一行新逻辑都不执行；只多一步「生效层里有残留的 `low-pollution-layout.json` 就删掉」（没残留时什么都不发生）。测试锁住：关闭时 `Overwrite/` 全部文件与不传该参数时逐字节相同，且没有 layout 文件。

### 10.7 验收（离线）

- 单测：分槽/ID 规划器（3 槽、2 槽、缺部位、分体/重复/披风肩的不压缩理由、ID 稳定）；layout 序列化稳定；关闭时逐字节一致。
- 真数据（环境变量见 `SectionalPhysBoneMergeTests`）：雫、蚀骨魂龙的临时副本各编 3 槽与 2 槽：件数 3/2、重编两次 ID 与产物字节相同、来源物理骨一根不少（`SectionalPhysBoneRig.FindMissing` 对每个压缩 unit 对着它的来源集合核对）。
- 实机（用户）：开开关 → 把该 Mod 的目标设回「自己的素体」→ 一键重构建 → 直接部署，看显示是否正常、物理是否还在（日志见 §9.7）。
