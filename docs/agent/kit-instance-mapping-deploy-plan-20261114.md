# P6 规划：专属多目标改用软映射部署

日期：2026-11-14。上接 P5（`kit-instance-multi-target-plan-20261114.md`，界面与存储）。§6 的决定**待用户拍板**。

## 1. 为什么

用户转述 Mod 作者的话：用常规 patch 的方式替换全部护甲，显存和内存会暴涨；用映射的方式会好很多。

现在的专属切换（P4a/P4b）是打补丁：把模型数据用承载件的 ID 写进 `Overwrite/`。选一套目标就有一份；合并模式下每份是一整个模型 unit，选 N 套就是 N 份。P5 的多选会把这个问题放大。

用户已决定：多目标部署改用映射。P5 先把界面做完（勾两个以上目标时暂不能确认），部署由本阶段接上。

## 2. 现状（代码事实）

- **软映射链路**（护甲映射页在用）：
  - 意图写在 `armor-registry.protocol` 和 workspace；
  - `WardrobeLinkCompiler.Compile` 把意图编译成 `<ArmorRegistry>/wardrobe.links`，内容是一组 unit 对：目标 unit → 源 unit；
  - 运行时 `HD2RuntimeArmorOverride/src/armor_override_runtime.lua` 每秒读一次这个文件，对新增的映射调用 `Application.set_resource_override('unit', 源, 目标)`，每帧最多 32 条。
  - `set_resource_override` 和 `clear_resource_override` 都在 API 白名单里（`hd2pbx_api.txt:330/369`）。
- **映射只增不减。** 删除映射不会释放，要重启游戏才恢复。一次性释放大量映射会让游戏当场崩溃（`soft-mapping-armory-crash-recon-20261112.md` §1）。
- **源 unit 必须真的在游戏数据里。** 指向不存在的 unit，引擎会记住这次加载失败，之后军械库整页空白并崩溃。这就是 `WardrobeLinkCompiler.HiddenUnit` 存在的原因。
- **sectional Mod 的部署**（`ModDeployableFiles.cs:20/59`）：部署基底（`sectional/`，Mod 自己的 unit ID），`Overwrite/` 里同名的文件会顶替基底。所以切换过目标的 Mod，Mod 自己 ID 的 unit 不会进游戏。
- 按实例隐藏（Hider）和映射是两条独立的运行时链路，互不影响。

## 3. 方案

### 3.1 部署内容

- **模型只部署一份，用 Mod 自己的 ID：**
  - P4a 逐格目标：直接用基底里的各部位 unit（`079d…0001`…`0007` 这一类）。
  - P4b 合并目标：合并后的 unit 用一个新 ID 部署。同一组来源、同样的头部处理，合并结果只做一份，多个目标共用。新 ID 的生成规则要稳定、可复现，由实现方定，写进文档。
  - 头落在头盔上时，头部 unit 也只部署一份。
- **映射**：每个目标的每个承载件写一条「承载件 → 模型 unit」。同一个承载件被多个目标选中时（同名组）只写一条。
- **隐藏**：照旧，每个目标一条 Hider 规则（P5 的多目标 workspace）。
- **专属模式下不再写 `Overwrite/`**（见 §6 H2）。普通模式完全不变。

### 3.2 映射写到哪里

- 和护甲映射页共用 `wardrobe.links` 和同一个运行时，不另起一套 Lua。
- 编译时把专属的映射和映射页的映射合在一起，文件的协议和 schema 不变。
- 同一个承载件被两边都映射时，按 §6 H3 处理。

### 3.3 撤销与改动

- 去掉一个目标、关掉专属或删除 Mod：映射从 `wardrobe.links` 删掉，Hider 规则也删掉。但已经生效的映射要**重启游戏**才释放，界面要明说「重启游戏后恢复原版」。
- 重启之前，被删掉目标的隐藏规则已经撤掉，原版部件会露出来，而承载件还显示模型。这段时间外观可能不对，所以同一条提示也要写清楚这一点。

## 4. 风险

1. 源 unit 没部署成功却已经写了映射，会导致军械库崩溃。所以部署顺序必须是：先确认模型 unit 已进游戏数据，再写映射；任一步失败，整份回滚（沿用 G4 的失败弹窗）。
2. 映射是全局的。承载件按定义只属于目标组，不会波及别的护甲，但这依赖 P4a/P4b 规划的正确性。
3. 运行时映射在角色加载之前就要生效。现在映射页每秒轮询，进游戏以后才加的映射，对已经加载出来的角色可能要换一次装才生效。实机时要专门看这一点。
4. 合并后 unit 的新 ID 不能和游戏或其它 Mod 撞。

## 5. 不做

- 不改普通切换。
- 不改 Hider 协议。
- 不尝试释放映射（`clear_resource_override`）。

## 7. 定稿方案（2026-11-14，按作者方案重写；§3 只适用于详情页多选，以本节为准）

### 7.1 总览

设置页加一个全局开关「低污染模式」（J1 已定）。打开后：

1. **sectional 编译层**：每个模型 Mod（素体）编译成压缩版，只有 3 个或 2 个 unit，都用新 ID（规则稳定、可复现）：
   - 头身合并关：头、躯干（含胯、左右腿）、手臂（含左右臂），共 3 槽；
   - 头身合并开：头＋躯干（含胯、腿）、手臂，共 2 槽，头和躯干的几何合成一个 unit。
   - **物理容器跟着合并**：被合并 unit 的物理骨架和参数并进同一个 unit 的容器里。
   - `custom-model.json` 只写压缩后的件。
2. **软映射编译层**（护甲映射页「应用」）：把目标护甲映射到素体时，**只映射非污染部件**：
   - 躯干槽：固定落在目标独有的躯干部件上；
   - 头：固定落在目标头盔独有的部件上（2 槽模式没有这一项）；
   - 手臂槽：落在目标任何一个剩余的独有部件上。
   - 「独有」沿用 P4b 的口径：同名组和同 set 头盔算一组。
   - 目标其余的原版部件**不再映射**，改由 Hider 按实例隐藏。每个被映射的目标生成一条规则，签名取躯干承载件。
   - 2 槽模式下，原版头盔也进隐藏集。
3. **自动工作流**：开关打开或关闭后，依次自动执行：
   1. 一键重构建所有 sectional 系 Mod；
   2. 重新应用软映射；
   3. 重新部署。
   有进度、能取消；失败时沿用 G4 的弹窗。
4. **详情页**：压缩模式下，「目标护甲」只保留「自己的素体」，并显示一行「护甲替换请到护甲映射页」和跳转按钮。P5 做的搜索和多选组件搬到映射页复用（§8 J4）。
5. **压缩模式关闭时**：一切照旧（现有映射页、P4a/P4b 补丁专属、P5 单选）。

### 7.2 为什么能解决「100 多套」

- 素体数据只有一份：3 或 2 个 unit。映射 100 套只是 100 组映射行，加 100 条 Hider 规则。
- 只映射独有部件，所以不会连带别的护甲。

### 7.3 必须先解决的硬约束

1. **Hider 上限**：现在最多 64 条规则、文件 64 KiB。映射 100 多套就要 100 多条规则，必须提高上限。这要改 Lua 和规则协议，见 §8 J2。实现前先在 lupa 里压测：200 条规则时每帧的开销。
2. **承载件不够的护甲**：没有独有躯干的目标（约 30 套，大多是换色孪生护甲），压缩模式下怎么办，见 §8 J3。
3. **先部署、后映射**：素体的压缩 unit 没进游戏数据之前，不写映射行，否则军械库会崩溃。
4. **物理容器合并**：见 §6.2 作者补充。P4b 的缺口一起补。
5. **映射不释放**：改了映射要重启游戏才恢复，界面提示（H1）。

### 8.3 J6：专属入口并入护甲映射页（用户决定，2026-11-14）

用户提出把详情页的专属逻辑整体搬到护甲映射页。定下来的做法是「S4 搬，S3 后删」：

- **S4 搬**：详情页的专属（专属开关、预览、转专属/撤销专属、多选）去掉，防污染只在护甲映射页做。用户已转专属的 Mod 要迁移（workspace 记录转成映射页的映射，或提示重设），在 S4 设计。
- **S3 后删**：S3 实机验证映射路线（先部署后映射、映射不释放、Hider 上限）之前，专属写 Overwrite patch 的那条输出保留当退路；验证通过后在 S4 删除。
- **保留复用**：独有承载件规划器（P4）、合并器与物理自检（P4b、S1）、Hider（P1）都不动，S2/S3 本来就要用。

用户补充（同日，看过映射页截图后）：

- **映射页不要下拉**：映射页右侧本来就有带搜索的护甲列表，P5 的下拉不搬过去。
- **详情页下拉只留搜索、改单选**：详情页回到普通 patch 替换，「这边污染的还是污染」；想不污染去映射页。改单选后，P5 多选里同一套护甲能被加两次的问题（截图里两个 DP-8 2846302183）自然消失。
- **映射覆盖详情页规则（用户选 A：部署时跳过）**：部署时，如果某个 Mod 的 patch 目标护甲已经是映射页的映射目标，这套护甲就不部署那个 Mod 的 patch，详情页标「已被护甲映射覆盖」。理由：低污染模式只映射独有部件，若 patch 照部署，共用部件上会残留 patch 模型又被 Hider 藏掉，白占一份数据，还会混搭。

### 8.4 映射页的单件与组合（用户同意写入，2026-11-14）

现状：映射页右侧「可用护甲」默认「类型：自动组合」，把同名 / 同 set 的 1 件护甲 + 1 个头盔配成一条（`ArmorRegistryPageViewModel.BuildDisplayChoices`），点这行文字可循环到「仅护甲」「仅头盔」。也就是说单件已经能映射，只是入口藏得深；作者设计时默认用组合，没考虑低污染模式。

改法：

1. **（S4）筛选改成看得见的三档**：组合 / 护甲 / 头盔，替换循环文字按钮；默认仍是组合。
2. **（S4）组合名去重**：同名时显示一次名字加「头盔+护甲」标签（现在是「TG-8"神枪手" + TG-8"神枪手"」，见 `RuntimeArmorChoiceViewModel.Composite`）；名字不同才两个都写。
3. **（S4）复用 P5 的识别**：默认隐藏 0x 未命名记录和非玩家记录（`KitNonPlayerArmors`），可切换显示；同名多条标「玩家版本」；FS-05 这类有歧义的（2 护甲 7 头盔）不再平铺，改为玩家版本护甲配玩家版本头盔。
4. **（S3）低污染模式下各类型映射什么**：

| 类型 | 3 槽（头身分开） | 2 槽（头身合并） |
|---|---|---|
| 组合 | 头 → 头盔独有部件；躯干 → 护甲独有躯干；手臂 → 护甲另一个独有部件 | 头+躯干 → 护甲独有躯干；原版头盔整个进隐藏集 |
| 仅护甲 | 只上躯干和手臂；模型的头不显示，玩家戴什么头盔就显示什么 | 头+躯干、手臂全上 |
| 仅头盔 | 只上头 | 不可用（头已并进身体），标「不可」并说明 |

组合在 3 槽下最顺：头落在头盔的独有部件上，不占护甲本就紧张的承载件。
- 理由：两个入口都能决定「护甲→模型」会互相打架，也和 J4「只在映射页指定」矛盾；patch 专属每套护甲各占一份数据，正是 100 套会卡的那条路。

## 9. 物理容器（S1 调研，2026-11-14）

目的：回答 §6.2 作者说的「物理容器按 unit 分区、合并必须连容器一起合」在**本仓库的实现**里指什么。结论先写：**容器本身不按 unit 分区，没有可合并的 per-unit 条目；物理跟着「unit 的骨骼表」走。** 下面是证据，调研时没有写任何实现代码，等用户拍板（见 §9.6）。

### 9.1 容器的结构与位置

- 格式 `HD2PBX01`（`HD2SourceModel/PhysBoneContainer.cs`，协议 `docs/agent/hd2physbone-embedded-patch-protocol.md`）：48 字节头 + 索引 + 数据 + 56 字节 footer（`HD2PBFT1`）。追加在**含 unit 的 patch 的 `.gpu_resources` 末尾**，TOC 不动。
- 我们只写**一条记录**：`hd2_spring_rig.bin`（`HD2SRG01` v2：每骨 148 字节，字段是源骨下标、父骨下标、骨名偏移、父骨名偏移、flags、世界位置、29 个参数；骨名与父骨名是字符串）。协议文档里提到的 `lua_units.txt`（按 unit ID 关联）和 `hd2_ib_needle.bin`，**本仓库没有任何代码写或读**（`HD2PBX01` 的 `Entry` 只在测试里出现过这两个名字）。
- 一个 Mod 一份：转换期落 `sectional/physbone-rig.bin`（`PhysBoneRigSidecar`，`VpkPayloadCollector` 按 `physbone-*.bin` 前缀搬运，`PhysBoneAuxFiles`），`physbone embed-mod`（`VpkPhysBoneEmbedder` → `PhysBoneContainerEmbedder.EmbedAsync`）把它嵌进根目录 / `sectional` / `vpk2patch` / `Overwrite` 下**每个含 unit 的 patch**。所有走 `PatchArchiveWriter.WriteAsync` 的重写都会把来源的容器原样搬过去（`PhysBoneCarrier`），`SectionalUnitPatchWriter` 最后也走它。
- 实测（真数据只读，样本复制到临时目录）：雫 3730700338 的 `physbone-rig.bin` 34 骨（head 25 / chest 2 / hips 2 +…），蚀骨魂龙 3621723720 的 42 骨（hips 19 / head 9 / chest 3 +…）；各自只有 `patch_0`（含 unit）里有 1 个容器、`patch_1`（材质）没有；`Overwrite/` 里同样 1 个容器。

### 9.2 运行时怎么「按 unit 找物理」

`HD2PhysBoneCompat/src/physbone_runtime.lua`（约 1127–1290 行）：遍历场景里的候选 unit，对每个 unit 用 `Compat.select_rig(S, {unit}, carriers)` 给「所有 patch 载体里读出的容器」打分，打分方式是 `Unit.has_node(unit, "骨名")`——**按骨名问这个 live unit 有没有这根骨**。命中 ≥1 根就挂载，`Compat.attach` 逐链解析节点，缺节点的链跳过。判据里**没有 unit key / fileId**。所以：

- 容器里没有任何东西「属于某个 unit」；
- 「躯干 unit 只带躯干的物理、手臂 unit 只带手臂的」是转换器的 `ExtraBoneSubset`（每个 unit 的 TransformInfo 只带它顶点蒙皮用到的物理骨 + 祖先链）造成的，见 `docs/agent/physbone-per-unit-rig-for-converter.md` §7.1。

### 9.3 P4b 合并会不会丢物理（离线实测）

探针 `HD2ModCore.Tests/SectionalPhysBoneProbeTests.cs`：对每个来源 unit，取节点表里「骨名哈希（`Murmur64A(name) >> 32`）在 rig 里」的节点；再把全部来源 `SectionalUnitMerger.MergeAsync` 成一个 unit，比对。

| Mod | 来源 unit 里的 rig 骨数 | 合并后的 rig 骨数 | 丢失 |
|---|---|---|---|
| 雫，7 件全合并 | 头 30 / 躯干 4 / 胯 2 / 左腿 1 / 右腿 1 / 左臂 0 / 右臂 1（并集 34） | 34 | 0 |
| 雫，去掉头合并 6 件 | 并集 4 | 4 | 0 |
| 蚀骨魂龙，7 件全合并 | 头 20 / 躯干 3 / 胯 19 / 腿 0 / 左臂 1 / 右臂 1（并集 42） | 42 | 0 |
| 蚀骨魂龙，去掉头 6 件 | 并集 24 | 24 | 0 |

再用 `SectionalCompiler.CompileAsync` 真编 CE-67（4081083564）与神射手（3970674111）各一次（雫、蚀骨魂龙各一份副本）：4 次都成功，`Overwrite/…patch_0.gpu_resources` 末尾都带完整容器，`hd2_spring_rig.bin` 长度与来源一致（雫 5941、蚀骨魂龙 7148）。

也就是说：在本仓库「容器 = 每 Mod 一份、按骨名匹配」的口径下，P4b 合并出来的 unit 节点表里**有**所有来源的物理骨，容器也**在**产物里。§6.2 说的缺口，在节点和容器这两层**没有复现**。

### 9.4 仍然没有被证明的部分（只能实机）

1. 合并 unit 里的物理骨在游戏里是否真的按链驱动（`Compat.attach` 的 `可用链 N 条` 日志）；
2. 作者说的「按 unit 分区」是否指的是**他自己的插件**（读 `lua_units.txt`/per-unit 记录）而不是我们的 Lua 兼容层；如果用户实机用的是他的插件，规则就可能不同。

### 9.5 如果要做「合并物理容器」，对象只能是什么

按骨名匹配的口径下，唯一有意义的「合并」是**合并两个来源 Mod 的容器**（`hd2_spring_rig.bin` 之间按骨名并集 + 父骨下标重排）；同一来源 Mod 内合并 unit 时容器不用动。S2 的压缩编译也是同一个来源 Mod，同样不需要合容器。
可以补的有价值的东西：把「合并后每个来源的 rig 骨都在节点表里」做成真数据回归测试，并在合并器里加一道**自检**（合并结果缺了 rig 骨就把它报成警告，而不是静默）。

[physbone] attach：可用链 X 条（缺节点 M、缺锚点 K）

## 10. S2 实现方案：sectional 压缩编译 + 设置开关（2026-11-14）

### 10.1 开关与传递

- `SettingsService.SettingsModel.LowPollutionMode`（默认关）；设置页一个开关「低污染模式」，下面一句说明，并固定提示「切换后需一键重构建才生效」。切换**不自动重构建**（S4 的事）。
- 传递：`VpkHostContext` 加一个可选属性 `LowPollutionMode`（默认 `false`），管理器所有构造点改走 `SettingsService.CreateVpkHostContext()`；`ModCompileService.CompileAsync` 读 `context.LowPollutionMode`，传给 `SectionalCompiler.CompileAsync(lowPollution:)`。CLI 不接（默认关，S2 不需要）。
- 头身合并沿用每个 Mod 自己的 `wardrobe.json` 的 `headMergeIntoBody`（现有的 per-mod 设置），不新增设置。

### 10.2 什么时候压缩

- 只在编译**落到自身素体**（`CompileOwnModelAsync`，即目标为空或自己的素体）且 `lowPollution` 为真时压缩。目标是游戏护甲（含专属）的编译**完全不变**；S2 不替用户改 wardrobe 目标（详情页只留自己素体是 S4）。
- 来源形状不支持时**不压缩、照常编译**，并在编译结果的 `Warnings` 里写明原因（不失败，不猜）：
  - 来源里出现 `Slim`/`Stocky` 分体的 unit（实测两份样本都是全 `Any`）；
  - 同一部位有多于一个来源 unit；
  - 来源 unit 没有可识别部位。
- 披风的来源 unit **原样保留**，不并入任何槽（Info 里说明）。肩（左右）并入手臂槽（用户 2026-11-14 决定，P6 S3 实现时改的；S2 提交时肩还是原样保留）。认不出部位的来源 unit 本来就整体不压缩（见上）。
- 缺部位（比如没有手臂）：那个槽没有成员就不生成；有成员就照常。
- 需要合并（某个槽成员 ≥2）而没有游戏 data 目录时：失败并明确提示去设置页指定游戏目录（与专属合并同一口径）。没有任何合并发生（比如每槽只有一个成员）时不读游戏 data。

### 10.3 分槽规则

| 模式 | 槽 | 成员（来源部位） |
|---|---|---|
| 3 槽（头身合并关） | 头 | 头盔 |
| | 躯干 | 躯干、胯、左腿、右腿 |
| | 手臂 | 左臂、右臂、左肩、右肩 |
| 2 槽（头身合并开） | 头身 | 头盔、躯干、胯、左腿、右腿 |
| | 手臂 | 左臂、右臂、左肩、右肩 |

### 10.4 压缩 unit 的 ID 规则（稳定、可复现）

**不造新 ID，压缩 unit 沿用来源里本槽「主部位」的 unit ID。** 理由：来源 ID 是 Mod 自己的 64 位 ID（如 `079d…0002`），本来就和游戏及别的 Mod 不撞；规则只依赖 `sectional/sections.json`，所以同一个 Mod 重编 ID 一定不变，且不依赖编译顺序、时间、随机数。

| 槽 | ID 取自（按顺序取第一个存在的来源部位） |
|---|---|
| 头 | 头盔 |
| 躯干 | 躯干 → 胯 → 左腿 → 右腿 |
| 手臂 | 左臂 → 右臂 → 左肩 → 右肩 |
| 头身 | 躯干 → 胯 → 左腿 → 右腿 → 头盔 |

- 合并时 ID 所有者放在 `SectionalUnitMergeSpec.SourceFileIds` 的最前（宿主仍由 `SectionalUnitMerger` 按「自定义骨最多」自选，它只决定几何搬运方向，不影响 ID）。
- 单成员槽不合并，字节原样改名到同一个 ID（等价于原 unit）。
- 被吸收的来源 ID（胯、腿、右臂、2 槽模式的头盔等）不再出现在产物里。

### 10.5 产物

`Overwrite/` 里（`sectional/` 一个字节不动）：

1. unit patch：只含压缩后的 2/3 个 unit（外加原样保留的披风/肩）。几何合并复用 `SectionalUnitMerger`（含 S1 物理骨自检），**不另写合并**。关闭的 section 先在来源副本上烘好再合并（与专属合并同一条路径，合并后不再支持就地开关 section）。
2. `custom-model.json`：只保留压缩 unit 的注册件（主部位那几条，`body`/`slot`/`pieceType` 不变）；被吸收部位的注册件剪掉（与 `CustomModelSectionalCompaction` 同一个口径：不留悬空引用）。`CustomModelCatalog` 优先读这份。
3. **`low-pollution-layout.json`**（新，S3 靠它写 `wardrobe.links`）：

```json
{
  "schema": "hd2mod.low-pollution-layout/1",
  "mode": "three-slot | two-slot",
  "headMerge": false,
  "units": [
    { "role": "head | body | arms | head-body",
      "unit": "079d12e38aec0002",
      "idFrom": "Torso",
      "parts": [ { "part": "Torso", "sourceUnit": "079d12e38aec0002" }, { "part": "Hip", "sourceUnit": "…0003" } ] }
  ],
  "passthrough": [ { "part": "Cape", "unit": "…" } ]
}
```
   `parts[].part` 用 `ArmorStructure` 的部位名；`sourceUnit` 是来源里对应的 unit ID（供 S3 反查「这个压缩 unit 对应哪些原部位」）。内容只依赖来源，排序固定（槽顺序 → 部位顺序），同一 Mod 重编逐字节一致。
4. `sections.json`（生效层）：按压缩后的 patch 重建，身份（部位/层/身形）取 ID 所有者来源的那条；组表 `components.json` 不写（合并后序号已变，同专属合并）。

### 10.6 关闭时

开关关（默认）= 代码路径与现在完全一致：`lowPollution` 为假时一行新逻辑都不执行；只多一步「生效层里有残留的 `low-pollution-layout.json` 就删掉」（没残留时什么都不发生）。测试锁住：关闭时 `Overwrite/` 全部文件与不传该参数时逐字节相同，且没有 layout 文件。

### 10.7 验收（离线）

- 单测：分槽/ID 规划器（3 槽、2 槽、缺部位、分体/重复/披风肩的不压缩理由、ID 稳定）；layout 序列化稳定；关闭时逐字节一致。
- 真数据（环境变量见 `SectionalPhysBoneMergeTests`）：雫、蚀骨魂龙的临时副本各编 3 槽与 2 槽：件数 3/2、重编两次 ID 与产物字节相同、来源物理骨一根不少（`SectionalPhysBoneRig.FindMissing` 对每个压缩 unit 对着它的来源集合核对）。
- 实机（用户）：开开关 → 把该 Mod 的目标设回「自己的素体」→ 一键重构建 → 直接部署，看显示是否正常、物理是否还在（日志见 §9.7）。

## 11. S3 实现方案：软映射只映射非污染部件 + Hider 扩容（2026-11-14）

S3 的规格是 §8.4 第 4 点那张表。本节写「怎么落地」，**标「待确认」的几条在 §11.9，没回答前不写对应代码**。

### 11.1 触发条件与入口

低污染映射只在**同时满足**时走新路径，否则走现有路径，一个字节都不变：

1. 设置开关「低污染模式」开（`ApplyAsync` 新增末尾可选参数 `lowPollutionMode`，默认 `false`；映射页传 `SettingsService.GetLowPollutionMode()`；CLI 不传）；
2. 映射的来源是素体（`IsModelMapping`），且该素体所在 Mod 的生效层有 `Overwrite/low-pollution-layout.json`（用 `CustomModelCatalog.Collect` 给出的 `ModDirectory` 定位，**不另扫盘**）；生效层没有布局文件 = 素体没压缩过，走旧路径；**布局文件在但读不出来 = 该目标「不可」**（要用户对该 Mod 再点一次一键重构建），**不退回旧路径**（退回就是全量映射）；
3. 目标是游戏护甲或头盔（`GameDataAuthorityKit`）。

游戏护甲 → 游戏护甲（J5）、关开关、来源不是压缩素体（没重构建过）：走旧路径，测试锁住（同一输入有 / 没有新参数，`wardrobe.links` 逐字节一致）。

### 11.2 规划器：`LowPollutionMappingPlanner`（纯函数，不碰盘）

输入：`SectionalExclusivePlanner.Index`、layout、目标 kit。输出：每个目标一条 `LowPollutionMappingPlan { Status, Reason, Links(承载件→压缩 unit), Hide, Signature, Notes }`。

**「独有」口径复用 `SectionalExclusivePlanner`，不另写：** 把里面三处闭包提成 `internal static`（行为不变，原测试兜底）——

- 同名组：`GroupItems`（同名护甲记录 ∪ 自己）；
- 护甲部件是否独有：`owners ⊆ GroupItems`（`IsGroupUnique`，P4b 放宽口径）；
- 头盔部件是否独有：`owners ⊆ (同套 ∪ 同名头盔记录 ∪ 本护甲)`（`HelmetUnique`，合并那一遍的放宽口径）；
- 换色孪生的说明：`TwinNames`（J3 的原因文案）。

候选排序同它：层数大的优先，同层按 unit ID；非玩家记录（`KitNonPlayerArmors`）不特殊处理，只用于映射页标注（口径同专属下拉）。

**按目标类型和槽数（layout 的 `headMerge`）：**

| 目标 | 3 槽 | 2 槽 |
|---|---|---|
| 护甲 | 躯干承载件 ← body 槽；手臂承载件 ← arms 槽 | 躯干承载件 ← head-body 槽；手臂承载件 ← arms 槽 |
| 头盔 | 头承载件 ← head 槽 | **不可**（「头已并进身体，请映射护甲」） |

- 躯干承载件 = 目标躯干部位里第一个独有部件（每种身形各一个；两种身形共用同一个就只一个）。没有 ⇒ **不可**，原因文案：有换色孪生 → 「和 X、Y 用同一套模型，只有颜色不同」，否则「躯干部件都被别的护甲共用」。
- 手臂承载件 = 目标里**躯干之外**、头盔槽之外的任意独有部件（躯干在第一人称被游戏隐藏，手臂要看得见，所以不能放躯干槽）。优先级：左臂 → 右臂 → 左肩 → 右肩 → 胯 → 左腿 → 右腿；同槽按上面的排序。只在 layout 里有 arms 槽时才要。**找不到时的规则（Q1，用户已定）按顺序找：**
  1. 目标护甲上除躯干以外的独有部件；
  2. **2 槽且是组合**（同套头盔也映射到同一个素体）：头已并进身体，同套头盔记录的独有头部件空着，手臂放在那里（只有躯干槽和头盔在第一人称下被游戏隐藏，这个部件是头盔记录自己的，穿这顶头盔时手臂才显示；说明里写明）。3 槽组合时头盔的独有部件已被头占用，**不能**再放手臂；单独映射护甲（头盔没一起映射）也够不着；
  3. 都没有 ⇒ 整套「低污染模式下不可」，原因写明（2 槽下提示「可把同套头盔一起映射」或「同套头盔的独有头部件也没有可用的」），不做半套。
  「组合」靠 `ApplyAsync` 里的映射表认出来：`LowPollutionMappingService.Plan` 给每个目标传「映射到同一个素体的其它目标」（`companions`）。2 槽组合里的头盔那一半本身不写映射（头已并进身体），算「已映射」（不标不可），它的原版部件由护甲的规则隐藏；单独映射头盔 2 槽仍然不可。
- 头承载件（3 槽头盔目标）= 头盔记录头部位的第一个独有部件。
- 映射行：`link=<承载件>,<压缩 unit>`，**只发承载件**。不再有 HiddenUnit。披风不动（保持原版）。
- **只要有任一承载件或压缩 unit 缺失，整个目标不写任何一行。**

**Hider 规则（每个能映射的目标一条，规则名 `lp-<item_id>`，多个签名时加 `-s2`…）：**

- 隐藏集 = 目标记录的全部非披风部件 − 承载件（与 `SectionalExclusivePlan.Hide` 同口径：既包括共用部件，也包括独有但没当承载件的）。2 槽的护甲目标再加上**同套 / 同名头盔记录的全部非披风部件**（原版头盔，口径同 P4b 的 `helmetHide`）。**所有目标的承载件再全局扣除**：同名组里甲的非承载件可能是乙的承载件，乙的角色身上它显示模型，不能被甲的规则藏掉。
- **每个目标两套签名，规则内容相同（Q2 的决定）**：`lp-<item>`（`-s2`…）签名取躯干承载件的**原 ID**（两种身形各有一个承载件时第二个当备用签名，和 P5 的 `ExtraAll` 同做法）；`lp-<item>-u` 签名取**压缩躯干 unit 的 ID**（3 槽护甲 = body 槽、2 槽 = head-body 槽、头盔 = head 槽）。`Unit.resource_name` 在映射覆盖后返回覆盖前还是覆盖后的 ID，离线无法验证；两条规则各管一种：返回原 ID 时只有承载件签名会触发，返回覆盖后的 ID 时只有压缩 unit 签名会触发（压缩 unit 的 ID 从不出现在隐藏集里，所以不会互相干扰）。`radius` = 0.3，`none` 空。规则数因此按 2 倍算进上限。
- **压缩 unit 签名取并集为什么安全（核对结论，成立）**：压缩 unit 签名在每个穿「映射到同一个素体的护甲」的角色身上都成立，于是所有这类目标的隐藏集在这些角色身上都生效。隐藏集里只有**原版部件 ID**，不含任何目标的承载件（全局扣除）、也不含压缩 unit。X 的隐藏部件 S 出现在 Y 的角色身上，说明 S 是 X、Y 共用的部件；Y 同样被映射，Y 的共用部件本来就要藏；S 不会是 Y 的承载件（承载件只属于 Y 的同名组，而 S 与 X 共用，X 不在 Y 的同名组里；同名组里的情形由全局扣除兜住）。所以多藏的只会是本来就该藏的，或根本不在场的部件。**两个边界**：① 同名组内两条记录的承载件互相在对方的非承载件里时，靠全局扣除保证不被藏；② 「混搭」——玩家穿着 Y 的同时戴着别套头盔，这顶头盔的部件恰好在某个 2 槽目标的隐藏集里（它含同套头盔）——会被一起藏掉，这是想要的结果（2 槽下原版头盔本来就该藏）。3 槽目标的隐藏集不含头盔部件（头盔记录里偶尔出现在护甲记录上的头盔槽件除外）。
- 隐藏集超过协议单条上限时按上限拆成多条规则（同签名，名字加 `-h2`…），不当失败。
- 日志：`sweep` 行带 `rules_hit`（签名成立的规则名，最多 12 条）和 `rules_hit_count`，`rules` 行带 `mapping_rules`、`mapping_revision`；用户实机回报时说出哪条签名触发了（`lp-…` 还是 `lp-…-u`）就能判断 `resource_name` 返回哪种。

### 11.3 写到哪里

- `WardrobeLinkCompiler.Compile` 新增可选参数 `LowPollutionPlans`（按映射对应的规划结果）；对应映射走新分支写 `link=`，其余不变。`Result` 加 `LowPollution`（每个目标的状态和原因，给界面和日志）。`map=` 行不变。
- **规则单独写一个文件** `<ArmorRegistry>/kit-instance.mapping.rules`（格式同 `kit-instance.rules`，原子写，revision 单调），由 `ApplyAsync` 写。不并进 `kit-instance.rules`：那份由部署整份重写，映射页「应用」不会触发部署，合进去会被下次部署覆盖，或者要让部署去编译映射。待确认 Q3。
- Lua（`kit_instance_hider.lua` 0.3.0）每 2 秒读**两个**文件，分别解析（各自一套规则名空间）、规则列表拼起来用；任一文件文本变了就整体重装。任一文件坏了：保留那一份的上一版（日志 `rules_error` 带 `file` 标明哪份坏）。
- **两个文件的规则冲突时谁优先：没有优先级，互相独立、取并集。** hide 是只增不减的操作（`Unit.set_unit_visibility(false)`），不存在「覆盖」；两个文件里同名的规则、同签名的规则各自照常生效，不去重、不报错（`source` 字段标明来源）。文件缺失只影响自己那一份，另一份照常。测试：`test_kit_instance_hider.lua` 的「两个规则文件」一节（只有映射文件 / 并集同签名 / 同名分处两文件 / 一份坏一份好 / 映射文件被清空 / 映射文件不存在）。
- **撤销映射、关开关、目标变成不可时清空**：`ApplyAsync` 每次都重算规则；没有规则时，只要映射规则文件已存在就写一份空的（revision 递增），Hider 读到 0 条后不再隐藏新生成的部件（已经藏掉的按协议不恢复）。关开关后映射走旧路径，规则同样清空。
- 部署门（`LuaDeploymentService`）：`kitRuleCount` 原来只数 workspace 规则，数为 0 时**不投放 Hider**。要改成「workspace 规则数 + mapping 规则文件里的条数」，否则只用映射页、没有任何专属记录的用户永远没有 Hider。首次点「应用」时部署已经跑过，Hider 还没投放，`ApplyResult` 带 `HideRuleCount`，界面提示「需要重新部署一次才能启用隐藏」（自动化是 S4 的工作流）。

### 11.4 先部署后映射（§7.3 第 3 点）

现有守卫：`ApplyAsync` 在给了 `gameDataDirectory` 时读已部署 unit，`RuntimeArmorResourceFilter.Compile` 把素体件表裁成「真的在游戏数据里的」，整个素体一个都没有时直接抛 `InvalidDataException`。S3 加一层**逐目标**检查：layout 里的每个压缩 unit 都必须在这份「已部署」集合里（部分部署也算没部署），否则该目标状态 `NotDeployed`、不写映射行、不写规则，结果里说明「压缩 unit 还没部署进游戏，请先部署」。没给 `gameDataDirectory` 时本来就不编译 `wardrobe.links`，守卫不变。测试：模型 unit 不在已部署集合 → 0 行。

### 11.5 J3：映射页怎么标「不可」

规划器的 `Status/Reason` 经 `ApplyAsync` 的结果带回（`LowPollution` 列表），映射页在映射行上显示「低污染模式下不可：<原因>」，并在状态栏汇总「N 套未映射」。**S3 只做行内标注和汇总**；「应用前预览、把不可的护甲在右侧列表里置灰」属于 §8.4 第 1–3 点的 UI 改造，归 S4。不可的目标：不写映射、不退回全量映射、保留在工作区（用户改完再应用）。

### 11.6 Hider 上限（J2）与压测

压测脚本在 `HD2RuntimeArmorOverride/tests/stress_kit_instance_hider.lua`（可重复跑，纯 lupa，假引擎；构造 R 条规则、每条 H 个 hide、30–60 个角色各带一条规则的签名和 24 个隐藏候选件、4750–9500 个 unit 的场景）。lupa 的 LuaJIT 2.1，这台机器：

| 规则 R | hide H | 文件 | 解析一次 | 平均帧耗时（300 unit/帧） | 平均整轮 |
|---|---|---|---|---|---|
| 64 | 128 | 140 KiB | 5 ms | 0.042 ms | 0.67 ms |
| 200 | 24 | 91 KiB | 3 ms | 0.043 ms | 0.68 ms |
| 200 | 64 | 224 KiB | 9 ms | 0.041 ms | 0.65 ms |
| 200 | 128 | 436 KiB | 17 ms | 0.041 ms | 0.65 ms（60 角色 / 9500 unit：1.08 ms） |
| 256 | 128 | 558 KiB | 19 ms | 0.043 ms | 0.68 ms |
| 512 | 128 | 1117 KiB | 40 ms | 0.042 ms | 0.67 ms（60 角色 / 9500 unit：1.03 ms） |

结论：
- **每帧开销与规则数、hide 长度基本无关**（查表是哈希；规则数只影响文件解析和规则文本变化时的重建，都是一次性的）。每帧上限仍由 `UNITS_PER_FRAME=300` 决定。这里量的是 Lua 侧开销（假引擎调用近零）；引擎调用的开销还是探针实测的约 0.25 ms / 300 unit，规则数不改变它。
- 真正的约束是**文件大小和一次性解析卡顿**：1.1 MiB / 512 条解析 40 ms，只发生在规则文件内容变化时（2 秒轮询、文本不变不重解析）。
- 内存：512 × 128 个 ID 字符串约几十万字节量级的表，不是问题。

**新上限（Q2 之后规则数按 2 倍算）：规则 1024 条（每文件）、文件 2 MiB（每文件）、单条 hide 256、all/none 不变（8/8）。** 依据：200 个目标 × 2 套签名 = 400 条是目标场景，1024 留 2.5 倍余量；2 MiB 容得下 1024 条 × 平均 100 个 hide（真实平均隐藏集 8.5～20 个、最大 26 个）；单条 hide 128 → 256 只是留余量，每帧开销与它无关。补测（脚本里的第 3～8 行，Q2 之后）：

| 规则 R | hide H | 文件 | 解析一次 | 平均帧耗时 | 平均整轮 |
|---|---|---|---|---|---|
| 400 | 30 | 222 KiB | 8 ms | 0.041 ms | 0.65 ms |
| 400 | 128 | 873 KiB | 31 ms | 0.044 ms | 0.70 ms（60 角色 / 9500 unit：0.95 ms） |
| 1024 | 56 | 1010 KiB | 38 ms | 0.045 ms | 0.72 ms |
| 1024 | 100 | 1758 KiB | 63 ms | 0.035 ms | 0.97 ms（60 角色 / 9500 unit） |
| 1024 | 256 | > 2 MiB | 被 Lua 拒绝（file too large），所以 C# 写入侧用 `FitToLimits` 丢弃超出的规则并给 Warning | | |
写入侧不再「超过 64 KiB 就整份抛异常」，改成「超出条数或字节数的规则丢弃并给 Warning」，保证文件永远能被 Lua 接受。两侧同时改：`KitInstanceRulesProtocol`（`MaximumBytes = 2 MiB`、`MaximumRules = 1024`、`MaximumHide = 256`）、`kit_instance_hider.lua`（同名常量）；`SectionalExclusivePlanner.MaximumHide=128`（专属 patch 路线自己的上限）不动。Lua 只用白名单 API，不新增任何引擎调用，没有 `IdString64`。

## 12. S4a 实现方案：低污染模式自动工作流 + 映射优先于详情页 patch（2026-11-14）

范围只有三件事：①低污染素体的准备放进映射页「应用」（开关本身不触发任何流程）；②映射页「应用」后不再弹「再部署一次」；③部署时跳过已被映射覆盖的详情页 patch。**不改**详情页专属 UI、映射页筛选，**不删** patch 专属输出（S4b）。

### 12.1 低污染模式的素体准备：触发点在映射页「应用」（2026-11-14 返工，替换此前「开关切换后自动跑」的方案）

**用户原话：**「点切换我希望不要去做这么大的事情，只是一个开关，你现在会直接跑所有护甲，这不对。真正要跑，应该放在映射的流程里。应用映射的时候，如果启用了映射，那就要读是否开了防污染，然后判断哪些护甲跑过防污染了，哪些没有（避免等太久，本来也可以跳过已经弄过的了）」

**开关只存设置，不触发任何流程。** 设置页 `LowPollutionMode` setter 只写设置；提示文字改成「只保存设置，切换时不会做任何事。下次在护甲映射页点「应用」时生效」。上一版的 `RequestLowPollutionWorkflow` 事件、`LowPollutionWorkflow` 编排、Shell 里的整套自动流程**全部删除**。

**映射页「应用」在映射已启用、且有来源是素体（`SourceItemId` 为空、有 `ModelKey`）的映射时，按顺序：**

| 步 | 做什么 |
|---|---|
| a | 本次映射用到的素体 key = 这些映射的 `ModelKey`（不是全部 VPK Mod；`LowPollutionFreshness.SourceModelKeys`）。**只有映射已启用、且至少有一条映射指向它的素体才进判断；只列在映射页左边、没有任何目标的素体一律不编译**（用户：「如果关联了，才跑，如果只是存在左边，不要跑（毕竟啥用户护甲也没关联）」，测试 `Prep_OnlyModelsLinkedByAnEnabledMapping_AreEverConsidered` 锁住）。用 `CustomModelCatalog` 找到持有它的 Mod 目录 |
| b | 逐个判断（`LowPollutionFreshness.Assess`，只读生效层，不读游戏数据）：开关开 ⇒ 生效层没有布局文件 / 布局读不出来 / 布局没有指纹 / 头身合并和 wardrobe 不一致 / 指纹不一致 ⇒ 重编；开关关 ⇒ 生效层还有布局文件（或不可压缩标记）⇒ 重编回普通产物；其余跳过 |
| c | 只对要重编的编译：`ModCompileService.CompileAsync(目标 = 自己的素体 archive id，开关取设置)`，即详情页「切换」那条编译；不走「用来源重构建」，不做一键重构。编完让库里的内容事实失效并刷新 |
| d | 有重编的 ⇒ 原有的「先部署」（应用本来就在游戏没运行时、有模型映射时先 `FlushAsync` 一次）正好是「先部署后映射」；然后写映射；最后沿用原有的那次部署（Hider 投放）。**没有需要重编的 ⇒ 与以前的「应用」完全一样，不多部署** |
| e | 进度：后台任务（消息中心，可取消）+ 映射页状态栏；某个素体编译失败 ⇒ 只跳过它对应的映射目标并说明原因，不让整次应用失败；游戏在运行 ⇒ 不编译不部署，需要重编的素体的映射本次跳过，提示退出游戏后再点「应用」；取消 ⇒ 整次应用中止（没写映射），再点会接着做（已是最新的跳过） |

**「已经是最新的压缩产物」的判据 = 布局文件里的指纹。** `Overwrite/low-pollution-layout.json` 新增 `fingerprint` 字段：`SHA256(版本号 + 头身合并 + 生效的关闭 section（按 unit 与序号排序）+ 来源 sections.json 的哈希)`，编译压缩素体时写入。检查时用同一个函数、同样的输入（`wardrobe.json` 的关闭 section 与 `headMergeIntoBody`、基底目录的 `sections.json`）重算：来源重转换、section 勾选改了、头身合并变了，指纹都会变，下次应用就会重编；没有指纹的旧布局（S2/S3 写的）会重编一次。不写指纹的话其它字段（`mode`、`units`）不变，旧文件字节不变。

**不可压缩的素体**（分体 / 同部位多个 unit / 认不出部位）：编译时留一个 `Overwrite/low-pollution-unsupported.json`（同样的指纹 + 原因）。同样条件下判为「已处理」，不会每次应用都重编；来源或勾选变了会重新试一次；关开关时标记也算压缩痕迹，会被清掉。这种素体照旧走普通映射，并有编译警告说明原因。

**本次跳过的映射目标怎么处理（`ApplyAsync` 新参数 `skipModelKeys`）：** 映射仍留在 workspace（用户的意图不丢），但不进写出的协议、不编译成 `wardrobe.links`、不生成 Hider 规则。这样既不会退回全量映射造成污染，也不会让「映射优先」把对应 Mod 的 patch 跳过而护甲没有模型。

**目标不是自己素体的 Mod**（`wardrobe.json` 的目标是游戏护甲）：需要重编但不替用户改意图 ⇒ 标「不能自动重编」，跳过它的映射并提示「请先在详情页切回自己的素体」。

**取舍：** 编译只在应用时做，开关本身没有动静；代价是切开关之后第一次应用会等重编（只重编用到的素体，之后再应用直接跳过）。

### 12.2 映射页「应用」后自动补部署

读代码发现：`ArmorRegistryPageViewModel.ApplyAsync` 在 `service.ApplyAsync` **之后**本来就有一次 `deploymentCoordinator.FlushAsync()`（游戏没运行时），而部署门 `kitRuleCount` 已经数了映射规则文件，所以 Hider 在这一次部署里就投放了——「首次启用需要再部署一次」的话已经不对。改法：

- 游戏没运行：不再说那句话，改成「Hider 规则 N 条，已随本次部署投放」；
- 游戏在运行（跳过了部署）：说「游戏正在运行，Hider 规则 N 条要退出游戏后再点一次应用 / 立即重新部署才会投放」；
- 部署失败沿用现有错误路径。
- 不另加第二次部署。

### 12.3 映射优先于详情页 patch（§8.3 A）

**patch 和目标护甲在部署里的对应关系（读代码结论）：**

- 部署只认「文件」：`PatchFileIndexBuilder` 用 `ModDeployableFiles.Resolve` 给出每个 Mod 会进游戏的文件（管理器物化过的 `Overwrite/` 整层，或基底层），之后 `LuaDeploymentService.BuildAsync` / 计划器按 patch 组（`ArchiveHex16 + SourcePatchIndex`）部署。**没有任何一处把 patch 和「目标护甲」关联起来。**
- 关联只存在两处：`wardrobe.json`（非专属：`TargetArmorArchiveId`/`TargetArmorName`，一个目标；专属：`ExclusiveTargets` 的 item_id 列表）和 patch 里 unit 资源的 ID（换甲时被改成目标护甲的 unit ID）。
- 非专属换甲产物（`Overwrite/` 的 unit patch + 材质 patch）整层都是「这个 Mod 对目标护甲的替换」，没有别的内容；`Overwrite/` 里一个 patch 同时含目标的全部 unit（含与别的护甲共用的），所以「只跳过针对某套护甲的那部分」在非专属下就是**跳过这个 Mod 的整层 patch**。
- 专属多选产物：一份 `Overwrite/` 同时含多个目标的承载件，Hider 规则在 `kit-instance.rules`（按节点编译）。

**判定（Mod 的声明目标全被映射时才跳过）：**

1. 映射集合 = **已应用的协议**（`armor-registry.protocol`，解析后 `Enabled` 为真时的 `Mappings.TargetItemId`），不是映射页里未应用的编辑——没应用的映射不会改游戏，patch 不能先被跳过。
2. Mod 的声明目标：专属 ⇒ `wardrobe.json` 的 `ExclusiveTargets` item_id；非专属且 `TargetArmorArchiveId` 是游戏护甲 ⇒ 护甲索引（`ArmorAuthorityIndexReader`）里 `ArchiveId` 相同的全部记录的 item_id；没有目标 / 素体目标 / 读不出索引 ⇒ 空，不跳过。
3. 声明目标 ⊆ 映射集合（且非空）⇒ **跳过这个 Mod 在本次部署里的全部 patch**：做法是 `ProfileApplyService` 在 `ResolveEffectiveProfile` 之后、建文件索引之前，把这些节点从有效配置里去掉。这样文件索引、Lua 部署、计划器、**按实例隐藏的规则编译**（专属 Mod 的 `kit-instance.rules` 按启用节点编译）都自然不再看见它；不会出现「patch 没部署、Hider 规则还在藏部件」导致缺身体。
4. 每个被跳过的节点产生一条 `Info` 级 `CoreIssue`（`ArmorMappingCoversPatch`，「『Mod 名』针对 X 的 patch 已被护甲映射覆盖，本次部署跳过」），GUI 在部署完成时把它们写进应用日志；CLI 的计划输出同样看得到。
5. 判定逻辑放进 Core 的纯函数 `ArmorMappingPatchCoverage`（输入：节点声明目标、映射集合；输出：跳过 / 部分覆盖 / 不覆盖），部署和详情页共用同一个函数，不各写一份。

**详情页**：VPK 卡「目标护甲」行下面加一行「已被护甲映射覆盖：X（本 Mod 针对它的 patch 部署时被跳过）」，同样的判定（读协议 + 护甲索引）。只加这一行提示，不碰专属控件。

**不变量**：没有映射 / 映射未启用 / 协议读不出来 / 护甲索引没建 ⇒ 一个节点都不会被跳过，部署字节与现在完全一致；测试锁住。

### 12.4 待用户拍板（拆不开的情况）

**一个 patch 同时覆盖多套护甲、而其中只有一部分被映射**（只可能出现在专属多选：`ExclusiveTargets` ≥ 2 个，声明目标里有的被映射、有的没有）。patch 文件拆不开（要重写 patch 去掉部分承载件，还要同步改 Hider 规则，S4b 就会删掉这条输出路线）。推荐：**不跳过，整份照常部署**，部署日志记一条 Warning（「目标 A 已被映射覆盖，但本 Mod 的 patch 同时覆盖未映射的 B，无法拆分，未跳过」），详情页那一行也写「部分被映射覆盖，未跳过」。理由：跳整份会让没映射的那套护甲丢模型，比多占一份数据严重得多。

## 13. S5 规划：压缩支持两种体型分开做的素体（2026-11-14）

### 13.1 为什么

实机（2026-11-14）：「碧蓝航线-埃吉尔睡衣」映射到 CW-9 后，CE-27 也穿上了睡衣。原因链：

1. 这个素体的胸、左臂、右臂各有壮实（Stocky）和苗条（Slim）两份**不同**的模型（头、胯、双腿是通用 Any）。
2. S2 的压缩规划器（`SectionalCompressionPlanner`，§10.2）遇到 Slim/Stocky 分体就放弃压缩，写 `low-pollution-unsupported.json`（原因「胸部是 Slim 分体」）。
3. 不能压缩的素体在映射时按普通素体处理（§11.1 第 2 点、`LowPollutionFreshness`「按普通素体映射」），也就是全量映射：CW-9 的每个部件都被链到睡衣上。
4. CW-9 护甲（3017717209）和 CE-27 护甲（2128569605）共用 15 个部件，这 15 个都在 `wardrobe.links` 里 → CE-27 被污染。

Gemini 加的「同几何去重 / 单边体型提升为 Any」（`SectionalSplitPlanner.NormalizeSlotBodies`）只处理「两份一样」和「只做了一种体型」，埃吉尔的两份确实不同，所以仍然是分体。

目标侧的事实（真实索引，玩家护甲 138 条）：135 条的躯干部件本来就按体型分开（健壮 / 纤细各自的 unit），3 条混合。所以「壮实模型 → 健壮承载件、苗条模型 → 纤细承载件」在绝大多数护甲上天然成立。

### 13.2 压缩规则（按体型分组）

只改「有分体时」的行为；全是 Any 的素体规划结果、产物、layout **逐字节不变**（测试锁住）。

- 每个槽（头 / 躯干 / 手臂，2 槽时是头身 / 手臂）单独判断：
  - **槽里所有成员都是 Any** ⇒ 和现在一样，一个 Any 压缩 unit。
  - **槽里有任一成员是 Stocky 或 Slim** ⇒ 拆成两个压缩 unit：
    - 壮实那个 = 该槽的 Stocky 成员 + 该槽的 Any 成员；
    - 苗条那个 = 该槽的 Slim 成员 + 该槽的 Any 成员。
    - Any 成员的几何**两边各并一份**（同一来源 unit 被两次合并读取，`SectionalUnitMerger` 只读来源，不冲突）。
- 同一体型、同一部位仍然只能有一个来源 unit，否则照旧「不支持」（原因写明哪个部位、哪个体型）。认不出部位照旧「不支持」。
- 某一体型在这个槽里**一个专属成员都没有**（例如只有苗条胸，没有壮实胸）：那一体型的压缩 unit 只由 Any 成员组成；连 Any 成员都没有就不生成那一体型的 unit；映射与注册件都用另一体型的那个顶上（§13.4、§13.6 Q2）。
- 埃吉尔 3 槽的结果：头（Any，`0001`）；躯干·壮实（`0003` + `0004` + `0009` + `000a`）；躯干·苗条（`0002` + `0004` + `0009` + `000a`）；手臂·壮实（`0006` + `0008`）；手臂·苗条（`0005` + `0007`）。共 5 个 unit。

### 13.3 ID、注册件、layout

- **ID**：拆开的槽，每个体型的压缩 unit 取「该体型的第一个**专属**成员」的来源 ID（部位顺序沿用 §10.4）；该体型没有专属成员时取第一个 Any 成员。这样两个体型的 ID 一定不同（专属成员各是各的 unit），重编稳定。没拆的槽规则不变。
- **注册件**（`custom-model.json` / 协议 `model_piece`）：拆开的槽写两条，`body` 分别是 0（健壮）和 1（纤细），各指自己的压缩 unit；没拆的槽和现在一样；某体型没有自己的压缩 unit 时，那一条指另一体型的。
- **layout**：`units[]` 每项加 `"body": "any" | "stocky" | "slim"`（没拆的槽写 `any`）。schema 升到 `hd2mod.low-pollution-layout/2`；读取器同时认 `/1`（没有 `body` 一律按 `any`）。`LowPollutionLayout.UnitOf(role)` 改成 `UnitOf(role, body)`：先找该体型的，再退到 `any`。
- **sections.json（生效层）**：身份取 ID 所有者那条来源（含它的体型），与现在一致。

### 13.4 映射（S3 规划器）

`LowPollutionMappingPlanner` 本来就按体型挑承载件（`bodies` 0/1，每种身形一个躯干承载件、一个手臂承载件）。改动只有：

- 体型 b 的承载件链到 `UnitOf(role, b)`（b=0 → 壮实压缩 unit，b=1 → 苗条压缩 unit），而不是同一个 unit。
- 某体型没有对应压缩 unit（§13.2 最后一点）：**用另一体型的压缩 unit 顶上**（用户 2026-11-14 定，§13.6 Q2），`UnitOf(role, b)` 的退回顺序因此是「该体型 → any → 另一体型」；结果 `Notes` 写明「壮实体型没有自己的 X 模型，用苗条的顶上，可能穿模」。
- **一个承载件同时承载两种体型**（承载件是 Any 部件，raw 3）而模型这个槽是拆开的：一个承载件只能链到一个 unit，**这个目标在低污染模式下不可**（用户 2026-11-14 定，§13.6 Q1），原因写「X 的通用部件两种体型共用，模型的 Y 分壮实 / 苗条两份，没法同时放下」，不写任何映射行、不做半套。挑承载件时先优先找每个体型各自的专属承载件（现有排序之前加一条「体型专属的优先」），只有找不到时才会走到这里（真实索引里只有 SC-34、PH-9 的手臂槽）。两个体型若都只剩同一个承载件、且模型这个槽**没拆**（Any），照旧链到那一个 Any unit，不受影响。
- Hider 规则：隐藏集口径不变。`UnitSignature`（备用签名）改成该目标用到的**全部**躯干压缩 unit（拆开时两个）。规则数不变（还是每目标两套签名）。

### 13.5 已有产物怎么过渡

- 关闭低污染模式时的行为不变。

### 14.4 定半径：藏住的部件离锚点多远（Hider 0.4.2）

### 14.5 一整局的距离数据：大距离来自锚点滞后，不是模型偏移

- 0.4.2 一整局：飞船上（每轮约 3000 unit，扫一轮约 0.2 秒）藏住的部件离锚点 **≤ 0.06 米**（只有一次 0.51）。任务里（约 1.9 万 unit，扫一轮约 1.2 秒 + 0.5 秒间隔）分布散到 0.2–1.0 米，`hidden_max_d` 多次贴着上限 0.99–1.00；同一时刻整套部件的距离几乎一样（例如 8 个 ID 都是 0.99）。
- 解读：部件本身就贴着锚点（飞船上的 0.06 米），任务里的距离是**锚点位置用的是上一轮扫描**造成的——人在跑，一轮 1.2 秒前的位置已经差出去一米左右。`misses` 里 `markers=1` 时同一套部件在 1.85–5.8 米，也多半是自己跑动中已藏好的部件被重复统计（藏了不会恢复，所以看不出问题）。
- 风险：Hider 藏了就不恢复。半径 1 米时，贴身经过、穿着共用部件原版的队友会被**永久**藏掉那几个部件（直到重生）。半径越大越容易发生；只是把半径收小，跑动时又会藏得更慢。
- 建议（待用户拍板）：锚点在本轮被再次扫到时就地刷新位置（只用已有 API，不跨帧保存 unit 句柄），把滞后从一轮降到接近 0；然后把 `LowPollutionHiderRules.Radius` 收到 0.3。

## 17. 「身体+手臂」合体 unit（2026-11-14）

**目标**：躯干外只有一个独有部件的护甲也能整套映射：身体和手臂合成一个 unit，挂在那一个独有部件上。

**压缩（S2）**：
- 新角色 `body-arms`（`SectionalCompressionRole.BodyArms`）。素体同时有身体槽（`body` 或 `head-body`）和手臂槽时，**额外**生成一个合体 unit：成员 = 身体槽的全部部位 + 手臂槽的全部部位（2 槽时含头，即 head-body + arms）。原有的 body / head-body / arms unit 一个不少，现有映射不受影响。
- 按体型拆开的素体：合体 unit 也按体型各一个（与现有拆分规则一致，Any 成员两边各并一份）。
- unit ID 不能复用来源 ID（已被身体槽占用），改为派生：`SHA256("hd2mod.low-pollution.body-arms:" + 身体槽 ID 所有者的来源 ID)` 的前 8 字节，16 位小写 hex。同一来源重编结果不变。
- 布局文件多一项 `role = "body-arms"`；schema 不变（/1 或 /2 照旧，读取器本来就接受任意角色名）。
- 素体注册表（生效层 `custom-model.json`）**不登记**合体 unit：它只经映射行用到，不是素体自己穿的部件。
- 几何合并照旧走 `SectionalUnitMerger`（读同一份烘好的来源副本，与身体槽的合并互不影响）。

**需要重编的判断**：已压缩的素体布局里没有 `body-arms`（有身体槽和手臂槽时）⇒ 视为过期，原因「布局里缺『身体+手臂』合体 unit（新版低污染需要），重新压缩一次」。映射页「应用」会照现有流程自动重编；合体 unit 要部署进游戏后才能映射（现有「未部署」检查覆盖它）。

**规划器（S3）**：手臂槽找不到承载件时，新增一步，放在借头盔（§11.9 Q1 第 ② 步）之前：
- 条件：该体型的身体承载件**不在躯干槽**（即 §16 退回到了别的部件），且布局里有 `body-arms`。
- 做法：把这个承载件的映射从身体 unit 改成该体型的合体 unit，手臂就跟着身体一起显示。
- 身体承载件在躯干槽时**不用**合体 unit：第一人称下躯干被游戏隐藏，手臂会一起消失。这种情况照旧走借头盔 / 不可（用户 Q1 的决定不变）。
- 两个体型共用同一个通用承载件、而合体 unit 按体型拆开 ⇒ 放不下两份，整套不可（同 §13.6 Q1 的口径）。
- Hider：承载件签名不变；备用签名（压缩 unit ID）加上用到的合体 unit。
- 说明：「躯干外只有一个独有部件：身体和手臂合成一个 unit 挂在「X」上（第一人称下模型身体可能露出来）。」

**测试**：压缩规划器（3 槽 / 2 槽 / 分体都多出合体组，ID 派生稳定、不等于任何来源 ID，披风仍原样保留）；布局读写；注册表不含合体 unit；新鲜度判断（缺 body-arms ⇒ 要重编）；规划器（只剩一个独有部件 ⇒ 合体 unit；身体在躯干槽时不用；分体冲突 ⇒ 不可）；真数据重算 B-08。
