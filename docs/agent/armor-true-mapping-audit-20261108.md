# 真映射（改注册表）护甲值异常 —— 链路审计

日期：2026-11-08　　范围：只考察，未改任何代码。

样本：`tmp/regedit/plain.bin`（453 204 字节明文，422 个 LDLD 子数据块，来源为
`D:\SteamLibrary\...\data\game\generated_customization_armor_sets.dl_bin`），
用 `ArmorRegistryDataMapper.Compile` 实跑后逐字段对比。
复现工具：`E:\tmp\forgeprobe`（引用 HD2ModCore）；分析脚本 `E:\tmp\armor*.py`。

## 0. 一句话结论

真映射的写入器**不是"只改 unit id"**，它是"用来源的件表重建目标的件表"。重建过程中
每个新件的整条 112 字节记录都从**目标表里的某一个件**抄过来，而"抄哪一件"的规则是错的：
它按**来源件声明的身形**去找模板，不看**正在写的那一行**，最后一级回退是"同一身形行的
第一件"。而护甲套件的"任意身形(Any)"行第一件通常就是**披风**——披风有自己的护甲等级。
于是披风的 weight（= 轻/中/重）和整套材质引用被复制到躯干、盆骨、肩膀等部位上。

实测：素体映射场景下 **2938 个被写入的件里有 2198 个（75%）抄了别的槽位，其中 1694 个
（58%）抄的是披风**。轻甲(50 护甲值)会变成中甲(100)。

## 2. 文件结构实测（这次才真正读懂的部分）

```
明文 = u32 条目数 + 若干个 LDLD 块（每条 24 字节头 + payload）
LDLD 头：magic(4) / version(4) / type=0xd9a55aa0(4) / size(4) / platform(8)
```

422 块，全部是护甲自定义类型：

| kitType | 套数 | 每套件数 | body 行 | 槽位 |
|---|---|---|---|---|
| 0 护甲 | 138 | 15–29 | **3 行**（bodyType 0/1/3） | 2..9 + 披风 1 |
| 1 头盔 | 161 | 1（2 套 2 件） | 1 行（3） | 0（2 套另有 0/2 与 1） |
| 2 披风 | 123 | 1 | 1 行（3） | 1 |

**bodyType 是 0 / 1 / 3**（0=Slim，1=Stocky，3=Any），不是 1/2/3。

### 2.1 kit payload

```
+0   u32 id            +24 u32 rarity
+4   u32 dlcId         +28 u32 passive（护甲被动，额外加减护甲的那个"额外字段"）
+8   u32 setId         +32 u64 archiveHash
+12  u32 nameUpper     +40 u32 kitType
+16  u32 nameCased     +48 i64 bodyOffset（422 套全部 = 64）
+20  u32 description   +56 i64 bodyCount
+44..47 未解码
```

body 行 24 字节：`+0 bodyType`、`+8 i64 pieceOffset`、`+16 i64 pieceCount`、`+20..23` 未解码。

### 2.2 件记录 112 字节

```
+0   u64 unit id           ← 映射真正要换的
+8   u32 slot
+12  u32 pieceType（层 0/1/2）
+16  u32 weight（轻/中/重 → 50/100/150 护甲值的基准）
+20..23 未解码
+24..80  8 个 u64 资源哈希（MaterialLut / PatternLut / CapeLut / CapeGradient /
        CapeNac / DecalScalarFields / BaseData / DecalSheet）
+88  u8 tone
+89..95   全 3527 件恒为 0            ← 真自由
+96..103  i64 偏移 ┐ 指向 payload 内第二张表
+104      u8 条目数 ┘ （实测恒为 4）
+105..111 恒为 0                       ← 真自由
```

### 2.3 **`+96..103` 不是"未解码的保留区"** —— 它在 6 套里有真实数据

3 套护甲（`0x0b2045c7` / `0x983c1ac3` / `0xa2441063`，passive=42）和它们各自的头盔，
每件都带 `+96 = payload 内偏移`、`+104 = 4`，指向 **4 × 16 字节的条目表**：

```
@偏移  u64 类型(=3/4/2/5 固定) + u64 hash  ×4
```

验证：`0x0b2045c7` 15 个不同偏移、步长 64；第二张表合计 15×64 = 960 字节 = 该套 payload
的盈余字节数。`0x983c1ac3` 24×64=1536，`0xa2441063` 22×64=1408，三个头盔各 1×64=64。
**全部精确相等。**

而且这些表是**穿插在件数组之间**的，不是简单坠在末尾：`0x0b2045c7` 的记录里只有 384 字节
落在"件数组之后"，576 字节落在件数组区间内部。也就是说该套 payload 的布局是
`header / bodies / 件数组 / 条目表 / 件数组 / 条目表 / …`，**不是连续的**。

这一条直接推翻了 `ArmorRegistryDataMapper.cs:229` 那句注释"bodyOffset 恒为 64，第一个件数组
紧接在 body 数组之后——这是游戏自己的排布"。

### 2.4 重量分布：48/422 套的件不共享同一个 weight

披风件（装甲套件里 slot 1 那条占位）经常是**另一个等级**：

```
kit 0x0b2045c7（轻甲）：b0/b1 全部 weight=0，Any 行里披风 weight=1
kit 0x1773940042（重甲）：躯干/盆骨/腿/肩 weight=2，手臂与披风 weight=1
```

`(slot, weight)` 全库计数：`(1,0)=133 (1,1)=103 (1,2)=27` —— 披风自己的等级和本体无关。

## 3. 缺陷清单（按严重度）

### D1 `FindTemplate` 按「来源件的身形」找模板，不按「正在写的那一行」　★★★

`ArmorRegistryDataMapper.cs:209-225`

```csharp
foreach (var piece in target.Pieces)
{
    if (piece.BodyType != sourcePiece.BodyType) continue;   // ← 问题在这
    sameBody ??= piece;                                     //   行内第一件
    if (piece.Slot != sourcePiece.Slot) continue;
    sameSlot ??= piece;
    if (piece.PieceType != sourcePiece.PieceType) continue;
    exact = piece;
}
return exact ?? sameSlot ?? sameBody;
```

`CloneKit` 是**按目标行**逐行写的（`:258` `for b in target.Bodies`），并且把来源里
`BodyType == 3`（Any）的件**展开进每一行**（`:262`）。但 `FindTemplate` 拿到的是
`sourcePiece`，于是永远去目标表的 **bodyType==3 那一行**找模板——不管当前写的是
第 0 行还是第 1 行。

Any 行通常是**残缺的**（只有腿、手臂、披风），于是：

* `exact` 命中不了躯干/盆骨/肩 → `sameSlot` 也命中不了 → 回退 `sameBody` = **Any 行第一件**；
* Any 行第一件实测就是**披风（slot 1）**。

**实测（把 138 套护甲全部映射到同一个素体件表）**：被写入的 2938 个件里

| 模板来源 | 件数 |
|---|---|
| 同一行、同槽同层（正确） | 938（32%） |
| 同一行、别的槽位/层 | 897 |
| **别的 body 行** | **1902（65%）** |
| 找不到（只可能是被 D2 改写坏了那一件） | 1 |
| **合计"抄了别的槽位"** | **2198（75%）** |
| 其中抄的是**披风** | **1694（58%）** |

**实测（138 套护甲全部映射到同一套游戏护甲）**：exact 3429（63%）、同行别槽 1121、
跨行 831、抄披风 48。

### D2 后果：护甲等级被改

抄模板抄的是**整条 112 字节**，于是 `+16 weight`、`+24..80` 八个资源哈希、`+88 tone`、
`+96` 条目表指针全部跟着搬。

具体可复现的一例（`0xb92e1781`，轻甲）：

```
原始   body0: s2pt0=0 s2pt1=0 s3pt0=0 s3pt1=0 s6pt1=0 s7pt1=0 s8pt0=0 s9pt0=0
       body1: 同上
       body3(Any): s1pt0=1(披风) s4pt0/1=0 s5pt0/1=0 s6pt0=0 s7pt0=0
映射到素体后
       body0: s2pt0=1 s3pt0=1 s4pt0=0 s5pt0=0 s6pt0=0 s7pt0=0 s8pt0=1 s9pt0=1
       body1: 同上
       body3(Any): 同 body0 + s1pt0=1
```

躯干、盆骨、双肩的 weight 从 0 变成 1 = **轻甲 50 → 中甲 100**，而且材质 LUT 全换成了
披风的。这就是"护甲值异常"的直接原因，也解释了为什么是"有时候"——取决于目标套件的
Any 行有没有该槽位、以及 Any 行第一件是谁。

全库统计（素体场景）：**138/138 套出现 weight 漂移**；游戏护甲场景只有个别槽位漂移
（因为来源带着完整的三行件表，`exact` 命中率高）。

### D3 校验和伪造写进了 `+96..99`（确定性，每次都发生）　★★

`ArmorRegistryDataMapper.cs:356-367` + `Skill: PieceFreeStart = 89`（`:45`）

```csharp
var freeStart = piece.Offset + PieceFreeStart;      // +89
var slot = (freeStart + 7) / 8 * 8;                 // 8 字节对齐
```

件偏移恒满足 `piece.Offset ≡ 4 (mod 8)`（前缀 4 + 块头 24 + header 64 + 24×bodyCount，都是
8 的倍数），所以 `freeStart ≡ 5 (mod 8)`，对齐后落点是 **`piece.Offset + 92`**，写 8 字节 =
`+92..99`。其中 `+92..95` 确实是自由区，**`+96..99` 是第二张表偏移的低 4 字节**。

实测（三个产物文件，`kit 0x1f9bfa78` 的第 0 件）：

```
原始     tail=00000000 000000 ffffffffffffffff 0000000000000000   +96 = -1
allgame  tail=000000b4 f5122538 4bad4cffffffffff 00000000         +96 = -3008541896
allmodel tail=0000000d 9e7255ae 1d6bc9ffffffffff 00000000         +96 = -915726930
```

每次应用都会把**文件里第一套护甲第一件**的 `+89..99` 写脏 6 个字节。当前它恰好落在一件
`+96 = -1`（无第二张表）的件上，负数大概率被游戏当"没有"忽略，所以还没炸；一旦某次更新
让第一件带上真实偏移，就会写坏一张真表。

> 注：`HD2RuntimeArmorOverride/notes/content-checksum-forged-20261025.md` 里那次"改了 9 个
> 字节、游戏能进"的 A/B 只验证了**能启动**，没有验证护甲值；它改的正是 `0xfd` 与
> `0x100..0x107`（= `piece+89` 与 `piece+92..99`），也就是这次发现的同一个位置。

### D4 重建 payload 会删掉第二张表　★★

`CloneKit` 的假设是 `payload = header + bodies + 连续件数组`（`:308`），实测 413/422 套成立，
**9 套不成立**（盈余 64 / 960 / 1408 / 1536 字节，或件数组之间有 576 / 896 / 960 字节的洞）。

映射这 9 套中的护甲套件时，重建把第二张表整段丢掉，而每件的 `+96` 仍然写着旧偏移：

```
0x0b2045c7  payload 盈余 960  → 0
0xa2441063  payload 盈余 1408 → 0   （+96 仍为 920..4056，全部变成悬空偏移）
0x983c1ac3 / 三个头盔    盈余 64 / 1536 保留（这批不是本次映射目标）
```

### D5 多层被压平（"替换"语义的必然结果，但值得确认）　★★

素体件表每槽只有 1 件，重建后每一行每个槽位只剩 1 件：

```
0xdae4a744  25 → 25 件，但丢了 14 条、加了 14 条
138 套合计：丢 1565 条原有件
```

即躯干的 `pt0/pt1/pt2` 三层被压成一层。若游戏里"外层/内层"靠层号区分，这会让内层
（undergarment）或外层（armor plate）之一消失。这不是 bug 判定，是行为判定——需要确认
"素体映射"是否本来就该把护甲压成单层。

### D6 `applied` 计数虚报 + 无谓写盘　★

`CloneKit` 在"一个件都给不出来"时返回原样副本（`:300-305`），但 `Compile` 仍然 `applied++`
（`:495`）。于是"拿头盔当来源去映射护甲"会显示"已应用 1 条"，实际一个字节都没变，
`Changed` 仍为 true，还会顺手把同一个文件写一遍。

### D7 测试结构性失明　★

`ArmorRegistryDataMapperTests.cs` 的夹具（`:27-58`）每套 kit **只有一个 body 行**、
每个槽位一件，且 `+96..102` 硬写 `0xFF` 并注释成"容器忽略的哨兵"（`:36-37`）。

于是：

* 只有一个 body 行 ⇒ `FindTemplate` 的 body 过滤永远命中，D1 不可能暴露；
* 没有第二张表 ⇒ D3/D4 不可能暴露；
* 单层 ⇒ D5 不可能暴露。

`Apply_KeepsTargetArmorRatingWeight`（`:283`）是本轮最该抓住这个 bug 的用例，但它跑在
单行夹具上，永远绿。

## 4. 修复方向（三选一，需要拍板）

### 方案 A：只改 unit id，结构一个字节不动（最小、最健壮）

对每一行、每个槽位、每一层：在来源里找同 `(slot, pieceType)` 的件（`BodyType==3` 视作通配，
同身形优先），把它的 `unit` 写到**目标原有的那件**的 `+0`。件数、顺序、weight、资源哈希、
tone、`+96` 表、盈余字节全部原样保留。代价：

* 目标有、来源没有的件怎么办？三条子路：
  * A1 保持原样（会露出旧护甲 = 缝合怪）
  * A2 写**隐藏 unit**（`WardrobeHiddenUnitTemplate` / `CanonicalHiddenUnitBuilder`，项目里
    已经有 3 顶点占位件）→ 该件变不可见，结构不变；
  * A3 不处理，只报"这几层没有来源件"给用户。
* 目标没有、来源有的件：**不新增**（新增就必须借元数据，D1/D2 的根）。需要新增的部位
  只能靠"该套护甲本来就有这个槽位"来覆盖；实测护甲套件覆盖 2..9 + 披风，素体 8 个部位
  全在范围内，所以这条约束基本不咬人。

优点：完全不需要伪造之外的任何重建逻辑，D1/D4/D5 一次性消失，`+96` 偏移永不失效。
缺点：需要先决定 A1/A2/A3。

### 方案 B：保留重建，但把模板规则和盈余搬对

* `FindTemplate` 改成按**正在写的行**找：同 `(body, slot, pieceType)` → 同 `(slot, pieceType)`
  任意行 → 同 `(body, slot)` 任意层 → 该行同槽位 → **绝不跨槽位**（披风永远当不了供体）。
* 无供体时不要写全零记录，按 A2 写隐藏 unit 或跳过该件。
* 重建后把 `[header+bodies+件数组]` 之外的所有字节按原相对顺序搬过去，并把每件 `+96`
  偏移按位移量重算。

优点：保留"替换"语义，能去掉目标多余层。
缺点：偏移重算 + 穿插布局处理，比 A 复杂得多，也更容易在下次更新时再踩坑。

### 方案 C：先把伪造挪出数据区（与 A/B 正交，必须做）

`TryForge` 不能再用 `+89..111` 那一带。可行落点：

* **给最后一条 LDLD 块的 payload 追加 8（对齐后 16）个零字节并改它的 size 字段**。
  已实测 9 套的 payload 带盈余字节时游戏正常，说明块尾多余字节不被读；
  `+104` 那条规则也表明 payload 尾部可以是表。追加后按原内容哈希闭式求解。
* 备选：`LDLD` 头的 platform 字段只有 7 个自由字节（56 位 < 64 位，单独无解，已有实测）；
  件记录 `+89..95` 与 `+105..111` 各 7 字节，都不够一格。

### 推荐的组合

**A（+A2 隐藏占位）+ C**。理由与上一轮 sectional 编译层同一条：只做"换 id"这一件事，
其余字节一律不碰；凡是要"消失"的东西用已有的隐藏 unit 表达，而不是重排数据结构。

> **→ 最终落地的口径见 §7（2026-11-08 已实现）。** 隐藏改用 `unit = 0`，不用隐藏占位 unit；
> 伪造改到 payload 末尾追加的字，不再借用件记录里任何字节。

## 6. 补充（同日，读完旧软映射链路之后）

### 6.1 旧链路本来就把这件事做对过

`HD2RuntimeArmorOverride/src/armor_registry_composition.lua` 的 `C.plan` 有两条分支，
其中 **`existing_only`（第 47–108 行）就是"只换 unit"**：

```lua
按 (body, slot, piece_type) 把来源 unit 分组成队列
逐行、逐件遍历目标：
    queue = grouped[目标行.body, slot, kind]
    if not queue and 目标行.body ~= 3 then queue = grouped[3, slot, kind] end   -- Any 兜底
    candidate = 从 queue 弹一个（一件只消费一次）
    candidate ? 只替换该件 +0 的 unit : 保留原件
```

同一文件 `full` 分支（第 109–241 行）才是"重建"：改件数、改顺序、注入新件、
`resolve_weight` 从元数据恢复 weight、把 tone 写进件、处理 20 件预算与行序。

`notes/armor-mapping-boundary-20261023.md` §5 已经把两者的能力差别列成表，并写下
"新链路不是退化版，而是旧实现里那个本来就更安全的模式被单独留下来"。

**所以现在的 C# `CloneKit` 是把 `full` 分支硬移植了过来，还在三处比 Lua 版更差：**

| | 旧 Lua `full` | 现在 C# `CloneKit` |
|---|---|---|
| 模板取哪一件 | `by_position[目标行.body:slot:kind]`——**目标自己的位置** | 按 `sourcePiece.BodyType` 过滤的槽位/同形行回退（D1） |
| 无模板时 | `string.rep('\0', 96)` 全零记录 | `new byte[112]` 全零记录（同） |
| weight 从哪来 | `resolve_weight(weights, 目标行.body, slot, kind)`：exact → 该 body 的多数 → 全局多数 | 抄模板那条记录的 `+16`（D2） |
| 行序 | `rank={[3]=1,[0]=2,[1]=3}` 强制 Any 在前 | 保持原顺序（原生本来就 3/0/1，等价） |
| 件序 | 保持 | `chosen.OrderBy(Slot).ThenBy(PieceType)`，披风追加到行尾 |

### 6.2 新增 D8：Any 行被重复展开 → 撞 20 件硬上限

`CloneKit` 把 `BodyType == 3`（Any）的来源件**展开进每一行**（`:262`），同时 Any 行自己
也保留一份。于是同一格在 Any 行和各身形行**同时存在**，原生消费者按
`row.body == 当前身形 || row.body == 3` 收集时会把它算两遍。

原生消费者（`game.dll+0x81f470`）的预算是**每个 (kit, 身形) 20 件**，第 21 件起
`cmp ..., 0x14; jae` 静默丢弃；而行序是 **Any 在前**（原生 137/138 套确实是
`(3, 0, 1)`），所以先花预算的是 Any 行，被挤掉的是**身形专属的身体件**——身体部件直接不渲染。

实测：

| 场景 | 每 (kit, 身形) 最大生效件数 | 超 20 的组合 |
|---|---|---|
| 原生 | 20（恰好 1 套顶到 20） | 0 |
| 138 套 → 同一套游戏护甲 | **22** | **274 个 (kit, 身形)** |
| 138 套 → 同一素体 | 17 | 0 |

(`0x1f9bfa78`：16 → 22；`0x69bc2d4a`：15 → 22)

### 6.3 新增 D9：破掉「Any 与身形行互斥」这条不变量

原生数据里同一 `(kit, slot, pieceType)` 上 Any 与 Stocky/Slim 共存次数 = **0**（138/138）。
映射之后的实测：

```
kit=0x1f9bfa78   body0 ∩ Any = [(4,0),(4,1),(5,0),(5,1),(6,0),(7,0)]   ← 6 格
                 body1 ∩ Any = 同上
```

写出来的文件不再具备任何原生文件都有的结构性质。是否被引擎容忍未知，但至少意味着
同一个 `(身形, 槽, bank)` 会拿到两个句柄——按 `bank = pt0→A / pt1→B / pt≥2→C` 的规则，
它们会在同一个 bank 容器里互相覆盖。

### 6.4 旧文档给出的三条硬事实（本轮据此修正判断）

1. **每个部位每个身形最多 3 个 unit**：`ArmorStructure.UnitSlotsPerRegion = 3`、
   `MaxPieceType = 2`；内存侧 `max_pieces_per_body_slot = 3`、`observed_piece_types = 0,1,2`。
   但**消费者只有 3 个 bank**：`bank = 0 if pt==0, 1 if pt==1, else 2` —— 即 **pt=2 与
   任何 ≥2 的层共用一个通道**，同通道里"最后写入者赢"。所以"第 3 层"不是一个独立通道。
2. **行序 Any 在前**：原生 137/138 套是 `(3, 0, 1)`（另 1 套是 `(1, 0, 3)`）；20 件预算
   按行序遍历，所以 Any 先吃预算。
3. **清场只清槽 1..9**（`r14d = 9`、首偏移 `+4`），槽 0 头盔不参与——与"护甲与头盔是
   两套装备"一致。

### 6.5 `ArmorStructure.cs` 顶部有两处记载需要更正

* 第 80 行：`+89..111 保留 23 字节，恒为 7×00 7×FF 9×00（从未使用，可安全借用）`。
  实际主模式是 **7×00、8×FF、8×00**（23 字节），其中 `+96..103` 是整个 8 字节
  `0xFFFFFFFFFFFFFFFF`（= "没有第二张表"的哨兵），`+104` 是条目数（0 或 4）。
  **把 FF 的个数数错成 7，正好把"96..103 是一个 int64"这件事藏住了**，也是 D3 敢往那里
  伪造的直接原因。6 套里这 8 字节是真实偏移。
* 第 82–85 行 weight："具体语义未确认"。口径已确认：**0/1/2 = 轻/中/重**，
  基准护甲值 50 / 100 / 150（轻甲移速 550、中甲 500、重甲 450），
  部分护甲另有额外加减护甲的字段（`passive`，见 §2.1 `+28`）。
  另：实测 48/422 套的件不共享同一个 weight，最常见的是**披风件等级与本体不同**。

## 7. 最终实现（2026-11-08）

### 7.1 一句话

`ArmorRegistryDataMapper.Compile` 现在**只写件记录第 0 字节起那 8 个 unit**，
其余 104 字节、件数、件序、payload 布局、文件结构，一个字节都不动。

```
for 目标套件的每一格 (身形行, 槽位, 层):
    unit = 来源同格 → 共用(Any)格 → (目标是共用行时)来源按身形拆的件 → 否则 0
    写 piece+0 = unit
```

### 7.2 格子取值顺序（`ResolveUnit`）

| 顺序 | 条件 | 结果 |
|---|---|---|
| ① | 来源有 `(该行身形, 槽, 层)` | 用它的 unit |
| ② | 来源有 `(Any=3, 槽, 层)` | 用它的 unit（Any 是"两身形共用"，原生常态） |
| ③ | 目标这行**就是** Any 行，且来源只有按身形拆的件 | 两份相同 → 用；只声明一份 → 用；两份不同 → **0**（共用格表达不了两份网格） |
| ④ | 以上都没有 | **0**（隐藏） |

④ 就是"未覆盖一律写 0"。它在素体场景下覆盖了披风格、护甲板层、装饰层等所有来源不提供的部位。

### 7.3 为什么写 0 而不是删记录

| | 结构 | 第二张表 | 20 件预算 |
|---|---|---|---|
| **写 0**（采用） | 不变 | 指针不动 | 不变 |
| 删记录 | 变 → 必须重排数组 | 必须搬移重算 | 件数变动 |

写 0 也是游戏自己的写法：123 套披风套件里有 **118 套**的披风格就是 `unit = 0`，记录照样留着。

### 7.4 校验和伪造：挪到 payload 末尾

件记录里没有连续 8 个自由字节（`+89..95` 与 `+105..111` 各 7 字节，中间 `+96..104` 是第二张表）。
现在的做法：**给最后一条 subdata 块的 payload 追加 `pad + 8` 字节**（`pad` 让那个 8 字节字在文件里
8 字节对齐），同步改块头的 `size` 字段，然后闭式求解那一个字。

- 原生文件里本来就有 9 套 payload 带 64 / 960 / 1408 / 1536 字节的多余数据，游戏正常 ⇒
  payload 末尾多余字节不被读，这条做法有实测支撑。
- 实测产物：453 204 → 453 216 字节（`pad = 4`），`HashContent` 与原件逐位相同。
- 若某天末尾出现无法解析的多余数据，直接抛 `InvalidDataException` 放弃写入，不做猜测。

### 7.5 真数据实测（138 套护甲全部映射）

| | 素体来源 | 游戏护甲来源 |
|---|---|---|
| 结构（格子/件数/顺序）被改的套件 | **0** | **0** |
| unit 之外被改的套件 | **0** | **0** |
| 每 (kit, 身形) 超 20 件的组合 | **0**（原生也是 0） | **0** |
| Any 与身形行共存的格子 | **0**（原生 0） | **0** |
| `HashContent` 与原件相同 | 是 | 是 |
| 改动格子 | 3239（换 1536 / 隐藏 1703） | 3111（换 3030 / 隐藏 81） |

对比修复前：结构被改 420 套、unit 之外被改 137 套、超 20 预算 274 组、共存格子 6/套。

### 7.6 连带改动

* `GameDataAuthorityProvider`：**「件数比副本少 = 我们改过」这条判据失效了**（新编译不减件数）。
  换成真映射产物的唯一签名 —— **内容哈希等于原件、字节却不同**（伪造的必然结果）。
  件数判据保留作为第一道闸。
* `ArmorRegistryDataMappingResult` 增加 `Hidden` / `Replaced`，界面与命令行都会报出来
  （"真映射：12 条映射 · 换 1536 格 · 隐藏 1703 格"）。
