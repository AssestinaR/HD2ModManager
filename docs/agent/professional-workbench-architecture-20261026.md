## 1. 先把七条不变量钉死

这七条是后续所有设计的判据，任何实现与它们冲突就是实现错了。

| # | 不变量 |
|---|---|
| **I1** | 游戏目录里的护甲注册表**不再是权威事实**——管理器会改它。权威是备份 B。 |
| **I2** | 只有 **Steam 校验完成的那一瞬间**，游戏目录里的文件才是权威的。校验结束后，权威立刻回到 B（由 Steam 恢复件重建）。 |
| **I3** | 用户点「Steam 校验完整性」的**那一刻**，B 和游戏文件都视为不可信；只信 Steam 恢复出来的新文件。 |
| **I4** | 「某件护甲有哪些 unit」只问**管理器自己的 gamedata 缓存**，工具不许自己读注册表、更不许自己推。 |
| **I5** | 其他 archive（武器 / NPC / 载具）的 unit 事实当前**不完整**，需要补强。 |
| **I6** | 部件显示必须正确；详情用**树**，不用表格。 |
| **I7** | 功能可以合并、可以重做，但不能继续散落成"一个功能一个页面"。 |

### 1.1 I3 有一个现存缺陷，修法很明确

**现状**：点校验 → 直接 `steam://validate/553850` → 等完成 → 用恢复件重建 B。

**问题**：如果 B 是完好的，游戏文件被我们改过，Steam 会**重新下载整份注册表**。
对网络差的用户，这是一次完全不必要的下载，而且失败率高。

**修法**（在触发校验之前多做一步）：

```
1. 读 state，判断 B 是否可信：
     B 存在 && sha256(B) == state.pristineSha && state.buildId == 当前 manifest.buildId
2. 可信 → 用 B 覆盖游戏目录的注册表文件（逐字节还原官方原样）
   不可信 → 不覆盖（覆盖等于把未知内容写进游戏目录）
3. 触发 steam://validate/553850
4. 校验完成 → 以 Steam 恢复的文件为唯一真源，重建 B，写新 state
```

覆盖这一步只写**注册表这一个文件**，不碰别的。它把"我们改过"变成"官方原样"，
Steam 校验时发现哈希已经正确，就不会重下。

**顺带一个推论**：既然 B 可信时我们会主动写回官方文件，那么"刷新状态"这类按钮
**绝不能**触发这条路径——它只在用户明确点校验时执行。

## 2. 事实分层：谁读哪一层

现在最大的混乱是：**同一件事，不同代码从不同层读**。

```
L0  原始文件
    ├─ 游戏目录 generated_customization_armor_sets.dl_bin   ← 会被我们改，不可信
    └─ 备份 backup/...original.dl_bin (B)                   ← 权威（I1）

L1  管理器缓存  data/indexes/asset-index.sqlite
    ├─ archives / archive_entries        全量 3567 个 archive
    ├─ game_data_authority_kits          422 个 kit
    ├─ game_data_authority_pieces        3527 个件（四元组 + unit）
    ├─ game_data_unit_parts              16569 行 mesh 级部位事实（仅 armour/helmet）
    └─ game_data_stream_layouts          顶点布局（当前 0 行，见 §2.1）

L2  派生视图（内存 / 投影）
    ├─ 部署图（谁最终赢）
    ├─ 覆盖状态（这个 AssetKey 被谁改）
    └─ 护甲映射协议（armor-registry.protocol / wardrobe.links）
```

### 2.1 规矩

| 谁 | 只能读 |
|---|---|
| GUI / CLI 的一切工具 | **L1 与 L2** |
| 索引构建器（唯一例外） | L0 → 写 L1 |
| 部署器 | L1 + L2 → 写游戏目录的 Overwrite |

**违反这条的现有代码**：`ArmourUnitTableSource.ReadUnitIds` 每次从注册表快照取 unit 键。
它读的是 provider 已经解密好的快照（尚可），但它和 `game_data_authority_pieces` 是**两条路**，
一条从文件来、一条从缓存来，两者可能不一致。按 I4，应该只留缓存那条。

### 2.2 `game_data_stream_layouts` 是空的（已知缺陷）

上一轮实测：3233 个 armour/helmet unit 全部有部位事实，但 `game_data_stream_layouts` **0 行**。
`HasCompleteEquipmentFactsAsync` 要求这张表有行，所以 `gamedata index inspect` **永远报"缺失或过期"**。

这不是显示问题，是**状态撒谎**：用户和 agent 都被永久告知数据不全，而数据是全的。

## 3. 其他 archive 的 unit：差距有多大

| 指标 | 当前 |
|---|---:|
| archive 总数 | 3567 |
| 有部位事实的 archive | **298**（只有 armour + helmet） |
| 覆盖率 | **8.4%** |

也就是说：武器、NPC、载具、场景里的 unit，管理器**只知道它存在，不知道它是什么**。
mod 换了一把武器的模型，详情里只能看到 `0xe0a48d...:0x...`，没有任何部位/几何信息。

### 3.1 两级事实（建议）

| 层级 | 内容 | 范围 | 成本 |
|---|---|---|---|
| **轻量事实** | unit 存在、大小、版本、依赖、是否可见 | **全部 archive** | 低（已有 `archive_entries`） |
| **深度事实** | 几何、部位、section、材质绑定 | 按需 / 后台 | 高（要解析 Unit 二进制） |

规则：
- 打开某个 archive 的详情 → 只对该 archive 算深度事实（按需）
- 用户标记"常用"的 archive → 后台批量算
- 全局默认只保证 armour / helmet（因为映射功能只吃这些）

这样既补上 I5，又不会让索引时间爆炸。

## 4. 「右臂-内衣-健壮」为什么错

这个症状几乎可以确定是**层判定方向反了**：`pieceType == 1`（外层护甲）被判成 `Undergarment`。
上一轮 `2fe05ac` 已修（改成 `0 = 内层、1/2 = 护甲`）。

但要彻底正确，还需要两条：
1. **重建索引**（旧行还带着反的层）
2. **别用骨名覆盖 `CustomizationInfo`**（审计里的 N12，未修）——
   现在骨名会把 `g_torso_undergarment_slim` 拆成 `slot=g / piece=undergarment / body=slim`，
   覆盖掉游戏自带的正确字符串。

修完这两条，「部件」列才可信。不过按 I6，这一列所在的表格**本来就要换成树**。

## 5. 骨架：工作区 → 资源树 → 基层能力 → 向导 → 输出

这是"专业软件"和"一堆按钮"的根本区别。

```
┌─────────────┬──────────────────────────────────┬──────────────┐
│ 资源树       │ 检视器 / 作业面板                  │ 作业队列      │
│ (左)         │ (中)                              │ + 输出 (右)   │
└─────────────┴──────────────────────────────────┴──────────────┘
```

### 5.1 工作区（Workspace）

**一个工作区 = 一个目标 + 一组素材 + 一串作业。**

| 工作区类型 | 目标是什么 | 典型用途 |
|---|---|---|
| 游戏护甲工作区 | 一件护甲（armor kit + helmet kit） | 替换护甲、真映射、规整 |
| Mod 工作区 | 一个 Mod（或它的一个 Patch 家族） | 修复、重打包、材质、装饰来源 |
| Archive 工作区 | 一个 archive | 浏览、导出、诊断 |

**关键**：工作区是有状态的。选中的目标、展开的树节点、未提交的作业，都留在里面。
现在每点一个按钮就跳走、回来全忘——这是"不专业"的最大来源。

### 5.2 资源树（唯一导航）

```
工作区
├─ 游戏数据
│   └─ 护甲套（来自 L1 的 kit）
│       ├─ 头盔 archive
│       │   └─ unit · helmet_0_any
│       │       └─ mesh / section
│       └─ 身体 archive
│           ├─ unit · torso_0_slim   ← 四元组即节点身份
│           │   └─ mesh / section
│           └─ unit · torso_1_slim
├─ Mod 库
│   └─ Mod
│       └─ Patch 家族
│           └─ patch_0
│               └─ 条目 0xe0a48d…:0x…
│                   ├─ unit 结构
│                   ├─ 材质
│                   └─ 贴图
└─ 产物
    └─ <一次作业的输出>
```

**节点身份用四元组，不用 `SemanticName`**。名字只做显示，且只来自 `ArmorStructure`。

### 5.3 基层能力（原子操作）

每个都能独立预览、独立执行、独立回退。

| 能力 | 作用 | 现在叫什么 |
|---|---|---|
| 读结构 | 显示 unit 的骨骼/流/mesh/section/材质 | 「模型解析」「详情表格」 |
| 读部位 | 显示四元组与几何质量 | 散落在各页 |
| 重定向 unit | 让 A 引用 B 的 unit（不复制） | 替换护甲的内核 |
| 复制 unit | 把 unit 复制成新 ID | 转素体的内核 |
| 隐藏 unit | 把 unit 换成不可见占位 | `patch hide-unit` |
| 追加/替换 mesh | 把 mesh 拼进现有 unit | Canonical 重构的内核 |
| 搬运条目 | 把 AssetKey 从一个 patch 搬到另一个 | 资源重打包 |
| 改写注册表件 | 改 `unit/slot/piece_type` | 真映射 |
| 算哈希 | 内容校验和 / 指纹 | 各处 |
| 导出 | 把工作区状态物化成新目录 | 「生成」 |

**基层能力不做向导的事**：不选目标、不问输出目录、不自动导入。

### 5.4 向导（编排）

向导 = 固定顺序的基层能力 + 目标选择 UI + 预览。

| 向导 | 由哪些基层能力组成 |
|---|---|
| 替换护甲 | 读部位 → 重定向 unit（×N）→ 隐藏 unit（缺槽填充）→ 导出 |
| 转自定义素体 | 读部位 → **复制 unit** → 重定向 → 登记注册表 → 导出 |
| 装饰包 | 读部位 → 追加/替换 mesh 到主体 → 导出 |
| 头盔合并 | 装饰包的固定分支（来源=头盔 kit，目标=身体 kit 的 slot 0） |
| 规整护甲包 | 读部位 → 选出承载 unit → 补身形 → 导出 |
| 修复 patch | 读结构 → 追加/替换 mesh → 导出 |
| 材质打包 | 搬运条目 → 导出 |

### 5.5 作业与输出：把"途中"和"成品"分开

这是用户明确要求的。

| 状态 | 含义 | 落在哪 |
|---|---|---|
| **草稿** | 向导里填了一半 | 内存（工作区） |
| **预览** | 参数齐了，能算出影响面 | 内存，显示在检视器 |
| **已提交** | 加进工作区作业队列，**还没写盘** | 工作区 |
| **已导出** | 物化成新目录 | `Output/` |

**关键变化**：现在每个向导"点生成 = 立刻写目录"。
新模型里**生成 = 提交作业**，多个作业可以叠加，最后统一导出一次。

好处：
- 可以叠加（先规整、再替换、再挂装饰）
- 可以整体撤销（还没写盘）
- 输出位置只问一次

## 6. 四组合并（这是重做的核心）

### 6.1 装饰 + 头盔合并 = 「挂载」

两者都是"把某个 unit 挂到主体的某个部位/层"：

| | 来源 | 目标 | 差异 |
|---|---|---|---|
| 装饰 | 装饰 unit | 主体的某个 mesh 位置 | 挂多个、可开关 |
| 头盔合并 | 头盔 kit 的 unit | 身体 kit 的 torso | 固定分支、要生成隐藏头盔 |

**统一成一个「挂载」向导**，头盔合并是它的一个预设模板。
装饰页和头盔合并页合并成一页。

### 6.2 替换护甲 + 转素体 = 「重定向（可选复制）」

两者都是"让目标护甲的 unit 指向来源的 unit"，唯一差别是**要不要复制 unit**：

| | 复制 unit | 为什么 |
|---|---|---|
| 替换护甲 | ❌ 不复制 | 共享 unit，省 VRAM（这也是当初的硬约束） |
| 转素体 | ✅ 复制 | 隔离，避免一个 unit 被多件护甲共用导致污染 |

**统一成一个向导 + 一个「复制 unit（隔离污染）」开关。**
转素体 = 勾上这个开关 + 填个名字 + 登记注册表。

这直接解决了"护甲映射与素体连通性极差"：素体就是**来源选择器里的一个选项**，
而不是另一套流程。

### 6.3 规整护甲包 = 替换护甲的「来源前置检查」

制作者自己都忘了它干什么，这本身就是设计错误的证据。

它实际做的事：**让一个手工护甲 Mod 符合 7 区域 × 2 身形的结构**，
这样后续替换护甲时才能按四元组匹配。

所以它不该是独立功能，应该是替换护甲向导里的**第一步检查**：

```
选择来源护甲 → [检查结构]
   结构完整 → 直接进映射
   结构不完整 → "这个来源缺左肩的 Slim 身形，是否自动补齐？" → 自动规整
```

独立按钮消失，功能保留，且用户永远不会忘记它存在。

### 6.4 资源重打包 = 资源树上的操作

它现在是一个独立页面 + 4 个命令。新模型里它就是：

```
资源树里多选条目 → 右键「导出为新 Patch」
```

没有独立页面，没有 plan/validate/apply 三件套（那是给 CLI 的，GUI 不需要）。

## 9. 待你定的三件事

1. **工作区是"单目标"还是"多目标"？**
   单目标（一次只处理一件护甲/一个 Mod）更简单；多目标能一次批量替换但作业队列会复杂得多。
2. **作业队列要不要真的可叠加？**
   叠加很强大（先规整再替换再挂装饰），但"中间态"很难预览——用户看到的到底是哪一步的结果？
   保守做法是**同一时间只有一个作业**，提交即导出。
3. **「真映射」属于哪个工作区？**
   它改的是游戏注册表，不属于任何 Mod。是放在护甲工作区里，还是单独一个"游戏数据"工作区？
