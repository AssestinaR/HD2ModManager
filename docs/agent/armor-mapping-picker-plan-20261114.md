# 护甲映射页「可用护甲」列表重做（规划，2026-11-14）

相关：`kit-instance-mapping-deploy-plan-20261114.md` §8.4（单件与组合）、§8.3（J6）、§11（低污染映射）；
`kit-instance-multi-target-plan-20261114.md` §6.3（玩家版本的社区依据）。本文件取代 §8.4 第 1–3 点，属于 S4b。

## 1. 为什么要改（用户 2026-11-14）

映射页右侧「可用护甲」现在很难用（截图：开头一长串 `0x09a7c0da 头盔`、`0x2eec8681 头盔` ×7……）：

- 没名字的 `0x…` 记录、非玩家记录全列出来；
- 同名多条（B-01 ×9、FS-05 头盔 ×7）逐条重复；
- 「类型：自动组合」是一行循环切换的文字，几乎发现不了；
- 选了组合以后，组合里的头盔、护甲还能单独再选，反过来也一样，很容易配出重复或冲突的映射。

## 2. 用户要的（原话要点）

1. 只显示玩家护甲。神射手（FS-05）是特例，因为它有一条是民主官 NPC 穿的。
2. 去重。
3. 列表框最顶部加一条不随列表滚动的分类栏：**套装**（默认）/ **护甲** / **头盔**。
4. 联动：选了套装，它包含的头盔和护甲就要消失或不能选；先选了头盔或护甲，再去选别的，也要联动。

## 3. 数据：一行代表什么

### 3.1 玩家护甲 / 头盔的判定

- 有正式名字（`SectionalExclusivePlanner.IsNamed`：不以 `0x` 开头）。
- 不在非玩家表 `KitNonPlayerArmors` 里（FS-05 124623533 民主官 NPC、CM-09 2107035846、SC-30 1969314276）。
- 例外：FS-05 民主官那条照样显示，但单独成一行，标「民主官 NPC」（见 Q1）。
- **头盔也有依据**（用户指出，2026-11-14 核对）：P5 下载的两份资料本来就含头盔，只是当时只用了护甲那部分。
  - helldivers-2/json 的 `armor.json` 有头盔（slot 0，112 条）。按护甲同样的方法——同名多条里官方 Items API 漏掉的那条就是非玩家——得到 4 个候选非玩家头盔：CM-09 `0x4db09ca4`，SC-30 `0x782087b2`、`0x9b5bc520`，SC-34 `0x0542e6f1`。这几套都是 2025-02 之前的，漏掉有意义（和三条非玩家护甲同一口径）。实现时先对本地权威索引核对：这 4 个 ID 存在、是同名重复的那条，再加进非玩家表（护甲、头盔分开记）。
  - FS-05 的 7 个同名头盔都在 `armor.json` 里，都算玩家头盔。
  - OneClickArmorSet 的 `ocas.lua` 里有一张生成的套装表（MIT，`research/build_set_table.py` 生成，按 wiki 的战争债券 / 超级商店页面配对）：126 套，150 个头盔、128 个护甲，`[item id] = {套装名, h/b/c/p}`，多个副本共用的头盔写成 `{'*', 'h', {套装…}}`。它**不**区分能不能拿到（CM-09 的两件护甲都在同一套里，作者靠运行时「是否拥有」过滤），所以玩家判定仍用上一条，**套装配对**用这张表：比按 dlc_id / 同名猜准。表里没有的（之后游戏更新加的新护甲）退回现有的两轮配对。
  - 引用要保留出处和 MIT 授权说明；表放进仓库时按 `docs/.gitignore` 白名单规则处理，C# 侧生成一个只含 ID→套装名的数据文件。

### 3.2 去重

- 同名的多条玩家记录合成一行（例：B-01 九个版本 → 一行「B-01」）。
- 映射这一行 = 把这个名字下所有玩家版本都设为映射目标。理由：玩家实际拥有的是哪个副本不确定，只映射其中一个，可能正好不是玩家穿的那个。这和 P5「全选只选玩家版本、同名玩家版本全勾」是同一口径。
- 名字不同、几何相同的换色孪生不合并，仍是两行（它们是不同的护甲）。

### 3.3 套装怎么配

- 套装 = 一个护甲名 + 一个头盔名。配对优先用 OneClickArmorSet 的套装表（§3.1），表里没有的再按现有两轮配对（先注册表 `(dlc, set_id)`，再同 dlc 同名）。
- 现在规则是「恰好 1 护甲 + 1 头盔才配」，FS-05 这种 2 护甲 7 头盔就配不上而平铺。去重后按名字配：同名的玩家护甲组和玩家头盔组各算一份，就能配上。
- 没有配套头盔的护甲（以及没有配套护甲的头盔）不进「套装」，只在「护甲」或「头盔」里出现。
- 套装名：护甲名和头盔名相同时只写一次，加标签「头盔+护甲」；不同才两个都写（例：「DS-42 + DS-42 头盔名」）。

## 4. 界面

- 列表框内部最顶部一条固定栏（不随列表滚动）：`套装 · 护甲 · 头盔` 三个选项卡，默认「套装」，每个后面带数量。替换现在的「类型：自动组合」循环按钮。
- 「Unit 覆盖：全部」那个筛选和搜索框保留，在三个选项卡下都生效。
- 一行显示：图标、名字、类型标签；去重合并的行加「N 个版本」；FS-05 民主官那行加「民主官 NPC」。

## 5. 联动规则

把每一行看成它包含的**护甲记录集合 + 头盔记录集合**（套装 = 两者都有；护甲行只有护甲；头盔行只有头盔）。两行**冲突** = 它们包含同一条记录。

1. **已映射的**：某条记录已经是某个来源的映射目标（左侧列表 / 已管理），包含它的所有行都不能选。
   - 护甲或头盔行本来就不显示（现在已是「未管理护甲」口径）。
   - 套装行：两件都已映射 → 不显示；只有一件已映射 → 显示但置灰，原因写「护甲已映射到 X」或「头盔已映射到 X」（见 Q2）。
2. **当前选中的**（多选，还没加到左边）：和已选行冲突的行置灰、不能勾，悬停说明「已包含在所选套装 X 里」或「所选头盔 X 属于这个套装」。
   - 切换选项卡时，选择保留，联动在三个选项卡之间都生效。例：在「套装」选了 DP-8，切到「护甲」时 DP-8 护甲置灰；先在「头盔」选了 B-01 头盔，切到「套装」时 B-01 套装置灰。
   - 同一选项卡里，只要不冲突就可以多选（选几个不相干的套装、几个不相干的头盔，都可以）。
3. 置灰而不是隐藏：用户看得到「为什么这套没了」。是否改成隐藏，见 Q3。
4. **低污染模式**（§8.4 第 4 点）：开着、而且当前来源是压缩素体时，「头盔」行在 2 槽来源下置灰，原因「头已并进身体，单独映射头盔不可用」；`LowPollutionTargetReport` 标「不可」的目标，在行上标原因（S3 已经做了标注，这里沿用）。

## 6. 实现落点（S4b）

- 数据：在 `ArmorRegistryPageViewModel.BuildDisplayChoices` 那一层改成「玩家过滤 → 按名字去重 → 配套装」，产出带成员记录集合的行模型；判定函数复用 `SectionalExclusivePlanner.IsNamed`、`KitNonPlayerArmors`，不另写一套。
- 联动：行模型上加 `IsBlocked` 和 `BlockedReason`，选择变化、已管理集合变化、选项卡变化时重算（O(行数 × 成员数)，几百行没有压力）。
- 加到左侧：一行展开成它的全部成员记录（去重行 → 所有玩家版本；套装 → 护甲组 + 头盔组），写成多条映射；已有的「组合映射目标」显示沿用。
- 左侧「映射目标」列表也按同样规则合并显示（同一来源下 B-01 的 9 条映射显示成一行「B-01 · 9 个版本」），否则左边又会是一长串（见 Q4）。
- 测试：玩家过滤、去重、FS-05 配套、冲突判定、三个选项卡之间选择的联动、低污染置灰；真实索引上统计三个选项卡的行数写进本节。

## 8. 原始问题（已回答，留档）

- **Q1 FS-05 民主官那条**：用户说「神射手这种特例不算」。理解为：FS-05 民主官 NPC 的记录**照样显示**（可能有人想改民主官的样子），单独一行标「民主官 NPC」，不和玩家版 FS-05 合并、不进 FS-05 套装。对吗？另外两条拿不到的（CM-09、SC-30）不显示。

## 9. 实施方案与核实结论（2026-11-14）

### 9.1 4 个候选非玩家头盔的本地权威索引核对结论

对照 `HD2ModManager/bin/Release/net10.0-windows/data/indexes/asset-index.sqlite`（表 `game_data_authority_kits`）、`docs/agent/external/armor-sets/ocas.lua` 与 `helldivers2-json-armor.json`：

- `0x782087b2`（`2015397810`）与 `0x9b5bc520`（`2606482720`）：`ocas.lua` 中归属 `SC-30 Trailblazer Scout` 头盔；权威索引中存在，`kit_kind = 1`，`display_name = "0xd8bce5f1"`，`helldivers2-json-armor.json` 中缺失；而命名的 2 条 `SC-30“拓荒者侦察兵”` 头盔（`3606389079`、`4087059373`）均在 `armor.json` 中 → 将 `0x782087b2`、`0x9b5bc520` 一并记入 `KitNonPlayerArmors` 头盔表做双重兜底，2 条命名 `SC-30` 头盔按玩家版本合并为 1 行（`2 个版本`）。
- `0x0542e6f1`（`88270577`）：`ocas.lua` 中归属 `SC-34 Infiltrator` 头盔；权威索引中存在，`kit_kind = 1`，`display_name = "0x2eec8681"`，`helldivers2-json-armor.json` 中缺失 → 一并记入 `KitNonPlayerArmors` 头盔表。

### 9.2 真实权威索引三选项卡行数统计

基于本地 `asset-index.sqlite`（`kit_kind IN (0, 1)` 共 299 条 kit 记录）：

- **「套装」选项卡：116 行**
  - 116 个玩家护甲组与 118 个玩家头盔组中，111 套由 `OneClickArmorSetTable`（折叠 `(1)`..`(9)` 等变体编号后缀）直接配对，4 套新装备（`GS-11“民主代理人”`、`SS-500“苍白检察官”`、`SS-33“拟态元帅”`、`SS-15“焦点”`）由 `(dlc_id, set_id)` 配对，1 套（`DS-42“联邦之刃”`）由同 `dlc_id` 同名配对，合计 **116 套**；
  - 无配套护甲的 2 顶头盔（`IX-寂域行者`、`B-02阴霾守望者`）仅在「头盔」选项卡出现。
- **「护甲」选项卡：117 行**
  - `kit_kind = 0` 共 138 条 → 剔除 8 条 `0x...` 未命名 → 130 条命名 → 剔除 2 条隐藏非玩家护甲（CM-09 `2107035846`、SC-30 `1969314276`）→ 剩 128 条；
  - 其中 FS-05 民主官 NPC（`124623533`）单独成 1 行（标 `民主官 NPC`，不参与同名合并与套装配对），其余 127 条玩家护甲按名字合并为 **116** 行玩家护甲组 → 合计 **117 行**。
- **「头盔」选项卡：118 行**
  - `kit_kind = 1` 共 161 条 → 剔除 20 条 `0x...` 未命名 → 141 条命名 → 剔除 1 条非玩家头盔（CM-09 `0x4db09ca4` / `1303420068`）→ 剩 140 条玩家头盔；
  - 按名字合并为 **118 行**（`0x782087b2`、`0x9b5bc520`、`0x0542e6f1` 亦写入 `KitNonPlayerArmors` 头盔表协同排除）。
