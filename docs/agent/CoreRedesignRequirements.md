# Core 重做需求总结（讨论稿）

> 目标：从零重做核心（`Core`），并为后续 WinUI 3（Unpackaged）前端提供稳定、可测试的业务能力。
> 
> 本文仅总结需求与约定，不涉及现有旧代码实现。

## 1. 总体目标

1. 管理《绝地潜兵 2》（Helldivers 2）基于 `*.patch_n` 的模组。
2. 支持从压缩包/文件夹导入，自动将导入内容组织为“对象树”（目录树每个节点都是一个可管理对象）。
3. 通过扫描 patch 的 TOC 快速获得资产条目键（AssetKey），用于：
   - 冲突检测（基于资产键交集）。
   - 自动推导“此对象替换了哪些原版内容”（盔甲/武器等类别）。
4. 用户可使用“配置（Profile）”快速切换模组方案。切换应快速，避免占用大量磁盘：采用软链接（symlink）应用。
5. 以可携带为目标：应用生成的文件（索引、库、设置、日志、导入的模组对象内容等）均位于程序目录下的固定子目录中。

## 2. 基础术语与数据模型约定

### 2.1 Patch 文件与文件组

HD2 模组文件通常由 2~3 个文件组成：

- `{ArchiveHex16}.patch_{n}`
- `{ArchiveHex16}.patch_{n}.stream`（可选）
- `{ArchiveHex16}.patch_{n}.gpu_resources`（可选）

其中：
- `ArchiveHex16` 为 **16 位十六进制**字符串（严格）。
- `n` 为从 0 开始的十进制序号。
- 游戏按 `n` 顺序加载：后加载覆盖先加载。

Core 需提供严格解析器以识别：
- ArchiveHex16
- PatchIndex(n)
- SidecarKind（base/stream/gpu）

### 2.2 对象树（Mod Object Tree）

导入后并不将“压缩包根目录”视为单一模组对象，而是：
- **目录树的每一个目录节点**都是一个可管理对象（称为 Object/Node）。
- 一个节点对象可以包含多个 patch 文件组（多个 `patch_n` 组合）。
- 同一目录内若存在多个 patch 文件组，视为同一个对象节点。

导出时亦以“结构化对象组”进行导出，而不是将复杂结构塞进一个对象。

### 2.3 资产键（AssetKey）

冲突与自动标签的事实依据来自 patch TOC：

- `AssetKey = (TypeID, FileID)`，均为 `ulong`。
- 冲突检测使用 `AssetKey` 的交集。

说明：
- patch 文件名前缀 `ArchiveHex16` 常为 BaseArchive 容器（例如 `9ba626afa44a3aa3`），不能用于推导“替换了哪件盔甲/武器”。必须依赖资产键/索引推导。

## 3. 快速扫描 patch TOC（资产键提取）

### 3.1 目标

在不解包/不解析资源体的情况下，快速从 `.patch_n`（TOC 文件）扫描得到该 patch 所含资产键集合：

- 输入：`.patch_n` 文件路径
- 输出：`HashSet<AssetKey>`

### 3.2 参考实现依据

已验证 `HD2SDK-CommunityEdition` 采用 TOC entry 的 `(TypeID, FileID)` 作为资源键：
- `TocEntry.Serialize()` 读取 `FileID`、`TypeID` 为 `uint64`
- `SearchToc.FromFile()` 可在固定步长 entry 表中用 `<QQ` 读取键值

Core 在实现时不得直接依赖 Blender；仅复刻必要二进制解析逻辑。

## 4. 原版内容索引（推导“替换了哪些原版内容”）

### 4.1 索引的意义

由于大量 patch 归属 BaseArchive 容器，无法从文件名推导替换目标。

因此构建反向索引：
- `AssetKey -> ArchiveId候选集合`

应用到对象节点时：
- 对象的所有 patch 扫描得到 `AssetKeySet`
- 通过索引统计命中各 `ArchiveId` 的次数
- 得到该对象“可能替换的原版内容列表”（按命中排序）

### 4.2 扫描范围

- 扫描目录固定为游戏 `data` 目录。
- Archive 清单以实际安装的 GameData 为准；`archivehashes.json` 仅用于补充显示名称与分类，不能决定是否扫描某个实际存在的 Archive。

### 4.3 索引生成触发

- 若检测到索引文件不存在：应用启动后后台自动生成一次。
- 设置页提供“手动重建索引”按钮：
  - 可选地尝试从 GitHub 同步更新最新版 `archivehashes.json`。
  - 即使在线资料缺失或不可解析，也应允许使用 GameData 权威关系表建立索引。
  - 若同步失败或格式变更不可解析，则继续使用本地旧版文件。

### 4.4 后台生成与进度

- 索引生成应后台执行。
- 进度为 `current/total`（例如 30/150）。

### 4.5 共享资源过滤（降低噪声）

由于贴图/材质等共享资源可能出现在大量 archives 中，影响投票结果：

- 默认采用 **比例阈值** 过滤：出现于超过 `X%` 的 archives 的 `AssetKey` 可忽略。
- 设置中允许用户将阈值切换为：
  - 固定数量阈值 或
  - 百分比阈值
- 以便用户测试并最终确定更合适的默认值。

### 4.6 输出替换目标列表

- 默认显示 Top 5 替换目标（Archive/原版内容）。
- 其余候选在详情中折叠展示，但应可被搜索。

## 5. 友好名称与分类

### 5.1 资源键展示与搜索

- 冲突检测与内部计算使用 `AssetKey`。
- UI 展示时不显示纯 ID，尽可能用可读名称。

### 5.2 友好名称来源

计划支持多来源映射（不强耦合索引）：
- `friendlynames.txt`：`FileID -> name/path`（可能存在歧义，仅作辅助）
- `typehash.txt`：`TypeID(hex64) -> type name`
- `archivehashes.json`：`ArchiveId(hex) -> display name`（按分类，仅显示辅助）
- 安装目录中的 `generated_customization_armor_sets`：Armor / Helmet / Cape 与 Unit 的权威关系（索引身份与装备部位的首选来源）

未来可在管理器内提供窗口进行增补维护：
- 支持别名（aliases），用于搜索与俗称。

## 6. 导入与导出

### 6.1 导入来源

必须支持：
- 从文件夹导入（递归识别）
- 从压缩包导入：`zip` / `7z` / `rar`
- 支持多选导入

导入时按目录结构生成对象树，并解析/归并 patch 文件组。

### 6.2 导出

按结构化对象组导出（保持树结构），可生成规范 `manifest.json` 以兼容其他管理器。

## 7. 配置（Profile）、应用与软链接

- 支持多 Profile 快速切换。
- 应用到游戏目录时以软链接为主（不使用硬链接）。
- 软链接特征明显，切换时可先清理旧链接，再创建新链接。

## 8. 存储与落盘位置（便携式）

### 8.1 便携式原则

- 所有程序生成文件均位于程序目录下固定子目录，避免散落污染。
- 模组对象本体也在程序目录下（如 `mods/`）。

### 8.2 SQLite

- 索引与库信息可使用 SQLite 落盘。
- 选用 `Microsoft.Data.Sqlite`。
- 索引应与友好名称字典解耦：友好名称更新不要求重建索引。

## 9. 需要后续明确但已预留的点

- WinUI 3 前端采用 **Unpackaged** 形态以满足“程序目录可写/便携式”目标。
- 若未来需要更高准确度：可引入 `Type` 权重、TF-IDF 等更复杂评分；当前先以简单统计与阈值过滤为主。
