# 进任务后全员没物理：打分队列被队首饿死（2.1.28）

> 日期：2026-11-12　版本：运行时 2.1.27 → 2.1.28
> 现场：`%LOCALAPPDATA%\hd2physbone.log`（11:41:52 起的那一段，运行时 2.1.27）

## 0. 结论先说

**症状**：进舰船（基地）物理正常；进任务地图后**我和队友们都没有物理**，且再也不恢复。

**根因**：挂载前的"候选打分"是**每拍从头开始**的固定顺序循环，而每拍只允许打分
`scoreUnitsPerFrame`（默认 2）件。两次尝试的间隔（等待期 `pollFrames`=20，等久后 ×3 = 60 帧）
**比"重试门"（`negativeRetryFrames`=30 帧）长** ⇒ 排队首的那 2 件每一拍都能重新轮到、
把额度吃干，**后面的件永远轮不到**。

日志特征是一条数字一动不动的行，连续 8 分钟：

```
[physbone][等待] 装填中（本拍打分额度用完）：已打分 2 件、未轮到 15 件
```

（`未轮到 15` = 17 件候选里剩 15 件没轮到；每拍都恰好是 2 + 15，说明进度恒为 0。）

进任务后玩家身边会多出十几件"永远不可能全命中"的 unit（枪 / 背包 / 尸体 / 人台），
它们排进队首 ⇒ 真护甲永远排在后面 ⇒ **一个都不挂**。

也就是说：**舰船能好是因为"刚好只需要前 2 件"**，不是那一版真的好了。同一份代码换个场景就塌。

## 2. 改法（运行时 2.1.28）

### ① 处理顺序改成"最久没处理过的先来"（**这一条是决定性的**）

`tryAttach` 的候选循环不再 `for index = 1, #nearCandidates`，而是先按
`scoreAttemptAt[unit]` 升序排（没处理过的 = -1，排最前），处理过的自然沉到队尾。
只要有一次尝试，进度就**单调前进**，永远不会有"某件永远轮不到"。

### ② 加一层便宜预筛，把"不可能全命中"的件挡在真打分之前

全命中要求该 unit 含有容器的**每一根骨** ⇒ 只要它连容器第 1 根骨都没有，
就一定不可能全命中。于是：**每份容器只问一根骨**（10 份容器 ⇒ 10 次 `has_node`），
而不是 `骨数 × 容器数`（57 × 10 ≈ 570 次）。

- 通过 ⇒ 才真打分（`select_rig`）；
- 不通过 ⇒ 记一次"处理过"（沉到队尾），到点再探（骨骼可能只是还没就绪）。

成本差两个数量级（≈0.04 ms vs ≈3 ms/件），所以预筛额度是 `scoreUnitsPerFrame × 4`。
`allowPartial` 时**整段跳过**（部分命中合法，不能筛）；外置包只有旧 compat 时也自动跳过。

⚠️ 严格性：这条只对"全命中"成立，而且第 1 根骨解析不出 id 时**保守放行**（不筛）。

### ③ 装填期间不减速、整组释放时清重试门

- 等待期那套"等久了把 poll ×3"的退避，在装填进行中（`fillPending`）**让位**：
  否则 2 件/拍 × 1 秒/拍 = 十几件要十几秒才轮完，观感是"进图后十几秒完全没物理"。
- `dropAllOnDeath` 整组释放后清 `scoreAttemptAt` / `fillPending` / `probeRejected`，
  让新场景从第一拍就开始补挂。

### ④ 等待原因里带上量化线索

```
装填中（本拍额度用完）：打分 2 件 / 预筛 8 件（过 1）、还剩 5 件待处理；最近 171 节点·预筛挂
没有 unit 命中任何物理容器：17 个候选 unit × 10 份容器，最高命中 3/68 根骨（…）
没有 unit 命中任何物理容器：17 个候选 unit × 10 份容器，预筛全挂（连容器的第 1 根骨都没有）
```

下一轮日志就能直接分辨：**不可能命中**（预筛全挂）／**部分命中**（最高命中 x/68，说明骨骼
还没就绪或换了一套模型）／**打分成问题**。

## 4. 实机结果（2.1.28 上机后追加）

**死结确实解开了，但任务里卡在更前面一步。**

2.1.28 实机日志（`11:59:56` 起这一段）：

| 时间 | 事实 |
|---|---|
| 12:00:16 | 舰船：`attach 进入 rig 57 根骨` ×2、`已挂载 2 个 unit / 78 条链`、`本轮新打分 8 件` ⇒ **舰船上有 8 件通过了预筛、2 件全命中**，物理正常（用户确认）。 |
| 12:01:25 | 进任务：2 个会话销毁 ⇒ `dropAllOnDeath=1` 整组释放。 |
| 12:01:25 起 | 每一拍都是 `打分 0 件 / 预筛 8 件（过 0）、还剩 21 件待处理；最近 171 节点·预筛挂`，连续 5 分钟**一次都没过**，`预筛全挂` 的终态也从没落过（因为每拍都还有 deferred）。 |

结论：**队列会转了（选中的 8 件每拍在换），但任务里 ~29 件候选没有任何一件含有
容器的第 1 根骨**。同一份代码、同一份容器，舰船上过 8 件、任务里过 0 件。

两个可能，修法完全相反：

- **A. 任务里的护甲 unit 真的没有那些骨**（不同资源 / 软映射换成了另一份资源）⇒ 匹配思路要换；
- **B. `has_node` 在骗人**。本仓早有记录（`IDENTITY` 那行）：同一根骨会从 true 翻成 false，
  而 `num_scene_graph_items` 不变。本次舰船段的日志里就出现了两次
  `[IDENTITY] 抽样骨名 has_node=false（nodes 171→171）` —— 而那两根骨是**刚刚全命中过**的。

因为这两种可能修法相反，2.1.29 **不再猜**，改成"异常态自动普查"（见 §5）。

## 5. 2.1.29：异常态普查（诊断，不是修复）

触发条件：**一拍里探过 N 件候选、但没有一件含容器的第 1 根骨且一件都没真打分**。
所以正常场景（能过预筛）一个字节都不花，不会挤掉心跳的日志预算（mp_harness 的
900 字节断言就是这条线：`T17` 专门守住"只在异常态落、且只落一次"）。

落三行，直接回答上述 A/B：

```
[physbone][普查] 近距 29 件 / 远端 35 件 · 资源：cha_armor_xxx×12、cha_armor_yyy×17 · 节点：171节×12 148节×17
[physbone][普查] #ID[...]（171 节）对 patch_18.gpu_resources（57 骨）：首骨 has_node=false node=142 ；第2骨 … ；末骨 … ；对照组 has_node=false node=?
[physbone][普查] 该件完整打分：0/57 0/68 0/57 ⇒ 未全命中
```

读法：

- **资源名**：任务里的候选到底是不是那套改过的护甲资源（和舰船同一份）？
- **`node=` 与对照组的对比**：如果真骨返回一个合理的节点下标（`0 ≤ node < 171`）而对照组
  返回 `nil`/`-1`/越界，⇒ 骨头在，是 `has_node` 在骗人 ⇒ 把匹配判据换成 `node`（B）；
  如果对照组也返回一个"合理"下标 ⇒ `node` 不可用作判据（2026-10-31 的老结论），
  那就要看资源名判断是不是 A。
- **`该件完整打分 0/57`**：差几根骨。0 根 ⇒ 完全不是同一套模型。

## 6. 用户反证推翻了上面的 A/B 二分（2.1.30 的转折）

> 「我们的 1.5.14 版本明确是可以在任务里运行物理的，只是只有我自己有，而更早的版本
> 甚至全体都有，这不是我们明显的自我防御过度导致的？」

这是对的，而且 §5 的 A/B 二分本身就有问题：它默认了"当前这份候选表/这套判据是对的"，
于是把"我的过滤器没让真护甲进真打分"误当成"骨头不在"。

**拿 v1.5.14 的源码对照，差异只有一处**（`discover` 自 v1.5.14 起一行未改，候选表完全一样）：

| | v1.5.14（2.1.23，任务里有物理） | 2.1.25→2.1.28（任务里没有） |
|---|---|---|
| 每拍处理 | **一次给前 12 件全部真打分**（`max(12, 4×玩家数)`） | 先预筛 8 件，**只有过预筛才真打分 2 件** |
| 判据 | 只有 `select_rig` 全命中 | 多了我加的 `probe_carriers`（`has_node` 问第 1 根骨） |

也就是说：老版"把最近 12 件无条件真打分"，真护甲只要在这 12 件里就**必然**被真打分；
新版在这前面插了一道我说不清可靠性的闸门，一旦这道闸门对所有候选都判死，真护甲
**永远进不了真打分**。这就是"自我防御过度"的具体形态：**优化被当成了判据。**

## 7. 2.1.30 的处置（去防御，不靠身份）

1. **预筛默认关闭**（`probeUnitsPerFrame` 默认 0）。它只是省调用的优化，前提
   （`has_node` 说没有就真没有）在实机上没有得到验证，不能拿它当判据。要开必须显式给数。
2. **队列改成整数游标轮转**，不再依赖"unit 句柄跨帧同一"。
   2.1.28 的"按上次处理帧排序"依赖 `scoreAttemptAt[unit]` 命中；一旦这个假设不成立
   （弱键表里的 userdata 被回收 / 引擎每次枚举新建包装），排序就退化成 index 序，
   队首反复处理、后面永远轮不到。游标只依赖一个整数：
   **n 件候选保证在 `ceil(n / 每拍额度)` 拍内被覆盖一遍。**
3. **`maxUnits` 64 → 128。** 实机任务里日志正好是"近距 29 + 远端 35 = 64"，顶满了上限 ——
   候选表是按引擎枚举顺序截断的，真护甲**有可能压根没进表**。列表长一点也不多花每拍的钱
   （花钱的是每拍额度），只多 discover 里每件 2 次调用。
4. 异常态普查保留（§5），触发条件改成 `#plan == 0` 且当前没有会话：只在"真的什么都挂不上"
   时落三行。
5. "装填中"那行改成 `真打分 N 件 / 预筛 M 件、还剩 K 件；最近 <tag>·<节点>节·打分 x/y`
   —— **游标有没有在动，看连续几行"最近"变不变就知道**。

预期：任务里最多 `ceil(件数/2)` 拍（每拍 20 帧左右 ≈ 0.3 s）覆盖一遍 ⇒ 几秒内真护甲必然
被真打分一次；命中就挂上，没命中日志里就带着 `x/y` 的具体数字。

## 9. 真正的根因（2.1.31）：缓存了会失效的 `IdString32`

2.1.30 上机后日志给了决定性一行（进任务后）：

```
[普查] #ID[5c44f3fe7b7c0001]（171 节）对 patch_1（56 骨）：
       首骨 has_node=抛错 node=0 ；对照组 has_node=抛错 node=0
[普查] 该件完整打分：0/68 0/58 0/57 ⇒ 未全命中
```

**同一件护甲、同一资源（`5c44f3fe7b7c`）、同样 171 节**：舰船上它 57/57 全命中并挂上，
进任务后它对**所有**容器都是 0，连"绝不存在的名字"也一并抛错。

而**我们自己的代码里早就写着答案**（`physbone_runtime.lua` 的 snapshot 段）：

> ⚠️ 一律**先用名字字符串**：实测 `Application.string_to_id32` 返回的是 `IdString32` userdata，
> 而且它是**会失效的**（探针日志里直接印出 `[Stale IdString32]`）。
> 把它存起来跨帧用，`has_node` 一律返回 false。

**2.1.25（`15d953e`）我加的"优化"正是这么干的**：把每根骨的 `string_to_id32` 结果缓存进
`boneIdsByRig`，理由是"每件候选白花 580 次调用"。后果：

| 版本 | 匹配判据 | 任务里 |
|---|---|---|
| v1.5.14（2.1.23） | 每次调用**当场**算 id | **有物理**（用户实测） |
| 2.1.25 起 | id 按 rig 缓存、跨帧复用 | **再也没有**：舰船首挂之后，所有候选恒为 0/68 |

舰船看起来正常，是因为进程刚起、那批 id 还是刚算出来的；一旦进入第二次大规模匹配
（换场景），缓存里的 `IdString32` 已失效 ⇒ 全部 false/抛错。**1.5.14 能跑、之后不能跑，
分界线正好是这一版。**

## 10. 2.1.31 的处置

1. **匹配一律按骨名问**（`has_node(unit, "骨名")`），完全不碰 `string_to_id32` ——
   既修掉失效问题，又省掉每根骨 1 次引擎调用。`boneIdsByRig` 整体删除，
   换成只缓存**字符串别名**的 `boneNamesByRig`。
2. `Compat.attach` 的 `resolveNode` 也改成**先按名字、再退回当场算的 id**（双保险）。
3. 发现玩家的 `support_mg` 挂点、抬升探针、第一人称探针里的 `head` 全部改成名字。
4. `session.identityNode` 存**骨名**而不是 id —— 原来那条 `[IDENTITY] has_node=false`
   日志是"必然为假"的，它把排查带偏了两次，现在它说真话了。
5. 普查保留（异常态触发），并且**同时打印按名字和按 id 的结果 + 错误原文**，
   下次再出这类问题一眼就能分辨。

回归钉子：

- `rig-select-test` T10：`has_node` 只认名字（传数字直接抛错），按 id 匹配必然 0 命中。
- `runtime-harness-test` T18：整条链（发现 → 匹配 → attach）在"只认名字"的假引擎上
  必须挂满 6 件。**反向验证过**：把 `unit_has_bone` 改回按 id 传，整套 harness 立刻全红。
- `lifecycle-test`：`identityNode` 断言改成"是字符串（骨名）"。

## 11. 附：这一轮踩坑的教训

连着四版都栽在同一类问题上：**把"我加的状态/闸门"当成事实，而不去核对它与引擎真实语义、
与时间形状是否一致**。而且这一轮我自己把答案写进了代码注释、又在匹配路径上违反了它。

1. 2.1.25：把 `select_rig` 在 0 命中时**非 nil 的 best** 当正匹配缓存 ⇒ 该件既不挂也永不重试。
   **同一版还顺手缓存了会失效的 `IdString32`** —— 那才是"进任务后全员没物理"的真凶，
   但它的现象被后面两层的表象盖住了。
2. 2.1.27：修掉了"缓存不可用结果"，但没意识到**重试门（30 帧）比尝试间隔（60 帧）短**。
3. 2.1.28：队列改了，又在真打分之前插了一道基于 `has_node` 的预筛（同样是拿失效的 id 去问）。
4. 2.1.30：把预筛关掉、换成整数游标 —— 队列终于对了，才**让真凶浮出来**（0/58 0/57 一直在，
   只是之前被"预筛挂"挡住看不见）。

原则（下次直接照做）：

- **引擎返回的句柄/对象一律当成"这一帧有效"**：`IdString32`、`Matrix4x4`、`Vector3` 都是
  临时对象。要跨帧/跨调用复用，只能复用**字符串和数字**，绝不能复用引擎对象。
  这条本仓早就写过（"任何句柄都必须当场转成数字"），我却在匹配路径上破例了。
- **优化不能改变判定结果**：只准"重排顺序 / 延后处理"，不准"判定死刑"（2.1.28 的预筛、
  2.1.25 的负缓存都是反例）。
- 遇到"什么都没有"的现象，先问"**是不是我的过滤器/缓存把它挡住了**"，
  最省事的验证是**把优化全关掉再跑一遍**（回到老版本的判定路径）。
- **"日志里写着 X" 也要怀疑**：`[IDENTITY] has_node=false` 我们看了两轮，它其实是
  我们自己存了个会失效的 id 造成的必然假象。观测代码本身也要按"它会不会骗人"审一遍。
- 用户说"某个版本能跑"时，**把那个版本的代码 diff 出来**，比在现版本里找理论快十倍。

写测试时必须把**时间形状**和**引擎语义陷阱**都写进去：
`pollFrames` 与 `negativeRetryFrames` 的相对大小是前者；"只认名字、传 id 就抛错"的
假引擎（T18）是后者。否则本地 `pollFrames=1` 的用例永远绿、实机永远红。
