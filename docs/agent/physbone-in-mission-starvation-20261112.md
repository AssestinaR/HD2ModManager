# 进任务后全员没物理：打分队列被队首饿死（2.1.28）

> 日期：2026-11-12　版本：运行时 2.1.27 → 2.1.28
> 现场：`%LOCALAPPDATA%\hd2physbone.log`（11:41:52 起的那一段，运行时 2.1.27）

## 0. 结论先说

**症状**：进舰船（基地）物理正常；进任务地图后**我和队友们都没有物理**，且再也不恢复。

**根因**：挂载前的"候选打分"是**每拍从头开始**的固定顺序循环，而每拍只允许打分
`scoreUnitsPerFrame`（默认 2）件。两次尝试的间隔（等待期 `pollFrames`=20，等久后 ×3 = 60 帧）
**比"重试门"（`negativeRetryFrames`=30 帧）长** ⇒ 排队首的那 2 件每一拍都能重新轮到、
把额度吃干，**后面的件永远轮不到**。

日志特征是一条数字一动不动的行，连续 8 分钟：

```
[physbone][等待] 装填中（本拍打分额度用完）：已打分 2 件、未轮到 15 件
```

（`未轮到 15` = 17 件候选里剩 15 件没轮到；每拍都恰好是 2 + 15，说明进度恒为 0。）

进任务后玩家身边会多出十几件"永远不可能全命中"的 unit（枪 / 背包 / 尸体 / 人台），
它们排进队首 ⇒ 真护甲永远排在后面 ⇒ **一个都不挂**。

## 2. 改法（运行时 2.1.28）

### ① 处理顺序改成"最久没处理过的先来"（**这一条是决定性的**）

`tryAttach` 的候选循环不再 `for index = 1, #nearCandidates`，而是先按
`scoreAttemptAt[unit]` 升序排（没处理过的 = -1，排最前），处理过的自然沉到队尾。
只要有一次尝试，进度就**单调前进**，永远不会有"某件永远轮不到"。

### ② 加一层便宜预筛，把"不可能全命中"的件挡在真打分之前

全命中要求该 unit 含有容器的**每一根骨** ⇒ 只要它连容器第 1 根骨都没有，
就一定不可能全命中。于是：**每份容器只问一根骨**（10 份容器 ⇒ 10 次 `has_node`），
而不是 `骨数 × 容器数`（57 × 10 ≈ 570 次）。

- 通过 ⇒ 才真打分（`select_rig`）；
- 不通过 ⇒ 记一次"处理过"（沉到队尾），到点再探（骨骼可能只是还没就绪）。

成本差两个数量级（≈0.04 ms vs ≈3 ms/件），所以预筛额度是 `scoreUnitsPerFrame × 4`。
`allowPartial` 时**整段跳过**（部分命中合法，不能筛）；外置包只有旧 compat 时也自动跳过。

⚠️ 严格性：这条只对"全命中"成立，而且第 1 根骨解析不出 id 时**保守放行**（不筛）。

### ③ 装填期间不减速、整组释放时清重试门

- 等待期那套"等久了把 poll ×3"的退避，在装填进行中（`fillPending`）**让位**：
  否则 2 件/拍 × 1 秒/拍 = 十几件要十几秒才轮完，观感是"进图后十几秒完全没物理"。
- `dropAllOnDeath` 整组释放后清 `scoreAttemptAt` / `fillPending` / `probeRejected`，
  让新场景从第一拍就开始补挂。

### ④ 等待原因里带上量化线索

```
装填中（本拍额度用完）：打分 2 件 / 预筛 8 件（过 1）、还剩 5 件待处理；最近 171 节点·预筛挂
没有 unit 命中任何物理容器：17 个候选 unit × 10 份容器，最高命中 3/68 根骨（…）
没有 unit 命中任何物理容器：17 个候选 unit × 10 份容器，预筛全挂（连容器的第 1 根骨都没有）
```

下一轮日志就能直接分辨：**不可能命中**（预筛全挂）／**部分命中**（最高命中 x/68，说明骨骼
还没就绪或换了一套模型）／**打分成问题**。

## 4. 实机结果（2.1.28 上机后追加）

**死结确实解开了，但任务里卡在更前面一步。**

2.1.28 实机日志（`11:59:56` 起这一段）：

| 时间 | 事实 |
|---|---|
| 12:00:16 | 舰船：`attach 进入 rig 57 根骨` ×2、`已挂载 2 个 unit / 78 条链`、`本轮新打分 8 件` ⇒ **舰船上有 8 件通过了预筛、2 件全命中**，物理正常（用户确认）。 |
| 12:01:25 | 进任务：2 个会话销毁 ⇒ `dropAllOnDeath=1` 整组释放。 |
| 12:01:25 起 | 每一拍都是 `打分 0 件 / 预筛 8 件（过 0）、还剩 21 件待处理；最近 171 节点·预筛挂`，连续 5 分钟**一次都没过**，`预筛全挂` 的终态也从没落过（因为每拍都还有 deferred）。 |

结论：**队列会转了（选中的 8 件每拍在换），但任务里 ~29 件候选没有任何一件含有
容器的第 1 根骨**。同一份代码、同一份容器，舰船上过 8 件、任务里过 0 件。

两个可能，修法完全相反：

- **A. 任务里的护甲 unit 真的没有那些骨**（不同资源 / 软映射换成了另一份资源）⇒ 匹配思路要换；
- **B. `has_node` 在骗人**。本仓早有记录（`IDENTITY` 那行）：同一根骨会从 true 翻成 false，
  而 `num_scene_graph_items` 不变。本次舰船段的日志里就出现了两次
  `[IDENTITY] 抽样骨名 has_node=false（nodes 171→171）` —— 而那两根骨是**刚刚全命中过**的。

因为这两种可能修法相反，2.1.29 **不再猜**，改成"异常态自动普查"（见 §5）。

## 5. 2.1.29：异常态普查（诊断，不是修复）

触发条件：**一拍里探过 N 件候选、但没有一件含容器的第 1 根骨且一件都没真打分**。
所以正常场景（能过预筛）一个字节都不花，不会挤掉心跳的日志预算（mp_harness 的
900 字节断言就是这条线：`T17` 专门守住"只在异常态落、且只落一次"）。

落三行，直接回答上述 A/B：

```
[physbone][普查] 近距 29 件 / 远端 35 件 · 资源：cha_armor_xxx×12、cha_armor_yyy×17 · 节点：171节×12 148节×17
[physbone][普查] #ID[...]（171 节）对 patch_18.gpu_resources（57 骨）：首骨 has_node=false node=142 ；第2骨 … ；末骨 … ；对照组 has_node=false node=?
[physbone][普查] 该件完整打分：0/57 0/68 0/57 ⇒ 未全命中
```

读法：

- **资源名**：任务里的候选到底是不是那套改过的护甲资源（和舰船同一份）？
- **`node=` 与对照组的对比**：如果真骨返回一个合理的节点下标（`0 ≤ node < 171`）而对照组
  返回 `nil`/`-1`/越界，⇒ 骨头在，是 `has_node` 在骗人 ⇒ 把匹配判据换成 `node`（B）；
  如果对照组也返回一个"合理"下标 ⇒ `node` 不可用作判据（2026-10-31 的老结论），
  那就要看资源名判断是不是 A。
- **`该件完整打分 0/57`**：差几根骨。0 根 ⇒ 完全不是同一套模型。

## 5. 附：这一轮踩坑的教训

连续两版都栽在同一类问题上：**"缓存/额度"里的状态与真实时间形状不匹配**。

1. 2.1.25：把 `select_rig` 在 0 命中时**非 nil 的 best** 当正匹配缓存 ⇒ 该件既不挂也永不重试。
2. 2.1.27：把"不可用"的当成可用修掉了，但没意识到**重试门（30 帧）比尝试间隔（60 帧）短**，
   于是"从头开始的队列"本身就等价于"恒不前进"。

写测试时必须把**时间形状**写进去（`pollFrames` 与 `negativeRetryFrames` 的相对大小），
否则本地 `pollFrames=1` 的用例永远绿、实机永远红。
