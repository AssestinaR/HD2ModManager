# 护甲「按实例替换」可行性探针 — 计划（2026-11-23）

> 目的：用**一次进游戏**回答三个问题——克隆件能不能带物理、隐藏原件能不能回收 CPU、
> 克隆件本身多贵。附带验证「全局覆盖污染」与「克隆修正」是否如预期。
> 本文只定实验与判据，不改产品代码。

---

「按实例替换」在仓库里**已经有实现**，不是新想法：

| 通道 | 实现 | 状态 |
|---|---|---|
| D 克隆显示 | `player_armor_instances.lua`（213 行，spawn + link + hide + **可逆**） | 存在，但触发条件窄到只服务一个特殊 case |
| C 只隐藏 | `kit_instance_hider.lua`（1056 行，**不可逆**） | 从未投放 |
| B 只发独有件 | `WardrobeLinkCompiler` 的 `lowPollution` 分支 | 从未跑过 |

且低污染整套在这台机器上**从未真正运行过**（`kit-instance.rules` 95 B / 0 条规则；

**所以本探针刻意绕开那套机制**，用一个独立 Lua 直接调用引擎原语，
只回答「物理上可不可行、代价多少」。产品怎么落地是后一步的事。

## 1. 要回答的五个问题

| # | 问题 | 判据 |
|---|---|---|
| Q1 | 隐藏原件后，游戏是否**回收**它的成本 | 隐藏前后帧时延差 > 5% ⇒ 回收；≈0 ⇒ 不回收 |
| Q2 | 一件克隆件的成本 | spawn 1 件前后帧时延差 |
| Q3 | 克隆件能不能挂物理 | 克隆件上能解析出 rig 的全部骨名 ⇒ 能 |
| Q4 | 全局覆盖的污染是否真实可见 | 覆盖共享件后，两套甲**同时**变 |
| Q5 | 克隆能否只修「被污染的那套」 | 只对穿戴中的那套 clone；另一套不 clone |

Q1/Q2 是胜负手：**Q1 不回收且 Q2 不便宜 ⇒ 克隆模式净亏，应当放弃。**

## 2. 实验场景（真实索引数据，已核对）

用**共用一条左腿**的一对原版护甲：

| 角色 | 护甲 | 左腿（slot 4）unit |
|---|---|---|
| 共享件 | AC-2「服从指挥」+ AC-1「恪尽职守」 | `0x2438f1abb362382e` ← **两套都用它** |
| 意图目标 | AC-2 应变成 | PH-56「捷豹」的腿 `0xd318fdfa79042965` |
| 污染目标 | AC-1 应变成 | CE-27「裂地者」的腿 `0xc03b0336c87667bf` |
| 各自独有 | AC-2 / AC-1 | `0x5753932a6d8c0dca` / `0x8e852d1be7cb20f6` |

两套甲共享的只有 5 件（slot 1/4/5/6/7），其余各自不同 ⇒ 外观可区分，
**只覆盖 slot 4 这一件**就能做出干净的最小污染场景。

预期现象：

1. 覆盖 `0x2438f1abb362382e → 0xd318fdfa79042965` 后，
   **AC-2 和 AC-1 在军械库里同时换腿** ⇒ 污染成立（Q4）。
2. 穿 AC-2：正确，**不需要克隆**。
3. 穿 AC-1：错误（它该是 CE-27 的腿），对它 clone + hide ⇒ 正确（Q5）。

## 3. 探针设计

单文件 Lua，挂在 boot 上跑（`tmp/lua-boot/build_probe.py --probe`），
日志落 `%LOCALAPPDATA%\armorprobe.log`。按帧推进阶段机，每阶段跑固定帧数后进下一阶段。

| 阶段 | 做什么 | 记什么 |
|---|---|---|
| P1 环境 | 找 main_world、找 avatar（有状态机 + `support_mg`） | unit 总数、avatar 实例名、世界数 |
| P2 能力 | `clear_resource_override` 是否存在；`set_unit_visibility` 读回；ADS/第一人称状态 | 三个布尔 |
| P3 污染 | `set_resource_override('unit', 共享腿, PH56腿)`；统计世界里持有该 id 的实例 | 覆盖前后实例数与资源名 |
| P4 克隆 | `World.spawn_unit(donor)` → `World.link_unit` 到 avatar 对应节点 → 原件 `set_unit_visibility(false)` | spawn/link 是否成功、克隆件骨名解析率 |
| P5 计时 | 五档各 120 帧，取帧时延中位数：①基线 ②覆盖后 ③隐藏原件后 ④加克隆后 ⑤销毁克隆后 | 每档中位数 + 均值 |
| P6 收尾 | `destroy_unit`、`clear_resource_override`、可见性恢复 | 是否全部成功 |

计时用 `Application.time_since_launch` 的**帧间差分**（它每帧只更新一次，块内首尾差恒 0）。

## 4. 判据与结论映射

| 观测 | 结论 |
|---|---|
| Q1 回收 > 5% 且 Q2 单项 < 5% | 克隆模式可用，净成本可能接近零（素体件通常少于原版） |
| Q1 ≈ 0 | 克隆是净亏 ⇒ **放弃克隆**，维持当前轻量做法 |
| Q3 解析率 < 100% | 克隆件挂不上物理 ⇒ 需要另找骨名对齐手段 |
| Q4 不成立 | 场景没做对，回去查覆盖是否生效（不是结论） |

## 5. 风险与回滚

- `set_resource_override` **只进不出**（审计 §1.3）；探针会尝试 `clear_resource_override`，
  但**不保证**能撤。最坏情况是这一局腿不对，**重启游戏即恢复**。
- `spawn_unit` / `link_unit` 的生命周期是已知坑：探针在 P6 无条件 `destroy_unit`，
  且每阶段失败只记日志不重试。
- 探针**不写任何游戏文件**，不改管理器配置，不改映射注册表。
  ⇒ 与用户要求的「改映射注册表造污染」相比，探针自己在会话内覆盖，
  效果等价但**可回滚、且不动你的配置**，所以采用这个做法（理由见 §6）。

## 6. 为什么不动用户的映射配置

用户原建议是「改我的映射注册表，造一个干净污染场景」。可行，但：
1. 会改到 `armor-registry.workspace.json` / `wardrobe.links`，回滚要重新 apply 一次；
2. 低污染链路上有 12 个 P0，走产品路径做实验等于把变量从 1 个变成 5 个；
3. 覆盖本身就能造出完全一样的现象，而且探针能自己撤。

⇒ **结论：探针自带覆盖，不碰用户的映射与部署。**

## 7. 尚未覆盖（明确写出，不假装）

- 只测**一件**克隆件的成本。23 件全克隆的成本要靠「单价 × 件数」外推，会在报告里标注为推算。

## 8. v1 实测失败（2026-11-23）与 v2 修正

v1 跑出来的日志**没有任何可用数字**：

| v1 现象 | 原因 |
|---|---|
| `选中世界 unit 数=1`、`avatar=false` | 探针一挂上 `update` 就开始走阶段，4.5 秒跑完全部阶段——那时还在**主菜单** |
| `共享腿实例=0`、`spawn 失败` | 同上：玩家身上还没有任何护甲 |
| 基线 4.68ms、各阶段 +0.5% | 量的是菜单帧率，**Q1/Q2 一个数没拿到** |

两条设计错误（第二条是本仓库早就写过的结论，我读到了却没用）：

1. **没有"场景就绪"门**：阶段按帧数推进，不等 avatar 出现。
2. **只看 `main_world`**：而 `softmapping-runtime-identity-api-recon-20261114.md` §4.1 明确写着
   「军械库预览不在 `main_world()`」。`unit 数=1` 就是证据。

v2 的修正：

- **全遍历 `Application.worlds()`** 找 avatar（要求 alive 且 nodes>0），并记住它所在的世界；
- **动态等待阶段**：每 30 帧重试，条件 = 找到 avatar **且** 它附近（0.6 m）有那条共享腿；
  每 2 秒打一次心跳说明"还差什么"，超时 180 秒；就绪后才开始测量并丢弃等待期的计时基准；
- **护甲判定用"穿在身上的件"**：AC-2 独有 `0x5753932a6d8c0dca`、AC-1 独有 `0x8e852d1be7cb20f6`，
  谁在身上就是哪套——不看配置，只看事实；
- **只对被污染的那套做按实例修正**：穿 AC-2（本就正确）⇒ 完全不克隆；穿 AC-1 ⇒
  spawn CE-27 的腿 + 按骨名逐骨 `link_unit` + 隐藏身上那条被污染的腿；
- **收尾还原**：unlink + destroy 克隆件、恢复可见性、`clear_resource_override`；
- 每档记录 n>0 的帧时延中位数，并在汇总里给出相对基线的百分比。

离线冒烟（假引擎，刻意让 `main_world` 是空的菜单世界）：

| 场景 | 结果 |
|---|---|
| 穿 AC-1（应克隆） | 11 项断言全过：等待→判出 AC-1→覆盖→spawn 1 次→link 报告→隐藏 1/1→收尾→n>0 |
| 穿 AC-2（不该克隆） | 10 项断言全过：判出 AC-2→**spawn 0 次**→明确打「本就正确⇒不克隆」 |

### 8.1 实测前置条件（不满足会一直等待）

玩家身上必须**真的有**那条共享腿 `0x2438f1abb362382e`。而当前配置是「全量映射」
（2000 条覆盖，覆盖 1056 套），所以穿 AC-1/AC-2 时身上多半已经被替换成自定义素体，
共享腿根本不出现 ⇒ 探针会一直停在等待阶段（每 2 秒报一次原因，不会白跑但也不会有数字）。

⇒ 跑之前需要把**护甲映射关掉**（或确认这两套没被映射），再重新部署一次。

## 9. v3/v4：常驻 + 三件 unit（2026-11-23，用户纠正后）

用户在 v2 实测后指出两个真问题，都成立：

1. **角色搞反了**。需求是「两套护甲各显示**不同**的腿」，所以要引入**三件** unit：
   - 载体件（两套共用，要被隐藏）`0x2438f1abb362382e`
   - A 的目标腿（PH-56「捷豹」）`0xd318fdfa79042965`
   - B 的目标腿（CE-27「裂地者」）`0xc03b0336c87667bf`

   穿 A ⇒ clone 目标腿 A + 隐藏载体；穿 B ⇒ clone 目标腿 B + 隐藏载体。
   **没有一个"路人"档**——两套都是目标。基线由"穿第三套甲"提供。

   v2 之所以"没克隆 AC-2"，是因为它先用全局覆盖把载体改成了 AC-2 的目标腿，
   于是 AC-2 看起来已经对了。那是**用错机制**（覆盖必然同时改两套，就得再修一套），
   而正确形态里覆盖根本不参与。

2. **探针不该自己结束**。真实映射链路是「映射一次 → 只等待 → 等外部变化再动」，
   而 v2 处理完就退出，人还没换甲就结束了。⇒ 改成常驻。

### 9.1 v4 的形态

| 项 | 值 |
|---|---|
| 检测频率 | 每 0.2 秒（只数实例，低开销） |
| 换甲响应 | 拆旧的（unlink+destroy、恢复可见）→ 建新的 |
| 分桶统计 | `none` / `A` / `B` 三档帧时延，心跳每 2 秒打一次 |
| 生命周期 | 30 分钟兜底；随时可退游戏，日志里已有累计数据 |
| 挂骨 | 按骨名逐骨 `link_unit`；名字两边都有才挂，0 匹配就如实报失败 |

### 9.2 人工测试成本是需求的一部分

用户明确指出：人工测试不能像离线那样高频迭代，一次进游戏要尽量把话说全。
所以 v4 的设计原则是「一次跑够」：常驻、可无限次换甲、心跳随时给数、不需要等它收尾。
后续任何探针都按这条来，不再写"跑一遍就结束"的脚本。

## 10. 实机：地上出现洋红色问号（2026-11-23，v4 实测）

现象：穿 AC-2 时腿没变，地上出现一个巨大的洋红色 `?`。

**那个问号是 Stingray 的「缺资源占位体」**：`World.spawn_unit` 被要求实例化一个
**当前没有加载**的 unit 资源时，引擎不会报错，而是给一个占位网格（粉色问号），
并且它同样 `alive`、同样能被 `link_unit`、同样有节点数。

根因：`Application.can_get('unit', 目标腿)` 为 false。三个目标腿都是**原版护甲件**，
只有"正穿在身上"的那些才是已加载状态；没穿的（PH-56 / CE-27 的腿）根本没加载。

v2 探针其实早就打出过这个信号（`can_get unit 0xd318… = false`），但我当时按仓库笔记
「can_get 不是有效性闸门」把它忽略了 —— 那句话的意思是"can_get 为真不代表资源可用"，
不反过来等于"can_get 为假无所谓"。**为假就是没加载，spawn 必得占位体。**

### 10.1 这对方案意味着什么（重要）

- **克隆的 donor 必须是"已加载"的 unit。** 原版护甲件只有穿在身上时才加载 ⇒
  想 clone 一件"别的护甲的腿"，得先让它加载过。
- 好消息：真实产品里 donor 是**我们自己发布的素体 unit**（随映射包一起部署、由护甲运行时
  引用），它天然是已加载的 ⇒ 产品路径不受这个限制。受限的只是"拿原版件当 donor"这种实验做法。

### 10.2 v5 的三条硬性保护

1. **spawn 后必须验证**：`resourceId(clone)` 等于目标 id 且节点数 > 0，否则判定为占位体、立刻销毁。
   （v4 缺这一步，于是拿占位体当替代品。）
2. **can_get 为假就不 spawn**，并明确报出三个 unit 各自的加载状态 —— 这是"洋红问号"问题的唯一判据。
3. **挂骨 0 根就绝不隐藏原件**。藏了原件又没有替代品，那条腿会直接消失，比不替换更糟。

### 10.3 退路

目标 donor 不可用时，退回「clone 载体件自身」（它一定已加载，因为正穿在身上）：
视觉上和原件一样，但能验证 `spawn + link + hide` 整条链路是通的。
离线冒烟已覆盖这条退路，以及"连载体都不可用 ⇒ 放弃且不隐藏"。

### 10.4 v6：donor 改用"正穿在身上的件"+ 左右互换（用户指出自克隆无法目视验证）

用户两条批评都成立：

1. **退回"克隆载体件自身"视觉上没有变化** ⇒ 日志说成功也证明不了任何事。
2. **日志本身不能自证**，必须让肉眼能分辨。

于是 donor 改成**各套自己的右腿件**（正穿在身上 ⇒ 必然已加载）：

| 套 | donor（右腿，slot 5） |
|---|---|
| AC-2「服从指挥」 | `0x03c18a25a3e03f4a` |
| AC-1「恪尽职守」 | `0xc0c0a9a5b2289ad1` |

挂骨时做**左右互换**（`r_*` ↔ `l_*`）：右腿件被挂到左腿骨上，于是左腿显示"镜像的右腿件"——
视觉上明显不同，轮廓仍是腿。

这样三种结果**肉眼可分**，同时也就能校验日志：

| 看到什么 | 说明 |
|---|---|
| 左腿变成镜像的右腿件 | spawn + link + hide 全部成功（日志可信） |
| 左腿**消失** | hide 成功、spawn/link 失败 |
| 什么都没变 | 什么都没执行（`can_get` 为假 / 挂骨 0 根） |

自克隆退路已删除。保护不变：spawn 后校验 `resourceId` 与节点数、`can_get` 为假不 spawn、
挂骨 0 根不隐藏。

### 10.5 v7 实机崩溃：`Unit.resource_name`（2026-11-23）

现象：日志停在 `[16.39s] 就绪：avatar 找到（换场景/新角色）`，游戏崩溃。

原因：v7 在"就绪"之后立刻遍历玩家附近所有 unit 并读 `Unit.resource_name`。
这条路仓库**早就标死了**：

> `Unit.resource_name` | 崩溃 | ❌ 禁止（改用 `debug_name`）
> `Unit.bones` / `Unit.mesh` / `Unit.resource_name` 批量调会 AV 崩溃，不是抛 Lua 错误，`pcall` 拦不住
> —— `docs/agent/hd2-physics-roadmap-and-handover.md:694,714`

v8 处置：

1. **删掉整个遍历式 dump**，换成「候选 id 探测」：只对**已知 id** 调 `can_get` + `units_by_resource`
   （给 id 找实例，安全），绝不遍历 unit。
2. **全文件彻底移除 `resource_name`**，身份读取一律改用 `debug_name`（返回 `"#ID[hex]"`，已在两千多 unit 上验证安全）。
3. spawn 校验从"比对 resourceId"退化为"拿得到身份 + 节点数 > 0"，再叠加"挂骨成功才隐藏原件"，
   三重闸门保证不会拿占位体替换原件。

教训：**仓库里标了"禁止"的 API，不要因为"看着能用"就去试**。这次崩的是游戏，代价是用户一轮实机时间。

## 11. 克隆成功，但原腿没被隐藏（2026-11-23，v8 实测）

日志证据（`%LOCALAPPDATA%\armorprobe.log`，15:49）：

```
候选 id 探测：
  0x2438f1abb362382e 载体（两套共用左腿）  can_get=true  实例=1
  0x5753932a6d8c0dca AC-2 独有左腿         can_get=true  实例=1   ← 关键
  0x49dd02a1c4990004 lilium 左腿（donor A）can_get=true  实例=0
挂骨：候选=99 命中=9 成功=9 [hips,l_thigh,r_thigh,l_knee,r_knee,l_foot,r_foot,l_toe,r_toe]
隐藏载体件 1/1
```

结论三条：

1. **克隆链路成立**。素体 donor `can_get=true` → spawn 成功 → 9 根骨挂上 → 可见。
   ⇒ 先前"只有已加载的 unit 才能 spawn"的判断是**错的**：素体件随 patch 部署，一直可用；
   只有**没穿在身上的原版件**才是不可用（PH-56 的腿 `can_get=false` 印证这一点）。
2. **原腿没隐藏的原因：一条腿不止一个 unit**。AC-2 的左腿 = 载体 `0x2438…`（共用）
   **+ 该套独有 `0x5753…`**。v8 只隐藏了载体，独有那件继续渲染 ⇒ 看起来"原腿还在"。
