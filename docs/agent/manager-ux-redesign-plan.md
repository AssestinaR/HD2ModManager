# Manager 人机工效重构方案

**制定日期：** 2026-07-18
**性质：** 产品与架构实施基线；本方案先统一交互与页面模型，再分批实现，不把高风险 Patch 重建改动混入本轮。

## 结论与目标

当前 Manager 的核心问题不是某个单独控件不好看，而是三套交互模型并存：

1. 原生 WPF 输入、选择、按钮与局部自定义卡片、圆形浮动按钮混用；
2. 主窗口已有双槽位页面系统，但高级详情、资产索引、跨护甲、任务、候选输出仍使用模态弹窗；
3. 自动维护、后台任务、短时通知各自独立，用户不知道程序正在做什么、为什么做、是否可取消、操作是否已经生效。

重构后的普通玩家路径应当只有四个顶级入口：

- **首页**：当前配置、最重要的健康状态、继续操作入口；
- **配置与模组库**：默认双栏工作区，左边管理当前配置，右边管理库；
- **设置与资产**：所有目录、在线资产、自动维护、索引状态和手动维护操作；
- **任务中心**：全局浮动入口，展示任务和最近消息。

`Status` 顶级页面移除。所有内部功能页均进入主页面工作区，不再使用内部功能模态窗口；仅保留 Windows 的文件/目录选择器以及危险操作最终确认。

## 设计语言：建立一套 Manager 控件系统

PCL 的可借鉴点是：先定义颜色 token 与控件状态，再统一文本框、下拉框、按钮、滚动条的模板；动画只表达状态变化（hover、focus、展开、切页），而不是装饰性堆叠。Manager 应借鉴这种**控件系统优先**的思路，但不复刻 PCL 的视觉或控件源码。

### 视觉 token

- 背景：一个应用背景、一个卡片背景、一个悬浮层背景；避免页面自行硬编码白色、灰色、蓝色。
- 文字：主文字、次文字、弱提示、危险文字四级；不通过随意变化字号与颜色表达层级。
- 品牌色：只用于主要动作、选中状态、可交互 focus；成功/警告/危险只能表达语义。
- 间距：4 / 8 / 12 / 16 / 24 的固定尺度；圆角、描边、阴影也使用 token。
- 动画：100–160ms hover/focus，160–220ms 面板展开/切换；统一 `CubicEase` / `QuinticEase`，尊重系统减少动画设置。

### 必须统一的控件族

| 控件 | 规范 |
|---|---|
| 主按钮 | 高对比填充，仅用于每一区域一个主要动作；hover 轻微变亮，pressed 轻微缩放或变深。 |
| 次按钮 | 透明/浅底描边，用于打开、浏览、刷新、返回；不可与主按钮争夺视觉权重。 |
| 危险按钮 | 红色只用于删除、停用、不可逆操作；始终显示明确文字，不只用图标。 |
| 图标按钮 | 只用于行内快捷动作；必须 `ToolTip`，默认不承担首次使用的重要操作。 |
| 文本输入 / 搜索 | 统一高度、圆角、focus 描边、placeholder、错误/禁用状态；搜索统一带图标和清除动作。 |
| 枚举选择 | 统一为“输入框外观 + 下拉列表”；常用静态枚举可选滚轮切换，但必须支持键盘和点击。滚轮不得在非悬停状态截获页面滚动。 |
| 开关 | 使用明确的 `ToggleSwitch`，旁边始终写清开关行为；涉及周期时显示关联的间隔输入。 |
| 筛选器 | 采用可组合的筛选 chips / 输入框，不在每页各造一套 ComboBox。 |
| 卡片 | 只承担分组或摘要；页面顶部卡片仅保留标题、主要说明、筛选/上下文，不能塞入低频表单。 |
| 列表行 | 使用统一行高、选中、hover、操作显现动画；虚拟化列表避免整表重新创建。 |
| 空状态 / loading | 统一 icon、标题、解释、下一步动作；页面必须先打开，再让局部内容显示 skeleton/loading。 |

应新增 `Themes/` 资源字典和少量可复用自定义控件（如 `AppButton`、`AppTextBox`、`AppComboBox`、`AppToggleSwitch`、`TaskHub`），而不是继续在每个 XAML 局部复制 `ControlTemplate`。

纯 UI 的 token、控件族、页面迁移批次和回归标准已独立固化为 [manager-ui-design-language-implementation-plan.md](manager-ui-design-language-implementation-plan.md)。该计划不参与业务功能、重建链路或自动维护改造，后续视觉工作以其为准。

new-api 默认 Web 前端提供了卡片和数据表的第二份参考：其有效模式是 token → 基础控件 → 数据表页面编排、首次 loading 与后台 refresh 区分、全宽宽表的固定表头和横向滚动、列预设/显示控制。WPF 的具体迁移和不照搬边界见 [new-api-ui-table-reference-analysis.md](new-api-ui-table-reference-analysis.md)。

## 新页面与导航模型

### 顶部导航

删除“状态”入口。顶部只保留：

1. 首页；
2. 配置 / 模组库（默认双栏）；
3. 设置与资产；
4. 任务中心悬浮入口，不占顶部常规导航。

用户只能通过顶部顶级入口回到首页、配置 / 模组库或设置与资产。页面系统不新增全局“返回”“关闭详情”“固定在左/右槽”动作；确有返回语义的独立工具页，应在该页自身提供明确的返回按钮。详情、工具、资产浏览均以页面或双槽承载替换，不再遮挡主窗口。

### 强制双槽页面

- Mod 详情：默认保持单槽，展示概览与基本操作。开启高级详情模式时转为双槽；如路由转换成本过高，可实现独立高级详情页，但该页顶部仍应保留基本 Mod 详情的关键卡片与上下文。
- cross-armor 计划与候选：固定双槽；左槽为 source/target 与映射，右槽为风险、影响、候选输出、报告和任务进度。
- Game Data 资产浏览与 archive 详情：固定双槽；左槽为 archive 列表，右槽为选中 archive / AssetKey 详情。

强制双槽页允许在各槽显示半宽卡片；但高级 Mod 详情的资产大表格及其他列数较多的数据表必须横跨左右槽位，占用完整工作区宽度，不能缩进任一半槽。打开这些页面时先立即显示 shell 与 loading 控件，再由各 pane 独立加载。离开或切换页面必须取消未完成的可取消读取。

### 需要迁出弹窗的功能

| 当前弹窗 | 目标页面 |
|---|---|
| `AdvancedModDetailsWindow` | 开启高级模式后的 Mod 详情双槽页，或独立高级详情页；资产大表格横跨全部槽位 |
| `CrossArmorTransferPlanWindow`、手动 source picker、candidate output | cross-armor 固定双槽工具页中的分步内容 |
| `GameDataIndexWindow`、`GameDataArchiveDetailsWindow` | Game Data 资产浏览固定双槽页 |
| `MaterialCandidateWindow`、Material 输出窗口 | Mod 详情工具页中的分步候选/输出面板 |
| `BackgroundTasksWindow` | 非模态任务中心浮层 / 页面抽屉 |

Same-key 不再占用独立输出页：单 Mod 手动操作直接生成到 Manager 的 `Output` 根目录下，并且不允许自动导入或部署。其长期定位是自动修复流水线中的底层能力，而不是需要用户配置输出参数的独立工具。

系统文件选择器和最终删除确认仍是合理的原生对话框，不纳入该迁移。

## 首页、状态和设置资产卡

### 移除状态页

`StatusPageViewModel` 的资产索引状态、手动索引构建和任务摘要迁入设置与任务中心。首页只保留精简健康摘要：

- 当前活动配置 / 已启用 Mod 数；
- Game Data：已设置、需检查、过期、可用之一；
- 在线资产：上次检查时间、是否允许自动更新；
- 当前任务：无任务或“n 项进行中”，点击打开任务中心。

首页不执行完整冲突扫描，不承载索引控制台，也不显示完整任务列表。

### 设置页的“游戏与资产”统一卡

卡片内部按依赖顺序分区，不再把“查看资产索引”挂在 Game Data 路径行上：

1. **游戏目录**：路径输入、浏览、打开、重置为自动检测；显示检测来源与路径有效性。
2. **Mod 库目录**：路径输入、浏览、打开、重置为推荐目录；目录迁移走单独向导，不放在普通编辑行。
3. **在线资产索引源**：仓库地址、重置默认源、立即检查 / 更新；显示最近成功、失败原因、版本/时间。
4. **自动更新在线资产**：开关 + 周期枚举（例如每启动、6 小时、1 天、7 天）；仅当距离上次成功检查超过周期时，启动时允许检查。
5. **自动检测 Game Data 过期**：开关 + 周期枚举；“检测”只做指纹比较，不能默认立刻触发完整重建。
6. **检测更新后自动重建损坏 Mod**：跟随 Game Data 状态检测设置；检测到更新后，依次重建 Game Data 资产缓存、比较全库 Mod 完整性，并修复所有护甲类损坏 Mod。该开关后续实现，本轮仅保留产品需求。
7. **立即操作**：立即检查在线资产、立即检查 Game Data 是否过期、重新建立资产索引、查看资产索引，以及“重建所有损坏的 Mod”。后者启动一次全量后台任务：重建 Game Data 资产缓存 → 比较所有损坏 Mod → 修复所有护甲类损坏 Mod。
8. **索引状态**：当前/过期/缺失/建立中、上次建立时间、Archive/AssetKey 数量、下一步建议。

“重建所有损坏的 Mod”在自动重建能力完成前仅作为临时手动入口，修复结果统一导出到 Manager 的 `Output` 文件夹，不自动导入、不自动部署。完整实现必须接入任务中心，报告三个阶段的进度、损坏清单、逐 Mod 修复结果与失败原因。

新增设置需要记录：`LastAssetMetadataCheckUtc`、`AssetMetadataCheckInterval`、`LastGameDataIndexCheckUtc`、`GameDataIndexCheckInterval`。启动自动检查必须进入后台任务系统并受周期限制；“索引过期”只提示用户或等待用户明确启动重建，不能与启动时的其他重任务无条件并发。

## 任务中心与消息中心

当前底部彩色通知只适合作为短时提示；`BackgroundTaskService` 只记录任务而没有消息历史、优先级、来源、进度或后续操作。两者应合并为一个**任务与信息中心**。

### 常驻入口

右下角保留一个统一的圆形/圆角悬浮按钮：

- 无任务：显示轻量铃铛/活动图标；
- 有进行中任务：显示数量和微型进度/呼吸动画；
- 有未读失败或警告：显示语义色角标；
- 点击：打开非模态右侧抽屉或工作区覆盖层；不再打开阻塞 `ShowDialog()` 窗口。

### 中心内容

- **进行中**：名称、原因、阶段、可取消性、可选进度、资源影响；
- **最近事件**：任务完成/失败、导入、部署、自动维护、用户操作结果；消息不应在 6 秒后丢失；
- **筛选**：全部 / 进行中 / 需要处理 / 已完成；
- **动作**：取消、重试、打开结果目录、打开报告、查看相关页面；
- **保留策略**：内存保留近期事件，必要时持久化最近历史；成功事件可自动折叠，失败必须保留直到用户确认。

`BackgroundTaskItem` 应新增 `Progress`（可空）、`Origin`、`StartedAt`、`UserVisibleReason`、`SuggestedAction` 和可选重试委托。`NotificationService` 改成向该中心写入 event；toast 只是 event 的短暂镜像。

## 配置页与模组库页

### 顶部卡片

- 模组库：只显示“模组库”标题、数量/简短说明、搜索和筛选。
- 配置页：只显示**当前配置名称**、活动状态、搜索和筛选；不再放 profile 下拉框和重命名输入框。

### 配置现有浮动菜单的收敛

现有配置页面已经通过 `PageActions` 注册“新建配置、设为活动配置、停用活动配置、重命名配置、删除当前配置、刷新配置”等动作，并由主窗口的 `FloatingActionCluster` 提供浮动菜单式入口。因此本轮不新建标题旁汉堡菜单；应保留并统一这个既有菜单入口，收敛其内容与交互，同时移除页面顶部常驻的 profile `ComboBox` 和重命名 `TextBox`。

- **切换配置**：作为浮动菜单的展开内容，使用统一枚举选择器；视觉为输入框，hover 时可看见上下模糊的相邻选项，支持滚轮、键盘和点击选择；选择后点击“切换当前配置”确认。
- **重命名**：作为“重命名配置”浮动动作的展开内容，显示 `输入新名称：[当前名称]`，输入完成后点击确认。输入仅在该低频动作展开时出现。
- 新建、设为活动、停用、删除和刷新继续复用既有动作模型；危险动作在菜单中使用危险样式，并在最终确认中说明不会删除库 Mod。

### 同步缺陷：删除库 Mod 后配置与详情滞留

根因已确认：Core `DeleteNodeAsync` 会正确移除所有 Profile entry；但 Manager `ModLibraryService.Remove()` 在删除后没有触发 `SnapshotChanged`。因此 `ShellViewModel` 不会调用 `ProfileService.ReloadFromLibrary()`，已打开的配置页和 Mod 详情保留旧快照。

首个功能修复批次必须：

1. `ModLibraryService.Remove()` 在成功删除后触发 `SnapshotChanged`；
2. Shell 收到快照变化后刷新所有已打开 slot，而不仅是当前页面；
3. 若 `SelectedModId` 已不存在，关闭/替换该详情页并清除选择；
4. profile 列表从新的 snapshot 立即移除该行；
5. 添加覆盖“删除库 Mod → Profile entries 移除 → 详情关闭”的集成/服务测试。

## 数据加载与预加载

- 页面 shell 立即创建，数据区域使用 loading/empty/error 三态；禁止为等待数据而延迟打开页面。
- 预加载仅做低成本、可取消、可缓存的事实：活动 Profile 状态、已打开 Mod 的基础 facts、最近访问 archive 的摘要。
- 重读取操作（全 Game Data index、完整 archive browser、Material closure、cross-armor catalog 全量读取）只在用户进入相应工具或明确操作后启动。
- 页面关闭、source Mod 切换、筛选条件快速变化时取消旧请求；结果必须按 generation/token 验证后才写入 UI。
- Library 和 Profile 列表采用增量更新或 `CollectionView` 过滤，避免每个状态变化都 `Clear()` 后重建全部卡片。

## 分批实施顺序

### 批次 0：规格和视觉基础

- 建立 `Themes/` token 与控件样式库；为按钮、输入、枚举、开关、卡片、列表、loading、empty/error 建立统一风格。
- 以 PCL 的“状态动画 + 清晰控件职责”为参考，写新控件而非拷贝其源码或视觉资产。
- 先在首页、设置页、库/配置顶部卡片试点，再替换全局控件。

### 批次 1：数据同步与任务基础（优先）

- 修复库删除同步缺陷。
- 扩展任务/事件数据模型，新增任务中心浮层和常驻入口；短时 toast 改为事件镜像。
- 不删除状态页，先让状态页和新中心共存以验证数据完整性。

### 批次 2：设置与资产整合

- 将资产索引状态/动作从状态页迁到设置页统一卡。
- 加入周期设置、上次检查时间和启动节流；禁止默认启动直接重建过期索引。
- 首页改为精简健康摘要。

### 批次 3：移除状态页与导航收敛

- 删除顶部状态入口、`WorkspaceMode.Status`、`WorkspacePageType.Status` 及 status page。
- 所有后台任务入口改指向任务中心；所有资产动作改指向设置/资产页。

### 批次 4：配置 / 库交互重构

- 顶部卡片收缩；复用并统一既有浮动操作菜单，将配置选择器和低频重命名输入作为其按需展开内容。
- 优化列表虚拟化、搜索防抖、增量同步、保持滚动和选择。

### 数据展示基础工作包：高级表格先行

- 建立 `DataTableCard`、`DataTableToolbar`、`DataTableEmptyState`、`DataTableSkeleton` 和行状态资源；统一 `DataGrid` 的表头、行状态、横向滚动、固定表头、截断 tooltip、数值/代码列。
- 建立列预设和列显示菜单；先支持高级数据表的默认列组与显隐，不要求首批实现任意列拖拽。
- 以高级 Mod 详情为第一个试点：开启高级模式后使用双槽，基本详情关键卡片保留在顶部，资产大表格横跨全宽。
- 以 Game Data archive 浏览为第二个试点，验证筛选、分页、行选择、右侧详情、加载取消与后台刷新不清空旧数据。

### 批次 5：弹窗迁入页面系统

- 先迁入高级 Mod 详情（默认详情保持单槽；高级模式转为双槽，资产大表格全宽）和 Game Data 浏览；再迁入 Material、cross-armor 分步工具。Same-key 直接输出，不建立独立页面。
- 每个工具先建立 page view model 和 loading/cancellation，再删除对应弹窗。
- cross-armor 计划刷新改为后台、防抖、可取消，禁止 UI 线程 `GetAwaiter().GetResult()`。

## 验收标准

- 新用户在首页能知道：当前配置是否生效、Game Data 是否需要处理、是否有任务需要关注。
- 所有重任务都能从任务中心看到原因、阶段、状态、失败细节和下一步。
- 删除库 Mod 后，不需要切页或手动刷新，配置列表立即同步，已打开详情自动关闭。
- 内部功能工具不再通过独立模态窗口阻塞主工作区。
- 状态页面移除后，资产配置和索引操作仍完整可用，且启动不会无条件抢占资源重建索引。
- UI 控件不再出现“同类元素不同形状、不同交互、不同语义色”的混用。
