# 按实例隐藏共用部件：做成管理器功能（规划）

日期：2026-11-13
状态：**待用户确认。确认前不改生产代码。**
前置：[交接](kit-instance-isolation-productization-handoff-20261113.md) · [方案与实机记录](kit-instance-isolation-plan-20261113.md)

要回答的问题（用户原话）：「如果我新加了替换神射手的护甲咋办？」

答案的形状：管理器导入或启用这个 Mod 时，告诉你它会连带改哪几套护甲；你点「转专属」，管理器把它改成只落在神射手身上，并写一条隐藏规则；随管理器一起部署的 Hider 按规则只在穿神射手的那个人身上藏掉原版共用部件。

---

## 0. 术语

| 词 | 含义 |
|---|---|
| 套 / kit | `game_data_authority_kits` 里的一条记录，用 `item_id` 标识。同名护甲可能有多条记录，例如 FS-05 有 `124623533`（民主官 NPC）、`3970674111`（玩家）、`1490803405`（未知） |
| 部件集 P(A) | 套 A 在 `game_data_authority_pieces` 里引用的全部 Unit（所有身形），**不含披风（slot 1）** |
| 独有部件 | 只被一个 `item_id` 引用的 Unit |
| 签名 | 一组用来认出「这个实例穿的是 A」的 Unit：`all` 全部在场、`none` 都不在场。只有一个独有部件时，签名就是 `all=[它]`，与爱弥斯的「标记部件」相同 |
| 原版资源 | 文件 ID 在游戏数据索引 `assets` 表里存在的资源。Mod 里 ID 不在其中的条目是它自己新增的，不会污染别人 |
| 污染 | Mod 覆盖了原版 Unit 或原版材质，而这些资源被不止一套护甲引用 |

资源类型 ID：Unit `e0a48d0be9a7453f`，材质 `eac0b497876adedf`，贴图 `cd4238c6a0c69e32`。

## 1. 范围

### 做

1. **规则文件与 Hider 改造**：Hider 不再写死规则，改读管理器写出的 `ArmorRegistry/kit-instance.rules`。
2. **随管理器部署 Hider**：部署时由管理器投放，不再手工导入 zip。
3. **发现污染**：按 Mod 算出它连带影响的护甲，在 Mod 详情页和部署问题列表里点名。
4. **转专属**：对一个 Mod 选定目标套 A，生成「只在 A 身上生效」的派生 patch 和一条隐藏规则；可撤销。
5. **爱弥斯迁移**：爱弥斯民主官改由规则文件驱动，效果与现在的手工版一致。

### 不做（本轮）

- 只改材质或贴图、不带 Unit 的 Mod（纯换色）：只提示污染，不能转专属。按实例换材质（`Unit.set_material`）以后再说。
- Mod 覆盖原版贴图、而这张贴图被原版材质引用时，没法按实例隔离：保留原样并提示「仍全局生效」。
- 取消隐藏：规则被移除后，已经藏掉的实例不主动显示回来，要等部件重新生成（重进飞船或打开军械库）。这与交接 §5 的验收一致，也避免 Hider 跨帧持有 Unit 句柄。
- 队友场景（方案 Q5）不做专门处理。按设计，队友穿 A 时他身上也有签名，本机同样隐藏，显示与 Mod 一致。
- 不碰 `generated_customization_armor_sets.dl_bin`，不用 ffi，不调用 `IdString64`。

## 2. 规则文件协议 `kit-instance.rules`

位置：`<ArmorRegistry>/kit-instance.rules`，也就是 `wardrobe.links` 的同目录（`%LOCALAPPDATA%\CowboyBingus\Helldivers2\ArmorRegistry\`，加载器提供 `log_directory` 时取它的上一级）。

```text
schema=1
revision=7
# 每条规则一行。字段用 ; 分隔，列表用 , 分隔，ID 一律 16 位小写 hex。
rule=name:aemeath_democracy_officer;radius:0.30;all:82595b5d94c57343;none:;hide:8d02a82d0c214171,3bdfa900f32cd83f,...
```

| 字段 | 约束 | 含义 |
|---|---|---|
| `schema` | 必须为 `1` | 其它值整份视为无效 |
| `revision` | 非负整数，必填 | 管理器每写一次加一 |
| `name` | `[a-z0-9_-]{1,64}`，文件内唯一 | 日志用 |
| `radius` | `0 < radius <= 1.0` | 判定「在同一个角色身上」的距离，米 |
| `all` | 1 至 8 个 ID，必填 | 这些 Unit 都在某个坐标簇里，才认定该簇穿的是 A |
| `none` | 0 至 8 个 ID | 簇里出现其中任何一个就不算 A（用于 A 的部件集是另一套子集的情况） |
| `hide` | 1 至 128 个 ID | 认定为 A 的簇里，这些 Unit 的实例调用 `set_unit_visibility(false)` |

整份文件上限：64 条规则、64 KiB。`#` 开头为注释，空行忽略，未知键忽略（为以后加字段留余地）。

**读写约定，沿用 `wardrobe.links`：**

- 管理器写临时文件后 `File.Move(..., overwrite: true)` 原子替换。
- 没有任何规则时**照样写一份空规则文件**（只有 `schema` 和 `revision`），以覆盖上一版。这是 `8d36210` 修过的坑：不覆盖，运行时会继续执行过期规则。
- Hider 解析失败、schema 不对、超限时，**保留上一版**，日志写一行原因，并且同一份坏文本不重复记录。
- 文件不存在等同于没有规则。

## 3. Hider 改造（`kit_instance_hider.lua` → 0.2.0）

1. **读规则**：每 2 秒用 `io.open(path, 'rb')` 读一次，最多读 64 KiB + 1 字节；文本没变就跳过；变了就解析，成功后重建查找表。**这里要用 Lua 标准库 `io`，见决策 D1。**
2. **签名判定**：扫描时记录所有 `all`、`none`、`hide` 里出现的 ID 的实例坐标。一轮扫描结束后，以每条规则 `all[1]` 的实例为锚点，检查其余 `all` 是否都在 `radius` 内、`none` 是否都不在，得到「已确认的锚点」。下一轮扫描中，`hide` 里的实例只要离某个已确认锚点在 `radius` 内就隐藏。
   - 代价：新出现的实例最晚约 1 秒（两轮）后被藏。现在是 0.5 秒。刚进飞船或刚打开军械库时可能闪一下原版部件，这是已知限制。
   - 只有一个 `all`、没有 `none` 时，行为与 0.1.0 等价。
3. **日志**：只在 `markers` 或 `hidden` 变化、或规则 revision 变化时写。不再因为 `left_visible` 变化而写。上限仍是 48 KiB。
4. **独占 boot 下也能写日志**：没有加载器的 `open_log` 时，退回到 `io.open(<base>/Logs/KitInstanceHider.log, 'ab')`，做法与 `armor_override_runtime.lua` 相同。
5. **规则移除**：新的一版里不再有的规则，下一轮起不再隐藏；已经藏掉的不恢复（见 §1）。
6. 其余不变：每帧最多 300 个 unit，每 0.5 秒开一轮，`set_unit_visibility` 连续失败 10 次就停手，不跨帧保留句柄。

**API 范围**：引擎调用仍只有 `Application.worlds`、`Application.time_since_launch`、`World.units`、`Unit.alive`、`Unit.resource_name`、`Unit.world_position`、`Unit.set_unit_visibility`、`Vector3.x/y/z`，全部在 `hd2pbx_api.txt` 里。新增的只有 Lua 标准库 `io.open`（D1）。

**离线测试**（`tests/test_kit_instance_hider.lua`，用 `run_lua_test.py` + lupa 跑）新增：规则解析的正常与各种非法输入；坏文件保留上一版；空规则；规则移除后不再隐藏；`all` 多件与 `none` 排除；日志节流；无加载器时退回 `io` 写日志。保留现有用例：调用白名单之外的 API 直接报错。

## 4. 部署 Hider

**何时投放**：当前启用的 Mod 里至少有一个处于「已转专属」，或者存在 §8 的内置规则（爱弥斯迁移用）时投放。否则不投放，但规则文件照样写成空的。与护甲映射是否开启无关，因为用户现在的映射模式可能是关闭，而爱弥斯靠的就是 Hider。

**怎么投放（决策 D2）**：跟随「谁占着 boot」。

| 当前状态 | Hider 去哪 |
|---|---|
| 护甲映射或物理选了「独占 boot」（管理器自己占 boot） | 作为一个块追加到**同一个** boot 文档的**最后**，与现有「映射 + 物理合并成一个文档」的做法相同 |
| 都不占 boot | 生成一个独立 addon patch（归档 `9ba626afa44a3aa3`，资源名 `mods/hd2modmanager/kit_instance_hider`，首行 `-- HD2-Addon:` 标记），由第三方加载器（MDL3 等）加载。与现有护甲外置入口 addon 用同一套打包代码 |
| 都不占 boot，并且库里没有任何提供 boot 的 Mod（没有加载器） | Hider 不会运行。部署问题列表给一条 Warning：「按实例隐藏需要一个 Lua 加载器（如 MDL3），或把护甲映射/物理设为独占入口」 |

**`update` 钩子的顺序**：`armor_override_runtime.lua` 现在直接 `update = function() ... end`，不调用之前的 `update`。如果 Hider 先装、映射运行时后装，Hider 的钩子会被整个替换掉，静默失效。改法：映射运行时改为包装前一个 `update`（与 Hider、物理运行时一致），并加一条 Lua 测试锁住。独占 boot 下 Hider 块放最后，两种顺序都安全。**这是对现有映射运行时的一处小改动，见决策 D3。**

**生成产物的位置**：与现有 addon 一样放在 `<mods>/.runtime/` 下按内容指纹命名的目录，指纹覆盖实际写出的字节。

## 5. 发现污染

### 5.1 数据

- Mod 覆盖了哪些资源：`ModContentFacts.Structure.Assets`，按类型取 Unit、材质、贴图三类，再用 `assets` 表筛出原版 ID。
- Unit 属于哪些套：`game_data_authority_pieces`（`unit_file_id` → `item_id`），名字取 `game_data_authority_kits.display_name`。
- 材质被哪些 Unit 引用：索引里**没有**这张表。新建一个派生缓存 `data/indexes/armor-unit-materials.json`：对 `game_data_authority_pieces` 里出现过的全部 Unit，从游戏数据读 TOC，用 `UnitMaterialReferenceReader` 取材质 ID。缓存键为索引库的生成标识，索引重建后自动失效。首次在后台构建，构建好之前，界面写「材质影响分析中」，只显示 Unit 部分的结论。
- 贴图：本轮不建「贴图 → 材质」的反查，只统计 Mod 覆盖了几张原版贴图，提示「另有 N 张原版贴图被全局替换，影响范围未分析」。

### 5.2 结论怎么算

对 Mod M：受影响套 = 引用了「M 覆盖的原版 Unit」或「绑定了 M 覆盖的原版材质的 Unit」的所有 `item_id`，按 `display_name` 加 `item_id` 列出。只影响一套的不算污染，不提示。

### 5.3 在哪显示

1. **Mod 详情页**新增一张卡片「共用部件」：
   - 「这个 Mod 会影响 6 套护甲：FS-05 神射手（124623533）、CE-64 …」，可展开看每套是因为哪些 Unit 或材质。
   - 下面是「转专属」按钮（§6）。已转专属时显示目标套和「撤销专属」。
2. **部署时**：每个启用中、有污染、且没转专属的 Mod，在部署问题列表里加一条 Warning：「『X』会连带改变 CE-64、CM-17 等 5 套护甲，可在详情页转专属」。不阻断部署。
3. 导入完成后，如果导入结果页能挂提示，就挂同一句话；实施时先核实导入流程的提示通道，没有现成通道就只做 1 和 2，不新造弹窗。

## 6. 转专属

### 6.1 用户流程

1. 详情页点「转专属」，选目标套 A。候选只列「Mod 覆盖的 Unit 至少有一个属于它」的套，并标出哪些没法转（没有独有部件，或独有部件不够用）。
2. 预览，列出：哪些 Unit 搬到 A 的哪个独有部件上；哪些原版部件会在 A 身上被隐藏，以及原因（被搬走，或材质被 Mod 改了）；哪些材质和贴图会改成新 ID；哪些内容做不到隔离（仍全局生效）。
3. 确认后生成派生 patch 和规则记录。下次部署后生效。
4. 「撤销专属」：删掉派生 patch 和规则记录，下次部署后回到 Mod 原样。

### 6.2 算法（纯函数，可离线单测）

输入：Mod 里的条目（Unit、材质、贴图），目标 A，P(A)，每个 Unit 的引用套集合 Owners(u)，A 的 Unit 绑定的材质，Mod 自己的 Unit 和材质里的引用。

1. **分类 Mod 覆盖的原版 Unit**
   - 已在 A 的独有部件上：原样保留，作为**承载件**。
   - 在 A 的共用部件上：要搬到 A 的一个空闲独有部件上（Unit 内容字节不动，只改条目 ID）。优先同 slot，其次任意 slot，按 ID 排序保证结果稳定。被占用的独有部件原本的原版外观会被 Mod 内容取代，预览里写明。空闲独有部件不够时**整个转换失败**，不做半套（决策 D5）。A 完全没有独有部件时，模型无处承载，不能转专属（例外见 D9）。
   - 不在 P(A) 里：不处理，预览中列为「仍全局生效」。
2. **材质**：对 Mod 覆盖的每个原版材质 m：
   - 如果 Mod 自己的 Unit 引用了 m：给 m 分配新 ID，并把这些 Unit 材质表里的 m 改成新 ID（TOC `0x70` 指向的表，u64 原地替换）。
   - 不再以原 ID 输出 m，也就是去掉这条全局覆盖。
   - A 里绑定了 m、又不是承载件的 Unit，全部进隐藏集。**这里假定「Mod 改原版部件的材质」的意图是把那个部件藏掉或换掉**，爱弥斯就是这种情况。决策 D4。
3. **贴图**：被改名后的材质引用的原版贴图，改成新 ID，并改写材质里的引用（`StingrayMaterialReferenceReader` 能读出位置，u64 原地替换）。没被这些材质引用的原版贴图原样保留，提示「仍全局生效」。
4. **新 ID**：`StingrayHash("hd2modmanager/kit/<A 的 item_id>/<原 ID hex>")`，同一个 Mod 重复转换结果不变。生成后在 `assets` 表里查重，撞上原版 ID 就加盐重算。
5. **隐藏集** = A 里被搬走的共用 Unit ∪ 第 2 步加入的 Unit，再减去承载件和披风。
6. **签名**：`all = [一个承载件]`，按 ID 排序取第一个；没有承载件时（Mod 只改了材质、Unit 都不在 P(A) 里）取 A 的任意一个独有部件。`none` 留空，`radius = 0.3`。
   - 协议里保留 `all` 多件和 `none`，是给 D9 的退路用的：承载件被几套同名记录共用时，可以用 `none` 把其中不想要的那套排除出隐藏范围。本轮编译器只在 D9 选了退路时才会产出它们。
   - 玩家穿的神射手 `3970674111` 的左肩 `90b57e54` 与 `1490803405` 共用，它到底有没有独有部件，实施第一步先查（§9 P0）。这直接决定「替换神射手」这个问题能不能按本方案回答。

### 6.3 产物放哪（决策 D6）

- **派生 patch** 写进该 Mod 节点目录的 `Overwrite/`，与根上 patch 同名。按 `ModNodePayloadLayout` 的现有语义，它会顶掉同名根 patch，原文件一个字节都不动。如果 `Overwrite/` 里已经有同名文件（装饰重建等功能的产物），本轮拒绝转换并说明原因。
- **规则记录**写进 `<mods>/.hd2modmanager/kit-instance.workspace.json`，按 ModNodeId 存：目标 `item_id`、签名、隐藏集、生成时 Mod 内容的指纹。
- **部署时**，只把**启用中**的 Mod 的记录编译成 `kit-instance.rules`。停用 Mod，规则就随之移除（交接 §5 最后一行）。Mod 内容指纹和记录不一致时（Mod 被更新了），这条记录不生效，部署问题列表里报 Warning，让用户重新转换。

## 8. 爱弥斯迁移（决策 D7）

库里的爱弥斯已经手工去掉了 9 个隐藏材质，管理器再分析它，算不出隐藏集。两条路：

- **A（推荐）**：用户提供原版爱弥斯 zip（带 9 个隐藏材质的那份），导入后对它点「转专属」，目标选 `124623533`。按 §6.2，预期得到 `all=[82595b5d94c57343]`、隐藏集为那 20 个 Unit、9 个材质被去掉。这正好是一次端到端验收：结果应与手写规则逐项一致。库里那份手工改过的副本由用户决定删除或保留。
- **B**：保留库里手工版，管理器写一条内置规则（就是 0.1.0 里写死的那条），挂在这个 Mod 的 ModNodeId 上。

## 10. 风险与未知

- **`io` 是否算白名单之内**（D1）。`hd2pbx_api.txt` 只列引擎命名空间。物理运行时 2.1.24 本身（也就是这张表的来源）和现在的映射运行时都在用 `io.open`，但用户此前没有明确确认过。
- **玩家神射手可能没有独有部件**。没有的话，本方案对它只能提示污染、不能转专属，除非走 D9 的退路。P0 先查清。
- **一个 patch 里放两个 Lua 资源**：本方案不这么做，Hider 单独一个 addon patch，避开加载器对多资源 patch 的未验证行为。
- **把材质覆盖当成隐藏意图**（D4）可能误判纯换色意图。预览会逐件列出，用户可以取消。
- **签名半径 0.3 米**：站进民主官身体里会被误藏。这是 0.1.0 已知的限制，不变。
- **新出现的实例最多约 1 秒后才被藏**，比 0.1.0 多 0.5 秒，可能看到原版部件闪一下。
- **材质缓存首次构建耗时**：需要读几千个 Unit 的 TOC，放后台做，不阻塞界面。P2 实测后记录耗时。
