## P1 白模：合成底色 + 没有 matcap 的重金属不该整包失败 —— **已完成（`b6cbebc`）**

**症状**：一批导入后某些 Mod 只有材质没有模型，或者模型是一片纯白/纯灰。

**根因（已定位到具体分支）**：
1. `$basetexture` 指向 `vgui/white` 而包里没有 `white.vtf`（milltina 的 6 个金属全是这个写法）
   → `syntheticBase` → `matcapIsSurface` 判真，但 VMT 里没有 `$matcaptexture`
   → 走"判定 matcap 承载表面却没有 matcap"的失败分支 → 该材质整条失败。
   6 个材质全挂在同一条分支上，产物里只剩 `*_fallback`。
2. 即使不失败，平坦金属色也没有来源：`$color`（Source 线性 0..1）从没被读过，
   于是只能退成兜底灰 —— 银不是银、金不是金。

**改法**：`syntheticBase` 且 VMT 没声明 matcap 时**不算失败**：保留合成底色，走 `advanced`，
底色取 `$color`；`$color` 缺失才退成中性灰。

**判据**：离线跑 milltina 的 6 个金属（`Silver / gemstone / gemstone_extra / gold / pearl / fur`），
`materialGap.fallback` 归零，且各材质底色 = 各自 `$color`（灰/金/宝石红），不再出现 `*_fallback`。

**结果**：milltina 材质包 54 个材质，failures 0、兜底 0；`HD2MOD_MATCAP_DEBUG=1` 打出的
合成底色 = silver 117.0 / gemstone_extra 69.7 / gold1 238.0，正好是各自 `$color` 的
线性→sRGB 值。顺带修掉 `VmtDocument` 的一个通用缺陷：不加引号的多段数值只吃到第一个
token（`$color 0.462 0.322 0` → `"0.462"`，剩两个变成垃圾键）。
**金属度仍未跟上**（`$phong + $envmap` 算不算金属证据需要实机 A/B，见文末"暂缓"）。

## P2 自定义素体必须依附 Mod —— **已完成主体（本轮）**

**现状问题**：自定义素体现在可以脱离 Mod 独立存在，用起来不好用。

**已经做到的一半**（`ad9a302`）：
- 拒绝单独删除 VPK 模组持有的素体，且提示点名是哪个 Mod；
- 所有权的事实来源 = Mod 目录里的 `custom-model.json`（`VpkCustomModelFile.ReadOwners`），
  扫库而不是查注册表。

**本轮做完的四件事**：

1. **删掉"新增自定义素体"入口**。原来那条路（`AddCustomModel` →
   `CreateDefaultCustomModelPieces`）给每个部位 × 两种体型**凭空编造 16 位 unit id**：
   既不来自任何 patch，也不可能被部署，运行时按它去找模型一个也找不到 ——
   这就是"素体不太好用"的根因。现在素体只有两条产生路径：
   Mod 详情页的「一键转为自定义素体」、导入 VPK 时的自动登记，两者都落成 Mod 目录。
2. **删 Mod ⇒ 素体一起走**。新增 `CustomModelOwnershipService`（Core，可离线测）：
   读工作区 → 按库里的 `custom-model.json` 判归属 → 孤儿连同**引用它的映射**一起删。
   触发点有两处：Mod 删除成功后（`ModLibraryService.PruneOrphanCustomModelsAsync`）、
   护甲映射页刷新时（有未保存改动则跳过，否则删掉的记录会被那次保存复活）。
3. **一键转素体改成强制导入**。删掉"自动导入 Mod 库"复选框：不导入就只剩一具没有
   归属的素体。导入失败时**回滚**刚登记的素体并报错，不留"登记了但没有 Mod"的半状态。
4. **同 key 替换而不是追加**（`CustomModelConversionService`）：重跑同一次转换
   不再堆出两个同名素体。
5. 顺带：`README.md` 里"素体保存在 workspace.json"那句改写成"素体属于某个 Mod，
   注册表只是它的投影"。

**验证**：真实库上跑了一次启动对账 —— 17 个素体 → 12 个，正好清掉 5 个孤儿
（milltina 的转换产物，Mod 从未导入成功），299 条映射一条没动（没有映射指向孤儿）。
单测 `CustomModelOwnershipTests` 6 条：孤儿与其映射一起删 / 全有主时不动 /
库目录不在时一个字都不删 / 预演与真删答案一致 / 撤销登记只摘一个。

**仍未做（继续挂在 P2 下面）**：
- **重复 Mod 目录**（P4）会让同一个 key 有两个持有者（`ReadOwners` 保留第一个）——
  本质是"重导入不幂等"，与 P4 一起做。
- 素体的**件表编辑**已经整块删掉（组件编辑器不要了，见下），将来跟 section 编辑一起
  在 Mod 详情页重做。要收敛"缺身形"得先决定它该由转换器补齐还是由用户手工造。

**第二轮（用户反馈后）**：

6. **行上的「删除自定义素体」按钮也去掉了**。素体只能随 Mod 删除，留着这颗按钮等于
   永远点出一句"请移除对应模组"。`CustomModelOwnershipService.PruneAsync` 仍在
   （删 Mod 时 + 页面刷新时各跑一次），只是不再有"手动删"这个入口。
7. **删 Mod 后护甲映射页会自己刷新**。挂的是 `library.ModContentFactsChanged`
   里 `Removed` 那一路，而不是在四个删除按钮旁边各写一次（库页 / 详情页 / 配置页 /
   命令行任务），否则少接一条就会出现"素体还在列表里"。有未保存改动时**不重读**：
   手里那份文档会把刚删掉的素体写回去。
8. **组件编辑器（"视觉组件"面板）整块删除**：面板、两条行动作（编辑视觉组件）、
   组件行模板、`AddComponentRow`/`Merge/Split/AddMissing`/`NewGeneratedUnit`、
   `Wardrobe` 树，以及 `RuntimeArmorComponentRowViewModel`/`GroupViewModel`、
   `RuntimeArmorModelPieceEditorViewModel`。素体只剩「改名」这一项编辑。
   `pieceOverrides` / `targetModes` **仍然原样读写**（协议字段没动，老数据不会丢），
   只是暂时没有编辑入口 —— 等 section 编辑加强到 Mod 详情页时再接。
9. **改名被还原的真凶找到了**：名字只写进了工作区，而重构建（`--reuse-model`）与
   重新登记都用 `custom-model.json` 里的名字，于是**下一次后台重构建就把名字盖回
   VPK 文件名**。两处一起修：
   - 改名时同时写 `custom-model.json`（`VpkCustomModelFile.TryRenameOwned`）；
   - CLI 两处登记都改成**先读工作区、已有的名字优先**
     （`CliApplication.ResolveRegisteredModelName`）——首次登记时工作区里还没有记录，
     所以照常用转换名，语义不变。

**设计取向（已落地）**：
- **不引入 schema 字段**。所有权继续以"Mod 目录里的 `custom-model.json`"为唯一事实来源，
  协议与 Lua 契约一行不动。理由：加字段就要改协议版本、改 Lua 解析，
  还要处理"字段与实际目录打架"的第二种真相。
- **代价：无法区分"Mod 被删了"和"这具素体压根没被导入"**（两者都没有那份文件），
  于是**一律按孤儿删**。这正好符合产品口径（素体只允许由两条转换路径生成），
  但意味着老版本手工建的 `custom-N` 也会被清掉 —— 所以清理时**通知 + 记日志并点名**，
  不是无声消失。实测库里那 5 个孤儿全是"转换成功但 Mod 没导入"的半成品，不是手建数据。
- **库目录不存在时一个字都不删**：那种状态更可能是盘没挂上 / 路径配错，
  按字面执行会把整份注册表清空（一次磁盘故障换掉用户所有映射）。

## P4 重导入不幂等 —— **已完成**

**症状**：同一个包导入两次，库里多一个 `X (2)` 目录。真实库上量到 **68 组**
（文件名 + 字节数完全相同）这样的重复，全部属于同一个宿主 `Cow_QiPao_Milltina_Bill`
（一个 68 色材质合集被整批导入了两次）。

**判据**：`VpkSourceIdentity.FindExistingMod`（Core，可离线测）——
Mod 目录根上躺着**同一个** VPK（文件名 + 字节数都相同），且该目录有 `vpk2patch/`。

**为什么字节数必须比**：同名但内容不同的两份包（作者发了第二版、或两个人各自把包
命名成 `材质.vpk`）若按同源处理，等于**覆盖掉别人的 Mod**；而多建一个只是让人烦。
两个方向的代价差得远，所以保守。

**改法**：
- 命中已有 Mod ⇒ 走 `--reuse-model`（沿用旧 `custom-model.json` 的 key 与 unit id 基），
  产物换进那个 Mod 的 `vpk2patch/`，**不建新节点**：名字、位置、启停、选项关系、
  `Overwrite/`、`wardrobe.json` 全部保留。
- 换载荷的规则抽成 `VpkPayloadSwap`（Core）：只读属性先清后补、保留文件
  （`custom-model.json` / `components.json`）不备份不删、旧载荷先备份再删。
  重构建与导入共用这一份 —— 以前是两份各写一遍，迟早漂移。
- 物理参数嵌入抽成 `VpkPhysBoneEmbedder`：**必须在换完之后、在真正的 Mod 目录上跑**
  （它要靠目录里那份 .vpk 找 jiggle 骨），而且**必须先嵌参数再把只读补回去**。
- 报告里区分"新建"与"更新原有 Mod"；命中多个同源目录时点名"库里另有 N 个同源 Mod"。
- 同一批里一个目标只更新一次（一个压缩包放两份相同 VPK 真会发生，后一个会静默盖掉前一个）。

**以后还会不会产生这种重复：不会。** 判据就是"同源就更新"，所以再导同一个包只会更新
原来那个。唯一会产生新目录的情况是**换了文件内容**（字节数不同）—— 那是新版本，本来就该
是新 Mod，不算重复。
