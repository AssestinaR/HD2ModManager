## P1 白模：合成底色 + 没有 matcap 的重金属不该整包失败

**症状**：一批导入后某些 Mod 只有材质没有模型，或者模型是一片纯白/纯灰。

**根因（已定位到具体分支）**：
1. `$basetexture` 指向 `vgui/white` 而包里没有 `white.vtf`（milltina 的 6 个金属全是这个写法）
   → `syntheticBase` → `matcapIsSurface` 判真，但 VMT 里没有 `$matcaptexture`
   → 走"判定 matcap 承载表面却没有 matcap"的失败分支 → 该材质整条失败。
   6 个材质全挂在同一条分支上，产物里只剩 `*_fallback`。
2. 即使不失败，平坦金属色也没有来源：`$color`（Source 线性 0..1）从没被读过，
   于是只能退成兜底灰 —— 银不是银、金不是金。

**改法**：`syntheticBase` 且 VMT 没声明 matcap 时**不算失败**：保留合成底色，走 `advanced`，
底色取 `$color`；`$color` 缺失才退成中性灰。

**判据**：离线跑 milltina 的 6 个金属（`Silver / gemstone / gemstone_extra / gold / pearl / fur`），
`materialGap.fallback` 归零，且各材质底色 = 各自 `$color`（灰/金/宝石红），不再出现 `*_fallback`。

## P1.5 跳过理由不能是空的

`VpkImportKind` 判成 unsupported 时 `skipReason` 目前可能是空串（Kaguya 的 `外套关.vpk`：
14 VMT + `addoninfo.txt` + `addonimage.jpg` = 16 条目，超 12 条目上限就被判成 unsupported，
用户看到一条没有任何理由的"跳过"）。任何跳过/失败都必须带一句能照做的理由。

**判据**：`VpkImportService` 产出的每条 skip/failed 记录都有非空 reason（加单测）。

## P2 自定义素体必须依附 Mod（本轮新记）

**现状问题**：自定义素体现在可以脱离 Mod 独立存在，用起来不好用。

**已经做到的一半**（`ad9a302`）：
- 拒绝单独删除 VPK 模组持有的素体，且提示点名是哪个 Mod；
- 所有权的事实来源 = Mod 目录里的 `custom-model.json`（`VpkCustomModelFile.ReadOwners`），
  扫库而不是查注册表。

**还缺的（本轮要做的）**：

1. **仍然可以手建**。护甲映射页有"新增自定义素体"动作
   （`ArmorRegistryPageViewModel.cs:149` → `AddCustomModel()`，`:1738`），
   它用 `CreateDefaultCustomModelPieces()`（`:1813`）**凭空编造 unit id**：
   每个部位 × 两种体型各造一个 16 位 hex，既不来自任何 patch，也不可能被部署。
   这就是"不好用"的根因 —— 运行时按这些 unit 去找模型，一个也找不到。
   → 删掉这个入口，`custom-model` 只能由两条路生成：
     **一键转为自定义素体**（`CustomModelConversionService`）、
     **导入 VPK 时自动登记**（`CliApplication.cs:2828` 那段）。
2. **删 Mod 不清理注册表**。删除走 `ModLibraryManager.DeleteNodesWithResultAsync`，
   护甲注册完全不知情（`ModLibraryService` 里没有任何 Vpk/注册表联动），
   于是工作区里留着指向已不存在 Mod 的素体，映射还指着它。
   → Mod 删除成功后触发一次对账（reconcile），清掉失去持有者的素体 + 引用它的映射。
3. **一键转素体可以不导入**。`CustomModelConversionBottomBarViewModel.ImportToLibrary`
   是用户可选项；不勾选时 `custom-model.json` 落在库外的输出目录，
   注册表里有主、库里没有 Mod —— 违反"必须依附"。
   → 生成后必须先成为 Mod 才登记（或登记前回填持有者），不能留这种半状态。
4. **重复登记**：`CustomModelConversionService.cs:210` 直接 `Append(plan.Model)`，重跑同一次转换
   会在工作区堆出同 key 的多份记录（CLI 那条路已经在做同 key 替换，管理器这条没有）。
5. **重复 Mod 目录**（P4）会让同一个 key 有两个持有者（`ReadOwners` 目前保留第一个）。

**设计取向**：
- **不引入 schema 字段**。所有权继续以"Mod 目录里的 `custom-model.json`"为唯一事实来源，
  协议与 Lua 契约一行不动；工作区读到模型后做一次对账：有主的留着，无主的视为孤儿。
  理由：加了字段就要改协议版本、改 Lua 解析、还要处理"字段与实际目录打架"的第二种真相。
- **README 里那句"自定义素体保存在 `.hd2modmanager/armor-registry.workspace.json`"要改写**，
  改成"素体属于某个 Mod，注册表只是它的投影"。

**开放决策（做到这条时先确认）**：
- 老库里手建的 `custom-N`（没有 `custom-model.json`）怎么处理：一次性提示迁移让用户选保留/删除，
  还是直接按孤儿清掉。倾向**先提示**，不静默删用户的旧数据。
- 素体建好之后还允许手工改件表吗？倾向保留"改名 / 启停 / 换 unit"，但不再允许"凭空增件"
  （新增的件没有对应部署产物，只会重现同一个坑）。

**判据**："新增自定义素体"入口消失；手建路径加单测证明不可达；删 Mod 后工作区里对应素体与
映射一并消失（单测）；一键转素体不导入时不会留下无主素体；重跑不重复登记。

## P3 开关包识别系统性重做

`VpkImportKind` 现在只认第一类，判据是魔数（`MaximumSwitchEntries = 12`、
`MaximumSwitchMaterialBytes = 64 * 1024`）。实际有三类：
`$no_draw` 覆盖（隐藏几何，已支持）、`$basetexture` 替换（`MaterialVariant`，有分类不产出）、
参数覆盖（描边关 / 手套关 / 光泽感肌肤关 / 表情切换，**整包跳过**，日志里 7 个）。
→ 改成内容型判据（看 VMT 差在哪，而不是数条目数），三类都给出明确结果或明确理由。
