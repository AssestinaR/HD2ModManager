## 关键发现：同一接口有不同基址视图

实机只读快照（仅对当前模块指纹成立）：

```text
[game.dll+3326308] = exe+27c8d80  (master root)
[master+e0]       = exe+27cab00  (已验证 link API table)
[master+08]       = exe+27cab40  (link API table + 40)
```

因此仅搜索 f8/100/108/110 会漏掉通过 `master+8` 调用的同一接口：

| link 表偏移 | master+8 视图的偏移 | EXE 函数 RVA |
|---|---|---|
| f8 | b8 | 3361c0 |
| 100 | c0 | 336240 |
| 108 | c8 | 3362c0 |
| 110 | d0 | 336310 |

这里说的是地址算术和已采到的表内容，不是凭函数语义猜出的映射。
根指针前后相同不等于原子快照；仍需在每次诊断时验证。

## 一条已经落到具体代码的静态链

第二轮 `game.dll-12ad186.asm.txt` 中：

```text
game+12ad1ac: mov rax,[rip+2079155]  ; RIP 目标 = game+3326308
game+12ad1b3: mov r9d,r15d
game+12ad1b6: mov edx,[r14+rdi+18]
game+12ad1bb: xor r8d,r8d
game+12ad1be: mov rcx,[rip+21beddb]
game+12ad1c5: mov [rsp+20],r12d
game+12ad1ca: mov r10,[rax+8]
game+12ad1ce: call [r10+c8]
```

在本次表快照成立时，`[r10+c8]` 使用 exe+27cac08，
就是已验证的 exe+3362c0（enqueue_node_link）。
此路径上参数装配已可见，但它们的对象身份/生命周期仍未知。
周围有 0x58 步长记录、变换数据与若干句柄检查，不能据此命名为护甲控制器。
捕获的 exception range 从 12ad05a 开始，不应当把这个范围开始地址当作函数入口。

## 为什么没有把筛选出的 5 条直接当成正确调用

V7 对 780 条 f8/100/108/110 字节候选增加“前 256 字节有 MOV disp=e0”
预筛选，留下 5 条，均能离线解码，无记录截断。
逐条追寄存器来源：

- 1041156 / 10411b1：master+128，排除为目标 link 表。
- 108fe56：master+40，排除。
- 12acce4 / 12ad186：master+8，但偏移 f8 实际是 link 表+138，
  也不是目标连接函数。
- **真正有用的 c8 调用位于最后一条的相邻代码中（12ad1ce）**。

故 V7 是降噪工具，而非完整查找器；不能把 5/780 作为召回率或认为没有其他入口。
指令解码验证不等于运行时调用观察。
