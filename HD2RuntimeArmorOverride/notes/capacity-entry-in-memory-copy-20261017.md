# 容量入口：资源里有，但要走**内存副本**而不是改文件（2026-10-17）

## 用户给的事实

* `generated_unit_customization_settings` 等资源里**确实有**槽位/层数相关的配置
* 管理器能解包这些文件
* 但**文件本身受哈希保护，改了过不了校验**

## 为什么这不等于堵死

我们现在的护甲映射运行时**从来没有改过文件**。它做的是：

1. 定位游戏加载后的**内存副本**（`runtime.status` 里的 `blob_base` / `index_base`）
2. 往那块内存写新的 Kit / Piece 数据
3. 游戏读内存，不读文件，所以**不触发文件哈希校验**

同理：如果 `generated_unit_customization_settings` 的**内存副本**里有
"每部位层数"或"bank 数"的字段，那么**在内存里改它**就是数据写入
（反作弊实测允许），不是改代码、也不是改文件。

## 反作弊边界回顾（三次实测的结论）

| 行为 | 可用 |
|---|---|
| 读游戏内存（`ReadProcessMemory` 自己进程） | ✅ |
| 写游戏**数据**（注册表 blob、协议） | ✅ |
| 替换**资源资产**（patch 归档） | ✅ |
| 改**资源文件**（磁盘上的 `dl_bin`） | ❌ 哈希校验 |
| 改**代码段**（`VirtualProtect` + 写） | ❌ 反作弊判定「可疑程序」 |

**内存副本这一格是空的——既没被证明可用，也没被证明不可用。这是唯一还没试过的扩容入口。**

## 探针要做的事（纯读优先，零风险）

用户建议继续用独立探针 Lua 探测。分两阶段：

### 阶段 1：纯读，定位配置

1. 用 `Mod Bindings Menu` 那套 `__asm__` 绑定 + `GetCurrentProcess` +
   `ReadProcessMemory` 读自己进程（不需要 `VirtualProtect`，安全）
2. 从 `game.dll + 0x3326d20` 拿到记录数组基址（护甲实例 bank 的基址，已验证）
3. 扫描 `generated_unit_customization_settings` 在内存中的副本：
   先用 `bcrypt` SHA256 对模块文件做**版本指纹**（照抄 Mod Bindings Menu 的做法），
   把偏移和构建号绑定，避免游戏更新后读错位置
4. 在候选结构里找"每部位层数 = 3"或"bank 数 = 3"这类常量

### 阶段 2：确认是哪个字段

1. 读当前值 → 截图 → 记下画面对应的槽位分布
2. **暂不改**，先用纯读建立"字段值 ↔ 可见件数"的对应
3. 只有在确认字段语义之后，才考虑写一次内存（写数据，不是写代码）

## 已知可复用的代码资产

* `src/bank_patch.lua` 里的 `trace()` 日志、`GetModuleHandleW` 宽字符串处理、
  代码洞/偏移常量 —— 但**代码写入部分要删掉**，只保留读取
* `Mod Bindings Menu` 的 `__asm__` cdef 绑定写法（已验证在沙箱里可用）
* 我们的 `peek_armor_banks.py` / `capture_window.py` 做外部对照

## 诚实的不确定性

* 内存副本里到底有没有这个字段、是不是可写、写后会不会被重新校验 —— **全都没验证**
* 即使字段可写，上限也受 `bank[10]` 结构约束：每部位最多 3 层（type 0/1/≥2 三个 bank），
  除非"bank 数"本身也是可配的
* 如果 `bank 数` 是编译期常量（我们已经从栈布局证明三个 20 项数组零余量），
  那么这条路的终点仍然是 18 件
