## 0 一句话

**section 的"能力"和"覆盖率"都已经到位，缺的是两样工程属性：生效成本、保存时机。**
常规 Mod 那条线的价值全在**生成期**（加几何），不该硬塞进"开关"；它身上真正该扔的是
已经没人消费的三个协议字段、一条跑不起来的运行时链，以及一处会让坏数据堵死整份工作区的校验。

## 2 六个必须先承认的事实

### 2.1 事实一：`wardrobe.masks` 那条链已经不可能生效，不是"没接线"

三个独立证据同时成立：运行时 Lua 因缺 `ffi` 加载即退出（`RuntimeArmorRegistryLuaSource.cs:11-20`）；
管理器没有一处写 `wardrobe.masks`；写权威数据 `wardrobe.workspace.json` 的唯一入口已删。
**结论：运行时那条路退场。** 但"按护甲保存隐藏策略"这个**能力**不该一起判死 —— 它完全可以
改成"护甲级策略 → 生成该护甲的烘焙产物"，不需要运行时 Lua。所以 Core 里的身份规范化、
读取迁移、纯投影逻辑要留（见 §6.2）。

### 2.2 事实二：`pieceOverrides` / `targetModes` / `CompositionMode` 是死数据

两条在役链路（真映射走 `generated_customization_armor_sets.dl_bin`、兼容模式走 `wardrobe.links`）
的签名里根本没有这三个参数；现网 0 条。
**结论：字段保留、编辑入口永不恢复。但校验要降级**（见 §7.5）—— 现在坏数据会让整份工作区
读不出来，一个没人消费的字段不该有这种权力。

### 2.3 事实三：section 覆盖率**没有缺口**（初稿在这里算错了）

初稿写"10/129 = 8%，要一次性补表"。**错在分母。** 129 个包里只有 **10 个含 unit**，
而这 10 个**全部**有 `sections.json`：

```
含 unit 的模型 Mod：10 个
其中有 sections.json：10 个
模型类但没有 sections.json 的：0 个
```

12 个 `standard` 节点里有 2 个是纯材质主体（没有 unit），本来就不该有 section 表。
**结论：初稿的 S2「一次性补表」整批删掉 —— 它是个凭空造出来的任务。**
这是本项目第三次同类教训（P1.5 空理由、`ParseTint` 误判）：**先把分母和现状按当前代码复现，
再决定要不要修。**

### 2.4 事实四：勾一下要等几分钟，这件事本身就是设计问题

`WardrobeSectionBaker` 已经是"就地、幂等、可逆"的（`WardrobeSectionBaker.cs:24-49`），
但「应用」现在走的是**重跑整条换甲**，因为 `disabled` 存在**来源** unit 键空间，
而 `Overwrite/` 里的 unit id 是**目标**键空间。
**结论：把来源→目标的 section 级映射落盘，「应用」就能降成秒级就地烘焙。**
但这件事的正确性门槛比初稿估计的高得多，见 §3.2。

### 2.5 事实五：勾选只存在内存里

`PersistVpkAsync` 唯一调用点是「启用组件卡」那个开关（`ModDetailsPageViewModel.Vpk.cs:125`）。
勾完不点「应用」切页 = 静默丢失（`:222-246` 会重读文件覆盖内存）。
**结论：勾选即保存。**

### 2.6 事实六：那 98 个"0 材质"包**不应因为零材质被判坏**（但别急着说它们能用）

`backlog-20261104.md:144-146` 记着"只换 matcap/贴图的颜色变体包转出来一个材质都不含，
装上什么都不会变"，把 `Lunalice基础材质C1/D1~D4/E1~E3` 等 9 个列成了缺口。**这条是误判。**

实测 129 个报告里 98 个是 `0 Unit / 0 材质 / 1~2 贴图`，而它们的贴图 id 与基础材质包**完全一致**：

```
lunalice基础材质a1主体   发出 white  = 0xb25d6ffd2612dba8
lunalice基础材质d1发色白  发出 white  = 0xb25d6ffd2612dba8   ← 同一个 id，不同内容
lunalice基础材质d1发色白  发出 shinano_hair_ear = 0xb5040b92a97479e7（同上，id 一致）
【材质】奶牛旗袍…基础材质 发出 nail   = 0xb3423bad0a6178fd
【材质】奶牛旗袍…美甲 白   发出 nail   = 0xb3423bad0a6178fd   ← 7 个美甲变体全是这个 id
```

`vpk2patch-contract-20261016.md:212-219` 的发布脚本验收条件第 3 条正是这个机制。

**但结论要分三级，不能一步跳到"能用"：**

| 级别 | 内容 | 现在的状态 |
|---|---|---|
| 已确认 | `0 Unit / 0 材质` **不是失败判据**；纯贴图产物是合法的选项形态 | ✅ 实测 |
| 静态可验证 | 产物提供的资源 id 确实被宿主当前材质引用；依赖闭包完整；产物格式有效 | ⬜ 未做 |
| 实机已验证 | 在指定组合 + 部署顺序 + 当前游戏版本下，外观确实变了 | ⬜ 未做 |

**所以 backlog 那条要改写成**："98 个包是纯贴图产物，不该因零材质判坏；其中已核对的样本符合
贴图覆盖机制，其余需引用闭包检查与代表性实机验证。"

## 3 VPK section 再优化：只剩两件事

### 3.1 （已删除）覆盖率补表

不存在缺口（§2.3）。要逐节名字（"猫耳"而不是"#3"）只有重新转换才有，而那是个别 Mod 的
「重构建」按钮已经能做的事，不需要新产品功能。

### 3.2 生效成本：「应用」改成秒级就地烘焙 —— **这一节是全文风险最高的地方**

#### 3.2.1 为什么一个 `sourceUnit` 字段不够

初稿打算给 `Overwrite/sections.json` 的每个 unit 加一个 `sourceUnit`（它在来源侧是谁），
然后按它把 disabled 翻成目标键空间。**这不够。** 下面每一种情况都能让"看起来成功、实际关错块"：

| 情况 | 单值 `sourceUnit` 怎么失效 |
|---|---|
| 一个来源 unit 落到多个目标 unit | 只更新一个落点，其余落点照旧显示 |
| 两个来源 unit 合并成一个目标 unit | 单值表达不了两个来源，更分不清各自的 section |
| 多个来源 section 融成一个目标 section | 即使记全来源，也**物理上无法**只关其中一部分（引擎里 section = 材质批） |
| 某来源 unit 在目标上没有落点 | 丢弃 disabled ⇒ "保存成功、应用无效"的假成功（**现在就是这样**，`CliVpkRekey.cs:341-361`） |
| 多次换甲 / Overwrite 被整体替换 | 旧映射与新 patch 跨代配对，偏移仍可能落在合法地址上 |
| 烘焙之后再换甲 | 若从已烘焙产物取基准，0 会被当成"原值"，永久失去恢复能力 |
| 来源表与目标表属于不同次构建 | unit id 相同不代表 section 布局、顺序、语义相同 |

**还要否掉一个隐含前提**：`当前值 ∈ {0, 原值}` **不是身份校验**。错位的 section 也可能恰好
索引数相同；已经置零的字段更容易通过。它证明的是"值看起来可写"，不是"写的是用户选中的几何"。

#### 3.2.2 要满足的契约

> **每一代产物必须携带可验证的「来源 section → 产物 section」映射；就地烘焙只能修改与该映射
> 绑定的同代产物。**

最低要求：

1. **映射粒度到 section**，且允许一对多 / 多对一：
   `来源包标识 + 来源(unit, mesh, section) → 产物(unit, mesh, LOD, section)`。
2. **索引只在指定生成代内有效**。跨代匹配必须靠稳定来源标识或显式迁移；
   `sourceMaterial` 与"材质 + 三角形数"只能当**辅助**匹配，不能当唯一身份。
3. **融合不可分时明确拒绝**：同一产物 section 的多个来源要求不同显隐状态时，
   要么重新分节生成，要么明确告诉用户"这几块在物理上是同一个 draw call，不能拆"。
4. **保留不可变基准**：`numIndices` 的原值只来自**未烘焙**的生成结果。
   换甲永远从权威来源重建，再投影当前选择 —— 不在已烘焙的产物上再烘。
5. **目标无落点要保留意图**：显示"当前目标不包含此部件"，不静默丢。
6. **同代校验**：绑定来源版本 + 目标护甲 + 合并选项 + 生成器版本 + 布局指纹。
   （"不校验可变 patch 的整文件 SHA"这条硬约束不用破 —— 校验的是不含可变 dword 的结构指纹。）
7. **同代发布（全有或全无）**：patch + 映射表 + 状态一起提交；先全量校验，
   再写临时产物，最后原子切换。不能改了半个 patch 再因为后面一条失败退出。
8. **并发控制**：换甲、重构建、烘焙、部署共用一把写协调；
   提交时核对生成代与状态修订号，旧任务不得覆盖新结果。

**已有产物缺这些信息时，走一次受控重建生成映射，不猜恒等关系。**

#### 3.2.3 落地形态

- 「切换目标护甲 / 头身合并 / 重构建」→ 完整 rekey，同时写出带 section 级映射的新一代产物。
- 「应用」→ 读当前代映射 → 翻键空间 → `WardrobeSectionBaker.BakeAsync` 就地烘 → 原子提交。
- `Overwrite/` 还不存在（没选过目标）：先跑一次**恒等 rekey**（`CliVpkRekey.cs:182-220`）建代，再烘。

#### 3.2.4 判据

- 快路径与完整 rekey 的**有效 section 状态一致**（差分测试）。
- 隐藏 → 恢复后，**同代 patch 字节恢复原样**（不是抽查一个字段）。
- 反例测试必须覆盖：相同材质、相同三角形数、LOD 重排、多来源合并、来源缺失、目标替换。
- 故障注入（中途失败 / 磁盘满 / 文件占用 / 进程退出 / 换甲与应用并发）后，
  产物必须是**完整旧代或完整新代**，不能是混合代。

### 3.3 保存时机：勾选即保存，但**不自动烘焙**

- 勾选 → 400 ms 防抖写 `wardrobe.json`（带修订号）。
- 「应用」保留，语义 = **把当前勾选烘进产物**。
- 两者必须分清，否则会出现"界面显示已保存 / 游戏里没变"的经典混乱：
  - 切页前若防抖还没触发 → 立刻 flush（不能靠 400 ms 赌用户不会马上切页）；
  - 写入失败不能显示"已保存"；
  - 所有写入按修订号串行，过期提交直接拒绝。
- 卡片上要能看出三种状态：**已勾选 / 已保存 / 已烘焙**（只有"已烘焙"才是游戏里生效的那份）。
- 判据：勾几个开关 → 立刻切页 → 回来，勾选还在；且卡片明确显示"待应用"。

## 4 常规 Mod 老线：留什么、删什么

| 功能 | 判定 | 理由 |
|---|---|---|
| 护甲映射页 | **留，不动** | VPK 素体必须靠它挂到护甲上；两线共用 |
| `pieceOverrides` / `targetModes` / `CompositionMode` | **字段留、编辑入口不恢复、校验降级** | 死数据；删字段会让老工作区读不出来，但也不该让它堵死整份工作区 |
| 组件编辑器 | **已删**，只剩孤儿 XAML（`ArmorRegistryPageView.xaml:10-52`） | 清掉 |
| 装饰（decoration）生成/合并 | **留，不再加新功能** | 现网 0 个；机制本身是好的"加几何"实现 |
| 装饰批量页 | **留，修一处坏分支** | 导出只复制 `stocky.bin/slim.bin`，而这两个文件自 PatchSnapshot 起再无写入者 |
| 头身合并（VPK `--head-merge`） | **留** | 换 unit 槽位，头是独立 unit ⇒ 可单独关 |
| 头身合并（常规 `HelmetToArmorMergeService`） | **留** | 几何追加，VPK 做不到；4 处调用点 |
| 「整体合并进护甲」 | **不动** | 默认 `DirectSourceUnitReuse = true` 是有意的：改键复用来源 payload，几何一字节不动 |
| `CanonicalMeshSemanticMerger` | **留**（跨甲分支已 obsolete，同 ID 重构仍在役） | — |

### 4.1 两份头身合并：算法不能合，但"只统一层排序"也不够

两者对"层"的排序方向是**相反**的：

```
VPK  (CliVpkRekey.cs:844-852)                Undergarment 0 < Armor 1 < Accessory 2 < Unknown 3
常规 (HelmetToArmorMergeService.cs:706-712)   Accessory 1 < Undergarment 2 < Armor 3
```

但**不能把"同一护甲必须选出同一层"当验收标准** —— 两种算法对骨骼绑定、unit 槽位与可见性、
材质 / LOD / 容量限制、来源 payload 保真的要求不同，得出不同结果是**可以合法**的。
真正的技术债是：两条路各自解释"头 / 宿主 / 合适承载层"，没有共同的输入输出契约。

改法：

- 抽 `HelmetArmorPairResolver`：共用**候选识别 + 物理可行性判定 + 诊断**，
  输入必须带生成模式与其约束，输出"选谁、为什么、哪些候选不兼容"。
- **先按物理可行性过滤候选，再谈内层 / 外层排序。**
- 相同候选 + 相同约束 ⇒ 必须同结果；不同约束 ⇒ 允许不同结果，但要说出来。
- **排序策略要版本化**：已有工程重构建不能因为软件升级静默换承载层。
- 若最终必须以 VPK 主线为唯一产品目标二选一，**选 VPK 那份** ——
  但那是"缩减产品范围"，不是"无损去重"，得明说。

## 5 融合的边界：section 只能控制产物里已有的几何

- **section 开关 = 减**：把已存在 section 的 `numIndices` 写 0。前提是"几何已经在 unit 里"。
- **装饰 / 头盔合并 = 加**：把来源三角形并进宿主 mesh 的 section 表末尾。

初稿把这条写成"装饰不能先追加再关"，**说过头了**。准确的说法是：

> **section 开关只能控制当前产物里已包含、且可独立寻址的几何；缺失的几何必须先生成。
> 是否预生成候选项，是资源预算与切换频率之间的成本策略，不是物理限制。**

于是有两种合法模式：

| 模式 | 做法 | 代价 |
|---|---|---|
| **精简**（现在） | 只生成选中的几何；要开缺失项 → 重新生成 | 切换要等生成 |
| **预装** | 生成有限候选集；显隐只需烘焙 | 关掉的仍占 section / 材质槽 / 内存 |

单 unit section 数实测已到 98，但**这不是引擎上限**，只是当前选择的结果。
选哪种模式要按预算算：section 数、材质槽、骨骼、内存、构建成本 —— 而且**不能假设置零之后
这些成本就消失了**。

**需要合并的不是"加/减两个操作"，是 section 的身份表与编辑入口。** 界面必须能区分
"可直接隐藏"和"需要生成"这两类条目。

> 另注：**改磁盘 patch ≠ 游戏运行中热切换。** 后者还需要验证资源重载机制（本项目实测过：
> 写完内存要在游戏里换装一次才生效）。产物期烘焙承诺的是"重启游戏后生效"，不是"当场生效"。

## 6 要退场的东西：按层退场，不按名字整包删

### 6.1 分层退场

| 层 | 动作 | 判据 |
|---|---|---|
| **分发** | 停止分发死 Lua：`armor_section_*.lua`、`armor_wardrobe_masks.lua`、`armor_registry_runtime.lua`、`armor_registry_composition.lua`、`armor_registry_transaction.lua` | 先确认全部部署 / 打包路径都不引用它们（`RuntimeArmorRegistryLuaSource.Load()` 只返回 `armor_override_runtime.lua`）；带 `require('ffi')` 的本版引擎加载即退出 |

| **Core** | 保留仍被新 section 系统需要的部分：身份规范化（`WardrobeSectionFingerprint`）、读取与迁移、纯投影逻辑；其余连同旧测试**归档到明确版本标签**，不必永远留在主干 | `WardrobeMaskProjection` 的"继承 → 扁平投影"思路将来做"护甲级策略 → 烘焙产物"时仍能复用 |

### 6.2 为什么不能"按名字整包删"

缺 `ffi` 证明的是**当前版本、当前脚本实现跑不起来**，不是"按护甲保存隐藏策略"这个能力永远没价值。
"管理器零调用"不等于 CLI 没有外部用户；"本机没有工作区文件"不等于别的用户没有历史数据；
"删完测试全绿"不能证明没删掉对外能力。**保留代表性旧数据 fixture，测"能迁移"或"明确拒绝
且不损坏其它数据"。**

### 6.3 `components.json.Disabled` 要删的理由

它是 `sections.json.sourceMaterial` 的缓存 join（`CliVpkComponentSwitches.cs:40-59`），
读取时现算即可。留着的代价是它会在重建后**静默变旧**：`VpkPayloadSwap` 保留
`components.json` 但替换 `sections.json`（`VpkPayloadSwap.cs:31`），节数一变，开关就会
**静默关掉别的几何**（见 §7.2）。删之前必须先做完 §7.2 —— 否则先丢掉了旧开关唯一可用的定位信息。

## 7 要修的清单

### 7.1 `MaterialVariant` 没被剔出材质解析集合（**早做**）
只有 `switchPaths` 被剔（`CliApplication.cs:2320-2322`），`MaterialVariant` 留在里面，
而同名材质冲突是"先出现的赢"（`SourceMaterialSource.cs:21`）——
一份"文身关"的 VMT 排在真材质前面，模型就绑到被替换的底色上。
这一条会改变后续生成结果，所以必须排在"补表 / 迁移"之前。

### 7.2 装载开关时只校验 unit 存在，不校验 section 下标（**早做**）
`ModDetailsPageViewModel.Vpk.cs:804`。改成按 `sourceMaterial` 重新解析下标，
解析不到就标 stale 并**阻断**（不是只给提示），烘焙那边也别只给 warning
（`WardrobeSectionBaker.cs:166-170`）。

### 7.3 装饰批量页的导出分支
`BatchDecorationPlanPageViewModel.cs:257-267` 按硬编码文件名复制，产出的包没有 patch。
改成和单页一样复制目录内全部文件（`DecorationPlanPageViewModel.cs:335-343`）。

### 7.4 贴图覆盖型选项：**先建账本，再定策略**（初稿这里下结论太早）

实测 7 个美甲变体提供**同一个**贴图 id；`Cow_QiPao_Milltina_Bill` 上 68 个选项全部 `enabled=true`，
而 `lunalice_bill` 是 12 个全开（正好 12 组每组一个）。

但"68 个全开"**不等于**"只有一个生效"：胜者可能是**逐资源**决定的（一个选项贡献发色、
另一个贡献指甲，结果是混合）。而且重叠关系不是简单的互斥分组 ——
设 A 提供 `{x}`、B 提供 `{x,y}`、C 提供 `{y}`，则 A 与 C 可以共存，却分别与 B 冲突；
把连通分量做成一个单选组会**错误禁止 A+C**。

**正确做法分两步：**

1. **先建"按资源类型 + id 的提供者清单与有效胜者解释"** —— 这同时也是 §9 生效账本的一部分。
2. 再按数据决定产品策略：完全可替代的变体 → 单选组；部分重叠 → 冲突提示或显式优先级；
   基础包与选项 → 依赖 + 覆盖关系，不纳入同一互斥组；同 id 同内容 → 标重复，不必强制互斥。

**最小验证实验**：选一张确定被当前材质采样的贴图，做视觉差异极大的 A/B →
分别验证"基础+A""基础+B"单独有效 → 同时部署 A/B，再交换实际部署优先级或文件排序条件 →
核对落盘产物、重启游戏排除缓存、重复一次。若稳定且组合合法，这是**语义与透明度**问题；
若重部署会变或结果不可复现，才是**正确性缺陷**。

> **这条超出 section 范围，但影响 98/129 个包，建议单独立项。**

### 7.5 把三个死字段的校验从"致命"降级为"警告"
`RuntimeArmorRegistryService.cs:1033-1058` 现在会因为 `piece_overrides` / `target_modes` /
`composition_mode` 的格式错误让**整份工作区读不出来**。一个没有任何在役消费者的字段不该有
这种权力。改成：原值往返保留 + 兼容警告，**只有真正参与生效计算时才做阻断性校验**。

## 9 新增：生效账本（astra 指出方案漏掉的东西）

现在的验收对象是单包、状态文件、某个 dword，但用户真正关心的是**最终生效组合**：

> 这个护甲最终用了哪一代模型、哪些 section 被隐藏、每张贴图由哪个选项胜出、
> 部署的到底是不是这份产物。

所以需要一个可解释的生效清单，把这条链串起来：

```
选择修订号（wardrobe.json / option-activations.json）
      │
      ▼
生成代（rekey 产出：patch + sections.json + 来源映射 + 布局指纹）
      │
      ▼
资源胜者（按 资源类型+id 的提供者清单 → 谁赢、为什么）
      │
      ▼
部署结果（实际部署了哪些 patch 文件、符号链接指向哪）
```

没有这本账，section 烘焙和贴图覆盖**各自正确**，组合起来仍然可能与界面承诺完全不同。
它可以先做成 CLI 的一个只读诊断命令（`hd2mod effective-report --host <X>`），
再决定要不要进界面。

### 10.1 开关包识别的三类判据（替换现在的两个魔数）

现在只有"条目 ≤12 / VMT 字节 ≤64 KiB / 无 vtf / 全 `$no_draw`"四条全中才算开关包
（`VpkImportPlanner.cs:456-478`）。略超限就掉进"整包 `$no_draw`" → `Unsupported`，
**开关彻底丢失而不是降级**。改成看内容：

| 类 | 判据（内容型） | 结果 |
|---|---|---|
| **隐藏几何** | 每份 VMT 都只写 `$no_draw`（不看条目数与字节数） | 产 section 开关（`components.json`） |
| **贴图覆盖** | 没有 `.vmt`，或 VMT 的 `$basetexture` 指向包内贴图；产出 ≥1 张贴图 | 明确标成"贴图覆盖包"：名字 + "作为选项挂到宿主上生效"；**从材质解析集合里剔除** |
| **参数覆盖** | VMT 有内容但 HD2 模板没有对应槽（`$phong`/`$envmap`/`$nocull`/`$lightwarptexture`…） | 明确理由，**不产出空材质包** |

条目数与字节数降级成 sanity 上限（防呆），不再是分类依据。
