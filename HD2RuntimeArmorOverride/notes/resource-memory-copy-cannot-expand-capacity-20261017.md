# 资源内存副本这条路：能读、能改，但容量不在里面（2026-10-17）

## 这轮实际做了什么

1. 造了离线解密 + 转储工具 `tmp/dumplib`（`Decryptor` 的 libsodium `crypto_box`
   密钥常量照抄 `Decryptor/KeyProvider.cs`），可以把任意 `generated_*.dl_bin`
   解成明文并逐条打印 `LDLD` 记录。**纯离线、只读，不碰游戏进程。**
2. 把用户点名的资源全部转储并逐条看过。
3. 回头把「bank 数 = 3」这条结论重新在反汇编里验证到**指令级**，并找到了
   之前没定位到的那一层：**三个 bank 指针是函数参数**，由调用方算出来。

## 转储结果：这些资源里没有容量字段

| 资源 | 明文大小 | 记录数 | 内容 |
|---|---|---|---|
| `generated_unit_customization_settings` | 27,744 | 12（全是 `0xa2ba274a`） | **载具/机甲皮肤目录**：`nui_customization_type_patriot_skins`、`emancipator_skins`… 每条是 `{itemId, archiveHash, nameStringId}` |
| `generated_weapon_customization_settings` | 29,528 | 9（全是 `0x1e604234`） | 武器皮肤/涂装目录，同样的 `{itemId, archiveHash, nameStringId}` 形状 |
| `generated_customization_armor_sets` | 384,196 | — | 护甲套装表（我们运行时一直在内存里写的那块） |

前两个是**目录（catalog）**：它回答"有哪些可选项、对应哪个 archive"，
不回答"一个部位能挂几层"。里面没有任何"每部位层数 / bank 数"语义的字段，
也没有和 `0x81f470` 那个循环边界（`r14d = 9`）对应的常量。

## 反汇编：`3` 是调用方的三个 `lea` 立即数

`0x81f470` 才是那个把句柄写进 bank 的函数。它的序言是：

```
0081f4a8: mov rax, [rbp+0x1d8]     ; arg8
0081f4bc: mov rdx, [rbp+0x1d0]     ; arg7
0081f4d1: mov r8,  [rbp+0x1e0]     ; arg9
0081f4e7: mov [rsp+0x58], rdx      ; bankA = arg7
0081f4ef: mov [rsp+0x60], rax      ; bankB = arg8
0081f4f7: mov [rsp+0x68], r8       ; bankC = arg9
```

**三个 bank 指针不是常量，是第 7/8/9 个参数。** 这一点以前没记下来过：
之前只看到 `bankA = rec+0x546b4c` 这类等式，就默认是函数内部算的。

再往上一层，唯一的护甲侧调用方 `0x877c70`：

```
00877c70: lea r8,  [r13 + 0x546b9c]   ; arg9  (bank C)
00877c7a: lea rcx, [r13 + 0x546b74]   ; arg8  (bank B)
00877c86: lea rdx, [r13 + 0x546b4c]   ; arg7  (bank A)
```

三个 `lea` 立即数就是全部容量来源。**没有表、没有循环、没有字段可以改。**
想变 8 个 bank，只有把这三条 `lea` 改成"查一张 8 项的指针表"或者
"按 type 算偏移"——两者都是改代码段。

## 顺带解释了一个旧崩溃

`0x877d12` / `0x877d21` 读了 `rec+0x546bc4` 和 `rec+0x546bc8`，
作为 arg10 / arg11 传进去，在 `0x81f470` 里被当作 `[rbp+0x1e8]` / `[rbp+0x1f0]`
用（type==1 时按 slot 2/3 传给 `0x81a650`）。

所以之前 4-bank 单点补丁把 bank D 放在 `rec+0x546bc4` 会崩，
不是巧合也不是对齐问题：**那两个 dword 是活的**。想扩 bank 必须整体搬移，
而搬移必然要改那三条 `lea`。

## 关于"可能只被读取一次"

这条担心对我们**已知的那块**已经有反证：`generated_customization_armor_sets`
的内存副本我们是在**运行时**（进图之后）改的，改完立刻生效，不需要重启。
说明这类 `LDLD` 数据块是按偏移**惰性读取**的，游戏保留整块明文，
不是加载时一次性消费掉。

但这条反证救不了容量问题：容量不在这些数据块里。

## 结论（可以当作定论）

* 资源内存副本这条路：**技术上可行**（读已证明、写同族数据已证明、
  惰性读取已证明），但它改的是"有哪些件、件指向哪个 archive"，
  **不是"一个部位能挂几层"**。
* 容量上限 = 3 bank × 10 slot = 30 个唯一 `(type, slot)` 键，其中身体段
  slot 2..7 只有 18。这是 `0x877c70` 的三条 `lea` 决定的。
* Lunalice 是 38 件身体 + 5 件头盔 = 43 > 30。**数据侧放不下，不是调参问题。**
* "把读取入口指向我们自定义的位置"= 改调用方/改 `lea`/改跳转，属于改代码段。
  两次实测都会被判「可疑程序」，这条路已经关闭。

## 还剩什么

1. **降到 ≤30 键**：把 38 件身体件压进 18 个键。用户明确禁止"在游戏外把多个
   unit 合成一个 unit"，所以这条不做。
2. **改代码段**：被反作弊挡住。
3. **重新审视"38 件身体"是不是真的需要 38 个键**——如果 Lunalice 的 38 件里
   有相当一部分是互斥的（同一位置的不同款式，用户一次只开一件），那么实际
   同时可见数可能远小于 38。这一条**还没验证过**，是唯一还有希望的缝隙：
   先量出"用户实际会同时打开多少件"，而不是按"全部 43 件都开"来设计。
