# **硬约束：禁止修改 game.dll 代码**（2026-10-17，反作弊实测）

## 发生了什么

为了让 `piece_type >= 3` 落到第 4 个 bank，我用**外部进程**对运行中的
`Helldivers 2` 执行了：

1. `OpenProcess(PROCESS_VM_OPERATION | PROCESS_VM_WRITE)`
2. `VirtualProtectEx(code_page, PAGE_EXECUTE_READWRITE)`
3. `WriteProcessMemory(0x82024e, jmp ...)` + `WriteProcessMemory(代码洞, trampoline)`
4. `FlushInstructionCache` + 恢复页保护

**游戏反作弊返回了「可疑程序」。** 随后游戏进程被终止，无残留。

## 结论：这条路**永久关闭**

之前有一条判断是"反作弊只做运行时外部保护，不会干扰官方允许的 Lua 插件"。
这个判断**只对 Lua 插件成立**，不包括：

* 从外部进程打开游戏句柄并请求 `VM_WRITE` / `VM_OPERATION`
* 把 `game.dll` 的 RX 代码页改成可写
* 往代码段写字节

这三件事本身就是反作弊要抓的行为。**即使补丁逻辑完全正确、字节可回滚、
游戏不崩，也依然会被判为可疑程序。**

## 因此

* **bank 从 3 扩到 8 的方案作废。** 不是因为技术上做不到（技术上已证明可行：
  trampoline 被执行、重定位地址正确、`deadbeef` 哨兵验证通过），
  而是因为**实现它的手段会触发反作弊**。
* 任何"改游戏代码"的变体（改分派、改栈数组、改销毁循环、加 bank）都同样作废。
* 数据侧的操作（写注册表 blob、写协议文件）不受影响，那是插件正常能力。

## 当前能力上限（数据侧，不变）

| 范围 | 同时可见件数 |
|---|---|
| 头盔 slot 0 | 3 |
| 披风 slot 1 | 3 |
| 身体 slot 2..7 | **18**（6 部位 × 3 层） |
| LUT slot 8/9 | 6 |
| **整个角色** | **30** |
| 每个 kit 每次处理 | 20（20 项栈数组，零余量） |

Lunalice 模型是 38 件身体 + 5 件头盔 = 43，**数据侧放不下**。

## 教训

以后任何"需要改游戏代码"的想法，必须**先确认它不触发反作弊**再动手；
不能因为"字节可回滚、游戏不崩"就认为安全。回滚解决的是崩溃，不是检测。
