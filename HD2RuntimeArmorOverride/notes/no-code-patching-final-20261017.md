# **最终约束：任何形式的 game.dll 代码段修改都会触发反作弊**（2026-10-17）

## 两次实测，两种方式，同一个结果

| # | 方式 | 具体做法 | 结果 |
|---|---|---|---|
| 1 | **外部进程注入** | `OpenProcess(VM_WRITE\|VM_OPERATION)` + `VirtualProtectEx` + `WriteProcessMemory` | 反作弊提示「可疑程序」，游戏被终止 |
| 2 | **插件内 LuaJIT FFI** | 模组自己在进程内调 `VirtualProtect` + 直接写指针改代码页 | **同样提示「可疑程序」，游戏退出** |

第 2 次是最关键的一次否证。此前的判断是：

> 反作弊抓的是"外部程序打开游戏句柄"，官方允许的 Lua 插件在自己进程内做同样的事
> 检测面完全不同。

**这个判断是错的。** 反作弊监视的是**对 `game.dll` 代码页的写保护变更与写入行为本身**，
不区分发起者是外部进程还是进程内的 Lua。两次都在 `VirtualProtect` + 写入之后被判定。

## 因此：bank 扩容方案**彻底作废**

不是技术问题——补丁机制已经被完整验证可行：

* 哨兵补丁让 bank C 六个槽全部变成 `0xDEADBEEF`，证明 `0x82024e` 是正确的分派点、
  trampoline 会被执行
* `ctypes` 的 `restype` 截断 bug 已修（64 位缓冲地址 `0x1c5f54e0000` 正确）
* 重定位 trampoline（52 字节）+ 5 字节 jmp + 93 字节代码洞，字节校验通过
* 插件内 FFI 通路本身也打通了：`GetModuleHandleW` 宽字符串 bug 修复后
  成功拿到 `game.dll base=0x7ffae9c40000`

**但落地手段必然触发反作弊。** 这条路永久关闭，且不再尝试任何变体。

## 已做的回滚

* `HD2ModCore.csproj` 与 `RuntimeArmorRegistryLuaSource.cs` 已还原到 `6140d34^`
  （不再嵌入 `bank_patch.lua`、不再调用 `install()`）
* 管理器已重新编译（0 警告 0 错误），后续部署不会再带补丁
* 游戏与管理器进程均已关闭
* `bank_patch.lua` 源码保留在 `src/` 但**不参与任何构建**

## 教训（写给未来的自己）

1. **"能回滚"不等于"安全"。** 回滚解决崩溃，不解决检测。
2. **"技术上可行"不等于"可以做"。** 补丁机制验证得再完整，触发反作弊就是不可用。
3. **任何需要改游戏代码的想法，必须先假设它会被检测**，再去找不改代码的替代方案。
4. 我在这件事上让用户冒了两次账号风险。第二次是在用户明确纠正"要走插件内"之后
   仍然失败——说明我的模型里"插件内 = 安全"这个假设从一开始就没有依据。
