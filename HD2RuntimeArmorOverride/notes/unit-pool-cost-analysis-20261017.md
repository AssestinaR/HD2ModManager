# 这条链路的重心在哪、会不会掉帧（2026-10-17）

## 先分层：谁在游戏进程里跑

| 环节 | 在哪跑 | 频率 | 帧时间成本 |
|---|---|---|---|
| 管理器合并（`TryAppendLodFamily`） | 用户机器，离线 | 点"应用"时一次 | **0**（不占帧） |
| 打 patch 归档、部署 | 离线 | 装 mod 时一次 | 0 |
| 启动时加载 union unit、上传 GPU 缓冲 | 游戏加载阶段 | 每次启动 | 0 帧内成本，但抬高加载时间和常驻显存 |
| **运行期：Lua 读选择 + 改 `NumSections`** | 游戏进程 | 每次切换 | **可忽略**（几十个 dword 写，微秒级） |

**所以"我们这条链路"本身不是掉帧源。** 真正吃帧的是几何体本身。

## 真正的成本，按大小排

### 1. 固有成本：43 件同时可见（这条躲不掉）

不管用哪种架构，43 件都意味着：

* **draw call**：每个 mesh 至少 1 个，多数有多个 section。43 件 × 2~4 section
  ≈ 100~170 个 draw。原版一套护甲大约 10~20 个。**净增 100+ 个 draw**。
* **蒙皮**：HD2 护甲是 skinned mesh，成本按顶点数走。Lunalice 43 件的总面数
  如果接近原版 10 倍，蒙皮和顶点着色就是 10 倍。
* **显存**：全部顶点/索引缓冲常驻。

这是"43 件全可见"这个需求自带的账单，**不是合并方案引入的**。
反过来说：如果最终只需要同时显示 5~8 件，成本立刻回到正常范围。

### 2. 设计相关成本：union unit 让"没开的那几件"也占资源

union unit 把该槽位全部候选件都装进去，启动时**全部上传**：

* 显存：**全量常驻**，哪怕玩家只开 1 件。这是 union 方案的主要代价。
* draw / 蒙皮：**取决于 `NumSections = 0` 到底管不管用**（见下）。

### 3. 离线成本：合并本身的墙钟时间

`TryAppendLodFamily` 会重建整族 LOD，是全链路里**最慢的一步**，但它只在用户点
"应用"时跑一次。**这是 UX 问题，不是帧问题。**

## 最大的两个风险点

### 风险 A：`NumSections = 0` 可能只跳过绘制，不跳过蒙皮

如果渲染器仍然把 mesh 的骨骼调色板算一遍再发现 0 section 不画，那么
**玩家只开 5 件，仍然要付 43 件的蒙皮成本**。这是 union 方案最可能翻车的地方，
必须第一个测。

如果确实翻车，退路是：把"关掉的件"的 `TransformIndex` 或 `StreamIndex` 指到
一个退化值（0 顶点），但要注意 `TransformInfo` 按骨骼名哈希共享，改错会连带别的件。

### 风险 B：LOD 放大

`TryAppendLodFamily` 把全部候选件写进**每一级 LOD**。如果 far LOD 里也是 38 件，
远处渲染成本同样被放大。要么让候选件不参与 LOD 家族，要么只在 LOD0 合并、
远 LOD 保留最小集。

## 怎么量（低成本）

1. **MDL 自带每 mod 帧成本显示**——它 README 里写了 "Frame cost per running mod"。
   可以直接当现成 profiler 用，先量出"43 件全开"和"原版护甲"的差。
2. 我们自己的 toggle 路径打时间戳，确认单次切换在微秒级。
3. 用 `capture_window.py` 截同一机位，对比全开 / 只开 1 件的帧率。

## 结论

* 我们这条链路（合并器在外部 + Lua 改 dword）**不会掉帧**。
* 掉不掉帧由**同时可见的件数**决定，和合并方案无关。
* union 方案的两个具体风险是"隐藏件是否仍付蒙皮成本"和"LOD 放大"，
  这两个都要在动工前先测。
* 如果只追求"能切换、不重启"，而且玩家实际同时开的件数远小于 43，
  性能完全不是问题；如果是"43 件全开常驻"，那 10 倍于原版的几何成本是需求本身的代价。
