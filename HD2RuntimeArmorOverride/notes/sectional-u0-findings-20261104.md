## 0 证据分级（本文所有结论必须落在其中一级）

| 级 | 含义 | 能支持什么 |
|---|---|---|
| **L1 代码事实** | 直接读代码得出 | "实现是这样"；不能推"引擎行为是这样" |
| **L2 静态样本** | 扫离线资源（游戏本体 / 我们的产物） | 存在性；不能推普遍性或引擎上限 |
| **L3 产品字节往返** | 跑产品代码生成产物，再解析回来 | "我们的管线产出什么形状"；**不是游戏内行为** |
| **L4 游戏内验证** | 进游戏看 | 只有这一级能说"能用" |

**本文最高只到 L3。** 凡写"已确认可用"的地方都降级了。

## 2 并段：会，而且是三处

### 2.1 实测（L3，端到端：`TryAppendLodFamily` 出 TOC 字节 → `UnitMeshReader` 重读回来数 section）

| 组 | 目标 unit | donor | 最终段数 | 结果 |
|---|---|---|---:|---|
| ① 对照：材质不同 | 1 段 M1 | 1 段 M2 | **2** | 边界保住 |
| ② 共用目标材质 | 1 段 M1 | 1 段 M1 | **1** | 并了（4 tri） |
| ③ 两 donor 共用目标材质 | 1 段 M1 | A:M1, B:M1 | **2** | 部分并（A 并入，B 独立） |
| ④ 目标没有该材质 | 1 段 M1 | A:M3, B:M3 | **3** | 全保住 |
| ⑤b 目标两槽同材质、donor 也同材质 | 2 段 M1 | 1 段 M1 | **2** | donor 并进槽 77 |
| ⑥ 目标自己同槽两段、donor 材质完全不同 | 2 段同槽 77 | 1 段 M2 | **2** | **目标自己两段被并** |
| ⑦ 同 ⑥ 但 donor 共用该材质 | 2 段同槽 77 | 1 段 M1 | **1** | 三段全并 |

### 2.2 三条结论（按证据等级收紧措辞）

1. **破口不是"一个 donor"，而是"每一个 occurrence 落在目标槽数组长度内的 section"。**
   ③ 里只有第一个 donor 被并，第二个反而拿到新槽。所以取决于"该材质在目标侧已有几个槽"。
   （L3）
2. **`MergeSectionsByMaterialSlot` 收的是"目标段 + 追加段"的整张最终 mesh**，
   所以**任何一次 append 都*可能*改变目标原有的 section 边界**（⑥）。
   —— 不是"必然"，只有发生同键聚合时才变；但对方案而言必须按"可能"设计。（L3）
3. **规避手段还没定**（见 §6 W2）。v1 写"加 `uniqueSlotPerSection` 开关"是**过早收敛**：
   - `CanonicalAppendBoneCompiler` 已经**按最终 `MaterialIndex` 逐段重写来源骨索引**
     ⇒ "共享一份 remap 就必须共享一个 section"不是已证的必要条件，
     **"直接跳过按槽合并"这条路还没被排除，而且它的代价是 0 个额外槽**；
   - `ordinarySlotsBySource` 的身份是 `(来源 unit, 来源 slot, materialId)`，**不含来源 section**
     ⇒ 只给每段不同 `PreferredTargetSlotId` 也**不保证**独占（那是 `Preferred` 不是 `Guaranteed`）；
   - 只给 donor 唯一槽，**宿主自己同槽的两段仍会被末尾合并**。

### 2.3 那句「non-SDK」注释：不能像 v1 那样否掉

v1 写"被游戏本体数据否掉了"。**这是越界。** 准确说法：

- **L2 事实**：本体 7132 unit / 47358 mesh 里有 12 张 mesh 同槽多段（最多 5 段共用 1 槽），
  来自**只有 2 个 unit**。
- 这证明"同槽多段是引擎**能加载**的形状"，**不能**证明"符合 SDK 导出惯例"，
  也**不能**推定"那句注释的唯一真实理由是本地 SetRemap 约束"。
- 且这 12 张是静态形状，**没有证据**说明它们的段边界被谁单独开关过。

## 3 位置与遮挡：代码上"有条件成立"，运行时未验证

### 3.1 位置（L1）

顶点位置 = 顶点 position（mesh-local）× **该 mesh 自己的 `TransformInfo` 矩阵**，再按**骨骼名哈希**蒙皮。
`(slot, pieceType, layer)` 不进这条算式。追加链路（`CanonicalDecorationUnitAppender` →
`CanonicalAppendMeshAssembler`）已做变换补偿（`SourceToTargetLocal`）。

**这支持的是"有条件的坐标补偿成立"，不支持"动画、逆绑定矩阵、LOD 切换、目标骨架、完整运行时行为都等价"。**

**在役证据的边界**：`CanonicalCrossArmorOrchestrator.cs:472-553` 的 `MergeSourceUnits` 分支
确实是"多来源 unit 合进同一输出 unit"的发版代码 —— 但**"存在生产代码"不等于"该分支被覆盖、
输出正确、且覆盖拆件边界条件"**。

### 3.2 真正依赖槽位的：**本仓库找到的五类**（不是对闭源引擎的穷举证明）

| # | 行为 | 依据 |
|---|---|---|
| 1 | 寻址：件记录四元组 `(itemId, body, slot, pieceType)` → unit | `ArmorStructure.cs:10-16` |
| 2 | 每部位最多 3 个 unit 槽，`pieceType` 就是槽序号 | `ArmorStructure.cs:54-62` |
| 3 | 某部位只有护甲层时"该部位唯一几何"的判定 | `CliVpkRekey.cs:619-624` |
| 4 | 隐藏槽位 = 可见 LOD 全最小化，但 `lod=-1` 深度代理**保留** | `CliPatchPrimitives.cs:524-530` |
| 5 | 隐藏 unit 的 id 必须真实存在，否则军械库空白崩溃 | `WardrobeHiddenUnitTemplate.cs:11-14` |

其余（`UnitMeshPartKind/Layer` 枚举、承载层"外层优先"策略、`layer` 文本启发式、
`MeshInfoIndex` 当身份、`IsCullingBody`、`AutoHideUnmappedTargetUnits`、两份相反的层排序）
是本仓库自己的分类习惯。

### 3.3 新发现的第三个风险：**LOD 不齐时静默少几何**（L1，astra 指出）

`CanonicalCrossArmorOrchestrator.cs:497-512`：donor 缺少对应 LOD 时直接 `continue`，
只有"全部没有共同 LOD"才失败。⇒ **可能"合并成功，但某些远 LOD 缺了一部分几何"。**
这不是 bounds 也不是深度代理能解释的问题，而且**距离远了才看得见**，最容易被漏掉。

### 3.4 `CullingBounds` 从不重算（L1 代码事实）

`MeshInfo` 里 7 个 float 是引擎剔除盒；`UnitMeshWriter.cs:46-56` 只原样写回；
`UnitAuthor.cs:275-282` 注释明说"不重算的话顶点出盒游戏就把网格丢掉"。

**v1 写"三条在役路径全部中招"越界了** —— 不重算是代码事实；
"具体消失现象的根因"仍需隔离验证，不是所有追加几何都会出盒。

**验收判据也不能只用 `vertices_outside == 0`**：坐标空间错了照样通过；静止姿态通过不代表动画姿态通过；
用静态顶点取紧盒可能**缩掉原本为动画预留的范围**；无限大的盒也能通过却让剔除失效；各 LOD 与半径字段都要查。
**包围盒相等也不等于逐顶点对应相等** —— 正确的局部坐标变换反而可能改变局部包围盒。

### 3.5 深度代理（L1 + L2）

`lod=-1` 的 mesh 是 depth-only 遮挡壳（section 的 `MaterialSlotId` 都不在材质表 ⇒ 只写深度）。
实测过：把几何挂内层会被它按深度剔除（"手套/丝袜整段不显示"）。

三个概念要分开（astra 的要求）：
1. `lod<0` + 无材质 + depth-only，**不能仅凭本地分类器就当作完全等价**；
2. Appender 拒绝代理，证明的是**当前实现不支持搬**，不是引擎永远不允许搬；
3. 删除代理记录 / 保留但最小化 / 保留原形状，是**三种不同干预**；"LOD contract 必须存在"
   不自动要求原形状必须保留。

**保留代理可能遮掉新几何；最小化代理可能暴露本应被遮挡的身体或内层。**
所以 v1 那个"两格 A/B"不够，要四格：

| 几何状态 | 代理保留 | 代理最小化 |
|---|---|---|
| 原布局 | 原始基线 | 观察代理本身承担什么功能 |
| 搬运后 | 检查残留遮挡 | 检查解除遮挡 + 新增穿帮 |

**架构门（astra 加的）**：如果一个代理服务多个独立组、却无法随组状态正确控制，
那"组只是可见 section 的开关视图"就不足以表达运行时语义 —— 要么引入代理依赖策略，
要么缩小支持范围。

### 3.6 两个附带事实（L1）

- **"隐藏"= 写空壳**（1e-4 退化三角形，`lod=-1` 代理保留），不是"不写它"。不写 → 引擎回落原版件。
- **追加只在同 LOD 内合法**，且要按 LOD 家族整体重建。

## 4 容量：两个数字互相矛盾，先对齐口径

### 4.1 我方产物的可靠数字（L2，`unitprobe` 直接读我们的 patch）

`lunalice_bill`：Helmet **22** 段、Torso **25** 段、Hip 9 段（另有 `lod=-1` 代理 mesh 各 1 段）。
这是**单 mesh（LOD0）的 section 数**，口径明确。

### 4.2 本体扫描的数字**不能直接用**（L2，口径未对齐）

同一份扫描里出现两组互相矛盾的数：

- 一处报"42462 个 unit，最大 16、>20 段 0 个"；
- 另一处按"slot"分组时报出 `tcs_main_tower max=75`、`frv_superearth max=59`，
  而那个"slot"字段里混着 `@`、`0`、`@@`、`sample`、`spawner`、`$ENUM:...`、路径串
  ⇒ **分组键本身就是脏的，而且这两组数很可能是"单个 LOD0 mesh"与"跨全部 LOD 求和"两种口径**。

**⇒ 在对齐"去重 / 解析失败 / mesh 与 LOD 汇总口径"之前，本体统计只能当"内容分布参考"，
不能当引擎容量结论。** 反过来也不能拿它宣布"本体支持 75"。

### 4.3 因此

**"25 段可用"要改写成"在我们的产物结构里观察到 25 段，其完整运行能力尚未验证"。**
它没有排除：加载的是缓存/另一份覆盖产物、部分 LOD 未进入、部分段被剔除、部分段从未实际提交。

**要能说"可用"，必须**：对这 25 段逐段做可辨识标记 → 确认实际生效的是这份产物 →
验证单段开关、LOD 切换、动画 → 通过后也只能写"该版本、该布局、该样本验证通过"，不能外推。

## 5 界面：结构上不构成障碍，性能未测

- 树是**扁平化行** + **固定行高**，`ItemsControl` + `CanContentScroll="False"`（目前无虚拟化）。
- 默认只展开到 `BodyType`（`WardrobeTreeNodeViewModel.cs:49`），unit 层折叠 ⇒ 初次只画 7 行。
- 注释写明"固定行高换来……将来打开虚拟化不需要重新量行"。

**"150 行撑得住"是 L1 的结构判断，不是性能实测** —— 展开、投影重建、通知风暴、
点击触发烘焙都还没计入。

## 6 由此产生的工作项（按 astra 的意见重排）

### 6.0 顺序（**v1 的顺序是错的，这里换掉**）

```
① 实机垂直切片（架构门，可否决整个方案）
      ↓ 通过
② 容量梯度（用"候选最终编码"造，不是脱离方案的 100 段文件）
      ↓ 通过
③ 冻结物理布局 → W2 可寻址契约 + split
      ↓
④ 组编辑器 → 生效成本（就地烘焙 + 勾选即保存）
      ↓
⑤ W1 在役路径推广 → 修剪
```

**为什么把实机提到最前**：v1 把"位置已确认不变、只剩深度代理要看图"当排期依据，
但那只证明了"有条件的坐标补偿成立"。而 §3.3 的 LOD 静默少几何、§3.5 的代理遮挡、
§2.2 的边界丢失，**任何一条都足以推翻"压成 7 个物理 unit"这个形态**。
把最可能推翻方案的实验排到投入最大之后，是这轮最大的判断错误。

### 6.1 ① 实机垂直切片（唯一能降低方案风险的事）

样本要**同时**包含：宿主自己同槽两段、同材质 donor、不同骨骼权重、多 LOD。
步骤：跨槽搬运 + donor 隐藏 + 来源映射 + 单段归零 → 进游戏验证
（每段只影响自己 / 动画不漂 / 近远不丢件 / 代理影响按 §3.5 四格隔离）→
**再重建一次并加载，验证开关对象没有漂移**。

**任何一步失败 ⇒ 禁止宣布"7 个物理 unit 的通用拆件方案成立"。**

### 6.2 ② 容量梯度

- 必须用**候选最终编码**造（即 W2 选定的那种槽/remap 布局），否则测的是另一个方案。
- 梯度：16 / 25 / 32 / 64 / 100 / 150，发现断点补测邻近值。
- **用真实骨骼规模**，不要单骨骼三角形。
- 要量的不只是"能写能读能加载"：每 mesh 段数、每 LOD 槽/remap 数、骨骼集合大小、
  顶点与索引量、**当前真正提交的段数**、材质与渲染 pass 成本、多角色同屏总负载。
- 失败时的退路：回到原合法 unit 布局，或拒绝该类拆件。
  **"7" 先定义为逻辑部位分类，不是不可变物理文件数**；更多物理 unit 必须受实际槽位图约束。

### 6.3 ③ W2：从"唯一槽"改成**可独立寻址契约**

先测**最便宜的那条**：开关跳过 `MergeSectionsByMaterialSlot`，验证同槽异骨骼来源的
逐段开关 / 全 LOD / 再次重建。失败再测唯一槽路线。

无论哪条，都必须：
- 覆盖**宿主 + donor**，显式绕过所有复用分支，处理哈希碰撞；
- 全链路传 provenance，**禁止事后凭材质 + 三角形数猜回来源**；
- 覆盖权威 `disabled` 的迁移（否则手工关闭状态照样会在重建后漂移）。

### 6.4 ④ 组身份与"耦合"的表达

身份不能靠 `materialId`（会因重映射变化）+ `triangles`（大量重复）+ 几何摘要（重排/量化会变）。
需要：**不可变来源快照标识 + 资源键 + 来源 mesh/LOD + 快照内 section 标识 + 引用实例标识**；
材质与几何摘要只作校验。

界面必须区分**三种状态**，不能只画复选框：

| 状态 | 表现 |
|---|---|
| **独立** | 可以单独开关 |
| **耦合** | 显示"与 A/B 共用一个不可分段"，只给共同开关；**不许展示两个貌似独立的复选框** |
| **失效 / 歧义** | 阻断新产物发布，保留上一份有效产物，允许重新绑定 |

`defaultEnabled` 只负责初始化，**不能每次加载都覆盖权威 `disabled`**。

验收不能只看"段数相等"或"每段三角形数相等"，要按目标 / body / LOD 检查：
**来源几何不漏、不重、归属正确；承诺可独立关闭的来源其产物段集合不得交叠；
关闭任一成员不得影响其他成员。**

### 6.5 ⑤ W1：拆成"能力 + 诊断"与"在役推广"两段

- 第一段：实现重算 + 诊断，**只在实验 / 拆件路径启用**；三条在役路径默认行为不动。
- 第一版取**保守策略**：确认坐标语义后，**保留原有效范围**，补入变换后的来源范围与必要余量，
  不要直接照抄静态顶点紧盒算法（会缩掉动画预留）。
- 推广要逐路径用固定样本验证；**扩大支持范围与更新已有产物分开发布，并保留回滚**。
- 注意：盒变大主要影响提交与着色工作，**不自动等于纹理/网格显存增加**，显存要另测。

## 7 每条结论的证据边界（astra 要求逐条标，这里集中列）

| 原结论 | 证据边界与正确口径 |
|---|---|
| 并段会发生 | 对**所测夹具**的产品代码字节往返成立；不是游戏端端到端测试 |
| 任何 append 都重排原边界 | 应写"**都可能**"；只有发生同键聚合时才变 |
| 唯一槽规避已证可行 | L2/L4 是 **layout 层**实验，不是完整 Appender + 实机；未覆盖同来源同槽缓存复用与宿主同槽段 |
| 本体否掉 non-SDK 注释 | 本体形状 ≠ SDK 导出惯例；不能推定注释的"唯一真实理由" |
| 跨槽位置不会变 | 代码支持**有条件的**坐标补偿；不证明动画 / 逆绑定 / LOD / 目标骨架 / 运行时等价 |
| 在役分支证明引擎没问题 | 存在生产代码 ≠ 该分支被覆盖、输出正确、覆盖拆件边界条件 |
| 真正依赖槽位的只有五条 | 是**本仓库找到的**五类依赖，不是对闭源引擎的穷举 |
| CullingBounds 已导致三路故障 | 不重算是代码事实；具体消失现象的根因仍需隔离验证 |
| 25 段可用 | 目前是**产物结构证据** |
| 150 行撑得住 | 结构判断，不是性能实测 |
| vanilla 一套 6–7 unit | 统计是按**相同材质集合**分组，混了 Slim/Stocky；共享材质 ≠ 同套件，两个体型也不同时装备 |
| rekey 不读 VPK ⇒ legacy 自动兼容 | 只证明**输入入口可解耦**；没证明 legacy 产物满足全部骨架 / LOD / 资源依赖 / 元数据契约 |

---

## 8 结论

**U0 的定位要改：它是"离线结构核查完成"，不是"拆件可行性已确认"。**

已经能确定的三件事（都不依赖游戏内验证）：

1. **并段是真的**，而且主场景（同一 Mod 的多个 unit 共用同一批材质）正中破口 ——
   所以"拆件"必须先解决可寻址性，否则拆出来的组会静默耦合。
2. **`CullingBounds` 从不重算**是现存缺陷，任何追加几何的方案都要先有修它的能力。
3. **追加路径有三个已知的"静默少东西"入口**：同键并段、LOD 不齐跳过、深度代理遮挡。
   三个都不报错，都只在游戏里表现为"某块没了"。

还不能确定的：**这套东西在游戏里同时正确工作的证据，一条都没有。**
所以下一步不是继续加离线实验，而是**一个可否决方案的最小实机垂直切片**。
