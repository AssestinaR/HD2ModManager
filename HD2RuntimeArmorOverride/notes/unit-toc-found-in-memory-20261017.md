# 运行期定位 unit TOC：已找到，且是逐字节副本（2026-10-17）

## 结论

**内存里存在 unit TOC 的副本，与 patch 文件里的字节 99.19% 相同**，
所以离线产出的 `section.Offset + 16` 偏移可以**直接**用在内存副本上。

实测（游戏运行中，角色穿着该护甲）：

```
推导基址        0x18e6e310080
与文件 TOC 相同  99.19%  (30003 / 30248 字节)
首个差异        +0x0   mem=0x5f  file=0x00
mem  numIndices @ sec11+16 = 17823   （文件同值）
mem  indexOffset @ sec11+12 = 47835  （文件同值）
```

唯一差异在头部（+0x0 起），是加载器写入的标志/引用计数，不影响 section 表。

## 定位方法（已验证）

**扫 section 记录本身**，而不是扫 TOC 头部：

```
sec11 记录 = 0b000000 00000000 685f0000 dbba0000 9f450000 0b000000
             (matIdx=11, vOff=0, nVtx=24424, idxOff=47835, nIdx=17823, group=11)
命中地址 = 0x18e6e316ff4
基址     = 0x18e6e316ff4 - 0x6f74 = 0x18e6e310080
```

24 字节的六元组数值组合足够独特；相邻 section 在内存里也连续（步长 24），
所以可以用 48 字节（两个连续 section）做更强的签名。

## 为什么早先扫 TOC 签名扫不到

第一次用 TOC+0x3d58 的 64 字节哈希做签名，只找到一些「相同率 26–60%」的候选，
都是别的结构（材质哈希表）里恰好重合的片段。真正对齐的副本在
`0x18e6e310080`，而它的头部被改写过，所以用整块比对而不是「头部签名」。

## 顺带修掉的三个扫描器 bug

排查过程中，扫描器本身有缺陷，导致我一度得出「内存里没有 TOC」的错误结论：

1. **`Copy-Item -Force` 覆盖只读文件会保留只读属性** → `File.WriteAllBytes`
   抛 `UnauthorizedAccessException`，而输出被 `Select-String` 过滤掉，看起来"写入成功"。
   （这是两次假阴性实验的根因，用户指出后才发现。）
2. **`iter_chunks` 的 `floor` 是 64KB，小于它的区域被整体跳过** —— 那正好是
   游戏堆里的大量小块。
3. **边枚举边扫描会让 `regions()` 提前中断**（`VirtualQueryEx` 一次瞬时失败就 `break`，
   后面所有高地址区域静默丢失）。必须先拍快照再扫。

第 3 条是最隐蔽的：它会让扫描"成功完成"却漏掉目标，且不报错。

## 运行期算法

1. 构建期产出（已实现）：每个装饰 → `[(section 字节偏移, 原 NumIndices)]`。
2. 运行期初始化：扫内存找 section 记录签名 → 算出 TOC 基址 → 缓存。
3. 每次切换：`写 基址 + sectionOffset + 16`，0 = 隐藏，原值 = 恢复。
4. 每次写之前用签名复验基址（防止资源重载后地址变化）。

## 性能

Python 全量扫描（8.9 GB 可读区）约 **72 秒**，只适合初始化时做一次。
Lua 侧应当：
* 先按区域尺寸过滤（TOC 在几十 KB 到几 MB 的私有堆块里）；
* 只在启动/换装时扫一次并缓存；
* 每次切换只做一次签名复验（几十字节比较）。

## 仍未验证

**运行期写入后是否需要让资源重新加载。** 文件级实验证明「加载时读 TOC」，
但内存副本若只在加载时被解析成 GPU 绘制列表，改副本可能不生效。
这一步需要实机测：改内存里的 `NumIndices` → 看几何是否当场消失。
